# 虚拟线程（Virtual Threads）

> 来源：Oracle 官方 [Dev.java 教程](https://dev.java/learn/) →《Virtual Threads》（作者 Cay Horstmann，UPL 许可）
> 忠实翻译，保留全部代码示例。Java 19 预览 / 20 预览 / **Java 21 正式**，是后端高并发面试的核心新特性。

---

## 一、为什么需要虚拟线程？（Why Virtual Threads?）

1995 年 Java 1.0 发布时，API 约有上百个类，其中就有 `java.lang.Thread`。**Java 是第一个直接支持并发编程的主流语言。**

自 Java 1.2 起，每个 Java 线程都运行在由底层操作系统提供的**平台线程（platform thread）**上（Java 1.1 之前，某些平台上所有 Java 线程由单个平台线程执行）。

**平台线程的成本很高**：启动需要几千条 CPU 指令，且消耗几 MB 内存。服务器应用要处理大量并发请求，让每个请求运行在独立的平台线程上变得不可行。在典型服务器应用里，这些请求大部分时间都在**阻塞**——等待数据库或其他服务的结果。

**传统提升吞吐量的办法是采用非阻塞 API**：不等待结果，而是告诉系统结果可用时调用哪个方法、失败时调用另一个。但这种回调嵌套会迅速变得难以维护。

**JEP 425 在 Java 19 引入了虚拟线程。** 大量虚拟线程运行在一个平台线程上。每当虚拟线程阻塞时，它会被**卸载（unmounted）**，平台线程转去运行另一个虚拟线程（"虚拟线程"之名，是类比映射到实际 RAM 的虚拟内存）。虚拟线程在 Java 20 成为预览特性（JEP 436），**在 Java 21 正式落地**。

**有了虚拟线程，阻塞变得廉价。** 当结果不能立即获得时，你只需在虚拟线程里阻塞，用熟悉的编程结构（分支、循环、try 块）代替一串回调。

> **适用场景**：当并发任务数量大、且任务大多阻塞在**网络 I/O**上时，虚拟线程非常有用。对 **CPU 密集型任务无益**——这类任务应考虑并行流（parallel streams）或递归 fork-join 任务。

## 二、创建虚拟线程（Creating Virtual Threads）

**工厂方法 `Executors.newVirtualThreadPerTaskExecutor()`** 返回一个 `ExecutorService`，它在单独的虚拟线程里运行每个任务：

```java
try (ExecutorService service = Executors.newVirtualThreadPerTaskExecutor()) {
    service.submit(() -> {
        long id = Thread.currentThread().threadId();
        LockSupport.parkNanos(1_000_000_000);
        System.out.println("线程 id = " + id);
    });
    // service 会自动关闭
}
```

> 代码用 `LockSupport.parkNanos()` 而不是 `Thread.sleep()`，这样就不必捕获烦人的 `InterruptedException`。

**若你用的是更底层的 API，需要一个线程工厂**，可用新的 `Thread.Builder` 接口：

```java
ThreadFactory factory = Thread.ofVirtual().name("request-", 0).factory();
// factory.newThread(myRunnable) 创建新的（未启动的）虚拟线程
// name() 配置线程名依次为 request-1、request-2 ...
```

**也可用 builder 创建单个虚拟线程**：

```java
Thread t = Thread.ofVirtual().name("worker-1").start(runnable);
```

**或想立即启动**：

```java
Thread.startVirtualThread(myRunnable);   // 便捷方法
```

> **注意**：只有第一种方式（用 executor service）能配合**带返回值的任务（Callable）**。

## 三、Thread API 的变化（Thread API Changes）

经过一系列 API 试验后，Java 虚拟线程的设计者决定**直接复用熟悉的 Thread API**。**虚拟线程也是 `Thread` 的实例**。取消机制与平台线程相同——调用 `Thread.interrupt()`。与往常一样，线程代码必须检查中断标志或调用会检查的方法（大多数阻塞方法都会）。

有几个差异：所有虚拟线程——

- 在**同一个线程组**中
- 优先级为 **`NORM_PRIORITY`**
- **是守护线程（daemon thread）**

没有 API 能为虚拟线程指定其他线程组；对虚拟线程调用 `setPriority` 或 `setDaemon` 无效。

- `Thread.getAllStackTraces()` 返回所有**平台线程**的栈轨迹映射，**不包含虚拟线程**。
- 新增实例方法 **`Thread.isVirtual()`** 判断线程是否为虚拟线程。
- **无法**找到虚拟线程运行在哪个平台线程上。

### Java 19 无关虚拟线程的其他 Thread API 变更

- 新增 `Thread.join(Duration)` 重载。
- 新增 `Thread.sleep(Duration)` 重载。
- `Thread.getId()`（非 final）被弃用，因为有人可能覆盖它返回非线程 ID 的值。改用 final 的 `Thread.threadId()`。

> `Thread.suspend()` 和 `Thread.resume()` 在 JDK 23 移除，`Thread.stop()` 在 JDK 26 移除；这些方法自 Java 1.2 起已弃用、自 Java 18 起标记 for removal。

## 四、捕获任务结果（Capturing Task Results）

你常需要组合多个并发任务的结果：

```java
Future<String> f1 = service.submit(callable1);
Future<String> f2 = service.submit(callable2);
String result = combine(f1.get(), f2.get());
```

**在虚拟线程之前**，你可能对阻塞的 `get()` 调用感到不安；但**现在阻塞很廉价**。一个更具体的例子（并发请求两个 URL 并拼接）：

```java
try (ExecutorService service = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f1 = service.submit(() -> get("https://horstmann.com/random/adjective"));
    Future<String> f2 = service.submit(() -> get("https://horstmann.com/random/noun"));
    String result = f1.get() + " " + f2.get();
    System.out.println(result);
}

private static HttpClient client = HttpClient.newHttpClient();

public static String get(String url) {
    try {
        var request = HttpRequest.newBuilder().uri(new URI(url)).GET().build();
        return client.send(request, HttpResponse.BodyHandlers.ofString()).body();
    } catch (Exception ex) {
        var rex = new RuntimeException();
        rex.initCause(ex);
        throw rex;
    }
}
```

**若有一列表同类型结果的任务**，可用 `ExecutorService.invokeAll()` 然后对每个 `Future` 调 `get()`：

```java
List<Callable<String>> callables = new ArrayList<>();
for (int i = 1; i <= 4; i++) {
    callables.add(() -> get("https://horstmann.com/random/adjective"));
    callables.add(() -> get("https://horstmann.com/random/noun"));
}
try (ExecutorService service = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> results = new ArrayList<>();
    for (Future<String> f : service.invokeAll(callables))
        results.add(f.get());
    System.out.println(String.join(" ", results));
}
```

## 五、限流（Rate Limiting）

虚拟线程因能承载远多于平台线程的并发任务而提升应用吞吐量——这会给被调用的服务带来压力（例如某个 Web 服务可能无法容忍海量并发请求）。

**用平台线程时**，一个简便（虽粗糙）的调优手段是该任务的线程池大小。但**不应该池化虚拟线程**——把任务调度到虚拟线程、再调度到平台线程显然低效。而且这样做有何意义？把虚拟线程数限制到服务可容忍的少量并发？那当初为何用虚拟线程？

**用虚拟线程时，应用替代机制控制对有限资源的访问**——对每个资源做恰当的防护，而不是限制总并发任务数。数据库连接可以用连接池（它可能已经做对了）；访问 Web 服务时，你了解自己的服务，可提供恰当的限流。

**示例**：用信号量（semaphore）允许少量并发请求，超过时 `Semaphore.acquire()` 阻塞——但没关系，**虚拟线程下阻塞很廉价**：

```java
private static final Semaphore SEMAPHORE = new Semaphore(20);

public static String get(String url) {
    try {
        var request = HttpRequest.newBuilder().uri(new URI(url)).GET().build();
        SEMAPHORE.acquire();
        try {
            Thread.sleep(100);
            return client.send(request, HttpResponse.BodyHandlers.ofString()).body();
        } finally {
            SEMAPHORE.release();
        }
    } catch (Exception ex) {
        ex.printStackTrace();
        var rex = new RuntimeException();
        rex.initCause(ex);
        throw rex;
    }
}
```

## 六、钉住（Pinning）

虚拟线程调度器把虚拟线程挂载到**载物线程（carrier thread）**上。默认载物线程数 = CPU 核心数，可用 VM 选项 `jdk.virtualThreadScheduler.parallelism` 调整。

当虚拟线程执行阻塞操作时，它应当从载物线程**卸载**，让载物线程执行别的虚拟线程。但有些情况无法卸载——此时调度器会通过**再启动一个载物线程**来补偿（例如 JDK 21 里很多文件 I/O 操作、调用 `Object.wait()` 时）。可用 VM 选项 `jdk.virtualThreadScheduler.maxPoolSize` 控制载物线程最大数量。

**线程被称为「钉住（pinned）」的两种情况**：

1. 执行 **`synchronized` 方法或代码块**时（JDK 21、22、23 均如此）
2. **调用 native 方法或 foreign function**（FFM）时

> 被钉住时，虚拟线程无法卸载，会阻塞载物线程。**实践建议**：虚拟线程里的阻塞代码尽量用 `ReentrantLock` 等替代 `synchronized`，并避免在其中调用 native 方法，以减少钉住，提升并发吞吐。

## 核心速查表

| 主题 | 要点 |
|------|------|
| 本质 | 轻量级线程，大量虚拟线程跑在少量平台（载物）线程上，阻塞廉价 |
| 版本 | Java 19 预览 / 20 预览 / **21 正式** |
| 创建 | `Executors.newVirtualThreadPerTaskExecutor()`、`Thread.ofVirtual()`、`Thread.startVirtualThread()` |
| 与 Thread 关系 | 虚拟线程是 `Thread` 实例，复用 Thread API |
| 特性 | 同一线程组、优先级 NORM_PRIORITY、守护线程 |
| 判断 | `Thread.isVirtual()` |
| 捕获结果 | `Future.get()`（阻塞廉价）、`invokeAll()` |
| 适用 | 大量并发 + 网络 I/O 阻塞；**不适用** CPU 密集 |
| 限流 | 用信号量/连接池保护资源，勿池化虚拟线程 |
| 钉住 | `synchronized` 或 native/FFM 调用导致，尽量减少 |

> **面试高频**：虚拟线程 vs 平台线程（成本/吞吐）、为何阻塞便宜（卸载+载物线程复用）、适用场景（网络 I/O 非 CPU 密集）、为何不能池化虚拟线程、`pin`（synchronized 导致的钉住）、与 Thread API 的关系（isVirtual、threadId）。
