# 数据组件

> 读完这一篇，你能给物品加上属于自己的数据（比如"充能次数"），并且知道它为什么比以前的 NBT 写法安全得多。

## 学习目标

- 能说清 1.21 为什么把物品 NBT 换成数据组件，解决了哪些老问题
- 能认出 `MAX_STACK_SIZE`、`MAX_DAMAGE`、`RARITY`、`FOOD` 这些内置组件，并知道怎么在 `Item.Properties` 上设置
- 能注册一个自定义 `DataComponentType<Integer>`，并给物品设置默认值
- 能用 `get` / `getOrDefault` / `set` / `update` 正确读写组件，理解"值不可变"这条规矩
- 能写出"右键充能 + tooltip 显示"的完整物品

## 一、先说背景：以前的 NBT 有什么问题

1.20.5 之前，`ItemStack` 上挂着一个 `CompoundTag`（也就是 NBT），你可以往里塞任意键值：

```java
// 旧写法（1.20.4 及以前），现在编译不过
stack.getOrCreateTag().putInt("Charge", 5);
int charge = stack.getTag().getInt("Charge");
```

看起来很方便，实际全是坑：

- **没有类型**。你写 `putInt("Charge", 5)`，别人写 `putString("Charge", "5")`，读的时候直接 `ClassCastException`。
- **没有约束**。键名随便起，`Charge` / `charge` / `dafeiyu:charge` 三种写法混着来，谁也管不了谁。
- **不知道有哪些数据**。想知道"这个物品能有哪些字段"，只能去翻源码。
- **性能差**。每次读写都要在树形结构里查找、装箱、拆箱。
- **默认值散落各处**。`getInt("Charge")` 没数据时返回 0，但这个 0 是"真的 0"还是"没有"，分不清。

1.21 的**数据组件**（data component）就是来解决这些的：把"物品上的每一类数据"变成一个**注册过的、强类型的、带序列化方案的键**。

```text
旧：ItemStack → CompoundTag（一坨任意键值）
新：ItemStack → DataComponentMap（类型安全的键值对）
                ├─ minecraft:max_stack_size → 64
                ├─ minecraft:rarity         → COMMON
                └─ dafeiyu:charge           → 5
```

## 二、三个概念

| 概念 | 是什么 | 类比 |
|---|---|---|
| `DataComponentType<T>` | 一个"键"，附带"怎么存盘/怎么发网络"的方案 | Map 的 key，还带了类型 |
| `DataComponentMap` | 只读的 `键 → 值` 映射 | 一个不可变的 Map |
| `DataComponentHolder` | "能持有组件"的东西，`ItemStack` 就是 | 一个有 `get` 方法的对象 |
| `MutableDataComponentHolder` | 能改的版本，多了 `set` / `remove` / `update` | 可写 Map |

`T` 就是值的类型。`DataComponents.MAX_STACK_SIZE` 是 `DataComponentType<Integer>`，`DataComponents.FOOD` 是 `DataComponentType<FoodProperties>`。**类型是编译期就确定的**，这就是它比 NBT 强的根本原因。

### 组件补丁：网络上只发"改动"

还有一个概念值得先知道：`DataComponentPatch`。

每个 `Item` 都带一份**默认组件表**（原型）。你手上那个 `ItemStack` 实际存的是"相对默认值改了哪些"——这份差异就是补丁。

```text
物品原型（dafeiyu:charged_ruby 的默认值）
  max_stack_size = 1
  rarity         = UNCOMMON
  dafeiyu:charge = 0
        ▲
        │ 应用补丁
        │
ItemStack 的补丁
  dafeiyu:charge = 3        ← 只存这一条差异
```

好处很直接：网络同步和存档只需要发补丁，不用把"最大堆叠 1、稀有度 UNCOMMON"这些早就知道的东西重复发一遍。一个背包 36 格，省下来的带宽很可观。

代价是：**客户端和服务端必须拥有完全一致的物品原型**。如果你的模组在客户端和服务端注册的物品默认组件不一样（比如一端写了 `.component(CHARGE, 0)` 一端没写），补丁应用后就会得到两个不同的结果——这种不同步极难排查。所以注册代码永远只有一份，两侧共用。

## 三、内置组件

`DataComponents` 这个类里有一长串现成的组件，常用的这些：

| 组件 | 值类型 | 作用 | 对应的 `Item.Properties` 快捷方法 |
|---|---|---|---|
| `MAX_STACK_SIZE` | `Integer` | 最大堆叠数 | `stacksTo(int)` |
| `MAX_DAMAGE` | `Integer` | 最大耐久 | `durability(int)` |
| `DAMAGE` | `Integer` | 当前已损耗 | （由游戏维护） |
| `RARITY` | `Rarity` | 稀有度（只影响名字颜色） | `rarity(Rarity)` |
| `FOOD` | `FoodProperties` | 食物属性 | `food(FoodProperties)` |
| `CUSTOM_NAME` | `Component` | 自定义名称（铁砧改名） | — |
| `LORE` | `List<Component>` | 描述文本 | — |
| `ENCHANTMENTS` | `ItemEnchantments` | 附魔 | — |
| `ATTRIBUTE_MODIFIERS` | `ItemAttributeModifiers` | 属性修饰 | — |
| `CUSTOM_DATA` | `CustomData` | 逃生舱：塞任意 NBT | — |
| `TOOL` | `Tool` | 工具（挖掘速度、耐久消耗） | — |

### 在 `Item.Properties` 上设置

注册物品时，`Item.Properties` 就是"默认组件表"的构建器。大部分常用组件都有快捷方法：

文件：`src/main/java/com/dafeiyu/registry/ModItems.java`

```java
public static final DeferredItem<Item> RUBY = ITEMS.registerSimpleItem(
        "ruby",
        new Item.Properties()
                .stacksTo(16)                 // → MAX_STACK_SIZE = 16
                .rarity(Rarity.RARE)          // → RARITY = RARE
);

public static final DeferredItem<Item> RUBY_PICK = ITEMS.registerSimpleItem(
        "ruby_pick",
        new Item.Properties()
                .durability(800)              // → MAX_DAMAGE = 800，并把堆叠锁成 1
);

public static final DeferredItem<Item> RUBY_APPLE = ITEMS.registerSimpleItem(
        "ruby_apple",
        new Item.Properties()
                .food(new FoodProperties.Builder()
                        .nutrition(6)
                        .saturationMod(0.5f)
                        .build())             // → FOOD
);
```

这些快捷方法**只是语法糖**，等价于：

```java
new Item.Properties().component(DataComponents.MAX_STACK_SIZE, 16)
```

`component(类型, 值)` 是通用入口，任何组件都能这样设——包括你自己注册的。记住这一句，后面自定义组件就顺了。

## 四、自定义组件

### 第一步：决定值的类型

组件值必须是**不可变**的，并且正确实现 `hashCode` / `equals`（因为它要参与 Map 的哈希）。

- 简单值（`Integer`、`String`、`Boolean`）直接用；
- 复杂结构用 **record**（record 天然不可变 + 自动 `equals`/`hashCode`）；
- 别用可变对象（`List`、`Map`、自定义可变类），除非你每次都 `set` 一个新对象。

本篇用最简单的 `Integer`，避开 record 和 Codec 的复杂度。

### 第二步：注册 `DataComponentType`

数据组件类型本身也是注册表对象，所以要用 `DeferredRegister`。NeoForge 提供了专用子类 `DeferredRegister.DataComponents`：

文件：`src/main/java/com/dafeiyu/registry/ModDataComponents.java`

```java
package com.dafeiyu.registry;

import com.dafeiyu.DafeiyuMod;
import com.mojang.serialization.Codec;
import net.minecraft.core.component.DataComponentType;
import net.minecraft.core.registries.Registries;
import net.minecraft.network.codec.ByteBufCodecs;
import net.neoforged.neoforge.registries.DeferredHolder;
import net.neoforged.neoforge.registries.DeferredRegister;

public class ModDataComponents {
    public static final DeferredRegister.DataComponents COMPONENTS =
            DeferredRegister.createDataComponents(Registries.DATA_COMPONENT_TYPE, DafeiyuMod.MOD_ID);

    // 充能次数：一个整数
    public static final DeferredHolder<DataComponentType<?>, DataComponentType<Integer>> CHARGE =
            COMPONENTS.registerComponentType("charge", builder -> builder
                    .persistent(Codec.INT)                    // 怎么存进存档
                    .networkSynchronized(ByteBufCodecs.VAR_INT) // 怎么发给客户端
            );
}
```

逐段解释：

- `createDataComponents(注册表键, modid)`：这个专用 `DeferredRegister` 帮你绕开 `DataComponentType.Builder` 在 `Supplier` 里的泛型推断问题；
- `registerComponentType("charge", builder -> ...)`：注册名是 `dafeiyu:charge`；
- `.persistent(Codec.INT)`：**存盘**方案。`Codec` 是 Mojang 的序列化抽象，`Codec.INT` 就是"整数 ↔ JSON/NBT"；
- `.networkSynchronized(ByteBufCodecs.VAR_INT)`：**网络同步**方案。`StreamCodec` 是"整数 ↔ 字节流"，`VAR_INT` 是变长整数编码。

这两个是**必须至少给一个**的，否则 `build()` 时直接抛 `NullPointerException`：

| 只给 persistent | 只给 networkSynchronized | 两个都给 |
|---|---|---|
| 能存盘，不同步 | 同步，但**不存盘**（重进世界丢失） | 正常，推荐 |

> 如果你的组件是纯客户端用的（比如"是否正在播放动画"），可以只给 `networkSynchronized`；如果永远不该发给客户端（比如服务端内部计数），给 `persistent` + `StreamCodec.unit(默认值)`。

### 另一种写法：直接用 `DataComponentType.builder()`

如果你不想用专用 `DeferredRegister`，也可以手写，但要显式指定泛型：

```java
public static final DeferredRegister<DataComponentType<?>> RAW =
        DeferredRegister.create(Registries.DATA_COMPONENT_TYPE, DafeiyuMod.MOD_ID);

public static final DeferredHolder<DataComponentType<?>, DataComponentType<Integer>> CHARGE_RAW =
        RAW.register("charge", () -> DataComponentType.<Integer>builder()
                .persistent(Codec.INT)
                .networkSynchronized(ByteBufCodecs.VAR_INT)
                .build());
```

注意 `DataComponentType.<Integer>builder()` 那个显式类型参数：不写的话，编译器很难从链式调用里推断出 `Integer`，会报一堆看不懂的错。**新手直接用 `DeferredRegister.DataComponents` 就好**，别为难自己。

### 第三步：挂到总线

文件：`src/main/java/com/dafeiyu/DafeiyuMod.java`

```java
public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
    ModDataComponents.COMPONENTS.register(modEventBus);   // 别忘了这句
    ModItems.ITEMS.register(modEventBus);
}
```

漏了这句的后果和漏注册物品一样安静：物品能拿到，组件读写"看起来正常"，但**一存盘就丢**，一发给客户端就丢。

### 第四步（可选）：给原版物品加组件

你的组件不只能用在自己的物品上。想给"西瓜种子"加个充能字段，用 `ModifyDefaultComponentsEvent`——注意它在**模组总线**上：

文件：`src/main/java/com/dafeiyu/event/ComponentEvents.java`

```java
@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class ComponentEvents {
    @SubscribeEvent
    public static void modifyComponents(ModifyDefaultComponentsEvent event) {
        event.modify(Items.MELON_SEEDS, builder ->
                builder.set(ModDataComponents.CHARGE.get(), 5));

        // 也可以批量：给所有有合成剩余物的物品删掉某个组件
        event.modifyMatching(
                item -> item.hasCraftingRemainingItem(),
                builder -> builder.remove(DataComponents.BUCKET_ENTITY_DATA)
        );
    }
}
```

这里改的是**物品的默认值**（原型），不是某个具体的 `ItemStack`。所以它对之后新造的每一个堆叠都生效，而且客户端、服务端会自动一致——这比自己挨个 `set` 靠谱得多。

## 五、读写组件

`ItemStack` 实现了 `MutableDataComponentHolder`，可用的方法：

```java
// 读：不存在时返回 null
Integer charge = stack.get(ModDataComponents.CHARGE.get());

// 读：不存在时返回默认值（推荐，省掉 null 判断）
int c = stack.getOrDefault(ModDataComponents.CHARGE.get(), 0);

// 判断是否存在
boolean has = stack.has(ModDataComponents.CHARGE.get());

// 写：返回旧值（可能为 null）
stack.set(ModDataComponents.CHARGE.get(), 7);

// 删：恢复成"没有这个组件"，读取时会回落到物品的默认值
stack.remove(ModDataComponents.CHARGE.get());

// 更新：读 + 改 + 写，一步完成
stack.update(ModDataComponents.CHARGE.get(), 0, old -> old + 1);
```

`update` 是最省事的一个：它内部会 `getOrDefault` 拿到当前值，传给你的 Lambda 加工，再 `set` 回去。上面那行等于"充能 +1"。

### 铁律：值不可变，改完必须 set

组件值参与 `DataComponentMap` 的哈希计算，所以**绝对不要**拿到对象后原地修改：

```java
// 错误：改了对象但没告诉 map
List<Component> lore = stack.get(DataComponents.LORE);
lore.add(Component.literal("新的一行"));      // 这行可能直接抛 UnsupportedOperationException

// 正确：造一个新对象再 set
stack.set(DataComponents.LORE, List.of(Component.literal("新的一行")));
```

用 `Integer`、`String`、record 这类不可变类型，就天然不会犯这个错。这也是为什么官方推荐用 record 做组件值。

### 客户端和服务端各有一份 `ItemStack`

这一点必须记住：**`ItemStack` 不是"同一个东西的两端视图"，而是两份独立的对象**。服务端那份是真相，客户端那份是同步过来的副本。

```java
// 客户端这段代码看起来"成功"了
stack.set(ModDataComponents.CHARGE.get(), 99);
// 但它只改了本地的副本。下一次服务端同步过来，立刻被覆盖回真实值。
```

所以规则还是那一条：**改状态在服务端，显示在客户端**。客户端要做"点了按钮立刻有反馈"的效果，正确做法是本地先做视觉反馈（播放动画/音效），同时发包给服务端，等服务端确认后再更新真实数据。这个流程在网络通信篇会完整实现。

顺便回答一个常见疑问："为什么我 `set` 完 tooltip 没变？"——因为 tooltip 是在客户端渲染时读的，而你的 `set` 发生在服务端，中间还差一次同步。等服务端把补丁发过来，tooltip 就变了。如果它一直不变，那多半是没给组件配 `networkSynchronized`。

## 完整示例

一个"充能红宝石"：右键充能（上限 10），tooltip 显示当前充能。

**① 组件注册**

文件：`src/main/java/com/dafeiyu/registry/ModDataComponents.java`

```java
package com.dafeiyu.registry;

import com.dafeiyu.DafeiyuMod;
import com.mojang.serialization.Codec;
import net.minecraft.core.component.DataComponentType;
import net.minecraft.core.registries.Registries;
import net.minecraft.network.codec.ByteBufCodecs;
import net.neoforged.neoforge.registries.DeferredHolder;
import net.neoforged.neoforge.registries.DeferredRegister;

public class ModDataComponents {
    public static final DeferredRegister.DataComponents COMPONENTS =
            DeferredRegister.createDataComponents(Registries.DATA_COMPONENT_TYPE, DafeiyuMod.MOD_ID);

    /** 充能次数，0 ~ 10 */
    public static final DeferredHolder<DataComponentType<?>, DataComponentType<Integer>> CHARGE =
            COMPONENTS.registerComponentType("charge", builder -> builder
                    .persistent(Codec.INT)
                    .networkSynchronized(ByteBufCodecs.VAR_INT)
            );
}
```

**② 物品类**

文件：`src/main/java/com/dafeiyu/item/ChargedRubyItem.java`

```java
package com.dafeiyu.item;

import com.dafeiyu.registry.ModDataComponents;
import net.minecraft.ChatFormatting;
import net.minecraft.network.chat.Component;
import net.minecraft.world.InteractionHand;
import net.minecraft.world.InteractionResultHolder;
import net.minecraft.world.entity.player.Player;
import net.minecraft.world.item.Item;
import net.minecraft.world.item.ItemStack;
import net.minecraft.world.item.TooltipFlag;
import net.minecraft.world.level.Level;

import java.util.List;

public class ChargedRubyItem extends Item {
    public static final int MAX_CHARGE = 10;

    public ChargedRubyItem(Properties properties) {
        super(properties);
    }

    @Override
    public InteractionResultHolder<ItemStack> use(Level level, Player player, InteractionHand hand) {
        ItemStack stack = player.getItemInHand(hand);

        if (!level.isClientSide) {                       // 只有服务端改数据
            int charge = stack.getOrDefault(ModDataComponents.CHARGE.get(), 0);
            if (charge < MAX_CHARGE) {
                stack.set(ModDataComponents.CHARGE.get(), charge + 1);
                player.displayClientMessage(
                        Component.literal("充能 " + (charge + 1) + " / " + MAX_CHARGE), true);
            } else {
                player.displayClientMessage(Component.literal("已经充满电了"), true);
            }
        }

        // 客户端返回 success（播放挥手动画），服务端返回 success
        return InteractionResultHolder.sidedSuccess(stack, level.isClientSide());
    }

    @Override
    public void appendHoverText(ItemStack stack, TooltipContext context,
                                List<Component> tooltip, TooltipFlag flag) {
        int charge = stack.getOrDefault(ModDataComponents.CHARGE.get(), 0);
        tooltip.add(Component.translatable("item.dafeiyu.charged_ruby.charge", charge, MAX_CHARGE)
                .withStyle(charge >= MAX_CHARGE ? ChatFormatting.GOLD : ChatFormatting.AQUA));
    }
}
```

**③ 注册物品，并给默认值**

文件：`src/main/java/com/dafeiyu/registry/ModItems.java`（片段）

```java
public static final DeferredItem<ChargedRubyItem> CHARGED_RUBY = ITEMS.registerItem(
        "charged_ruby",
        ChargedRubyItem::new,
        new Item.Properties()
                .stacksTo(1)
                .rarity(Rarity.UNCOMMON)
                // 默认组件：新造出来的物品充能为 0
                .component(ModDataComponents.CHARGE.get(), 0)
);
```

注意 `.component(...)` 是在物品的**工厂**里执行的（`() -> new ChargedRubyItem(props)`），那一刻数据组件类型已经注册完毕，所以 `.get()` 是安全的。**不要**在 `ModItems` 的字段初始化阶段就提前调用它。

**④ 主类**

文件：`src/main/java/com/dafeiyu/DafeiyuMod.java`

```java
public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
    ModDataComponents.COMPONENTS.register(modEventBus);   // 必须在前
    ModItems.ITEMS.register(modEventBus);
}
```

文件：`src/main/resources/assets/dafeiyu/lang/zh_cn.json`

```json
{
  "item.dafeiyu.charged_ruby": "充能红宝石",
```

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 崩：`NullPointerException` 在 `DataComponentType.Builder#build` | 既没给 `persistent` 也没给 `networkSynchronized` | 至少给一个 |
| 组件能读能写，重启就没了 | 没给 `persistent` | 补上 `Codec` |
| 服务端有值，客户端 tooltip 永远是 0 | 没给 `networkSynchronized` | 补上 `StreamCodec` |
| 崩：`Unknown data component type dafeiyu:charge` | 忘了 `COMPONENTS.register(modEventBus)` | 补上 |
| 崩：`ClassCastException` / 泛型编译错误 | 值类型和 `T` 不一致，或 `DataComponentType.builder()` 没写类型参数 | 检查 `Codec` 与字段泛型；写 `DataComponentType.<Integer>builder()` |
| 客户端改了，服务端没变 | 在客户端 `set`，没发包 | 所有状态改动放 `!level.isClientSide` 分支 |
| 改了 `stack.get(...)` 返回的对象，值没变 | 组件值不可变，且没调 `set` | 造新对象再 `set`，或用 `update` |
| 想改 `MAX_STACK_SIZE` 但容器行为异常 | 堆叠逻辑大量依赖物品默认值 | 别在运行时改这类"物品级"组件，改 `Item.Properties` |
| 存档里的旧物品没有这个组件 | 老物品是按旧原型创建的 | 读取时一律用 `getOrDefault` 兜底 |

## 练习

1. **热身**：给充能红宝石加一个"上限 20"的版本（新物品 `super_charged_ruby`），复用同一个组件类型，只是 `MAX_CHARGE` 不同。
2. **进阶**：把 `Integer` 换成 record `ChargeData(int value, boolean overloaded)`，写 `RecordCodecBuilder` 和 `StreamCodec.composite`，tooltip 在 `overloaded` 为真时显示红色"过载"。
3. **思考**：如果把 `.networkSynchronized(...)` 删掉，但保留 `.persistent(...)`，单人游戏里 tooltip 还能正确显示吗？多人呢？为什么？先推理再验证。
