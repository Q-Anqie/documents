# 资源位置与命名空间

> 读完这一篇，你能看懂任何一处 `dafeiyu:xxx` 到底指向哪个文件，也能自己推出"这个物品的纹理该放在哪"。

## 学习目标

- 能说出 `ResourceLocation` 由哪两部分组成，各允许哪些字符
- 能用 `fromNamespaceAndPath` / `parse` / `withDefaultNamespace` 正确创建资源位置
- 能由 `dafeiyu:ruby` 反推出它的模型、纹理、语言键、配方分别落在哪个路径
- 能避开"大写字母""空格""把 `.png` 写进注册 ID"这三类高频错误

## 一、它是什么

`ResourceLocation`（资源位置，常简称 RL）是 Minecraft 里用来**唯一标识一个东西**的字符串，格式固定为：

```text
命名空间:路径
namespace:path
```

```text
dafeiyu:ruby
└──┬──┘ └┬─┘
   │     └── 路径：这个命名空间里的哪一个
   └──────── 命名空间：哪个模组 / 资源包 / 数据包
```

- **命名空间**（namespace）：通常是 modid。原版用 `minecraft`。资源包和数据包也可以引入自己的命名空间。
- **路径**（path）：命名空间内的名字。可以带 `/` 表示"分层"，比如 `item/ruby`。

举例：

| 资源位置 | 大概在说什么 |
|---|---|
| `minecraft:dirt` | 原版的泥土 |
| `minecraft:cow` | 原版的牛（实体） |
| `dafeiyu:ruby` | 你的红宝石 |
| `dafeiyu:block/ruby_block` | 你的红石块模型 |
| `minecraft:textures/gui/container/furnace.png` | 熔炉 GUI 的背景图 |

注意最后一行：**同一个 `ResourceLocation` 在不同场合可以指不同东西**。`minecraft:dirt` 在方块表里是泥土方块，在物品表里是泥土物品，在配方里可能是一个配方 id。光看字符串判断不了用途，要看"谁在用它"。

## 二、为什么需要它

三个理由：

1. **唯一性**。全世界几万个模组，靠 `ruby` 这种名字必然撞车；加上 `dafeiyu:` 前缀就天然不冲突。
2. **可序列化**。存档、网络包、JSON 文件里都只能存字符串，不能存 Java 对象引用。RL 就是那个"能存下来的身份证"。
3. **可映射到文件**。`dafeiyu:item/ruby` 这样的路径，加上规则就能拼出磁盘上的 `assets/dafeiyu/models/item/ruby.json`。整套资源系统就是靠这个约定运转的。

### 命名空间的实际作用：所有权边界

命名空间不只是"前缀"，它是一条**所有权分界线**：

- `assets/dafeiyu/` 下的东西，只有你的模组（或专门针对你的资源包）会去写；
- `assets/minecraft/` 下的东西属于原版，任何资源包都能覆盖它——这也是材质包的工作方式：往 `assets/minecraft/textures/block/stone.png` 放一张图，石头就变样了；
- 数据包同理，`data/minecraft/recipe/...` 可以覆盖原版配方。

由此得出一条纪律：**不要用 `minecraft` 命名空间注册你自己的东西**。短期看能"替换"原版物品，长期看会和资源包、其他模组、游戏更新三方打架，而且你的物品在存档里会伪装成原版物品，卸载模组后直接变成"未知物品"甚至导致存档报错。

反过来，如果你想**兼容**别人的模组，就用 `ResourceLocation.tryParse` + `BuiltInRegistries.ITEM.containsKey(...)` 去探测，而不是硬编码假设它存在。

## 三、怎么创建

1.21 之后构造函数已经私有化（`new ResourceLocation(...)` 编译不过），必须用静态工厂：

```java
import net.minecraft.resources.ResourceLocation;

// 1. 最常用：命名空间 + 路径分开给
ResourceLocation id = ResourceLocation.fromNamespaceAndPath("dafeiyu", "ruby");

// 2. 从完整字符串解析（"ns:path" 形式）
ResourceLocation id2 = ResourceLocation.parse("dafeiyu:ruby");

// 3. 只给路径，命名空间默认 minecraft
ResourceLocation id3 = ResourceLocation.withDefaultNamespace("dirt");   // minecraft:dirt

// 4. 解析但不抛异常，失败返回 Optional
Optional<ResourceLocation> maybe = ResourceLocation.tryParse(userInput);
```

怎么选：

- 代码里写死的常量 → `fromNamespaceAndPath`，编译期就能发现拼错；
- 从配置文件、命令参数、JSON 里读来的字符串 → `parse`（格式错会抛 `ResourceLocationException`）或 `tryParse`（自己处理失败）；
- 引用原版资源 → `withDefaultNamespace`，省得写 `minecraft:`。

`ResourceLocation` 是**不可变**的，所有"修改"方法都返回新对象：

```java
ResourceLocation base = ResourceLocation.fromNamespaceAndPath("dafeiyu", "ruby");

base.getNamespace();                  // "dafeiyu"
base.getPath();                       // "ruby"
base.toString();                      // "dafeiyu:ruby"

base.withPrefix("item/");             // dafeiyu:item/ruby
base.withSuffix(".png");              // dafeiyu:ruby.png
```

## 四、命名规则（一定要背）

| 部分 | 允许的字符 | 不允许 |
|---|---|---|
| 命名空间 | 小写字母 `a-z`、数字 `0-9`、下划线 `_`、点 `.`、连字符 `-` | 大写、空格、`/`、中文 |
| 路径 | 同上，**额外允许** `/` | 大写、空格、反斜杠、中文 |

几条实践规则：

- **一律小写 + 下划线**：`ruby_sword` ✅，`RubySword` ❌，`ruby sword` ❌。
- **modid 不要用连字符**。虽然 RL 规范允许，但 Java 模块系统不允许 modid 带 `-`，所以 `my-mod` 这种 modid 会出问题。路径里用连字符是可以的。
- **路径里不要写扩展名**（注册 ID 场合）。`ruby.png` 会被当成"名字叫 ruby.png 的物品"，游戏会去找 `ruby.png.json` 的模型，然后找不到。
- **路径里不要带 `textures/`、`models/` 这类目录前缀**（除非那个 API 明确要求）。模型引用 `dafeiyu:item/ruby` 就够了，`models/` 是自动加的。

违反规则的后果分两种：注册时直接崩（`ResourceLocationException: Non [a-z0-9_.-] character in path`），或者不崩但资源永远加载不到（更难受）。

### 注册名一旦发布，就不要改

这条比字符规则更重要。

注册名是写进存档的。玩家的箱子里、地上的掉落物、机器里的过滤配置、任务书的进度条件，存的都是 `dafeiyu:ruby` 这个字符串。你一改名，玩家升级模组后所有旧物品都变成"未知物品"，运气不好还会让区块加载报错。

所以：

- 起名时多想三十秒，用**语义清晰、不易过时**的名字。`ruby` 比 `red_gem_2` 好，`charged_ruby` 比 `ruby_new` 好；
- 发现名字起错了，**不要删旧的**，而是保留旧 ID 并让它指向新物品（或用数据修复迁移），至少保留一个大版本；
- 内部测试阶段随便改没关系，一旦发到公开平台就要当成 API 对待。

同理，纹理、模型的文件名虽然不进存档，但改了对玩家装的材质包不友好，也尽量稳定。

## 五、它出现在哪些地方

| 场景 | 例子 | 谁在用 |
|---|---|---|
| 注册 ID | `dafeiyu:ruby` | 注册表（第 1 篇） |
| 物品模型引用 | `dafeiyu:item/ruby` | 模型 JSON 的 `parent` / `textures` |
| 纹理引用 | `dafeiyu:item/ruby` | 模型 JSON 的 `layer0` |
| 方块状态文件 | `dafeiyu:ruby_block` | `blockstates/*.json` 的文件名 |
| 配方 ID | `dafeiyu:ruby_block` | `data/dafeiyu/recipe/*.json` |
| 标签 | `#dafeiyu:gems` | `data/dafeiyu/tags/item/gems.json` |
| 声音事件 | `dafeiyu:ruby_charge` | `sounds.json` + `.ogg` 文件 |
| 进度 / 战利品表 / 伤害类型 | `dafeiyu:xxx` | `data/dafeiyu/...` |
| 粒子类型 | `dafeiyu:ruby_spark` | 注册表 + `particles/*.json` |

### 顺带认识两个亲戚

**`ResourceKey`** 是"注册表 id + 注册名"的组合，比如"物品表里的 `dafeiyu:ruby`"。它比单个 `ResourceLocation` 多了一层信息：这个 id 属于哪张表，因此能唯一定位一个元素。世界生成、数据包注册表里到处都是它：

```java
ResourceKey<Item> key = ResourceKey.create(Registries.ITEM,
        ResourceLocation.fromNamespaceAndPath("dafeiyu", "ruby"));
```

`DeferredHolder#getKey()` 返回的就是它。

**`ModelResourceLocation`** 是在 RL 后面再加一段"变体"（variant），用 `#` 分隔，例如 `minecraft:diamond_sword#inventory`。它用来区分同一个物品在不同场景下的模型。**注意它是仅客户端的类**，公共代码里当字段类型用会让专用服务器崩，详见[侧](03-侧-客户端与服务端.md)。

## 六、和文件路径的对应关系（重点）

这是最容易搞混的地方：**同样是 RL，有的会自动补目录和扩展名，有的必须写全**。

### 注册 ID → 没有对应文件，但决定了一堆路径

以 `dafeiyu:ruby` 这个物品为例，它会派生出：

```text
注册 ID:  dafeiyu:ruby
   │
   ├─ 语言键:      item.dafeiyu.ruby
   │                 → assets/dafeiyu/lang/zh_cn.json
   │
   ├─ 物品模型:    dafeiyu:item/ruby
   │                 → assets/dafeiyu/models/item/ruby.json
   │
   ├─ 纹理:        dafeiyu:item/ruby
   │                 → assets/dafeiyu/textures/item/ruby.png
   │
   └─ 配方(可选):  dafeiyu:ruby
                     → data/dafeiyu/recipe/ruby.json
```

注意模型和纹理的 RL 是 `dafeiyu:item/ruby`，比注册 ID 多了 `item/`。这个前缀不是必须的（你可以让模型叫 `dafeiyu:models/ruby` 之类），但**约定俗成**物品模型放 `item/`、方块模型放 `block/`。

### 三类"自动补全"规则

| 用途 | 你写的 RL | 实际文件 | 自动补了什么 |
|---|---|---|---|
| 物品模型 | `dafeiyu:item/ruby` | `assets/dafeiyu/models/item/ruby.json` | `assets/<ns>/models/` + `.json` |
| 方块模型 | `dafeiyu:block/ruby_block` | `assets/dafeiyu/models/block/ruby_block.json` | 同上 |
| 纹理（模型里引用） | `dafeiyu:item/ruby` | `assets/dafeiyu/textures/item/ruby.png` | `assets/<ns>/textures/` + `.png` |
| 方块状态 | `dafeiyu:ruby_block`（文件名） | `assets/dafeiyu/blockstates/ruby_block.json` | `assets/<ns>/blockstates/` + `.json` |
| 配方 | `dafeiyu:ruby_block`（文件名） | `data/dafeiyu/recipe/ruby_block.json` | `data/<ns>/recipe/` + `.json` |
| 物品标签 | `dafeiyu:gems`（文件名） | `data/dafeiyu/tags/item/gems.json` | `data/<ns>/tags/item/` + `.json` |

### 反例：GUI 纹理必须写全

GUI 背景不是"模型引用"，而是直接开一个纹理：

```java
// 熔炉界面的背景，注意这里有 textures/ 和 .png
ResourceLocation FURNACE_BG =
        ResourceLocation.withDefaultNamespace("textures/gui/container/furnace.png");
// 对应文件：assets/minecraft/textures/gui/container/furnace.png
```

对比一下：模型里写 `dafeiyu:item/ruby` 会自动补 `textures/` 和 `.png`；而 GUI 直接开流的时候，你得自己写全。**判断标准：这个 RL 是被"资源加载器"按类型解析的（自动补），还是被当成"完整路径"直接读的（写全）。**

不确定的时候，去看原版同类代码怎么写的，照抄路径格式。

### 资源没加载出来时怎么查

按这个顺序排查，基本五分钟能定位：

1. **看日志**。搜索 `Unable to load model`、`FileNotFoundException`、`Missing texture`。日志里通常会把它尝试过的完整路径打出来，照着这个路径补文件最省事。
2. **对大小写**。Windows 文件系统不区分大小写，Linux 服务器区分。你本地 `Ruby.png` 能跑，服务器上就找不到。**文件名一律小写**。
3. **确认注册名和文件名一致**。物品 `dafeiyu:ruby_sword` 的模型必须是 `models/item/ruby_sword.json`，差一个下划线都不行。
4. **按 F3+T 重载资源**。改完 JSON/PNG 不用重启游戏，但**新增**的注册项（新物品）必须重启。
5. **确认模型 JSON 语法正确**。少一个逗号，整个模型静默失败，物品显示紫黑格，日志里只有一行不起眼的解析错误。

## 完整示例

注册一个 `dafeiyu:ruby`，并配齐最小资源。

**① 注册（代码）**

文件：`src/main/java/com/dafeiyu/registry/ModItems.java`

```java
public static final DeferredItem<Item> RUBY = ITEMS.registerSimpleItem("ruby");
```

**② 物品模型**

文件：`src/main/resources/assets/dafeiyu/models/item/ruby.json`

```json
{
  "parent": "minecraft:item/generated",
  "textures": {
    "layer0": "dafeiyu:item/ruby"
  }
}
```

`parent` 用 `item/generated` 表示"就是个平面图标"，此时 `layer0` 指向的 RL 会被解析成 `assets/dafeiyu/textures/item/ruby.png`。

**③ 纹理**

文件：`src/main/resources/assets/dafeiyu/textures/item/ruby.png`

（16×16 或 32×32 的 PNG，文件名必须全小写。）

**④ 语言文件**

文件：`src/main/resources/assets/dafeiyu/lang/zh_cn.json`

```json
{
  "item.dafeiyu.ruby": "红宝石"
}
```

**⑤ 配方（可选）**

文件：`src/main/resources/data/dafeiyu/recipe/ruby_from_block.json`

```json
{
  "type": "minecraft:crafting_shapeless",
  "category": "misc",
  "ingredients": [
    { "item": "dafeiyu:ruby_block" }
  ],
  "result": {
    "id": "dafeiyu:ruby",
    "count": 9
  }
}
```

注意 1.21 的两个变化：目录是 `recipe/`（单数，1.20 及以前是 `recipes/`），结果里的物品字段是 `id`（1.20 及以前是 `item`）。

**⑥ 在代码里拼路径**

```java
// 由注册名派生模型位置，避免手写字符串
ResourceLocation modelId = ModItems.RUBY.getId().withPrefix("item/");
// → dafeiyu:item/ruby
```

`DeferredItem#getId()` 返回的就是注册名 `dafeiyu:ruby`，再 `withPrefix("item/")` 就得到模型 RL。批量生成资源时这个技巧很常用。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 崩：`Non [a-z0-9_.-] character in path of location` | 路径里有大写/空格/中文 | 全改小写 + 下划线 |
| 物品显示紫黑格 | 纹理路径不对 | 检查 `assets/dafeiyu/textures/item/ruby.png` 是否真存在 |
| 物品显示紫黑格，但纹理文件在 | 模型里 `layer0` 写成了 `dafeiyu:textures/item/ruby` | 模型里不要带 `textures/`，也不要带 `.png` |
| 物品显示成"未知物品"的模型 | 模型文件名和注册名不一致 | `models/item/<注册路径>.json` |
| `parse("Ruby")` 抛异常 | 缺命名空间 / 有大写 | 用 `fromNamespaceAndPath`，或写全 `dafeiyu:ruby` |
| 配方加载失败 | 目录写成 `recipes/` 或字段写成 `item` | 1.21 是 `recipe/` 和 `id` |
| 标签不生效 | 目录写成 `tags/items/` | 1.21 是 `tags/item/` |
| 服务端崩在 `ModelResourceLocation` | 它是仅客户端类 | 见[侧](03-侧-客户端与服务端.md) |
| 中文名不显示 | 语言键写成 `item.ruby` | 必须是 `item.<modid>.<path>` |

## 练习

1. **热身**：写出 `dafeiyu:ruby_sword` 这个物品的模型路径、纹理路径、语言键各是什么。
2. **进阶**：注册一个方块 `dafeiyu:ruby_block`，配齐 `blockstates/ruby_block.json`、`models/block/ruby_block.json`、`textures/block/ruby_block.png`、`models/item/ruby_block.json`（方块物品的模型通常 `parent` 指向方块模型），并说明这五个文件各自被谁引用。
3. **思考**：`ResourceLocation.parse("dafeiyu:item/ruby.png")` 会抛异常吗？如果不会，那它指向的文件是什么？动手验证一下，然后解释为什么"把 `.png` 写进 ID"是个隐蔽的错误。
