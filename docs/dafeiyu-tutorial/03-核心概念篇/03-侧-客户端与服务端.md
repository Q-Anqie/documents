# 侧：客户端与服务端

> 读完这一篇，你能解释"为什么我这边好好的，专用服务器一开就崩"，并且能把客户端专属代码放到正确的位置。

## 学习目标

- 能区分**物理侧**（`Dist`）和**逻辑侧**（`LogicalSide`），并说出各自的判断方法
- 能画出单人游戏里"一个物理客户端 + 两个逻辑侧"的结构
- 能列出至少五项"只有客户端能做"的事
- 能用 `@Mod(dist = Dist.CLIENT)`、`@EventBusSubscriber(value = Dist.CLIENT)`、`client` 子包三种方式隔离客户端代码
- 能解释专用服务器上 `NoClassDefFoundError` 的成因，并知道怎么避免

## 一、一个几乎人人都会遇到的崩溃

你在自己的电脑上开发，一切正常：物品能拿、GUI 能开、粒子能飘。然后你把模组丢进一个真正的服务器，启动，崩了：

```text
java.lang.NoClassDefFoundError: net/minecraft/client/Minecraft
    at com.dafeiyu.DafeiyuMod.<clinit>(DafeiyuMod.java:12)
```

你打开 `DafeiyuMod.java` 第 12 行，发现只是一句 `Minecraft.getInstance().doSomething()`。

"我本地明明能跑啊？"

能跑，是因为你本地跑的是**客户端**，`net.minecraft.client.Minecraft` 这个类存在。服务器上没有这个类——它压根不打包客户端代码。这就是"侧"的问题。

## 二、两种"侧"

Minecraft 的"侧"有两个完全不同的含义，混在一起讲永远讲不清。分开看：

### 物理侧（physical side）：你运行的是哪个程序

| 物理侧 | 你怎么启动的 | 有渲染吗 | 枚举值 |
|---|---|---|---|
| 物理客户端 | 双击启动器，点"开始游戏" | 有 | `Dist.CLIENT` |
| 物理服务端（专用服务器） | 运行 `server.jar` / 开服面板 | 没有 | `Dist.DEDICATED_SERVER` |

物理侧是**进程级**的，一次运行里永远不变。判断方法：

```java
if (FMLEnvironment.dist == Dist.CLIENT) {
    // 我是客户端程序
}
// 或者
if (FMLEnvironment.dist.isClient()) { ... }
if (FMLEnvironment.dist.isDedicatedServer()) { ... }
```

### 逻辑侧（logical side）：这段代码在为谁算

| 逻辑侧 | 负责什么 | 枚举值 |
|---|---|---|
| 逻辑服务端 | 世界 tick、时间天气、实体 AI、生成、物品栏数据、伤害结算 | `LogicalSide.SERVER` |
| 逻辑客户端 | 渲染、输入、屏幕、粒子、音效播放、动画插值 | `LogicalSide.CLIENT` |

逻辑侧是**对象级**的：同一个进程里可以同时存在两个逻辑侧。判断方法首选这个：

```java
if (level.isClientSide()) {
    // 逻辑客户端
} else {
    // 逻辑服务端
}
```

`Level#isClientSide()` 是你在模组开发里用得最多的一句判断，官方文档也明确说"只要手头有 `Level`，就用这个"。

### 两者不是一回事

关键差异就在单人游戏。

```text
【多人游戏】
你的电脑                          服务器
┌──────────────┐                 ┌──────────────┐
│ 物理客户端    │                 │ 物理服务端    │
│  └ 逻辑客户端 │◄──── 网络 ────►│  └ 逻辑服务端 │
└──────────────┘                 └──────────────┘
物理侧 = 逻辑侧，一一对应

【单人游戏】
你的电脑（一个 JVM 进程）
┌───────────────────────────────────────────────┐
│  物理客户端                                    │
│  ┌─────────────────┐   ┌──────────────────┐  │
│  │ 逻辑客户端       │   │ 逻辑服务端        │  │
│  │ 渲染 / 输入      │◄─►│ 世界 tick / 数据  │  │
│  │ Level.isClientSide = true │ = false      │  │
│  └─────────────────┘   └──────────────────┘  │
│         同一个进程，靠内存里的"连接"通信        │
└───────────────────────────────────────────────┘
```

所以：

- 单人游戏里，**两个逻辑侧在同一个 JVM 里同时跑**；
- `Dist.CLIENT`（物理）为真时，`isClientSide()`（逻辑）既可能真也可能假；
- 专用服务器里 `isClientSide()` **永远**为 `false`，但 `false` 不代表一定是专用服务器——单人世界的服务端也是 `false`。

这就是为什么"单人测试通过"根本不能证明"服务器能跑"。官方文档专门强调：**永远用专用服务器测一遍**。

### 还有一个隐蔽的坑：静态字段

单人游戏两个逻辑侧共用一个 JVM，意味着**静态字段是共享的**。你在客户端往 `static int counter` 里加一，服务端读到的也是那个被改过的值。多人游戏里根本不会这样。

所以：**不要用静态字段在两侧之间传数据**。要传，就发包（见网络通信篇）。

## 三、什么只有客户端能做

记住这张清单，凡是涉及"看得见"的东西，基本都只能在客户端：

| 能力 | 相关类/包 | 说明 |
|---|---|---|
| 渲染 | `net.minecraft.client.renderer.*` | 方块/实体/物品渲染器、GUI 绘制 |
| 屏幕与菜单界面 | `Screen`、`AbstractContainerScreen` | `Screen` 是纯客户端类 |
| 键盘鼠标输入 | `KeyMapping`、`InputConstants` | 只在物理客户端有意义 |
| 粒子 | `Level#addParticle` | 客户端调用才看得见 |
| 模型与纹理 | `BakedModel`、`TextureAtlas` | 资源加载在客户端 |
| 客户端配置 | `ModConfig.Type.CLIENT` | 专用服务器不读 |
| 音效的"本地播放" | `Minecraft.getInstance().getSoundManager()` | 服务端只能发指令让它播 |

而这些东西**两侧都能做**（但语义不同）：

- `level.addParticle(...)`：服务端调用会广播给附近玩家，客户端调用只在本机显示。所以通常客户端调。
- `player.displayClientMessage(...)`：服务端调用会自动同步给那个玩家；客户端调用只在本机显示（且可能被服务端覆盖）。
- `level.playSound(...)`：服务端调用会发给附近玩家。

## 四、心智模型：服务端权威，客户端显示

这是整个模组开发最重要的一条设计原则：

> **服务端是唯一的事实来源（authoritative），客户端只是它的显示器。**

具体表现为：

```text
玩家右键你的方块
   │
   ├─ 客户端：立刻播放动画 / 音效 / 粒子（"看起来"发生了）
   │
   └─ 服务端：真正扣物品、加进度、改方块、算伤害
                │
                └─ 把结果同步回客户端（物品栏、方块状态、血量……）
```

由此推出三条实践规则：

1. **改状态 → 服务端**。扣物品、加 buff、改方块、写数据，全部放在 `if (!level.isClientSide())` 里。
2. **放效果 → 客户端**（或服务端广播）。粒子、音效、动画。
3. **需要"客户端发起、服务端执行"→ 发包**。客户端按键想触发一个服务端行为，必须发网络包，不能直接改。

违反第 1 条的典型症状：客户端看起来成功了，一转身/一重进就复原（因为服务端从没改过），或者出现"幽灵方块""血量跳回"。

## 五、客户端代码怎么组织

有三种手段，通常组合使用。

### 手段一：`@Mod(dist = Dist.CLIENT)`

一个 modid 可以有多个 `@Mod` 类，各自绑定不同的物理侧。NeoForge 只会在对应侧加载它们。

文件：`src/main/java/com/dafeiyu/DafeiyuMod.java`（公共）

```java
@Mod(DafeiyuMod.MOD_ID)
public class DafeiyuMod {
    public static final String MOD_ID = "dafeiyu";

    public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
        ModItems.ITEMS.register(modEventBus);
        // 只放两侧都要执行的代码
    }
}
```

文件：`src/main/java/com/dafeiyu/client/DafeiyuClient.java`（仅客户端）

```java
package com.dafeiyu.client;

import com.dafeiyu.DafeiyuMod;
import net.neoforged.api.distmarker.Dist;
import net.neoforged.bus.api.IEventBus;
import net.neoforged.fml.ModContainer;
import net.neoforged.fml.common.Mod;

@Mod(value = DafeiyuMod.MOD_ID, dist = Dist.CLIENT)
public class DafeiyuClient {
    public DafeiyuClient(IEventBus modEventBus, ModContainer container) {
        // 这里可以放心用 Minecraft、Screen 等客户端类
        modEventBus.addListener(KeyBindings::register);
    }
}
```

专用服务器启动时，这个类**不会被加载**，所以里面写什么都不影响服务器。

### 手段二：`@EventBusSubscriber(value = Dist.CLIENT)`

给事件处理器类限定物理侧：

文件：`src/main/java/com/dafeiyu/client/ClientEvents.java`

```java
package com.dafeiyu.client;

import com.dafeiyu.DafeiyuMod;
import net.neoforged.api.distmarker.Dist;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.neoforge.client.event.ClientTickEvent;

@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, value = Dist.CLIENT)
public class ClientEvents {
    @SubscribeEvent
    public static void onClientTick(ClientTickEvent.Post event) {
        // 只有物理客户端才会执行到这里
    }
}
```

`value` 是 `Dist[]`，所以也可以写 `value = {Dist.CLIENT}`；要限定在专用服务器，用 `Dist.DEDICATED_SERVER`。

### 手段三：`client` 子包 + 一个入口

约定：**所有引用 `net.minecraft.client.*` 的类，一律放在 `com.dafeiyu.client` 包下**，公共代码只通过一个"入口类"调用它们。

```text
com.dafeiyu
├── DafeiyuMod.java          公共：注册、通用事件
├── registry/                公共：注册表
├── event/                   公共：游戏总线事件（两侧都跑）
└── client/                  仅客户端
    ├── DafeiyuClient.java   @Mod(dist = CLIENT) 入口
    ├── KeyBindings.java     按键定义
    └── ClientEvents.java    客户端事件
```

公共代码要触发客户端行为时，这样写：

```java
// 公共类里
if (FMLEnvironment.dist.isClient()) {
    ClientSetup.init();   // 这行只在物理客户端会执行
}
```

为什么这样就安全？因为 JVM 对"方法体里引用的类"是**惰性解析**的：`ClientSetup` 这个名字只存在于字节码的常量池里，只有真正执行到这一行时才会去加载它。专用服务器上 `isClient()` 为 `false`，这行永远不执行，也就永远不会去找 `ClientSetup`。

反过来，如果你把它写成字段类型、父类、方法参数或返回值，情况就不一样了：

```java
public class BadExample {
    // 危险：字段类型是客户端类，加载 BadExample 时就要解析它
    private static Minecraft minecraft;
}
```

## 六、`NoClassDefFoundError` 到底怎么来的

Java 加载一个类时，要验证它的结构：父类是谁、字段是什么类型、方法签名是什么。这些信息里只要出现了一个**当前 classpath 上不存在的类**，加载就会失败。

专用服务器的 classpath 里没有 `net.minecraft.client.*`（现代版本里服务端是客户端的子集，客户端类不在其中）。所以：

| 你的写法 | 专用服务器上 |
|---|---|
| 字段类型是 `Minecraft` | 加载这个类就崩 |
| 继承 `Screen` | 加载这个类就崩 |
| 方法签名里有 `BakedModel` | 加载这个类就崩（验证阶段） |
| 静态初始化块里 `new KeyMapping(...)` | 类初始化时崩 |
| 方法体里 `Minecraft.getInstance()` | 只要不执行就没事，执行到就崩 |
| 注解参数里引用客户端类 | 反射读取注解时崩 |

**结论**：不是"不能写"，而是"要写在一个服务器永远不会加载的类里"。`@Mod(dist = Dist.CLIENT)` 和 `client` 子包，做的就是这件事。

顺便说一句：`ModelResourceLocation` 也是仅客户端的类，在公共代码里拿它当字段类型一样会崩。

## 完整示例

一个客户端按键：按 R 在聊天栏上方提示当前手持物品。

**① 按键定义（仅客户端）**

文件：`src/main/java/com/dafeiyu/client/KeyBindings.java`

```java
package com.dafeiyu.client;

import com.mojang.blaze3d.platform.InputConstants;
import net.minecraft.client.KeyMapping;
import net.neoforged.neoforge.client.settings.KeyConflictContext;
import org.lwjgl.glfw.GLFW;

public class KeyBindings {
    // 第一个参数是翻译键，需要在 lang 文件里写 "key.dafeiyu.charge"
    public static final KeyMapping CHARGE = new KeyMapping(
            "key.dafeiyu.charge",
            KeyConflictContext.IN_GAME,          // 只在游戏内（不在 GUI 里）生效
            InputConstants.Type.KEYSYM,
            GLFW.GLFW_KEY_R,
            "key.categories.dafeiyu"             // 按键设置里的分类
    );
}
```

**② 注册按键（仅客户端，模组总线）**

文件：`src/main/java/com/dafeiyu/client/DafeiyuClient.java`

```java
package com.dafeiyu.client;

import com.dafeiyu.DafeiyuMod;
import net.neoforged.api.distmarker.Dist;
import net.neoforged.bus.api.IEventBus;
import net.neoforged.fml.ModContainer;
import net.neoforged.fml.common.Mod;
import net.neoforged.neoforge.client.event.RegisterKeyMappingsEvent;

@Mod(value = DafeiyuMod.MOD_ID, dist = Dist.CLIENT)
public class DafeiyuClient {
    public DafeiyuClient(IEventBus modEventBus, ModContainer container) {
        // RegisterKeyMappingsEvent 是模组总线事件
        modEventBus.addListener(this::registerKeys);
    }

    private void registerKeys(RegisterKeyMappingsEvent event) {
        event.register(KeyBindings.CHARGE);
    }
}
```

**③ 处理按键（仅客户端，游戏总线）**

文件：`src/main/java/com/dafeiyu/client/ClientEvents.java`

```java
package com.dafeiyu.client;

import com.dafeiyu.DafeiyuMod;
import net.minecraft.client.Minecraft;
import net.minecraft.network.chat.Component;
import net.minecraft.world.entity.player.Player;
import net.neoforged.api.distmarker.Dist;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.neoforge.client.event.ClientTickEvent;

@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, value = Dist.CLIENT)
public class ClientEvents {
    @SubscribeEvent
    public static void onClientTick(ClientTickEvent.Post event) {
        // consumeClick 会把"这一 tick 内按下的次数"消耗掉，所以要用 while
        while (KeyBindings.CHARGE.consumeClick()) {
            Player player = Minecraft.getInstance().player;
            if (player == null) {
                continue;                       // 还没进世界
            }
            player.displayClientMessage(
                    Component.literal("你按下了充能键：" + player.getMainHandItem().getHoverName().getString()),
                    true);
            // 注意：这里只改了客户端的显示。要真正改世界，得发包给服务端。
        }
    }
}
```

**④ 语言文件**

文件：`src/main/resources/assets/dafeiyu/lang/zh_cn.json`

```json
{
  "key.dafeiyu.charge": "充能",
  "key.categories.dafeiyu": "大肥鱼模组"
}
```

**⑤ 验证方式**

- 客户端启动，进世界，按 R，看到提示 → 客户端路径通了；
- 用 `runServer` 或真服务器启动，日志里**不应**出现 `DafeiyuClient` 相关的类加载错误 → 隔离成功了。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 专用服务器崩 `NoClassDefFoundError: net/minecraft/client/...` | 公共类里直接引用了客户端类（字段/父类/签名/静态初始化） | 移到 `client` 包 + `@Mod(dist = CLIENT)` |
| 服务器崩 `ClassNotFoundException` | 同上，通常是反射或注解参数 | 同上 |
| 客户端有效果，重进世界就没了 | 状态改在客户端 | 挪到 `!isClientSide()` 分支 |
| 方块变"幽灵"、物品数量对不上 | 两端都改了状态 | 只让服务端改 |
| 单人正常，多人不同步 | 用了静态字段跨侧传数据 | 改用网络包 |
| 按键没反应 | `KeyMapping` 没注册 / 注册到了游戏总线 | `RegisterKeyMappingsEvent` 是**模组总线**事件 |
| 按键设置里看不到你的键 | 缺 `key.categories.dafeiyu` 翻译键 | 补 lang 文件 |
| `Minecraft.getInstance().player` 空指针 | 主菜单/加载中 | 判 null 再操作 |
| GUI 打开时按键也在触发 | 用了 `KeyConflictContext.UNIVERSAL` | 改用 `IN_GAME` 或 `GUI` |

## 练习

1. **热身**：给上面的按键加一个"长按 1 秒才触发"的逻辑（提示：在 `ClientTickEvent.Post` 里用 `KeyBindings.CHARGE.isDown()` 数 tick）。
2. **进阶**：写一个类 `com.dafeiyu.client.DebugOverlay`，在屏幕左上角画一行文字显示玩家坐标（提示：`RegisterGuiLayersEvent`，属于模组总线且仅客户端）。
3. **思考**：如果把 `KeyBindings.CHARGE` 这个字段挪到公共类 `ModItems` 里，专用服务器启动会发生什么？为什么？把结论写下来，再动手验证。
