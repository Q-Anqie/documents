# 双冒号与方法引用

> 读完这篇，你能看到 `Block::new`、`this::commonSetup`、`ItemStack::getItem` 这类写法时不再愣住，并且能判断什么时候必须改回 `() -> ...`。

## 学习目标

- 能解释 `Block::new` 在干什么：它把「调用构造器」这件事本身当成一个值传出去
- 能认出方法引用的四种形式，并各自写出等价的 lambda
- 能判断一段代码必须写 `() -> new Xxx(参数)` 而不能写 `Xxx::new`，并说出理由
- 能看懂主类里的 `modEventBus.addListener(this::commonSetup)`
- 遇到方法引用相关的编译错误时，知道往哪个方向改

## 先看这段代码

注册方块，最省事的写法长这样。

文件：`src/main/java/com/dafeiyu/ModBlocks.java`

```java
public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.register("ruby_block", Block::new);
```

上一篇我们已经知道第二个参数要的是一个 Supplier——「一个能 `get()` 出 Block 的东西」。上一篇的写法是 `() -> new Block(...)`，这里却变成了 `Block::new`。两个冒号，左边是类名，右边是 `new`。既不是方法调用（没有括号），也不是方法定义（没有返回值、没有参数列表、没有方法体）。

**先说一句实话**：上面这行在 1.21.1 里直接抄是编译不过的。`Block::new` 作为 Supplier 使用，要求 `Block` 有一个**无参构造器**；而 1.21.1 的 `Block` 只有一个接收 `BlockBehaviour.Properties` 的构造器。所以这一行能成立的真实版本是下面两种：

```java
// 真实写法 A：把 Properties 一起传进去，Block::new 在这里是「吃 Properties、吐 Block」
public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.registerBlock(
        "ruby_block",
        Block::new,
        BlockBehaviour.Properties.of().destroyTime(2.0f)
);

// 真实写法 B：自己写 lambda，把 Properties 现场造出来
public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.register(
        "ruby_block",
        () -> new Block(BlockBehaviour.Properties.of().destroyTime(2.0f))
);
```

两种写法做的事完全一样。而它们之间的差别，恰好就是这一篇要讲的全部内容：**`Block::new` 到底指什么，以及为什么有时候它不够用。**

## 一、`Block::new` 在干什么

`new Block(props)` 是「**现在就造一个**」。

`Block::new` 是「**记下『怎么造』这件事**」。它不造任何东西，它只是把「调用 `Block` 的构造器」这个动作打包成一个值，交出去。谁拿到它，谁就能在需要的时候调用它，一调用就造出一个新的 `Block`。

用一个不太严谨但很好用的比喻：

```text
new Block(props)   →  你现在把菜炒好了端上桌
Block::new         →  你把菜谱递过去，说「照着这个做」
```

`Block::new` 之所以能放在「要 Supplier」的位置，是因为它的类型可以被编译器理解成 `Supplier<Block>`：`get()` 一调用，就等于执行 `new Block()`。它和 `() -> new Block()` 是同一件事的两种写法，后者啰嗦一点但更直白。

所以你在模组代码里看到 `::`，第一反应应该是：**这是个 lambda 的缩写，它把某个方法（或构造器）包装成了「可以被传递的行为」。**

## 二、一条规则：参数对得上就调用它

方法引用的全部规则可以压缩成一句话：

> `X::方法名` ≈ 一个 lambda，**参数对得上就调用它**。

「参数对得上」是指：编译器看你把 `X::方法名` 塞进了什么位置，那个位置要几个参数、要什么返回值，然后去 `X` 里找一个签名能对上的方法。对上了就合法，对不上就报错。

由此派生出四种形式。每一种我都给「模组里见到的写法」和「等价的 lambda」，你对着看就能记住。

### 形式 1：构造器引用 `类名::new`

```java
// 模组里见到的写法（物品的快捷注册，Properties 单独作为第三个参数传）
ITEMS.registerItem("ruby", Item::new, new Item.Properties());

// 等价 lambda：吃一个 Properties，吐一个 Item
props -> new Item(props)
```

```java
// 模组里见到的写法（方块，同上）
BLOCKS.registerBlock("ruby_block", Block::new, BlockBehaviour.Properties.of());

// 等价 lambda
props -> new Block(props)
```

```java
// 无参构造器的情况：ItemStack 有 ItemStack() 这个空构造器
Supplier<ItemStack> maker = ItemStack::new;

// 等价 lambda
() -> new ItemStack()
```

注意第三种：这里 `ItemStack::new` 被当成 `Supplier<ItemStack>`，也就是「零参数」，所以编译器去找的是 `ItemStack` 的**无参构造器**。同一个 `ItemStack::new`，如果塞进 `Function<Item, ItemStack>` 的位置，编译器就会去找 `ItemStack(Item)` 那个构造器。**`::new` 本身没有固定含义，含义由它被塞进去的位置决定。** 这句话是理解方法引用的钥匙。

### 形式 2：未绑定的实例方法 `类名::方法名`

```java
// 模组里见到的写法：把一堆 ItemStack 变成一堆 Item
List<Item> items = stacks.stream().map(ItemStack::getItem).toList();

// 等价 lambda：第一个参数被当成「调用者」
stack -> stack.getItem()
```

```java
// 方块状态取方块，写数据生成器时会遇到
state -> state.getBlock()   // 等价于 BlockState::getBlock
```

「未绑定」的意思是：你没有指定「在哪个对象上调用」。`ItemStack::getItem` 只说「要调 `getItem` 这个方法」，至于在哪个 `ItemStack` 上调，等 lambda 被调用时由第一个参数提供。

所以规则是：**未绑定的实例方法引用，会把第一个参数当作调用者，剩下的参数照常传进去。**

```java
// 两参数的例子：第一个是调用者，第二个是方法参数
String::startsWith          //  ↔  (s, prefix) -> s.startsWith(prefix)
```

### 形式 3：绑定的实例方法 `对象::方法名`

这是你在模组主类里**第一天**就会遇到的东西：

```java
// 模组里见到的写法
public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
    modEventBus.addListener(this::commonSetup);
}

private void commonSetup(final FMLCommonSetupEvent event) {
    // ...
}
```

```java
// 等价 lambda
modEventBus.addListener(event -> this.commonSetup(event));
```

「绑定」的意思是：调用者已经指定好了，就是 `this`。所以不需要再从参数里拿调用者，参数全部用来喂给方法本身。

再比如日志：

```java
LOGGER::info          //  ↔  msg -> LOGGER.info(msg)
System.out::println   //  ↔  msg -> System.out.println(msg)
```

`System.out` 是一个已经存在的对象，`println` 在它身上调用——这就是「绑定」。这也是为什么 `System.out::println` 是合法的：`out` 是 `System` 的一个静态字段，不是类名。

对比一下形式 2 和形式 3，差别只在冒号左边：

```text
类名::实例方法     →  未绑定，第一个参数当调用者    ItemStack::getItem
对象::实例方法     →  已绑定，调用者就是这个对象    this::commonSetup
```

### 形式 4：静态方法 `类名::静态方法名`

```java
// 模组里见到的写法：把字符串变成数字
int n = parseInt("16");        // 普通调用
Function<String, Integer> f = Integer::parseInt;   // 等价于 s -> Integer.parseInt(s)
```

```java
// 两个参数的静态方法，对应 BiFunction
BiFunction<String, String, ResourceLocation> make = ResourceLocation::fromNamespaceAndPath;
// 等价于 (ns, path) -> ResourceLocation.fromNamespaceAndPath(ns, path)
```

静态方法没有「调用者」这个概念，所以 `类名::静态方法` 的参数列表和方法本身的参数列表**完全一致**，一个不多一个不少。

### 四种形式汇总

| 形式 | 写法 | 等价的 lambda | 参数怎么对 |
|---|---|---|---|
| 构造器引用 | `Item::new` | `props -> new Item(props)` | 参数全给构造器 |
| 未绑定实例方法 | `ItemStack::getItem` | `stack -> stack.getItem()` | 第一个参数当调用者，其余给方法 |
| 绑定实例方法 | `this::commonSetup` | `e -> this.commonSetup(e)` | 参数全给方法，调用者已定 |
| 静态方法 | `Integer::parseInt` | `s -> Integer.parseInt(s)` | 参数全给方法 |

## 三、什么时候必须写 `() -> new Block(props)`

这是本篇的重点。`Block::new` 看起来很酷，但它有个硬限制：**它只能把参数原样转发给构造器，不能做任何别的事。**

具体来说，下面四种情况必须老老实实写 lambda：

**情况 1：构造器要参数，而你想在 `::` 里把它填好。**

`Block::new` 做不到「造一个 `destroyTime` 是 2.0 的方块」，因为它只会把收到的参数原样传给构造器。你必须自己写：

```java
// 想指定属性，就得自己造 Properties
() -> new Block(BlockBehaviour.Properties.of().destroyTime(2.0f))
```

或者把 Properties 作为独立参数交给 `registerBlock`（这时 `Block::new` 又合法了，因为它收到的就是那个 Properties）：

```java
BLOCKS.registerBlock("ruby_block", Block::new, BlockBehaviour.Properties.of().destroyTime(2.0f))
```

**情况 2：参数不是现成的，需要现场 `new` 出来。**

这就是为什么下面这行不能写成 `Item::new`：

```java
// 对：现场 new 一个 Properties 传进去
ITEMS.register("ruby", () -> new Item(new Item.Properties()));

// 错：Supplier 要零参数，Item 没有零参构造器
ITEMS.register("ruby", Item::new);
```

```text
error: incompatible types: invalid constructor reference
    constructor Item in class Item cannot be applied to given types
      required: Item.Properties
      found:    no arguments
```

这里的关键不是「要参数」，而是**「要的参数得当场造一个出来」**。`Item::new` 只会转发它收到的参数，可 `register` 那个位置一个参数都不给它，于是它既没东西转发、又没法自己造——死路。

对比一下上一篇讲过的快捷方法，同一个 `Item::new` 在那里就合法了：

```java
// 合法：这里 Item::new 被当成 Function<Item.Properties, Item>
// 位置要「吃一个 Properties、吐一个 Item」，构造器正好对得上
ITEMS.registerItem("ruby", Item::new, new Item.Properties());

// 等价于
ITEMS.register("ruby", () -> new Item(new Item.Properties()));
```

**同一行 `Item::new`，换个位置就从非法变合法。** 所以判断能不能用 `::`，永远要问「它被塞进哪个位置、那个位置要什么签名」，而不是问「`Item::new` 本身对不对」。

**情况 3：需要用到外部变量。**

```java
// 想根据一个字段决定颜色
private static final int RUBY_COLOR = 0xFF0000;

() -> new RubyBlock(RUBY_COLOR)    // 对：lambda 能捕获外部变量
RubyBlock::new                     // 错：:: 无法把 RUBY_COLOR 塞进去
```

**情况 4：`new` 之前或之后还要干别的事。**

```java
() -> {
    Item.Properties props = new Item.Properties().stacksTo(16);
    return new Item(props);        // 多行逻辑，:: 完全做不到
}
```

## 四、判断口诀

写不出来的时候，按这三步走：

```text
第 1 步：看位置。这个参数要的是 Supplier（0 参）、Function（1 参）、Consumer（1 参无返回）还是别的？
第 2 步：看方法。我要调的那个方法/构造器，参数列表和它一样吗？
          一样 → 可以用 ::
          不一样（缺参数、要现场造、要捕获变量） → 用 () -> ...
第 3 步：不确定就先写 lambda，能编译；然后试着缩写成 ::，编译器不认就退回去。
```

第 3 步很重要：**lambda 是「完整版」，`::` 是「缩写版」**。永远先写完整版，再缩写。反过来（先猜 `::` 再改成 lambda）会浪费很多时间。

再给你一个反直觉但很实用的经验：**在模组代码里，`() -> new Xxx(...)` 的出现频率远高于 `Xxx::new`。** 因为方块和物品的构造器几乎都要 Properties，而 Properties 几乎都要现场配置。`::` 真正高频的地方是方法引用（`this::commonSetup`、`LOGGER::info`），而不是构造器引用。

## 完整示例

文件：`src/main/java/com/dafeiyu/ModBlocks.java`

```java
package com.dafeiyu;

import net.minecraft.world.level.block.Block;
import net.minecraft.world.level.block.SoundType;
import net.minecraft.world.level.block.state.BlockBehaviour;
import net.neoforged.neoforge.registries.DeferredBlock;
import net.neoforged.neoforge.registries.DeferredRegister;

public class ModBlocks {
    public static final DeferredRegister.Blocks BLOCKS = DeferredRegister.createBlocks("dafeiyu");

    // 写法 A：registerBlock + Block::new，Properties 作为第三个参数传进去
    // 这里 Block::new 被当成 Function<BlockBehaviour.Properties, Block>
    public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.registerBlock(
            "ruby_block",
            Block::new,
            BlockBehaviour.Properties.of()
                    .destroyTime(2.0f)
                    .explosionResistance(10.0f)
                    .sound(SoundType.METAL)
                    .requiresCorrectToolForDrops()
    );

    // 写法 B：register + lambda，Properties 在 lambda 里现场造
    // 这里不能用 Block::new，因为 register 要的是零参 Supplier
    public static final DeferredBlock<Block> RUBY_ORE = BLOCKS.register(
            "ruby_ore",
            () -> new Block(BlockBehaviour.Properties.of()
                    .destroyTime(3.0f)
                    .requiresCorrectToolForDrops())
    );
}
```

文件：`src/main/java/com/dafeiyu/ModItems.java`

```java
package com.dafeiyu;

import net.minecraft.world.item.Item;
import net.neoforged.neoforge.registries.DeferredItem;
import net.neoforged.neoforge.registries.DeferredRegister;

public class ModItems {
    public static final DeferredRegister.Items ITEMS = DeferredRegister.createItems("dafeiyu");

    // Item::new 合法：registerItem 的第二个参数是 Function<Item.Properties, Item>
    public static final DeferredItem<Item> RUBY = ITEMS.registerItem(
            "ruby",
            Item::new,
            new Item.Properties()
    );

    // 等价写法：lambda 里现场 new 一个 Properties
    public static final DeferredItem<Item> RUBY_DUST = ITEMS.register(
            "ruby_dust",
            () -> new Item(new Item.Properties().stacksTo(16))
    );
}
```

文件：`src/main/java/com/dafeiyu/DafeiyuMod.java`

```java
package com.dafeiyu;

import net.neoforged.bus.api.IEventBus;
import net.neoforged.fml.ModContainer;
import net.neoforged.fml.common.Mod;
import net.neoforged.fml.event.lifecycle.FMLCommonSetupEvent;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Mod(DafeiyuMod.MOD_ID)
public class DafeiyuMod {
    public static final String MOD_ID = "dafeiyu";
    private static final Logger LOGGER = LoggerFactory.getLogger(MOD_ID);

    public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
        ModItems.ITEMS.register(modEventBus);
        ModBlocks.BLOCKS.register(modEventBus);

        // this::commonSetup 是绑定的实例方法引用
        // 等价于：modEventBus.addListener(event -> this.commonSetup(event));
        modEventBus.addListener(this::commonSetup);
    }

    private void commonSetup(final FMLCommonSetupEvent event) {
        // LOGGER::info 是绑定的实例方法引用
        // 等价于：event.enqueueWork(() -> LOGGER.info("大肥鱼模组初始化完成"));
        event.enqueueWork(() -> LOGGER.info("大肥鱼模组初始化完成"));
    }
}
```

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| `invalid constructor reference: constructor Item cannot be applied to given types; required: Item.Properties, found: no arguments` | 在要零参 Supplier 的位置用了 `Item::new`，而 `Item` 没有无参构造器 | 改 `() -> new Item(new Item.Properties())`，或用 `registerItem(..., Item::new, props)` |
| `invalid method reference: non-static method getItem() cannot be referenced from a static context` | 在要零参的位置用了未绑定的实例方法引用，没人提供调用者 | 补上调用者：`stack -> stack.getItem()`，或 `SomeObj::getItem`（绑定） |
| `incompatible types: ItemStack cannot be converted to Supplier<ItemStack>` | 把 `stack.getItem()`（已经调用了）写在了要 lambda 的位置 | 去掉括号：`ItemStack::getItem` |
| `illegal start of expression` / `';' expected`，指向 `::` | 在不需要函数式接口的位置用了 `::`，比如 `int x = Integer::parseInt;` | `::` 只能赋给函数式接口类型（`Supplier`、`Function`、`Consumer` 等），不能赋给 `int`、`String` |
| `reference to println is ambiguous` | `println` 有很多重载，编译器不知道挑哪个 | 显式写 lambda 并指定参数类型：`(String s) -> System.out.println(s)` |
| 主类里 `this::commonSetup` 报「找不到符号」 | `commonSetup` 的参数类型写错了（不是 `FMLCommonSetupEvent`），签名对不上 | 检查方法签名，参数必须是事件类型，返回值必须是 `void` |
| 静态方法里写 `this::xxx` | 静态上下文没有 `this` | 改成 `DafeiyuMod::xxx`（如果 `xxx` 是静态的）或把方法改成静态 |

## 练习

**1.（易）** 把下面三个 lambda 改写成方法引用：

```java
a) stack -> stack.getItem()
b) msg -> LOGGER.info(msg)
c) props -> new Block(props)
```

<details>
<summary>答案</summary>

```java
a) ItemStack::getItem      // 未绑定：第一个参数当调用者
b) LOGGER::info            // 绑定：LOGGER 是已存在的对象
c) Block::new              // 构造器引用，参数原样转发
```

注意 a 和 b 的区别只在冒号左边：`ItemStack` 是类（没有调用者，得从参数里拿），`LOGGER` 是对象（调用者已定）。

</details>

**2.（中）** 下面四行，哪些能编译？不能的说明原因。

```java
1) ITEMS.register("ruby", Item::new);
2) ITEMS.registerItem("ruby", Item::new, new Item.Properties());
3) BLOCKS.register("ruby_block", Block::new);
4) BLOCKS.registerBlock("ruby_block", Block::new, BlockBehaviour.Properties.of());
```

<details>
<summary>答案</summary>

1）不能。`register` 要 `Supplier<Item>`（零参），而 `Item` 只有 `Item(Item.Properties)` 一个构造器，`Item::new` 无处取参数。

2）能。`registerItem` 的第二个参数是 `Function<Item.Properties, Item>`，构造器签名正好对上，Properties 由第三个参数提供。

3）不能。理由同 1，`Block` 只有 `Block(BlockBehaviour.Properties)`。

4）能。`registerBlock` 的第二个参数是 `Function<BlockBehaviour.Properties, Block>`，Properties 由第三个参数提供。

结论：`Xxx::new` 能不能用，取决于它被塞进的位置要几个参数，而不取决于 `Xxx` 本身。

</details>

**3.（难）** 有人写了这个，想让红宝石方块有 7 级光照。哪里错了？怎么改？

```java
public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.registerBlock(
        "ruby_block",
        Block::new,
        BlockBehaviour.Properties.of().lightLevel(state -> 7)
);
```

<details>
<summary>答案</summary>

这段其实**没有错**，能编译也能跑。`Block::new` 收到的就是那个已经配好 `lightLevel` 的 Properties，原样转发给构造器，光照设置生效。

真正容易错的是把它改写成 `register` + `Block::new`：

```java
// 错：register 要零参 Supplier，Block::new 没参数可转发
BLOCKS.register("ruby_block", Block::new);
```

正确改法是写 lambda，把 Properties 现场造出来：

```java
BLOCKS.register("ruby_block",
        () -> new Block(BlockBehaviour.Properties.of().lightLevel(state -> 7)));
```

顺带一个观察：`state -> 7` 本身也是一个 lambda，它被塞进 `lightLevel` 这个要 `Function<BlockState, Integer>`（准确说是 `ToIntFunction<BlockState>`）的位置。所以这一行里同时出现了两种「把行为当值传」的写法——`::` 和 `->`，它们是一家人。

</details>
