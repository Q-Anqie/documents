# 性能优化与最佳实践

> 这一篇讲的是「为什么你的模组一装就掉帧」。优化不是玄学，是把几件具体的事做对：别在每秒 20 次的地方做重活，别让该缓存的东西每次都重算，别让静态字段抓住整个世界。

## 学习目标

- 能判断一段代码是不是跑在「热路径」上，并说清它一秒钟会被调用多少次。
- 能把 `tick`、渲染、事件处理器里常见的五种浪费改成正确写法。
- 能安全地做缓存，并知道什么时候必须让缓存失效。
- 能说清 `getTicker` 什么时候该返回 `null`、`setChanged()` 什么时候才该调。
- 能列出「静态字段持有 `Level`/`Player`/`ItemStack`」造成的两个具体后果。
- 能用事件、标签、软依赖替代 Mixin 和硬编码，写出与别的模组共存的代码。

## 一、先认清「热路径」

优化的第一步不是改代码，是**知道哪段代码跑得多**。模组里的代码按调用频率可以粗分成三档：

| 档位 | 调用频率 | 典型位置 | 允许做什么 |
|---|---|---|---|
| 冷 | 一次或几次 | 注册、配置加载、数据包重载 | 什么都可以，读文件、建索引、解析 json |
| 温 | 每秒几次到几十次 | 玩家交互、方块被破坏、发包处理 | 少量对象分配、查一次 Map |
| 热 | 每秒 20 次以上 | `tick`、`getTicker`、事件里的 `TickEvent` | 只做加减法和字段读写 |
| 极热 | 每秒 60~1000 次 | `render`、`getShape`、`getLightBlock`、粒子生成 | 什么都不做，除了读现成的值 |

给你一个尺度感：

- 一个区块是 16×16×384 = 98304 个方块位置。**遍历一个区块**，哪怕每次只花 10 纳秒，也要 1 毫秒。
- 20 个已加载区块半径（默认视距 10 是 21×21 个区块），就是 441 个区块。全扫一遍 = 400 毫秒。**一 tick 只有 50 毫秒。**
- 渲染一帧要跑 60 次以上，`render` 里 `new` 一个 `Component`，一秒钟就是 3600 个对象，全进新生代。

所以第一条规则很简单：

> **凡是「每 tick」「每帧」的代码，先问一句：这件事真的需要每 tick 做吗？**

九成的情况下，答案是「不需要，事件驱动就够了」。

## 二、tick 里不要做的事

### 2.1 每 tick new 对象

```java
// 反例：每秒 20 次分配，还带字符串拼接
public static void tick(Level level, BlockPos pos, BlockState state, RubyChargerBlockEntity be) {
    be.setChanged();
    level.sendBlockUpdated(pos, state, state, Block.UPDATE_CLIENTS);
    be.status = "充能中: " + be.charge + "/" + MAX;   // 每 tick 拼一个 String
}
```

`setChanged()` 每 tick 调，等于每 tick 都告诉存档「这个区块脏了」，存档线程会反复重写区块。`sendBlockUpdated` 每 tick 发一次包，20 个方块就是 400 个包/秒。字符串拼接更隐蔽：它不只是慢，还会让每秒产生 20 个短命对象，堆压力上去了 GC 就会更频繁。

```java
// 正例：只在"值真的变了"时做一次
public static void tick(Level level, BlockPos pos, BlockState state, RubyChargerBlockEntity be) {
    if (level.isClientSide || be.charge >= be.capacity) {
        return;
    }
    be.charge++;
    if (be.charge % 20 == 0) {                    // 每秒同步一次
        be.setChanged();                          // 一秒标脏一次，够了
        level.sendBlockUpdated(pos, state, state, Block.UPDATE_CLIENTS);
    }
}
```

### 2.2 遍历大集合

```java
// 反例：每 tick 扫全服玩家，只为找一个最近的
for (ServerPlayer player : server.getPlayerList().getPlayers()) {
    if (player.distanceToSqr(pos.getX(), pos.getY(), pos.getZ()) < 64) { ... }
}
```

玩家不多时这段代码「看起来没问题」，但它每 tick 都跑、每个充能台都跑。10 个充能台 × 20 个玩家 × 20 tick = 每秒 4000 次距离计算，全是平方根之前的乘法——还只是乘法，真正贵的是 `getPlayers()` 返回列表的迭代器分配。

正确做法是**反过来**：不要「方块找玩家」，而是「玩家靠近时触发」。原版有现成机制：

- `Block#onNeighborChange` / `Entity#playerTouch`：靠近才触发。
- `PlayerEvent.PlayerTickEvent`：只在玩家身上挂一个 tick，成本固定。
- `LevelChunk` 的加载/卸载事件：区块进来时算一次。

### 2.3 字符串拼接与日志

```java
// 反例：DEBUG 日志每 tick 刷
LOGGER.debug("充能台 " + pos + " 当前 " + be.charge);
```

两个问题：字符串在**判断日志级别之前**就拼好了，即使 `debug` 被关掉也照样分配；日志本身有 IO 锁，每秒几千行会直接把主线程拖住。

```java
// 正例：用占位符，并且加条件
if (LOGGER.isDebugEnabled()) {
    LOGGER.debug("充能台 {} 当前 {}", pos, be.charge);
}
```

`{}` 占位符是延迟格式化的：级别不够时，参数根本不会被转成字符串。**发布版里把调试日志全删掉**，或者至少改成 `TRACE`。

### 2.4 Stream

```java
// 反例
int count = be.getInventory().getSlots() == 0 ? 0
        : IntStream.range(0, be.getInventory().getSlots())
                .mapToObj(be.getInventory()::getStackInSlot)
                .filter(s -> !s.isEmpty())
                .mapToInt(ItemStack::getCount)
                .sum();
```

Stream 的每一环都会创建一个新的中间对象（Spliterator、Pipeline），还有装箱拆箱。它写起来漂亮，但在热路径上是纯粹的浪费。

```java
// 正例
int count = 0;
for (int i = 0; i < slots; i++) {
    ItemStack stack = be.getInventory().getStackInSlot(i);
    if (!stack.isEmpty()) {
        count += stack.getCount();
    }
}
```

**结论：Stream 用在初始化、数据加载、一次性计算里没问题；tick 和 render 里一律用 for 循环。**

### 2.5 在事件处理器里做重活

`@SubscribeEvent` 挂在游戏总线上的方法，很多是每 tick 调的：`TickEvent.ServerTickEvent`、`PlayerTickEvent`、`LevelTickEvent`。这些方法里读一次配置、查一次 `ModList`、建一个 `new ArrayList<>()`，成本都会被乘以 20 × 玩家数 × 世界数。

一个实用的写法是**提前算好、只算一次**：

```java
// 反例：每次 tick 都查模组列表
@SubscribeEvent
public static void onServerTick(TickEvent.ServerTickEvent event) {
    if (ModList.get().isLoaded("jei")) { ... }   // 这个结果永远不会变
}

// 正例：类加载时算一次
private static final boolean JEI_LOADED = ModList.get().isLoaded("jei");
```

## 三、缓存：把「每次都要算」变成「算一次」

### 3.1 `ResourceLocation` 提到常量

```java
// 反例：每次调用都拼字符串、算哈希
ResourceLocation id = ResourceLocation.fromNamespaceAndPath("dafeiyu", "ruby_" + type);
```

`ResourceLocation` 的构造会校验字符、分配对象、算 `hashCode`。在 `render` 或 `tick` 里每帧调一次，就是每帧一次分配。

```java
// 正例：集中放一个类，所有 id 只建一次
// src/main/java/com/dafeiyu/ModIds.java
public final class ModIds {

    private ModIds() {}

    public static final ResourceLocation RUBY =
            ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "ruby");
    public static final ResourceLocation RUBY_ORE =
            ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "ruby_ore");
    public static final ResourceLocation CHARGER_SYNC =
            ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "charger_sync");

    /** 需要按名字动态取时，用这个入口，别在调用点拼字符串 */
    public static ResourceLocation of(String path) {
        return ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, path);
    }
}
```

注意 `final class` + 私有构造器：这是一个「只有常量的工具类」，不该被 `new`，也不该被继承。

### 3.2 `ItemStack` 常量的陷阱

这一条要格外小心，因为 `ItemStack` **是可变的**。

```java
// 危险：这个"常量"随时可能被改
public static final ItemStack RUBY_STACK = new ItemStack(ModItems.RUBY.get());
```

只要有人写 `RUBY_STACK.setCount(64)` 或 `RUBY_STACK.shrink(1)`，全局状态就被永久改了，而且改的时候没有任何警告。更糟的是如果它被塞进了某个容器，计数会被容器继续改。

正确做法分三种情况：

| 需求 | 做法 |
|---|---|
| 只是「一个红宝石」这个概念 | 每次 `new ItemStack(ModItems.RUBY.get())`，它便宜到不值得缓存 |
| 要在渲染里反复画同一个图标 | 缓存**只读**的模板，用 `stack.copyWithCount(n)` 派生，绝不改原件 |
| 要判断「是不是红宝石」 | 用 `stack.is(ModItems.RUBY.get())` 或 `stack.is(ModTags.Items.RUBIES)`，不要比较 `ItemStack` |

```java
// 可接受的只读缓存：只在 GUI 里当图标用
private static final ItemStack RUBY_ICON = new ItemStack(ModItems.RUBY.get());

// 用的时候派生一份，不改原件
ItemStack shown = RUBY_ICON.copyWithCount(charge);
```

真正该缓存的是 `Item` / `Holder` / `DeferredItem` 这类**不可变**的引用：`ModItems.RUBY.get()` 每次调用只是一次字段读，但如果你在循环里调一万次，把它提到局部变量依然更清楚。

### 3.3 `Map` 缓存与失效

缓存不难，难的是**什么时候让它失效**。三种常用策略：

**① 版本号失效**（最简单，适合「数据包内容」）

自己维护一个 `int` 版本号，数据变了就加一：

```java
public final class ChargingIndex {

    private static Map<Item, Integer> cached = Map.of();
    private static int version;        // 每次数据变化就 +1
    private static int builtFor = -1;  // 缓存是按哪一版建的

    public static void invalidate() {
        version++;
    }

    public static int valueOf(Item item) {
        if (builtFor != version) {
            cached = buildIndex();     // 重建一次
            builtFor = version;
        }
        return cached.getOrDefault(item, 0);
    }
}
```

**② 事件失效**（最准确，适合「注册表 / 标签内容」）

```java
@SubscribeEvent
public static void onTagsUpdated(TagsUpdatedEvent event) {
    ChargingIndex.invalidate();   // 标签变了，索引作废
}
```

**③ 手动失效 + 上限**（适合「按位置缓存」）

```java
// BlockPos 是不可变对象，可以当 key；但大量条目建议用 long 当 key
private static final Map<BlockPos, CachedData> CACHE = new HashMap<>();
private static final int MAX_ENTRIES = 4096;

static void put(BlockPos pos, CachedData data) {
    if (CACHE.size() >= MAX_ENTRIES) {
        CACHE.clear();     // 简单粗暴但有效：别让缓存无限长
    }
    CACHE.put(pos, data);
}
```

**没有失效策略的缓存 = 内存泄漏 + 数据错乱。** 如果你说不清「这个缓存什么时候该清」，那就先别加缓存。

## 四、方块实体：ticker 与 `setChanged`

### 4.1 `getTicker` 只在真的需要时返回

`getTicker` 每 tick 都会被调用一次（每个加载中的方块实体）。它返回 `null` 时，游戏就完全跳过这个方块实体——**这是最便宜的优化**。

```java
// src/main/java/com/dafeiyu/block/RubyChargerBlock.java（片段）
@Nullable
@Override
public <T extends BlockEntity> BlockEntityTicker<T> getTicker(Level level, BlockState state,
                                                             BlockEntityType<T> type) {
    // 客户端不需要 tick：数据靠同步过来
    if (level.isClientSide) {
        return null;
    }
    // 服务端才 tick，且只在"有活干"的时候
    return createTickerHelper(type, ModBlockEntities.RUBY_CHARGER.get(),
            RubyChargerBlockEntity::tick);
}
```

三条经验：

1. **客户端能不算就不算。** 客户端只负责显示，所有逻辑都在服务端算完再同步。
2. **能事件驱动就别 tick。** 「玩家右键时充一次」用 `useWithoutItem`，不要用 tick 每帧检查玩家在不在旁边。
3. **`createTickerHelper` 的第三个参数是方法引用，不是 `new`。** 每次 `getTicker` 都 `new` 一个 ticker 对象是浪费，方法引用是现成的单例。

### 4.2 `setChanged()` 的时机

`setChanged()` 的语义是「这个方块实体的数据脏了，存档时要重写这个区块」。它**不是**「保存一下」，也不是「同步一下」。所以：

| 场景 | 该不该调 |
|---|---|
| 字段值真的变了（进度 +1、模式切换） | 该 |
| 每 tick 无条件调 | 不该 |
| 只是读了数据 | 不该 |
| 客户端改了本地副本 | 不该（客户端没有存档职责） |
| 库存内容变化 | 该，在 `onContentsChanged` 里调一次 |

```java
// 正例：变化点调一次，tick 里不调
public void addCharge(int amount) {
    int old = this.charge;
    this.charge = Math.min(this.charge + amount, capacity);
    if (this.charge != old) {       // 没变就不标脏
        setChanged();
        if (level != null && !level.isClientSide) {
            level.sendBlockUpdated(worldPosition, getBlockState(), getBlockState(),
                    Block.UPDATE_CLIENTS);
        }
    }
}
```

把「改值」和「通知」封在同一个方法里，比在十几个调用点各写一遍可靠得多。

## 五、网络：少发、合并、只发差量

### 5.1 别每 tick 发包

```java
// 反例：每 tick 一个包，一个充能台就是 20 包/秒
PacketDistributor.sendToPlayersTrackingChunk(serverLevel, chunkPos,
        new ChargerSyncPayload(pos, charge));
```

一个玩家在基地里放 20 个机器，就是 400 包/秒，还没算别的模组。网络线程和主线程都要处理这些包，延迟会肉眼可见地上涨。

```java
// 正例：脏标记 + 定时冲刷
private boolean dirty;

public void markDirty() {
    this.dirty = true;
}

public static void tick(...) {
    if (!be.dirty) {
        return;
    }
    if (++be.ticksSinceSync >= 10) {      // 半秒一次，肉眼完全看不出延迟
        be.ticksSinceSync = 0;
        be.dirty = false;
        PacketDistributor.sendToPlayersTrackingChunk(...);
    }
}
```

### 5.2 合并小包

「打开了」「关闭了」「进度变了」「模式切了」四个包，可以合成一个带枚举字段的包：

```java
// src/main/java/com/dafeiyu/network/ChargerActionPayload.java（片段）
public record ChargerActionPayload(BlockPos pos, byte action, int value)
        implements CustomPacketPayload {

    public static final byte ACTION_TOGGLE = 0;
    public static final byte ACTION_SET_MODE = 1;

    public static final StreamCodec<ByteBuf, ChargerActionPayload> STREAM_CODEC =
            StreamCodec.composite(
                    BlockPos.STREAM_CODEC, ChargerActionPayload::pos,
                    ByteBufCodecs.BYTE, ChargerActionPayload::action,
                    ByteBufCodecs.VAR_INT, ChargerActionPayload::value,
                    ChargerActionPayload::new);
    // ...
}
```

一个包 8+1+4 字节，比四个包各带 20 多字节的头部开销省得多。**包数比包大小更贵**：每个包都有固定开销（长度、id、序列化上下文）。

### 5.3 只发变化量

| 反例 | 正例 |
|---|---|
| 发整个 `ItemStackHandler`（27 格） | 发「第 3 格变成了什么」 |
| 发整个玩家背包 | 用原版同步，什么都别发 |
| 发方块实体的完整 NBT | 发 `getUpdateTag`，让原版机制处理 |
| 每 tick 发一次坐标 | 只在跨格时发 |

还有一条硬限制要记住：上行包必须小于 **32 KiB**，下行小于 **1 MiB**，超了不是变慢，是直接断线。所以「一次把 5000 个方块的改动发过去」这种设计从根上就行不通。

### 5.4 优先用现成通道

在写任何 `CustomPacketPayload` 之前，先查一遍：

| 你想同步的 | 现成机制 |
|---|---|
| 方块实体的数据 | `getUpdateTag` + `getUpdatePacket` + `sendBlockUpdated` |
| GUI 里的一个整数 | `ContainerData` |
| 物品上的自定义数据 | 数据组件的 `networkSynchronized` |
| 实体身上的状态 | `SynchedEntityData` |
| 玩家血量、经验、背包 | 原版封包 |

**自己发包是最后手段，不是第一选择。** 每多一条自定义通道，就多一份协议版本兼容的负担。

## 六、客户端渲染：别 new、合批、控粒子

### 6.1 `render` 里不要 new

```java
// 反例：每帧分配
public void render(GuiGraphics graphics, int mouseX, int mouseY, float partialTick) {
    graphics.drawString(this.font, new Component.literal("充能: " + charge), 8, 8, 0xFFFFFF);
}
```

`new Component.literal(...)` 每帧一次，60 帧/秒就是 3600 次分配 + 3600 次布局计算（`drawString` 要算字宽）。GUI 卡顿经常就是这么来的。

```java
// 正例：在 init() 或数据变化时算好
private Component chargeText = Component.empty();

@Override
protected void init() {
    super.init();
    updateText();
}

private void updateText() {
    chargeText = Component.translatable("gui.dafeiyu.charge", charge, capacity);
}

public void render(GuiGraphics graphics, int mouseX, int mouseY, float partialTick) {
    graphics.drawString(this.font, chargeText, 8, 8, 0xFFFFFF, false);
}
```

同理，`render` 里不要 `new ItemStack`、不要 `new PoseStack`、不要 `new ArrayList`、不要 `String.format`。

### 6.2 `RenderType` 与批次合并

Minecraft 的渲染是**按 `RenderType` 分批**的：同一个 `RenderType` 的顶点会被攒在一起，一次提交给显卡。这意味着：

- 相邻的两个实体如果 `RenderType` 相同，它们的绘制可以合并。
- 每切换一次 `RenderType`，就是一次「打断批次」，有固定开销。

所以自定义渲染里：

1. **同一个模型尽量用一个 `RenderType`。** 不要一半 `translucent` 一半 `solid`。
2. **不要为了「一点点透明」把整块改成 `translucent`。** `translucent` 需要排序，开销明显更高。
3. **`RenderType` 只建一次。** `RenderType.entityCutout(...)` 这类方法内部有缓存，但 `RenderType.create(...)` 没有——在 `render` 里调 `create` 会每帧新建一个渲染管线配置。

```java
// 反例：每帧建一次 RenderType
RenderType type = RenderType.create("ruby_glow", ...);

// 正例：类加载时建一次
private static final RenderType RUBY_GLOW = RenderType.create("ruby_glow", ...);
```

### 6.3 粒子数量控制

粒子是「便宜但量大」的典型。一个粒子本身只花几微秒，但 2000 个粒子就是几十毫秒。

```java
// 反例：每个方块每 tick 都喷
level.addParticle(ParticleTypes.END_ROD, x, y, z, 0, 0, 0);
```

控制手段有三个，按推荐顺序：

1. **只在事件点喷。** 充满电的那一刻喷一次，而不是整个充能过程都在喷。
2. **降频。** `if (level.random.nextInt(4) == 0)`，四分之一概率。
3. **看设置。** 原版有 `Minecraft.getInstance().options.particles()`（`ALL` / `DECREASED` / `MINIMAL`），尊重玩家的选择是基本礼貌。

另外，**粒子必须在客户端加**。在服务端 `level.addParticle` 什么也不会发生（或者更糟：在专用服务器上抛异常）。

## 七、内存：静态字段的三个雷

静态字段活得比世界久。这是它唯一的问题，但这个问题很致命。

### 7.1 别静态持有 `Level`

```java
// 反例
public static Level SERVER_LEVEL;

@SubscribeEvent
public static void onLevelLoad(LevelEvent.Load event) {
    SERVER_LEVEL = event.getLevel();
}
```

后果有两个：

1. **内存泄漏**：`Level` 引用着区块、实体、方块实体、玩家……退出世界后这个对象本该被回收，但静态字段抓着它不放。反复进出世界，内存一路涨。
2. **跨存档污染**：你进了第二个世界，`SERVER_LEVEL` 还指向第一个世界的对象。往里放方块会抛「方块实体不在这个 level 里」之类的怪异常，或者更糟——静默地改了错误的世界。

正确做法是**每次要用的时候现取**：`server.overworld()`、`player.serverLevel()`、`event.getLevel()`。这些调用都很便宜。

### 7.2 别静态持有 `Player`

```java
// 反例
public static Player LAST_CLICKER;
```

玩家退出后这个对象还在，它的 `connection`、`inventory`、`level` 全都被拖着。更常见的是**跨玩家串数据**：A 玩家点了按钮，`LAST_CLICKER = A`；B 玩家触发某逻辑时读到 `LAST_CLICKER`，结果是 A。

**永远从事件参数、`context.player()`、`stack.get(DataComponents...)` 里拿当前玩家。**

### 7.3 别静态持有 `ItemStack`

前面 3.2 说过可变性。这里补另一个角度：`ItemStack` 引用着 `Item`，`Item` 引用着它的 `Holder`，`Holder` 引用着注册表。虽然注册表本来就不回收，但如果这个 `ItemStack` 还带着自定义数据组件（比如一个存了大 `List` 的组件），那就是实打实的内存占用。

## 八、代码组织

### 8.1 注册类按内容拆分

一个 `ModRegistry` 装 200 个字段，会带来两个问题：一是打开文件要滚半天，二是**静态初始化顺序变得难以预测**——A 字段引用了 B 字段，B 还没初始化完，你就拿到 `null`。

按内容拆：`ModBlocks`、`ModItems`、`ModBlockEntities`、`ModMenus`、`ModEffects`、`ModSounds`、`ModDataComponents`、`ModAttachments`、`ModPayloads`。每个类只暴露一个 `register(IEventBus)`。

**依赖方向也要单向**：`ModItems` 可以引用 `ModBlocks`，`ModBlocks` 不要引用 `ModItems`。反过来的需求（方块要用物品）通常说明你该用 `Supplier` 延迟取值。

### 8.2 `client` 包隔离

判据只有一条：**import 里出现 `net.minecraft.client` 或 `com.mojang.blaze3d`，就放 `client` 包。**

配套的两件事：

```java
// ① 类上加 Dist 限制，让服务端根本不加载它
@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD, value = Dist.CLIENT)
public class ClientSetup { ... }
```

```java
// ② 公共代码里只能"间接"引用客户端类：方法引用、反射、或包一层入口
// ModPayloads 在服务端也会加载，但它只写 ClientPayloadHandler::handle
// 方法引用只解析类，不加载方法体里的客户端类型 —— 这是安全的
registrar.playToClient(SyncPayload.TYPE, SyncPayload.STREAM_CODEC, ClientPayloadHandler::handle);
```

反例是公共代码里直接写 `new RubyChargerScreen(...)` 或 `Minecraft.getInstance()`——专用服务器启动时就会 `NoClassDefFoundError`。

### 8.3 常量集中

把「魔法数字」和「魔法字符串」集中到一处：

```java
// src/main/java/com/dafeiyu/ModConstants.java
public final class ModConstants {
    private ModConstants() {}

    public static final int CHARGER_DEFAULT_CAPACITY = 100;
    public static final int CHARGER_SYNC_INTERVAL = 20;   // tick
    public static final float RUBY_SWORD_DAMAGE = 3.0F;
    public static final float RUBY_SWORD_SPEED = -2.4F;
}
```

好处不只是「好改」：当你发现「同步间隔 20 tick」要改成 10，只改一处，不会漏掉某个复制粘贴的 `20`。

### 8.4 别让 `@EventBusSubscriber` 泛滥

`@EventBusSubscriber` 很方便，但每加一个类，就多一次「这个类在什么时机被加载」的隐式行为。类一多，你会在日志里看到一堆莫名其妙的初始化顺序问题。

经验规则：

- **按关注点建类**，不按事件建类。一个 `ChargerEvents` 里放三个相关的事件处理器，比三个各含一个方法的类好。
- **模组总线（`Bus.MOD`）的事件和游戏总线（默认）的事件不要混在一个类里**——`bus` 参数写错的表现是「事件完全不触发」，而且没有报错。
- 需要精确控制加载时机时，改用主类里显式 `modBus.addListener(...)`，这样「什么时候注册」一目了然。

## 九、兼容性

### 9.1 优先事件与数据映射，而不是 Mixin

Mixin 是「改别人的字节码」。它能做到事件做不到的事，但代价是：**别人一改同一个方法，你就崩**。

判断顺序应该是：

1. **有现成事件吗？** 加掉落 → `LivingDropsEvent`；改战利品 → `LootTableLoadEvent`；加配方 → 数据包。
2. **有数据映射吗？** 给原版方块挂自定义数据 → `DataMapType`；改附魔行为 → 效果组件。见 [附魔与数据映射](../06-进阶篇/07-附魔与数据映射.md)。
3. **有标签吗？** 让镐能挖你的方块 → 加进 `minecraft:mineable/pickaxe`，不用 Mixin。
4. **都没有，才考虑 Mixin。** 并且写清楚注释：「这里为什么不得不用 Mixin」。

### 9.2 Tag 优于硬编码

```java
// 反例：写死原版物品，别的模组加了同类物品就享受不到
if (stack.is(Items.IRON_INGOT) || stack.is(Items.GOLD_INGOT)) { ... }

// 正例：用自己的标签，让别人能往里加
if (stack.is(ModTags.Items.CHARGEABLE)) { ... }
```

配套的标签文件：

```json
// src/main/resources/data/dafeiyu/tags/item/chargeable.json
{
  "values": [
    "minecraft:iron_ingot",
    "minecraft:gold_ingot",
    { "id": "#c:ingots", "required": false }
  ]
}
```

`"required": false` 是关键：如果 `#c:ingots` 这个标签不存在（没装提供它的模组），游戏**不会**因此报错。这样你的模组既能吃到通用标签的好处，又不会硬依赖它。

### 9.3 软依赖

```java
// 只在装了 JEI 时才注册它的插件
@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class ModIntegration {

    private static final boolean JEI_LOADED = ModList.get().isLoaded("jei");

    @SubscribeEvent
    public static void onInterModEnqueue(InterModEnqueueEvent event) {
        if (!JEI_LOADED) {
            return;
        }
        // 注册 JEI 插件（这段代码在 JEI 类上，必须保证不装 JEI 时不会执行到）
    }
}
```

注意 `JEI_LOADED` 是 `static final`，类加载时算一次。**不要**把「查模组列表」写进 tick。

更规范的做法是把集成代码单独放一个类（`com.dafeiyu.compat.jei.JeiPlugin`），只在 `JEI_LOADED` 为真时才 `Class.forName` 或通过事件间接调用——这样即使没装 JEI，那个类也永远不会被加载。

`neoforge.mods.toml` 里对应的依赖也要标成可选：

```toml
[[dependencies.dafeiyu]]
modId = "jei"
type = "optional"
versionRange = "[19,)"
ordering = "AFTER"
side = "CLIENT"
```

## 十、反模式对照表

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| tick 里 `new` 对象 / 拼字符串 | 每秒 20 次分配，GC 压力 | 提前算好，只在变化时更新 |
| tick 里遍历全服玩家/全区块 | 成本随规模爆炸 | 事件驱动，或反过来从玩家出发 |
| tick 里打日志 | IO 锁 + 字符串分配 | `isDebugEnabled()` 包住，发布版删掉 |
| 热路径用 Stream | 中间对象 + 装箱 | 普通 for 循环 |
| 每 tick `setChanged()` | 每 tick 标记区块脏，存档卡 | 只在值真的变化时调 |
| 每 tick 发包 | 网络与主线程双份开销 | 脏标记 + 定时冲刷 + 只发差量 |
| `getTicker` 永远返回 ticker | 白跑一堆空逻辑 | 不需要就返回 `null`，客户端通常不需要 |
| `render` 里 `new Component` | 每帧 3600 次分配 | `init()` 里算好，变化时重建 |
| `render` 里 `RenderType.create` | 每帧新建管线配置 | `static final` 建一次 |
| 静态 `Level` / `Player` | 内存泄漏 + 跨存档污染 | 用时现取 |
| 静态可变 `ItemStack` | 全局状态被悄悄改 | 缓存只读模板 + `copyWithCount` |
| 无失效策略的 `Map` 缓存 | 数据错乱 + 无限增长 | 版本号 / 事件 / 上限三选一 |
| 公共代码直接引用客户端类 | 专用服务器崩 | 放 `client` 包 + `Dist.CLIENT` |
| 一个巨型注册类 | 初始化顺序难预测 | 按内容拆 `Mod*` |
| 什么都用 Mixin | 与别的模组冲突 | 事件 → 数据映射 → 标签 → Mixin |
| 硬编码原版物品 | 别的模组无法扩展 | 自定义 Tag + `required: false` |
| 硬依赖可选模组 | 玩家不装就崩 | `ModList.get().isLoaded` + `optional` 依赖 |

## 完整示例

一个真实的改造案例：把「每 tick 全图扫描」改造成事件驱动 + 缓存。

需求：所有充能台在「充满」时给附近 8 格内的玩家一个提示。

**改造前**（每 tick 扫描，10 个充能台 × 20 tick = 200 次/秒，还要遍历玩家）：

```java
@SubscribeEvent
public static void onLevelTick(TickEvent.LevelTickEvent event) {
    if (event.phase != TickEvent.Phase.END || event.level.isClientSide) {
        return;
    }
    ServerLevel level = (ServerLevel) event.level;
    for (BlockEntity be : level.getChunk(...).getBlockEntities().values()) {   // 伪代码
        if (be instanceof RubyChargerBlockEntity charger && charger.isFull()) {
            for (ServerPlayer player : level.players()) {
                if (player.distanceToSqr(...) < 64) {
                    player.displayClientMessage(Component.literal("充满了"), true);
                }
            }
        }
    }
}
```

问题有四个：每 tick 扫、遍历所有方块实体、每 tick 拼字符串、没有「只提示一次」的状态。

**改造后**（事件点触发 + 每玩家只算一次 + 无分配）：

```java
// src/main/java/com/dafeiyu/blockentity/RubyChargerBlockEntity.java（片段）
public void addCharge(int amount) {
    int old = this.charge;
    this.charge = Math.min(this.charge + amount, this.capacity);
    if (this.charge == old) {
        return;                     // 没变，什么都不做
    }
    setChanged();                   // 值变了才标脏
    if (this.charge == this.capacity && this.level instanceof ServerLevel serverLevel) {
        notifyNearby(serverLevel);  // 只在"刚充满"这一刻通知
    }
}

private void notifyNearby(ServerLevel level) {
    // 只在充满的那一次遍历，而不是每 tick
    for (ServerPlayer player : level.players()) {
        if (player.distanceToSqr(worldPosition.getX() + 0.5, worldPosition.getY() + 0.5,
                worldPosition.getZ() + 0.5) <= 64.0) {
            player.displayClientMessage(
                    Component.translatable("message.dafeiyu.charger_full"), true);
        }
    }
}
```

成本从「每秒 200 次 × 玩家数」降到「每次充满 1 次 × 玩家数」。功能完全一样。

**再看一个缓存的例子**：给「可充能物品」建索引，避免每次都遍历标签。

```java
// src/main/java/com/dafeiyu/ChargingIndex.java
public final class ChargingIndex {

    private static Set<Item> cached;
    private static int version;
    private static int builtFor = -1;

    private ChargingIndex() {}

    public static boolean isChargeable(Item item) {
        if (cached == null || builtFor != version) {
            rebuild();
        }
        return cached.contains(item);
    }

    private static void rebuild() {
        // 只在标签变化后跑一次，遍历整个标签
        cached = new HashSet<>();
        BuiltInRegistries.ITEM.getTagOrEmpty(ModTags.Items.CHARGEABLE)
                .forEach(holder -> cached.add(holder.value()));
        builtFor = version;
    }

    /** 数据包重载时调一次，下次访问会重建 */
    public static void invalidate() {
        version++;
    }
}
```

```java
// src/main/java/com/dafeiyu/ModEvents.java（片段）
@SubscribeEvent
public static void onTagsUpdated(TagsUpdatedEvent event) {
    ChargingIndex.invalidate();
}
```

这样热路径里只有「一次 int 比较 + 一次 `HashSet.contains`」，而不是每次都遍历标签。注意 `invalidate()` 只加版本号、不立刻重建——**重建发生在下一次真正需要它的时候**，避免在重载数据包时做无用功。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 装了模组后帧率明显下降 | `render` 里有分配或每帧建 `RenderType` | 把常量提到 `static final`，文本在 `init()` 算好 |
| 服务端 TPS 掉到 15 以下 | tick 里遍历大集合 | 改事件驱动，或用缓存 |
| 内存一路涨，退出世界也不降 | 静态字段持有 `Level` / `Player` | 删掉静态引用，用时现取 |
| 第二个存档里方块行为异常 | 静态字段指向第一个存档的 `Level` | 同上 |
| 日志文件几秒钟涨到几十 MB | tick 里 `LOGGER.debug` 拼字符串 | 加 `isDebugEnabled()`，发布版降级到 `TRACE` |
| 存档时卡一下 | 每 tick `setChanged()` | 只在值变化时调 |
| 多人游戏里机器数据乱跳 | 客户端也在 tick 逻辑 | `if (level.isClientSide) return;` |
| 专用服务器启动崩 `NoClassDefFoundError` | 公共代码引用客户端类 | 移到 `client` 包 |
| 和另一个模组一起装就崩 | Mixin 目标被改了 | 优先改事件/数据映射 |
| 缓存的数据永远不更新 | 没有失效策略 | 加 `TagsUpdatedEvent` 失效 |
| 玩家改配置后要重启才生效 | 配置值被存进 `static final` | 每次 `.get()` 现读 |
| `ItemStack` 数量莫名其妙变成 0 | 静态 `ItemStack` 被 `shrink` 了 | 不要静态持有可变 `ItemStack` |

## 练习

1. **（易）** 找出你实战项目里所有 `setChanged()` 调用，逐个判断「这里真的变了吗」。把无条件调用改成条件调用。
2. **（中）** 给充能台加一个「附近玩家数」的显示。要求：不能每 tick 遍历玩家列表；用 `PlayerEvent.PlayerChangedDimensionEvent` 和 `PlayerEvent.PlayerLoggedInEvent` 维护一个计数，并处理玩家死亡重生、退出登录的清理。
3. **（难）** 写一个 `ChargingIndex` 的完整版：支持 `Item` 和 `ItemStack` 两种查询，用 `TagsUpdatedEvent` 失效，并加一个 `/dafeiyu dump index` 命令打印当前索引大小。然后用 [调试与游戏测试](../06-进阶篇/09-调试与游戏测试.md) 里的 profiler 对比改造前后的耗时。
