# 打包发布与版本管理

> 这一篇把「能跑」变成「能给别人装」。你会知道 `build/libs` 里那几个 jar 分别是什么、版本号该怎么编、`neoforge.mods.toml` 发布前要检查什么，以及为什么你的 jar 在别人电脑上会缺纹理。

## 学习目标

- 能看懂 `gradlew build` 产出的每个文件，并说清该往平台上传哪一个。
- 能按 `major.minor.patch` 编版本号，并写对 Minecraft 与 NeoForge 的版本范围。
- 能独立完成 `neoforge.mods.toml` 的发布前检查（含 `[[mixins]]`、`[[accessTransformers]]`）。
- 能写出符合 CurseForge / Modrinth 习惯的简介、分类和更新日志。
- 能配好 `updateJSONURL`，让玩家的模组列表提示「有新版本」。
- 能在干净环境、专用服务器、多人环境下完成发布前自测。

## 一、`gradlew build` 到底产出了什么

跑完构建，去看 `build/libs/`：

```text
build/libs/
├── dafeiyu-1.21.1-1.0.0.jar              ← 这个是要发布的
├── dafeiyu-1.21.1-1.0.0-sources.jar      ← 源码包
└── dafeiyu-1.21.1-1.0.0-slim.jar         ← 只在用了 jarJar 时出现
```

### 三个文件分别是什么

| 文件 | 内容 | 给谁 |
|---|---|---|
| `dafeiyu-1.21.1-1.0.0.jar` | 编译后的 class + `assets/` + `data/` + `META-INF/`，**含内嵌依赖** | 玩家、整合包作者、平台 |
| `-sources.jar` | 源码（`.java`），不含资源 | 想读你代码的开发者、IDE 的「下载源码」 |
| `-slim.jar` | 同样的 class 和资源，但**不含**内嵌依赖（JiJ） | 只在特殊场景用，几乎不发布 |

**结论：上传不带后缀的那个。**

### `-sources.jar` 为什么不能传

它不是模组，是一个「源码压缩包」。玩家把它丢进 `mods/` 文件夹，游戏会尝试按模组格式解析 `META-INF/neoforge.mods.toml`——大概率找不到，或者找到了也没有可执行的 class，最后在启动日志里留下一句看不懂的报错。

`sources.jar` 的正确用途是：你在 GitHub Release 里附带一份，或者发布到自己的 Maven，方便别人在 IDE 里看你的实现。

### `-slim.jar` 什么时候会有

当你用了 **jar-in-jar（JiJ）**——把一个小依赖库（比如某个轻量工具库）打包进自己的 jar 里，让玩家不用单独装。这时 Gradle 会产出两个版本：

- 主 jar：class + 资源 + `META-INF/jarjar/` 下的内嵌 jar。玩家装这个。
- `-slim.jar`：不含 `META-INF/jarjar/`。它是构建过程的中间产物，**不要发布**。

如果你的项目根本没用 JiJ，就不会有 `-slim.jar`，不用找。

### 想让文件名带 MC 版本

默认产物名是 `dafeiyu-1.0.0.jar`，看不出对应哪个 MC 版本。改 `build.gradle`：

```gradle
// build.gradle
base {
    archivesName = "dafeiyu-${minecraft_version}"
}
```

产物就变成 `dafeiyu-1.21.1-1.0.0.jar`。玩家一眼就知道该装哪个，你也不会在发布三个 MC 版本时传错文件。

## 二、版本号：三套数字，各管一件事

### 2.1 模组自己的 semver

`major.minor.patch`：

| 位 | 什么时候加 | 例子 |
|---|---|---|
| `major` | 不兼容的改动：删了物品、改了存档格式、换了 API | `1.4.2` → `2.0.0` |
| `minor` | 加了功能，但旧存档还能用 | `1.4.2` → `1.5.0` |
| `patch` | 只修 bug | `1.4.2` → `1.4.3` |

约定俗成：`0.x.y` 表示开发版，第一次正式发布升到 `1.0.0`。

「不兼容」的判断标准要具体一点。下面这些算 `major`：

- 删掉或重命名了注册项（玩家的存档里那些方块会变成「缺失方块」）。
- 改了方块实体的 NBT 结构且没写迁移。
- 改了网络包的字段（老客户端连不上）。
- 改了配置文件里键的名字（玩家的设置会丢）。

### 2.2 Minecraft 与 NeoForge 的版本对应

NeoForge 的版本号是「改编过的 semver」：

```text
NeoForge 21.1.80
         └┬┘ └┬┘
          │   └── 第 80 个构建（从 0 开始数）
          └────── 对应 Minecraft 1.21.1
                  （主版本 = MC 的次版本 21，次版本 = MC 的修订版本 1）
```

所以：

| Minecraft | NeoForge |
|---|---|
| 1.20.4 | 20.4.x |
| 1.20.6 | 20.6.x |
| 1.21 | 21.0.x |
| **1.21.1** | **21.1.x** |
| 1.21.4 | 21.4.x |

这条规则能帮你避免一个经典错误：**看到「NeoForge 21.1.80」就去装 MC 1.21.80**——没有这个版本。反过来，看到「MC 1.21.1」就该找 `21.1.*`，不要去装 `21.4.*`。

### 2.3 组合命名习惯

社区里最常见的三种写法：

```text
dafeiyu-1.21.1-1.0.0.jar          # MC 版本在前（最流行）
dafeiyu-1.0.0-1.21.1.jar          # 模组版本在前
dafeiyu-1.21.1-neoforge-1.0.0.jar # 再带上加载器（多加载器项目用）
```

选一种，**从第一个版本到最后一个版本都别改**。玩家和整合包作者靠文件名判断兼容性，中途换格式会让人以为你换了模组。

### 2.4 预发布标记

```text
1.0.0-beta.1     功能完整，可能有 bug
1.0.0-beta.2
1.0.0-rc.1       候选发布，只修 bug
1.0.0            正式版
```

注意：NeoForge 的更新检查器内部用 `ComparableVersion` 比较版本号，`-beta.1` 这类后缀它能正确排序，但**不要用奇怪的自定义后缀**（比如 `1.0.0-final-final2`），否则「谁更新」会判断错。

## 三、`neoforge.mods.toml` 发布前检查清单

这个文件在 `src/main/resources/META-INF/neoforge.mods.toml`。它是玩家在模组列表里看到的全部信息，也是游戏判断「能不能加载」的依据。

### 3.1 完整模板

```toml
# src/main/resources/META-INF/neoforge.mods.toml
modLoader = "javafml"
loaderVersion = "[4,)"          # 1.21.1 的加载器主版本
license = "${mod_license}"
issueTrackerURL = "https://github.com/yourname/dafeiyu/issues"

[[mods]]
modId = "dafeiyu"
version = "${mod_version}"
displayName = "大肥鱼模组"
authors = "大肥鱼"
credits = "感谢 NeoForge 团队与所有测试玩家"
description = '''
红宝石、充能台，以及一条从挖矿到毕业的完整进度线。
一个用来学习 NeoForge 的示例模组。
'''
logoFile = "icon.png"
logoBlur = false
displayURL = "https://github.com/yourname/dafeiyu"
updateJSONURL = "https://raw.githubusercontent.com/yourname/dafeiyu/main/update.json"

[[dependencies.dafeiyu]]
modId = "neoforge"
type = "required"
versionRange = "[21.1.0,21.2)"
ordering = "NONE"
side = "BOTH"

[[dependencies.dafeiyu]]
modId = "minecraft"
type = "required"
versionRange = "[1.21.1,1.22)"
ordering = "NONE"
side = "BOTH"

[[dependencies.dafeiyu]]
modId = "jei"
type = "optional"
versionRange = "[19,)"
ordering = "AFTER"
side = "CLIENT"
```

`${mod_license}` 这类占位符由 Gradle 的 `processResources` 在构建时替换成 `gradle.properties` 里的值。**所以改版本号、改许可证要去 `gradle.properties` 改，不要在这里改**——在这里改会被下一次构建覆盖。

### 3.2 逐项检查

| 字段 | 检查什么 | 漏了会怎样 |
|---|---|---|
| `displayName` | 是不是人类能读的名字，不要写 `dafeiyu` | 模组列表里显示 `dafeiyu` |
| `description` | 三行以内说清「这是什么、有什么内容」 | 显示 `MISSING DESCRIPTION` |
| `logoFile` | 文件名 + 扩展名，文件在 `src/main/resources/` 根目录 | 模组列表里是个空白方块 |
| `authors` | 你的名字/ID | 显示空白 |
| `credits` | 致谢（可选但推荐） | — |
| `license` | SPDX 标识符，如 `MIT`、`LGPL-3.0-only` | 构建能过，但平台审核会打回 |
| `issueTrackerURL` | 能打开的 issue 页 | 玩家没法报 bug |
| `displayURL` | 模组主页 | 模组列表里没有可点的链接 |
| `updateJSONURL` | 可公开访问的 raw JSON 地址 | 没有更新提示 |
| 依赖 `versionRange` | 是否过窄 | 玩家装了就报「版本不兼容」 |

**`logoFile` 的位置**：图片必须直接放在 `src/main/resources/` 下（打包后在 jar 根目录），不能放 `assets/dafeiyu/textures/` 里。尺寸建议 128×128 或 256×256 的正方形 PNG，透明背景。`logoBlur = false` 会让缩放时保持像素风，适合 MC 风格图标。

### 3.3 `[[mixins]]` 与 `[[accessTransformers]]`

这两个表很容易漏，因为**它们不影响开发环境**——开发时 Mixin 配置由 Gradle 插件直接喂给 JVM，所以你不写这两段也能跑。但打包之后，游戏只认 `neoforge.mods.toml` 里的声明，于是：

- 漏了 `[[mixins]]`：进游戏不崩，但你的 Mixin 一条都没生效，功能静默失效。
- 漏了 `[[accessTransformers]]`：直接 `IllegalAccessError`，因为 AT 没被应用。

```toml
# 用了 Mixin 就必须有这一段
[[mixins]]
config = "dafeiyu.mixins.json"

# 用了访问转换器就必须有这一段
[[accessTransformers]]
file = "META-INF/accesstransformer.cfg"
```

对应的文件位置：

```text
src/main/resources/dafeiyu.mixins.json
src/main/resources/META-INF/accesstransformer.cfg
```

> 注意 `config` 写的是**相对 jar 根目录的路径**，不带 `src/main/resources/`。`file` 同理。这两个路径写错的表现是「文件在 jar 里，但游戏说找不到」。

### 3.4 版本范围怎么写才不坑人

写太死是最常见的发布事故：

```toml
# 反例：只允许这一个 NeoForge 版本
versionRange = "[21.1.80]"
```

玩家装了 `21.1.81` 就被判定不兼容，模组列表里一片红。而实际上你的代码在 `21.1.81` 上跑得好好的。

```toml
# 正例：允许整个 21.1.x
versionRange = "[21.1.0,21.2)"
```

范围语法的读法：

| 写法 | 含义 |
|---|---|
| `[21.1.0,21.2)` | 大于等于 21.1.0，小于 21.2（推荐） |
| `[21.1.0,]` | 大于等于 21.1.0，无上限 |
| `[21.1.0]` | 恰好等于 21.1.0（几乎总是错的） |
| `*` | 任意版本（等于放弃检查） |

`[21.1.0,21.2)` 的边界为什么是 `21.2`？因为 NeoForge 的次版本号变化意味着 MC 修订版本变化（21.2 = MC 1.21.2），跨修订版本通常有二进制不兼容的改动。

Minecraft 那边同理：`[1.21.1,1.22)`。不要写 `[1.21,1.22)`——`1.21` 和 `1.21.1` 是两个不同版本，前者匹配不到后者。

## 四、发布到 CurseForge / Modrinth

两个平台都要填的东西差不多，但顺序和侧重不同。

### 4.1 简介怎么写

玩家在列表页只看到**前两行**。所以第一句必须是「这是什么」，第二句是「有什么特别的」。

```text
大肥鱼模组给主世界加了一种新矿物：红宝石。

挖到它，你可以打造一整套工具与盔甲，做一个能把物品充能的充能台，
并沿着一条 12 步的进度线从第一块矿石走到毕业装备。

- 红宝石矿与深板岩红宝石矿，主世界全高度生成
- 剑、镐、四件套盔甲，属性介于铁与钻石之间
- 红宝石充能台：放入物品即可积累能量，GUI 实时显示
- 全套中文/英文，可配置矿脉大小与充能上限
```

反例（别这么写）：

- 「这是一个模组」——等于没说。
- 一整段技术实现（「使用 DeferredRegister 注册了……」）——玩家不关心。
- 只贴一张图不写字——搜索引擎抓不到。

### 4.2 分类与标签

| 平台 | 关键选项 |
|---|---|
| CurseForge | Category：`Addons` → `World Gen`、`Equipment`、`Technology`；Game Version 勾 `1.21.1`；Mod Loader 选 `NeoForge` |
| Modrinth | Categories：`worldgen`、`equipment`、`technology`；Loaders：`NeoForge`；Environment：`Client and server` |

「Environment」这一项要如实填。你的模组如果在客户端加了 GUI，就是 `Client and server`（required on both）。填成 `Client` 会让服务器端不装它，然后玩家连不上。

### 4.3 图标

- 正方形，至少 256×256（CurseForge 会裁成圆形显示，主体别贴边）。
- PNG，透明背景。
- 别用 MC 原版素材（版权），也别用别人的模组图标。
- 同一套视觉风格贯穿：图标、模组列表 logo、宣传图用同一个配色。

### 4.4 更新日志

固定四段结构，玩家扫一眼就知道要不要更新：

```markdown
## 1.1.0 — 2026-10-31

### 新增
- 红宝石充能台现在支持堆叠充能，上限可在配置中调整
- 新增进度「充满一次」

### 修改
- 红宝石剑的攻击速度从 -2.4 调整为 -2.2

### 修复
- 修复充能台被活塞推动后数据丢失的问题
- 修复中文语言文件里「深板岩红宝石矿」名字错字

### 兼容
- 需要 NeoForge 21.1.80 或更高
- 与 1.0.x 存档兼容，可直接替换 jar
```

**「兼容」这一段最重要**。玩家最想知道的是「我能不能直接换 jar」。明确写「存档兼容」或「需要新建世界」，能省掉一半的 issue。

### 4.5 发布顺序建议

1. 先在 GitHub 建一个 tag 和 Release，把 jar 挂上去（这是最稳的备份）。
2. 再传 Modrinth（审核快，API 友好）。
3. 最后传 CurseForge（审核慢，但用户量大）。
4. 三个地方的文件**必须是同一个 jar**。不要在一个平台上重新构建——文件哈希不同会让整合包作者困惑。

## 五、更新检查器

NeoForge 内置一个很轻的更新检查：玩家模组列表里有新版本时，会显示闪烁图标和更新日志。它**不会自动下载**，只是提示。

### 5.1 打开它

在 `[[mods]]` 里加一行：

```toml
updateJSONURL = "https://raw.githubusercontent.com/yourname/dafeiyu/main/update.json"
```

必须是**能直接返回 JSON 的地址**。GitHub 的网页地址（`github.com/.../blob/...`）返回的是 HTML，不行；要用 `raw.githubusercontent.com`。

### 5.2 JSON 格式

```json
{
  "homepage": "https://modrinth.com/mod/dafeiyu",
  "1.21.1": {
    "1.0.0": "首个正式版：红宝石矿、装备、充能台。",
    "1.1.0": "新增充能台堆叠；修复活塞导致的数据丢失。\n需要 NeoForge 21.1.80+。",
    "1.1.1": "修复中文语言文件错字。"
  },
  "promos": {
    "1.21.1-latest": "1.1.1",
    "1.21.1-recommended": "1.1.0"
  }
}
```

三个部分的含义：

| 键 | 作用 |
|---|---|
| `homepage` | 模组过期时，玩家点「打开页面」跳转的地址 |
| `"1.21.1": { ... }` | 该 MC 版本下所有模组版本 + 各自的更新日志 |
| `promos` | `latest` 是「最新（可能不稳）」，`recommended` 是「推荐（稳定）」 |

`recommended` 指向 `1.1.0` 而不是最新的 `1.1.1`，意思是「1.1.1 有个小修复，但 1.1.0 是经过验证的稳定版」。玩家会在列表里看到两种提示。

更新日志里可以用 `\n` 换行。

### 5.3 版本比较的坑

NeoForge 用 `ComparableVersion` 判断「谁更新」。它对标准 semver 处理得很好，但下面这些会出问题：

| 写法 | 问题 |
|---|---|
| `1.0.0-final` | 后缀排序不符合直觉 |
| `1.0` vs `1.0.0` | 视为不同版本，容易误判 |
| `v1.0.0` | 前缀 `v` 会让比较结果错乱 |

**建议：所有地方（jar 名、`mods.toml`、`update.json`、平台上的版本号）用完全相同的字符串，不带前缀，三段式。**

### 5.4 别忘了这是「手动维护」的

`update.json` 不会自动更新。每次发版都要改它，否则玩家的更新提示永远停在旧版本。一个实用做法是在 `build.gradle` 里加个任务，构建时自动把当前版本写进去——但哪怕手动改，也**一定要改**。

## 六、发布前自测清单

这一节是整个实战篇的最后一关。逐项打勾，别跳。

### 6.1 环境矩阵

| 场景 | 怎么做 | 查什么 |
|---|---|---|
| 干净客户端 | 新建一个空的游戏目录，只装 NeoForge + 你的 jar | 有没有漏打包的资源 |
| 干净服务端 | 新建服务端目录，`java -jar neoforge-installer.jar --installServer`，放 jar 启动 | 客户端类是否泄漏 |
| 多人 | 两个客户端同时连 | 数据是否只对一个人可见 |
| 不同分辨率 | GUI 缩放：自动 / 大 / 小 | Screen 是否溢出、文字是否重叠 |
| 不同语言 | 切成英文 | 有没有漏翻译的 key |
| 资源包 | 装一个 32x 材质包 | 你的纹理是否正常 |
| 光影 | 装一个 shader | 自定义渲染是否崩 |
| 退出重进 | 放东西、退出、重进 | 存档是否完整 |

### 6.2 专用服务器为什么必须测

单人游戏里，客户端和服务端在同一个进程，**很多「客户端类被服务端加载」的问题不会暴露**。一旦上专用服务器：

- 服务端没有 `net.minecraft.client.*`，任何引用都会 `NoClassDefFoundError`。
- 服务端没有纹理、没有 Screen，任何「顺手在服务端 new 一个 Screen」的代码都会炸。
- 服务端的 `Level` 是 `ServerLevel`，`instanceof` 判断写错会静默失效。

跑一遍专用服务器，是发现这类问题最便宜的方式。

### 6.3 jar 内容自检

不用启动游戏，直接看 jar 里有什么：

```bash
# 列出 jar 内容（Windows 用 Git Bash）
unzip -l build/libs/dafeiyu-1.21.1-1.0.0.jar
```

必须有：

```text
META-INF/neoforge.mods.toml
META-INF/MANIFEST.MF
com/dafeiyu/DafeiyuMod.class
assets/dafeiyu/lang/zh_cn.json
assets/dafeiyu/textures/block/ruby_ore.png
data/dafeiyu/loot_table/blocks/ruby_ore.json
```

## 七、发布阶段容易踩的坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 玩家装了 jar，方块是紫黑格子 | 资源没打进 jar：`processResources` 没跑，或资源不在 `src/main/resources` | 检查 `build.gradle` 的 `sourceSets`，确认 `src/generated/resources` 被包含；跑一次 `./gradlew build --rerun-tasks` |
| jar 里没有 `data/` 目录 | datagen 输出目录没加进 source set | `sourceSets.main.resources.srcDir 'src/generated/resources'` |
| 模组列表里没图标 | `logoFile` 写的路径不对，或图片不在 `src/main/resources` 根目录 | 改成 `logoFile = "icon.png"`，图片放对位置 |
| 一启动就报「版本不兼容」 | `versionRange` 写成了 `[21.1.80]` | 改成 `[21.1.0,21.2)` |
| 玩家报「需要 NeoForge 21.1.81」 | 同上，范围太窄 | 同上 |
| 平台审核打回 | 没写 `license`，或 jar 里没有 LICENSE 文件 | `gradle.properties` 里填 SPDX 标识符，仓库根目录放 `LICENSE` |
| Mixin 在开发环境有效、发布后失效 | `neoforge.mods.toml` 漏了 `[[mixins]]` | 补上 `config = "dafeiyu.mixins.json"` |
| 发布后 `IllegalAccessError` | 漏了 `[[accessTransformers]]` | 补上 `file = "META-INF/accesstransformer.cfg"` |
| 中文全是 `item.dafeiyu.ruby` | `lang/zh_cn.json` 没进 jar，或 key 拼错 | 解压 jar 确认文件存在；key 必须带 `item.` / `block.` 前缀 |
| 更新提示一直不出现 | `updateJSONURL` 指向 HTML 页面，或 JSON 格式错 | 用 `raw.githubusercontent.com`，浏览器直接打开看是不是 JSON |
| 更新提示说「你比最新版还新」 | `update.json` 里版本号格式和 `mods.toml` 不一致 | 两处用完全相同的字符串 |
| 服务端崩 `NoClassDefFoundError` | 客户端类混进公共代码 | 移到 `client` 包，类上加 `Dist.CLIENT` |
| 玩家装了不启动，日志说「mod file is invalid」 | jar 是 `-sources.jar` 或 `-slim.jar` | 传不带后缀的那个 |
| 整合包作者说哈希对不上 | 在不同平台重复构建 | 一个 jar 传所有平台 |

## 完整示例

### 发布配置三件套

**① `gradle.properties`（发布相关部分）**

```properties
# gradle.properties
mod_id=dafeiyu
mod_name=大肥鱼模组
mod_license=MIT
mod_version=1.1.0
mod_group_id=com.dafeiyu
mod_authors=大肥鱼
mod_description=红宝石、充能台，以及一条从挖矿到毕业的完整进度线。

minecraft_version=1.21.1
minecraft_version_range=[1.21.1,1.22)
neo_version=21.1.80
neo_version_range=[21.1.0,21.2)
loader_version_range=[4,)
```

**② `build.gradle`（产物命名 + 资源目录）**

```gradle
// build.gradle
base {
    archivesName = "dafeiyu-${minecraft_version}"
}

// datagen 的输出也要打进 jar，否则数据文件全丢
sourceSets.main.resources {
    srcDir 'src/generated/resources'
}

// 让 processResources 把 gradle.properties 里的值替换进 neoforge.mods.toml
tasks.named('processResources', ProcessResources).configure {
    var replaceProperties = [
            minecraft_version      : minecraft_version,
            minecraft_version_range: minecraft_version_range,
            neo_version            : neo_version,
            neo_version_range      : neo_version_range,
            loader_version_range   : loader_version_range,
            mod_id                 : mod_id,
            mod_name               : mod_name,
            mod_license            : mod_license,
            mod_version            : mod_version,
            mod_authors            : mod_authors,
            mod_description        : mod_description
    ]
    inputs.properties replaceProperties
    filesMatching(['META-INF/neoforge.mods.toml']) {
        expand replaceProperties
    }
}
```

`expand` 就是「把 `${mod_version}` 换成 `1.1.0`」的那一步。**如果你改了 `gradle.properties` 却没看到 jar 里的值变化，九成是这段没配好，或者 Gradle 用了缓存**（`./gradlew build --rerun-tasks`）。

**③ `update.json`**

```json
{
  "homepage": "https://modrinth.com/mod/dafeiyu",
  "1.21.1": {
    "1.0.0": "首个正式版。",
    "1.1.0": "新增充能台堆叠充能；修复活塞导致的数据丢失。\n需要 NeoForge 21.1.80+。"
  },
  "promos": {
    "1.21.1-latest": "1.1.0",
    "1.21.1-recommended": "1.1.0"
  }
}
```

## 常见坑与报错

上面第七节讲的是「发布出去之后玩家会遇到什么」，这一节讲「构建和启动阶段自己会遇到什么」。

| 报错 | 原因 | 解决 |
|---|---|---|
| `Could not find or load main class ...` 启动开发环境失败 | Gradle 缓存损坏 | 删 `.gradle/` 和 `build/`，重新 `./gradlew build` |
| `Unresolved reference: minecraft_version` | `gradle.properties` 里少了这个键，或键名拼错 | 对照 MDK 默认值补齐 |
| `Cannot expand property` | `neoforge.mods.toml` 里有 `${...}` 但 `expand` 的 map 里没有对应键 | 补进 `replaceProperties` |
| `Duplicate key` | `neoforge.mods.toml` 里同一个 `[[mods]]` 下重复写了字段 | 删掉重复行 |
| `Invalid version range` | 用了 `[1.21.1-1.22)` 这种非法写法 | Maven 范围必须用逗号：`[1.21.1,1.22)` |

## 练习

1. **（易）** 把 `mod_version` 改成 `1.1.0`，重新构建，用 `unzip -p build/libs/*.jar META-INF/neoforge.mods.toml` 确认 jar 里的 `version` 字段跟着变了。如果没变，找出是哪一步没生效。
2. **（中）** 写一份 `update.json`，让 `latest` 指向 `1.2.0-beta.1`、`recommended` 指向 `1.1.0`，然后进游戏看模组列表显示的是哪个提示。再把 `1.2.0-beta.1` 改成 `1.2.0` 重新看一次，解释两次结果为什么不同。
3. **（难）** 给你的项目加一条 GitHub Actions 工作流：打 tag 时自动 `./gradlew build`、提取 `gradle.properties` 里的版本号、创建 Release 并上传 jar。要求产物名符合 `dafeiyu-1.21.1-x.y.z.jar`，并在 workflow 里校验 jar 中确实存在 `data/dafeiyu/loot_table/blocks/ruby_ore.json`。
