# 术语表

> 一篇可以随时翻的小词典：六十多个词，按主题分成六组，每个词告诉你它是什么、你在哪会撞见它、以及最容易跟谁搞混。

## 学习目标

- 遇到教程里没解释的名词，能在半分钟内查到它属于哪一类、大概指什么
- 能说清「注册」「初始化」「加载阶段」这三件事的先后关系，知道什么代码该放在哪一步
- 能一眼分辨 `Item` 与 `ItemStack`、`Block` 与 `BlockState`、`Menu` 与 `Screen` 这些成对出现的概念
- 看到一段陌生代码里的类型名，能判断它属于工程层、平台层、游戏层还是数据层

## 怎么用这本小词典

三条建议，先说清楚，能省你不少时间：

1. **不要背。** 第一次读教程时不需要从头看到尾。卡在哪个词上，回来查一条，看完就关掉。
2. **每条末尾的「易混」比定义本身值钱。** 模组开发里八成的困惑不是"不知道这个词"，而是"把它和另一个词搞混了"——`Block` 和 `BlockState` 混了会导致模型不显示，`Codec` 和 `StreamCodec` 混了会导致联机崩。
3. **复习时只看第七节那张对照表。** 八对最容易混的概念并排放着，考试前扫一眼就够。

分组速览：

| 组 | 管什么 | 代表词 |
|---|---|---|
| 一、工程与构建 | 项目怎么被编译、打包、跑起来 | Gradle、MDK、映射、源集 |
| 二、平台与加载 | 谁在启动游戏、谁在改原版代码 | NeoForge、Mixin、AT、加载阶段 |
| 三、游戏世界 | 游戏里那些"东西"本身 | 方块、方块实体、区块、刻 |
| 四、注册与数据 | 东西怎么进游戏、数据怎么写 | 注册表、DeferredRegister、标签、datagen |
| 五、客户端 | 画面怎么画出来 | 侧、渲染器、烘焙模型、Screen |
| 六、通信与存储 | 两端怎么说话、数据存哪 | 能力、载荷、Codec、SavedData |

## 一、工程与构建

这一组词你在 `build.gradle`、IDEA 的 Gradle 面板、以及各种"环境装不上"的报错里会反复见到。它们跟 Minecraft 本身没关系，是 Java 世界的通用工具。

### Gradle

**定义**：Java 生态里的自动化构建工具，负责下载依赖、编译源码、处理资源、打包成 jar。

**在哪碰到**：项目根目录的 `build.gradle` 就是它的"说明书"。你写的每一行 `implementation 'xxx'`、每一个 `neoForge { ... }` 配置块，都是写给 Gradle 看的。`gradlew build` 最后产出的那个 jar，也是它打的。

**易混**：Gradle 是工具，ModDevGradle 是"给 Gradle 装的插件"。你出问题时先分清是 Gradle 本身的问题（下载失败、内存不够）还是插件的问题（配置写错）。

### Gradle Wrapper（Gradle 包装器）

**定义**：项目自带的一小套启动脚本（`gradlew`、`gradlew.bat`、`gradle/wrapper/` 目录），保证每个打开这个项目的人都用同一个 Gradle 版本，不用自己装。

**在哪碰到**：你永远敲 `./gradlew`（Windows 上是 `gradlew.bat`），而不是 `gradle`。第一次运行会按 `gradle/wrapper/gradle-wrapper.properties` 里写的地址去下载对应版本，所以"第一次特别慢、卡在 Downloading"是正常的。IDEA 的 Gradle 设置里那一项 `Use Gradle from: gradle-wrapper.properties file` 就是在用它。

**易混**：`gradle` 是你系统里全局装的那个（可能版本不对），`gradlew` 是项目指定的那个。教程里统一用后者。

### ModDevGradle

**定义**：NeoForge 官方主推的 Gradle 插件（插件 id `net.neoforged.moddev`），负责把 Minecraft、NeoForge、映射表、运行配置全部接进 Gradle。

**在哪碰到**：`build.gradle` 顶部 `plugins { id 'net.neoforged.moddev' version '...' }`，下面 `neoForge { version = "21.1.xxx" }`。它会自动给你生成 `runClient`、`runServer`、`runData` 这些任务。本教程正文以它为准。

**易混**：和 NeoGradle 是**两套不同的插件**，配置语法完全不同。抄配置之前先看对方用的是哪一套。

### NeoGradle

**定义**：NeoForge 的另一套 Gradle 插件（`net.neoforged.gradle.userdev`），出现更早，配置写法是 `runs { client { ... } }` 那种。

**在哪碰到**：官方 MDK 有两个分支，一个 ModDevGradle 版、一个 NeoGradle 版。你在网上找到的工程如果是 `runs { client { client() } }` 这种写法，就是 NeoGradle。

**易混**：两套插件的配置**不能混着抄**。把 ModDevGradle 的 `neoForge { }` 块贴进 NeoGradle 工程，报错会是"Could not find method neoForge()"，看着像 Gradle 坏了，其实只是抄错了地方。

### MDK（Mod Development Kit）

**定义**：官方给的最小可运行模板工程，解压、`gradlew runClient` 就能进游戏。

**在哪碰到**：一切从它开始。`gradle.properties` 里的 `mod_id`、`mod_name`、`mod_version`、`mod_group_id` 都来自 MDK，Gradle 会把它们内联进 `neoforge.mods.toml`。

**易混**：改 modid 不是改一个地方。至少要同步四处：`gradle.properties` 的 `mod_id`、Java 包名 `com.dafeiyu`、`META-INF/neoforge.mods.toml` 里的 `modId`、`pack.mcmeta` 里的描述。漏一处就是"模组加载了但东西全不见了"。

### 依赖（dependency）

**定义**：你的工程需要用到的外部代码库，Gradle 负责下载并放进 classpath。

**在哪碰到**：`dependencies { ... }` 块。做模组时最典型的是跟 JEI、Curios 这类模组联动。四种常见声明要分清：

| 写法 | 编译时可见 | 打包进 jar | 典型用途 |
|---|---|---|---|
| `implementation` | 是 | 是 | 你自己的子模块 |
| `compileOnly` | 是 | 否 | 别人的模组 API（运行时由玩家自己装） |
| `runtimeOnly` | 否 | 否 | 只在开发环境跑起来用的东西 |
| `annotationProcessor` | 否 | 否 | 注解处理器 |

**易混**：`compileOnly` 写成 `implementation`，你的 jar 里就会塞进别人的模组代码，玩家一装两个就崩。

### 构建（build）

**定义**：把源码编译、资源处理、打成 jar 的整个过程。

**在哪碰到**：`gradlew build`，产物在 `build/libs/` 下，通常两个文件：`dafeiyu-1.0.0.jar` 和 `dafeiyu-1.0.0-sources.jar`。发布只用前者。

**易混**：`build` **不会**帮你跑数据生成。模型、配方这些如果靠 datagen 产出，必须先 `gradlew runData` 再 `build`，否则 jar 里就是空的。

### 混淆（obfuscation）

**定义**：把类名、方法名、字段名替换成 `a`、`b`、`c` 这类无意义名字，防止别人直接读你的代码。

**在哪碰到**：正式版 Minecraft 的 jar 是混淆过的；开发环境里你看到的是可读名字（`Level#getBlockState`），发布后变成 `f_46443_` 之类。这解释了一类经典 bug：**开发环境一切正常，做成 jar 进正式游戏就崩**——因为你在代码里用字符串写了方法名（反射、Mixin 的 `target`、`@Shadow` 的名字），混淆之后对不上。

**易混**：混淆（把名字变乱）和映射（把乱名字翻译回来）是一对反向操作，别当成一回事。

### 映射（mappings）

**定义**：混淆名与可读名之间的对照表。

**在哪碰到**：NeoForge 1.21.1 默认用 Mojang 官方映射（official），可以再叠一层 Parchment 来补参数名。你在 IDE 里 Ctrl+点击能看到 `getBlockState()` 这种名字，就是映射在起作用。

**易混**：Fabric 默认用 Yarn 映射，同一个方法在两个平台的教程里名字可能不同（`Level#getBlockState` 在 Yarn 里叫 `getBlockState` 但类叫 `World`）。跨平台抄代码时，先确认映射体系。

### 反编译（decompile）

**定义**：把 `.class` 字节码还原成近似 Java 源码。

**在哪碰到**：IDEA 里点一下 "Download Sources"，然后 Ctrl+点击进 `Level.class`，你看到的那份代码就是反编译产物。它不是原版源码：变量名可能是 `var1`、`$$0`，`switch` 可能被还原成 `while(true)`，`for` 循环可能变成 `while(iterator.hasNext())`。

**易混**：反编译出来的代码**只读不抄**。它缺少注释、缺少泛型信息，照着抄很容易抄出编译不过的东西。要理解行为，读它；要写代码，看文档。

### 源集（source set）

**定义**：Gradle 对源码的分组，每组有自己的编译输出和资源目录。

**在哪碰到**：默认的 `main` 源集对应 `src/main/java` 和 `src/main/resources`。有的工程会额外拆一个 `client` 源集，把纯客户端代码隔离出去，防止专用服务器加载到客户端类。

**易混**：源集是**编译期**的隔离，`Dist` 是**运行期**的隔离。拆了源集不代表服务端一定不会崩，运行时还得靠 `@EventBusSubscriber(value = Dist.CLIENT)` 之类的手段。

### gradlew 任务（task）

**定义**：Gradle 的最小执行单元，`gradlew <任务名>` 就是执行它。

**在哪碰到**：新手只需要记住五个：

```text
gradlew build        打包，产物在 build/libs/
gradlew runClient    启动开发客户端
gradlew runServer    启动开发服务端
gradlew runData      跑数据生成，产物在 src/generated/resources/
gradlew clean        删掉 build/ 目录
```

**易混**：任务之间有依赖关系。`build` 会自动先跑 `compileJava`，所以"我只想编译一下"用 `gradlew compileJava` 更快。忘了任务名就 `gradlew tasks` 列全部。

## 二、平台与加载

这一组词回答一个问题：**在 Minecraft 启动的那几十秒里，到底是谁在干活、按什么顺序干。**

### NeoForge

**定义**：Minecraft 的模组加载器兼 API 集合，2023 年从 Forge 分叉出来，从 1.20.2 起独立发展。

**在哪碰到**：你 `import net.neoforged.*` 的所有东西都来自它。版本号 `21.1.x` 对应 MC 1.21.1（前两位跟着 MC 走）。它提供事件总线、注册系统、能力系统、网络层、数据映射这些基础设施。

**易混**：NeoForge 不是"另一个 Minecraft"，它是一层补丁 + 一套 API。你写的仍然是原版的类，只是多了很多钩子。

### Forge

**定义**：老牌模组加载器，NeoForge 的前身。

**在哪碰到**：你在网上搜到的 1.12、1.16、1.18、1.19 教程，绝大多数是 Forge 的。标志是 `net.minecraftforge.*`、`RegistryObject`、`@Mod.EventBusSubscriber` 无参数写法。

**易混**：Forge 教程**可以看思路，不能抄代码**。`RegistryObject` 在 NeoForge 里叫 `DeferredHolder`，包名从 `net.minecraftforge` 变成 `net.neoforged`，`SimpleChannel` 整个没了。看到 `net.minecraftforge` 就当历史资料读。

### Fabric

**定义**：另一个轻量模组加载器，社区活跃、跟进新版本快。

**在哪碰到**：`net.fabricmc.*`、`ModInitializer`、`Registry.register`、`FabricLoader.getInstance()`。它的 API 设计跟 NeoForge 完全不同，两边的模组**互不通用**。

**易混**：Fabric 的教程看起来也在讲"注册物品"，但写法天差地别。搜教程时一定带上 "NeoForge" 或 "1.21.1 NeoForge"，别搜到 Fabric 就跟着做。

### Mixin

**定义**：在类加载时改写字节码的技术，能往原版方法的指定位置插入你自己的代码。

**在哪碰到**：`@Mixin(Level.class)` 加 `@Inject`、`@Redirect`、`@ModifyVariable`。配置文件叫 `dafeiyu.mixins.json`，还要在 `neoforge.mods.toml` 里用 `[[mixins]]` 登记。

**易混**：Mixin 是**最后手段**。能用事件解决的用事件，能用能力解决的用能力，只想改可见性用 AT。Mixin 改的是别人的代码，版本一升级就断，而且断起来是启动崩溃，很难查。

### Access Transformer（AT，访问转换器）

**定义**：一份声明式清单，把原版 `private` / `protected` 的成员改成 `public`，让你能直接调用。

**在哪碰到**：`src/main/resources/META-INF/accesstransformer.cfg`，一行一条：

```text
# 把 Level 的某个字段放开成 public
public net.minecraft.world.level.Level f_46443_
```

**易混**：AT 只改**可见性**，不改逻辑，所以它比 Mixin 安全得多。但它是全局生效的——你放开的成员对所有模组都可见，容易跟别人冲突。原则：**只放开你真正需要的那一个成员，别整类放开。**

### Coremod

**定义**：Forge 时代"在游戏启动最早期加载、直接改类"的插件机制（`IFMLLoadingPlugin`）。

**在哪碰到**：老教程里的 `coremods` 目录、`META-INF/MANIFEST.MF` 里的 `FMLCorePlugin` 字段、`LoadingPlugin` 类。

**易混**：现代 NeoForge **已经没有这套东西了**，它的职责被 Mixin 接管。看到"coremod"就当历史名词，不要试图在新版本里复刻。

### 模组加载器（mod loader）

**定义**：在 Minecraft 启动之前介入、发现并加载模组的程序。

**在哪碰到**：NeoForge、Forge、Fabric 都是。它做三件事：扫描 `mods/` 目录里的 jar、读每个 jar 的 `neoforge.mods.toml` 判断能不能加载（版本、依赖、side）、按依赖顺序调用你的入口类。

**易混**：加载器（loader）和启动器（launcher）不是一回事。HMCL、PCL 这些是启动器，负责下载游戏、拼 classpath、把加载器拉起来。

### 加载阶段（loading stage）

**定义**：游戏启动被切成若干阶段，每个阶段只允许做特定的事。

**在哪碰到**：你写的初始化代码放在哪个阶段，决定了它能不能跑。顺序大致是：

```text
@Mod 构造函数        → 建 DeferredRegister，注册到 mod 事件总线
注册事件             → 注册表开放，条目真正进表，然后冻结
FMLCommonSetupEvent  → 通用初始化（两端都跑）
FMLClientSetupEvent  → 客户端初始化（只客户端跑）
FMLLoadCompleteEvent → 全部加载完成
ServerAboutToStart   → 服务端要开世界了
```

**易混**：最常见的崩溃就是"阶段搞错"。在构造函数里访问 `Minecraft.getInstance().level` 必然是 null；在 `FMLClientSetupEvent` 里注册方块也来不及了（注册表早冻了）。

### neoforge.mods.toml

**定义**：模组的"身份证"，声明 modid、版本、显示名、依赖、Mixin 配置。

**在哪碰到**：`src/main/resources/META-INF/neoforge.mods.toml`。几个关键项：

```toml
modLoader="javafml"
loaderVersion="[1,)"

[[mods]]
modId="dafeiyu"
version="1.0.0"
displayName="大肥鱼模组"

[[dependencies.dafeiyu]]
modId="neoforge"
type="required"
versionRange="[21.1,)"
ordering="NONE"
side="BOTH"
```

**易混**：`modId` 必须跟 `@Mod("dafeiyu")` 里的字符串**完全一致**，大小写都算。不一致时游戏不会报"你写错了"，而是直接不加载你的模组，你会在模组列表里找不到自己。

## 三、游戏世界

这一组是 Minecraft 的"名词表"。它们的共同点是：**都能在存档里被引用，所以都需要注册名**。

### 方块（block）

**定义**：世界里占据一个格子、有碰撞箱和外观的东西。

**在哪碰到**：`Block` 类，注册进 `Registries.BLOCK`。一个"方块"在游戏里其实是三样东西的组合：`Block`（行为逻辑）、`BlockState`（当前形态）、可选的 `BlockEntity`（额外数据）。

**易混**：`Block` 是**类**，全世界所有红石块共享一个实例；你脚下那块红石块是 `BlockState` + 坐标。

### 方块状态（blockstate）

**定义**：一个方块在某一瞬间的"形态快照"，由若干属性（property）的取值组合而成。

**在哪碰到**：`block.defaultBlockState()`、`state.getValue(BlockStateProperties.FACING)`、`state.setValue(...)`。资源文件 `assets/dafeiyu/blockstates/ruby_block.json` 里的 `variants` 就是给每种状态指定模型。

**易混**：属性组合数是**相乘**的。一个 `FACING`（6 种）× 一个 `POWERED`（2 种）= 12 种状态，`variants` 里就得写 12 条（或者用 `multipart`）。加属性前先算一下，别一不小心搞出几百种状态。

### 方块实体（block entity）

**定义**：挂在方块上的"数据容器 + 每刻逻辑"，能存数据、能 tick，但不负责渲染。

**在哪碰到**：`BlockEntity` 子类 + `BlockEntityType` 注册 + 方块实现 `EntityBlock` 接口（`newBlockEntity`、`getTicker`）。箱子记住里面装了什么、熔炉记住烧到哪一刻，靠的都是它。

**易混**：`BlockEntity` 不做渲染，渲染是 `BlockEntityRenderer` 的事；`BlockEntity` 也不等于"方块"，一个方块可以没有方块实体（大部分都没有），有方块实体的方块也不一定每刻都要 tick。

### 物品（item）

**定义**：能进背包、能被拿在手上的东西的"类型"。

**在哪碰到**：`Item` 类，注册进 `Registries.ITEM`。它定义"这一类物品的行为"：能不能吃、能不能挖、右键干什么、堆叠上限多少。

**易混**：`Item` 不存"这一份物品的数据"。你背包里那 3 个红宝石的数据在 `ItemStack` 里。

### 物品堆叠（ItemStack）

**定义**：背包里的"一份具体物品"：物品类型 + 数量 + 数据组件。

**在哪碰到**：`new ItemStack(ModItems.RUBY.get(), 3)`、`stack.getCount()`、`stack.is(ModItems.RUBY.get())`。

**易混**：`ItemStack` 是**可变对象**。`ItemStack b = a;` 之后改 `b` 会改到 `a`，想要独立副本必须 `a.copy()`。另外判断物品用 `stack.is(...)`，不要用 `==` 比较 `Item` 实例（虽然通常能对，但空栈和代理场景会坑你）。

### 实体（entity）

**定义**：世界里能移动、有坐标的非方块对象。

**在哪碰到**：`Entity` 基类，注册进 `Registries.ENTITY_TYPE`。掉落物、箭、船、画、生物都是实体。

**易混**：实体是**运行时对象**，`EntityType` 是**注册的类型**。`EntityType<RUBY_GOLEM>` 只有一个，世界里可以有一百个 `RubyGolem` 实例。

### 生物（mob / living entity）

**定义**：有生命值、能受伤、有 AI 的实体。

**在哪碰到**：`LivingEntity` 是"活物"（有血量、能穿装备），`Mob` 是"有 AI 的活物"，`PathfinderMob` 是"会寻路的"，`Monster` 是"敌对生物"。

**易混**：**玩家也是 `LivingEntity`**。写状态效果、写伤害、写"给附近生物加 buff"时用 `LivingEntity` 能同时覆盖玩家和生物；用 `Mob` 就把玩家排除在外了。

### 维度（dimension）

**定义**：一个独立的世界，比如主世界、下界、末地。

**在哪碰到**：代码里客户端服务端通用的是 `Level`，仅服务端的是 `ServerLevel`。`level.dimension()` 返回 `ResourceKey<Level>`。自定义维度要写 `data/dafeiyu/dimension/xxx.json` 和对应的 `dimension_type`。

**易混**：判断"是不是主世界"要用 `level.dimension() == Level.OVERWORLD`，不要用 `level == server.overworld()` 之类的对象比较——模组维度、维度实例复用都会让对象比较失效。

### 区块（chunk）

**定义**：16×16 的水平柱状区域，是世界加载、保存、同步的基本单位。

**在哪碰到**：`ChunkPos`、`LevelChunk`、`level.getChunk(x, z)`。方块实体只在"所在区块已加载"时才 tick。

**易混**："区块加载了"和"区块被强制加载"是两回事。玩家走过去的区块会加载，走远了就卸载；机器要持续工作，得靠区块加载器或 `forcedChunks`。**"我的机器不动了"十有八九是区块被卸载了。**

### 生物群系（biome）

**定义**：决定一个区域的气候、生成什么生物、长什么树什么草的"环境配置"。

**在哪碰到**：`Biome`。实际开发里你很少直接改原版群系，而是用**生物群系修改器**（`data/dafeiyu/neoforge/biome_modifier/xxx.json`）往里加生成。

**易混**：群系（biome）决定"这里长什么样"，地物（feature）决定"具体放一个什么东西"。加一棵树是加地物，让这片区域变成"樱花林"才是改群系。

### 地物（feature）

**定义**：世界生成时"放一小块东西"的单元：一棵树、一丛草、一滩水、一块矿。

**在哪碰到**：`Feature<Config>`，配两个 JSON：`configured_feature`（长什么样）和 `placed_feature`（长在哪、多密、什么条件下长）。

**易混**：configured 管**内容**，placed 管**分布**。想让矿多一点，改 placed 的 `count`；想换矿的方块，改 configured。改错文件是新手最常见的"改了没效果"。

### 结构（structure）

**定义**：跨区块的大型建筑：村庄、要塞、神庙、林地府邸。

**在哪碰到**：`Structure` 子类 + `structure_set` + 模板池（template pool）+ NBT 结构文件（用结构方块导出）。

**易混**：结构比地物重一个数量级。新手想"加一个地下城"，正确路径是先学会地物和拼图（jigsaw），别一上来就写 `Structure`。

### 刻（tick）

**定义**：游戏逻辑的时间单位，20 刻 = 1 秒。

**在哪碰到**：`BlockEntity#tick`、`Entity#tick`、`Level#tickBlockEntities`。所有"随时间变化"的逻辑都在这里跑。

**易混**：`tick()` 里每秒钟执行 20 次 × 每个实例。你在里面 `new ArrayList<>()`、`stream()`、`getBlockState()` 扫一圈，TPS 就掉下去了。需要低频逻辑就写 `if (level.getGameTime() % 20 == 0)`，需要更慢就 `% 100`。

### NBT

**定义**：Minecraft 的树状二进制数据格式，对应 `CompoundTag`、`ListTag`、`IntTag` 这些类。

**在哪碰到**：存档、方块实体数据、结构文件，底层都是它。1.21 里你**很少直接写 NBT**：物品数据用数据组件，自定义结构用 `Codec`，全局存档用 `SavedData`。

**易混**：看到 `stack.getOrCreateTag()`、`stack.getTag()` 这种写法要意识到它是旧 API（1.20.5 之前）。1.21 里物品没有"自由 NBT"了，只有已声明的数据组件。

## 四、注册与数据

这一组是模组开发的"骨架"：东西怎么进游戏、数据怎么写、文件放哪个目录。

### 注册表（registry）

**定义**：一张 `ResourceLocation → 对象` 的全局表，游戏靠它保证"同一个名字在客户端和服务端指同一个东西"。

**在哪碰到**：`Registries.ITEM`（注册表的**键**，注册时用）、`BuiltInRegistries.BLOCK`（注册表的**实例**，遍历时用）。

**易混**：注册表在启动的某个窗口期开放，之后**冻结**。冻结后再往里塞就抛 `Registry is already frozen`。所以"我在 `main` 方法里 new 一个物品"永远不会生效。

### DeferredRegister

**定义**：NeoForge 提供的延迟注册器：先把要注册的东西排队，等注册事件来了再统一塞进注册表。

**在哪碰到**：每个 `Mod*` 类里都有这么一行：

```java
public static final DeferredRegister.Items ITEMS =
        DeferredRegister.createItems("dafeiyu");
```

**易混**：`DeferredRegister.create(...)` 只是**建了个队列**，必须在模组构造函数里再调一次 `.register(modEventBus)` 才算接上电源。**忘了最后这一步，前面全白写**，而且不报错，只是东西不见了。

### DeferredHolder

**定义**：`DeferredRegister.register(...)` 的返回值，是"将来会是某个对象"的占位符。

**在哪碰到**：`DeferredItem<Item>`、`DeferredBlock<Block>`、`DeferredHolder<BlockEntityType<?>, BlockEntityType<RubyBlockEntity>>` 都是它的子类型。

**易混**：用的时候必须 `.get()`。在注册完成之前调用 `.get()` 会抛异常——所以**不要在静态初始化块里 `.get()`**，那时候还没注册。

### 资源位置（ResourceLocation）

**定义**：`命名空间:路径` 形式的标识符，游戏里一切"引用"的通用写法。

**在哪碰到**：`ResourceLocation.fromNamespaceAndPath("dafeiyu", "ruby")`、`ResourceLocation.parse("dafeiyu:ruby")`。

**易混**：1.21 起构造函数是私有的，`new ResourceLocation(...)` **编译不过**。这是旧教程坑人最狠的一处，几乎每个人第一次迁移都会撞上。

### 命名空间（namespace）

**定义**：资源位置冒号前的那一半，通常就是你的 modid。

**在哪碰到**：`dafeiyu:ruby` 里的 `dafeiyu`。资源目录 `assets/dafeiyu/...` 和 `data/dafeiyu/...` 里的那层目录名必须跟它一致。

**易混**：命名空间写错的表现不是报错，而是"纹理不显示""模型找不到"。因为游戏只是"没找到这个名字对应的文件"，它不知道你想找的是哪个。

### 数据组件（data component）

**定义**：1.20.5 起取代物品 NBT 的"物品附加数据"系统：每个组件有类型、有 Codec、可以单独同步。

**在哪碰到**：`DataComponents.MAX_STACK_SIZE`、`Item.Properties#component(...)`、`stack.get(ModDataComponents.MANA)`。

**易混**：数据组件是**声明式**的——你必须先注册一个 `DataComponentType`，才能往物品上挂这个数据。它不能像旧 NBT 那样"随便塞一个键"。这看着麻烦，但换来了类型安全和自动同步。

### 数据映射（data map）

**定义**：NeoForge 加的"注册表对象 → 值"的只读映射，用 JSON 定义，可以被数据包覆盖。

**在哪碰到**：`data/dafeiyu/data_maps/...json`，代码里通过 `DataMapType` 取。

**易混**：数据映射**不改注册表**，只是给已有对象挂一张附加表。典型用途：给一堆物品标"烧了能出几个"、给方块标"什么工具能挖"。它比"给每个物品写一个子类"灵活得多，也比标签能装更复杂的数据（标签只能装"是/否"，映射能装数值）。

### 标签（tag）

**定义**：一组注册名的集合，用来做"批量判断"。

**在哪碰到**：`TagKey.create(Registries.ITEM, ResourceLocation.fromNamespaceAndPath("c", "gems"))`，判断用 `stack.is(tag)`。JSON 在 `data/dafeiyu/tags/item/xxx.json`。

**易混**：1.21 里标签目录是**单数**：`tags/item/`、`tags/block/`，不是 `tags/items/`。这是 1.21 目录单数化改动的一部分，抄 1.20 教程必踩。

### 配方（recipe）

**定义**："输入 → 输出"的规则，工作台、熔炉、切石机都靠它。

**在哪碰到**：`RecipeType`、`RecipeSerializer`、`RecipeInput`。JSON 在 `data/dafeiyu/recipe/xxx.json`。

**易混**：路径是 `recipe`（单数）。写成 `recipes` 不会有任何报错，配方就是不生效——游戏只会"没找到配方"，不会提示你目录名错了。

### 战利品表（loot table）

**定义**：描述"这东西被破坏 / 被杀 / 被打开时掉什么"的 JSON。

**在哪碰到**：`data/dafeiyu/loot_table/blocks/ruby_ore.json`。方块不用显式声明，游戏会按它的注册名自动去 `loot_table/blocks/<路径>.json` 找。代码里用 `LootPool`、`LootItemFunction` 构建。

**易混**：同样是单数目录 `loot_table`。另外方块"挖了什么都不掉"有两个完全不同的原因：没写战利品表，或者写了但方块属性里挂了 `.noLootTable()`。

### 进度（advancement）

**定义**：玩家达成的目标，可以带奖励、可以做教程引导、可以控制配方解锁。

**在哪碰到**：`data/dafeiyu/advancement/xxx.json`，`criteria` 里写触发器（`minecraft:inventory_changed`、`minecraft:player_killed_entity` 等）。1.21 起配方默认需要进度解锁，所以"配方不显示"有时是进度没写。

**易混**：进度（advancement）是**玩家维度**的成就；配方书里那个"新配方"提示靠的是 `recipe_unlocked` 触发器，两件事相关但不是一回事。

### 数据生成（datagen）

**定义**：用 Java 代码生成 JSON（方块状态、模型、配方、标签、战利品表、语言文件）。

**在哪碰到**：`GatherDataEvent` + 各种 `*Provider`，`gradlew runData` 把产物写进 `src/generated/resources`。

**易混**：生成出来的文件**不要手改**，下次 `runData` 会被覆盖。要改就改 Provider 代码。另外 datagen 只在开发环境跑，玩家拿到的 jar 里是生成好的 JSON。

## 五、客户端

这一组词的关键词是"只存在于客户端"。把它们误用到服务端，是专用服务器崩溃的头号原因。

### 侧（side）

**定义**：代码运行在哪一端：客户端，还是专用服务器。

**在哪碰到**：`level.isClientSide()`、`FMLEnvironment.dist`、`@EventBusSubscriber(value = Dist.CLIENT)`。

**易混**：客户端有渲染、有玩家输入、有 `Minecraft` 实例；服务端有权威数据、没有渲染、没有 `Minecraft` 实例。**把 `net.minecraft.client.*` 的类写进会在服务端执行的代码路径，专用服务器必崩。**

### 逻辑侧 / 物理侧

**定义**：逻辑侧指"这段代码此刻扮演的是服务端角色还是客户端角色"；物理侧指"这个进程本身是客户端还是专用服务器"。

**在哪碰到**：单人游戏里，一个进程同时跑着逻辑服务端和逻辑客户端（物理侧是客户端）。所以 `level.isClientSide()` 为 true 只说明"这是客户端那一半"，不说明"这个进程是客户端"。

**易混**：判断进程用 `FMLEnvironment.dist == Dist.CLIENT`；判断逻辑用 `level.isClientSide()`。这两个判断在单人游戏里会给出**不同**的答案，混用就会出现"单人没事、联机崩"。

### 渲染器（renderer）

**定义**：把游戏对象画到屏幕上的类。

**在哪碰到**：`EntityRenderer`（实体）、`BlockEntityRenderer`（方块实体）、`Screen`（界面）、`BlockEntityWithoutLevelRenderer`（物品在手上的特殊渲染）。

**易混**：渲染器**只在客户端注册**（`EntityRenderersEvent.RegisterRenderers`、`EntityRenderersEvent.RegisterLayerDefinitions`）。注册渲染器的代码如果被服务端执行，就是 `NoClassDefFoundError: net/minecraft/client/...`。

### 烘焙模型（baked model）

**定义**：模型 JSON 被"烤"成的、可以直接提交给渲染器的顶点数据。

**在哪碰到**：`BakedModel`、`BakingResult`、`ModelResourceLocation`。资源重载时生成。

**易混**：你平时写的是 JSON（未烘焙），只有做动态模型（根据数据换贴图、改形状）才碰 `BakedModel`。烘焙是**一次性**的，烘焙完之后每帧只是提交顶点，所以动态模型要用 `BakedModel` 的 `getOverrides` 或 `DynamicModel`，不能在渲染时改 JSON。

### 模型加载器（model loader）

**定义**：负责把某种格式的模型 JSON 解析成 `BakedModel` 的组件。

**在哪碰到**：默认有 `minecraft:model`，NeoForge 额外提供 OBJ 之类的加载器。自定义要写 `IGeometryLoader`，在 `ModelEvent.RegisterGeometryLoaders` 里登记。

**易混**：模型加载器（解析 JSON）和模型**渲染器**（画出来）是两层。你要"支持一种新模型格式"才写加载器；只是想"让方块长得不一样"，写 JSON 就够了。

### 粒子（particle）

**定义**：世界里的小特效点，不占实体、不参与碰撞、不影响逻辑。

**在哪碰到**：`ParticleType`（注册表条目）+ `ParticleOptions`（带参数的类型）+ `ParticleProvider`（客户端怎么画）。

**易混**：服务端只负责"发指令"（`level.sendParticles(...)`），真正画出来在客户端。所以"粒子不显示"要分两头查：服务端有没有发，客户端有没有注册 `ParticleProvider`。

### 屏幕（Screen）

**定义**：一层 UI，覆盖在游戏画面上，负责绘制和处理输入。

**在哪碰到**：`Screen`、`AbstractContainerScreen`。`render(GuiGraphics, mouseX, mouseY, partialTick)` 里画，`mouseClicked` 里处理点击。

**易混**：`Screen` **只在客户端存在**。它不存数据，也不做逻辑判断——数据从 `Menu` 来。

### 菜单（Menu）

**定义**：容器界面的"逻辑部分"：槽位布局、谁能往哪放、哪些数据要同步。

**在哪碰到**：`AbstractContainerMenu` + `MenuType`。服务端和客户端**都有** Menu 实例。

**易混**：Menu 管逻辑，Screen 管画。**Menu 里绝对不能写渲染代码**，Screen 里也不该写"这个槽能不能放"的规则。

### 容器（container）

**定义**：一堆物品槽的抽象，`Container` 接口。

**在哪碰到**：`SimpleContainer`（简单实现）、`ItemStackHandler`（能力版的物品栏）。

**易混**：容器（存东西）→ 菜单（把容器映射成槽位）→ 屏幕（把槽位画出来）。三层单向依赖，别反向调用。

## 六、通信与存储

这一组管"两端怎么说话"和"数据存哪里"。它们是最容易写出"单人正常、联机崩"的地方。

### 能力（capability）

**定义**：NeoForge 的"这个对象支持某种功能"的声明机制，用来跨模组协作。

**在哪碰到**：`IItemHandler`（物品栏）、`IEnergyStorage`（能量）、`IFluidHandler`（流体）。方块通过 `Capabilities.ItemHandler.BLOCK` 暴露，在 `RegisterCapabilitiesEvent` 里注册。

**易混**：能力是**按需查询**的接口，不是继承关系。你的机器实现了 `IItemHandler`，别的模组的漏斗就能往里塞东西——不需要知道你的类叫什么。所以**别用 `instanceof` 判断具体类**，用能力查询。

### 载荷（payload）

**定义**：自定义网络包的数据载体，实现 `CustomPacketPayload`。

**在哪碰到**：`record RubySyncPayload(int value) implements CustomPacketPayload`，配一个 `StreamCodec`，在 `RegisterPayloadHandlersEvent` 里注册。

**易混**：1.20.5 起 `SimpleChannel` 整个没了。旧教程里的 `channel.sendToServer(...)`、`NetworkRegistry.newSimpleChannel(...)` 全部作废，照抄就是编译错误。

### StreamCodec

**定义**：专门给网络用的编解码器，`StreamCodec<ByteBuf, T>`，负责"写进缓冲区 / 从缓冲区读出来"。

**在哪碰到**：`StreamCodec.composite(...)`、`StreamCodec.of(...)`、`StreamCodec.unit(...)`。

**易混**：读写顺序必须严格对称。你写的时候按 `(a, b, c)` 写，读的时候也必须按 `(a, b, c)` 读，错一个字段就是"客户端收到乱码然后崩"，而且报错位置离真正的错误很远。

### Codec

**定义**：通用的"对象 ↔ JSON / NBT"编解码器，`Codec<T>`。

**在哪碰到**：`RecordCodecBuilder`、`Codec.STRING`、`Codec.INT`、`Codec.list(...)`。数据组件、配方、附魔效果、世界生成配置都用它。

**易混**：**Codec 管磁盘和 JSON，StreamCodec 管网络字节。** 两者不能互换。一个常见错误是把 `Codec` 直接塞进网络注册，编译能过（有些重载接受），运行时序列化出来的东西对不上。

### 存档数据（SavedData）

**定义**：挂在维度上、随世界保存的任意数据。

**在哪碰到**：继承 `SavedData`，用 `level.getDataStorage().computeIfAbsent(new SavedData.Factory<>(...), "dafeiyu_data")` 取。

**易混**：`SavedData` 是**整个世界一份**，适合"全局计数器""已生成结构列表"。每个方块实体各自的数据用 `BlockEntity` 自己存，每个实体的用数据附件。**别把每 tick 都在变的东西塞进 SavedData**，它只在存档时写盘，但对象常驻内存。

### 数据附件（attachment）

**定义**：NeoForge 的"往实体 / 区块 / 方块实体上挂自定义数据"的机制。

**在哪碰到**：`AttachmentType`，注册进 `NeoForgeRegistries.ATTACHMENT_TYPES`，用 `entity.getData(ModAttachments.MANA)` 读写。

**易混**：**物品不用附件**，物品用数据组件（1.20.5 起原版就用组件取代了物品的附件）。看到教程给 `ItemStack` 挂 attachment，那是旧版本写法。

### 同步（sync）

**定义**：让客户端看到服务端的权威数据。

**在哪碰到**：容器用 `ContainerData`，方块实体用 `getUpdatePacket` / `getUpdateTag`，自定义数据用载荷。

**易混**：同步的方向是**服务端 → 客户端**（绝大多数情况）。客户端想改数据必须发载荷请求，不能直接改本地值然后指望服务端知道。这就是"多人游戏数据不同步"的根源。

## 七、易混概念对照表

复习只看这张表。

| 概念 A | 概念 B | 一句话区别 | 判断口诀 |
|---|---|---|---|
| `Item` | `ItemStack` | A 是"这类物品的行为定义"，全局唯一；B 是"背包里的这一份"，有数量和组件 | 问"几个"就是 Stack |
| 方块（`Block`） | 方块状态（`BlockState`） | A 是类，全世界一个实例；B 是"某个坐标此刻的形态" | 带坐标就是 State |
| `BlockEntity` | `Block` | A 存数据、能 tick、能存盘；B 管形状、碰撞、交互 | 要"记住"就需要 A |
| `Codec` | `StreamCodec` | A 管 JSON / NBT（磁盘）；B 管字节流（网络） | 存盘用 A，发包用 B |
| 逻辑侧 | 物理侧 | 逻辑侧是"代码此刻扮演谁"，物理侧是"这个进程是什么" | `isClientSide` 看逻辑，`Dist` 看进程 |
| 注册（register） | 初始化（setup） | 注册是"进表、拿到名字"；初始化是"配好、接上逻辑" | 注册在前，初始化在后 |
| `Menu` | `Screen` | A 管槽位与同步，两端都有；B 管绘制与输入，只在客户端 | 逻辑找 Menu，画图找 Screen |
| 数据包（datapack） | 资源包（resourcepack） | A 放服务端逻辑（配方、战利品、世界生成）；B 放客户端表现（模型、纹理、声音、语言） | 影响玩法是数据包，影响长相是资源包 |

## 常见坑：查术语时最容易踩的五个坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 按术语表里的名字去搜，搜到的全是 1.16 的代码 | 同一个概念在不同版本换了 API，但**中文译名没变** | 搜的时候加上 `1.21.1` 和 `NeoForge`，看到 `net.minecraftforge` 立刻关掉 |
| 知道 `BlockState` 是"形态"，但不知道为什么模型不显示 | 只记住了定义，没记住"blockstate JSON 的 `variants` 要覆盖所有状态组合" | 回头读[方块状态](../04-内容制作篇/02-制作你的第一个方块.md)那篇，重点看 `variants` 的写法 |
| 把 `Codec` 和 `StreamCodec` 当成同一个东西 | 两者名字太像，而且都能"序列化" | 记死一句话：**存盘用 Codec，发包用 StreamCodec** |
| 以为 `isClientSide` 为 true 就是"客户端进程" | 单人游戏里一个进程跑两套逻辑 | 判断进程用 `FMLEnvironment.dist` |
| 术语都认识，但不知道代码该写在哪个阶段 | 只查了"是什么"，没查"什么时候" | 看第二节的「加载阶段」，把它当成一张时间表 |
