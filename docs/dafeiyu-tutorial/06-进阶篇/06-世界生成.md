# 世界生成

> 读完这篇，你能让红宝石矿真正长在主世界里，并且知道为什么改「生物群系修改器」比改「生物群系 json」安全得多。

## 学习目标

- 能画出「生物群系 → 生物群系修改器 → 已放置地物 → 配置地物」这四层的关系，说清每层各管什么。
- 能写出一个 `neoforge:add_features` 修改器，把自定义矿石塞进主世界的 `underground_ores` 阶段。
- 能写 `placed_feature`，用 `count`、`in_square`、`height_range` 控制「多密、多高、在哪」。
- 能判断什么时候该复用 `minecraft:ore`，什么时候真的需要写一个 `Feature` 子类。
- 遇到「矿不生成」时，能按 step、生物群系标签、json 路径三条线依次排查。

## 一、世界生成到底分了几层

先建立一个整体印象。Minecraft 生成一个区块时，不是「随机撒方块」，而是按一张清单，一层层往上叠：

```
生物群系（biome）
 └─ features[ 生成阶段 ]  ← 一个 11 行的表格，每行是一串「已放置地物」
      └─ 已放置地物（placed_feature）
           ├─ feature → 配置地物（configured_feature）：放什么、多大、什么形状
           └─ placement：放几次、在哪个高度、要不要按生物群系过滤
```

**生物群系（biome）** 回答的是「这片地方长什么样」：温度、降水、地表方块、能生成什么生物，以及——本篇的重点——**在哪个阶段生成哪些地物**。它的 `features` 字段是一个二维数组，外层下标就是「生成阶段」，内层是一串地物 id。

**生成阶段（generation step）** 是 11 个固定名字，游戏严格按顺序执行。矿石必须放在 `underground_ores`，花和树放在 `vegetal_decoration`，雪和冰放在 `top_layer_modification`。顺序错了不会报错，只是生成结果很奇怪或者干脆看不见。

**配置地物（configured_feature）** 是「配方」：我要放的是一条 9 格长的矿脉，还是一棵橡树，还是一个晶洞。它只有形状和内容，没有位置信息。

**已放置地物（placed_feature）** 是「摆法」：这个配方在每个区块里试几次、水平方向要不要随机偏移、垂直方向取哪一段高度、要不要只在本生物群系生效。同一个 configured_feature 可以被多个 placed_feature 引用，摆出完全不同的密度。

至于**结构（structure）**——村庄、要塞、废弃矿井——是另一套系统（模板 + jigsaw），和地物不共用配置，本篇不展开。

## 二、为什么不要直接改生物群系的 json

你可能见过这样的做法：把原版的 `data/minecraft/worldgen/biome/plains.json` 复制一份到自己的数据包里，在 `features` 数组里加一行矿石。这能跑，但它是**整份覆盖**，不是追加。

具体会出三个问题：

第一，**和别的模组打架**。两个模组都想往平原加矿，数据包加载时同一个 id 的文件只会留下一份（后加载的赢），另一个模组的矿直接消失。玩家装十个模组，可能只有一半的矿能生成。

第二，**原版一更新你就过期**。你复制的那份 json 是 1.21.1 的快照，1.21.2 改了字段名，你的副本就成了定时炸弹。

第三，**没法单独关掉**。整合包作者想禁掉你的矿，只能整个替换平原的群系文件，连带把别人的修改一起干掉。

**生物群系修改器（biome modifier）** 换了个思路：它不是「替换群系」，而是「在世界加载时，对每个群系执行一条指令」。NeoForge 会把所有修改器收集起来，逐个作用到群系构建器上。你的修改器只负责「往 X 群系的 Y 阶段追加 Z 地物」，别人的修改器照样生效，互不干扰。整合包作者还可以在自己的数据包里放一个同名的 json，把内容改成 `{"type": "neoforge:none"}`，精确地只关掉你这一条。

代价是：修改器在**构建群系注册表时**执行，改完 json 后光 `/reload` 不一定够，最稳的是退出重进世界。

## 三、`neoforge:add_features` 的三个字段

这是最常用的修改器类型，只有三个字段：

```json
// src/main/resources/data/dafeiyu/neoforge/biome_modifier/add_ruby_ore.json
{
  "type": "neoforge:add_features",
  "biomes": "#minecraft:is_overworld",
  "features": "dafeiyu:ruby_ore",
  "step": "underground_ores"
}
```

- **`biomes`**：可以是单个群系 id（`"minecraft:plains"`）、id 列表、或者标签（`"#minecraft:is_overworld"`）。注意标签前面那个 `#`，漏了会被当成一个叫 `minecraft:is_overworld` 的群系，然后报「找不到」。
- **`features`**：写的是 **placed_feature 的 id**，不是 configured_feature。这是最容易错的一处——两者同名时你看不出区别，不同名时矿就静默不生成。同样支持 id、列表、标签。
- **`step`**：11 个阶段名之一，小写下划线。

阶段顺序和用途如下（顺序即执行顺序）：

| 阶段 | 放什么 |
|---|---|
| `raw_generation` | 最特殊的地形，如末地小岛 |
| `lakes` | 岩浆湖、水池 |
| `local_modifications` | 晶洞、冰山、巨石、滴水石 |
| `underground_structures` | 地牢、化石 |
| `surface_structures` | 沙漠水井这类地表小结构 |
| `strongholds` | 要塞专用 |
| `underground_ores` | **所有矿石**，包括泥土、花岗岩团 |
| `underground_decoration` | 洞穴装饰，滴水石簇、幽匿脉络 |
| `fluid_springs` | 泉水、熔岩瀑布 |
| `vegetal_decoration` | 花、草、树、藤蔓 |
| `top_layer_modification` | 雪、冰 |

把矿放进 `vegetal_decoration` 也能生成，但它会在植物之后执行，可能被树盖住、被草替换，看上去「矿很少」。所以别偷懒。

## 四、最小可用的矿石：直接用 `minecraft:ore`

写自定义 `Feature` 之前，先问一句：原版的 `minecraft:ore` 够不够用？它已经帮你处理了「只替换石头类方块」「不替换空气和基岩」「按椭圆分布」这些细节，90% 的矿都不需要自己写 Java。

红宝石矿用三个 json 就能跑起来。

**第一个：配置地物**，定义「一条矿脉长什么样」。

```json
// src/main/resources/data/dafeiyu/worldgen/configured_feature/ruby_ore.json
{
  "type": "minecraft:ore",
  "config": {
    "discard_chance_on_air_exposure": 0.0,
    "size": 9,
    "targets": [
      {
        "state": { "Name": "dafeiyu:ruby_ore" },
        "target": { "predicate_type": "minecraft:tag_match", "tag": "minecraft:stone_ore_replaceables" }
      },
      {
        "state": { "Name": "dafeiyu:deepslate_ruby_ore" },
        "target": { "predicate_type": "minecraft:tag_match", "tag": "minecraft:deepslate_ore_replaceables" }
      }
    ]
  }
}
```

`targets` 是一个「替换规则」列表：在石头里放红宝石矿，在深板岩里放深板岩红宝石矿。`size` 是矿脉的最大格数，原版钻石是 8、铁是 9。`discard_chance_on_air_exposure` 是「暴露在空气里时被丢弃的概率」，0 表示贴着洞穴也会生成，钻石用 0.5 让它更稀有。

**第二个：已放置地物**，定义「在哪儿、放几次」。

```json
// src/main/resources/data/dafeiyu/worldgen/placed_feature/ruby_ore.json
{
  "feature": "dafeiyu:ruby_ore",
  "placement": [
    { "type": "minecraft:count", "count": 6 },
    { "type": "minecraft:in_square" },
    {
      "type": "minecraft:height_range",
      "height": {
        "type": "minecraft:trapezoid",
        "min_inclusive": { "absolute": -64 },
        "max_inclusive": { "absolute": 48 }
      }
    },
    { "type": "minecraft:biome" }
  ]
}
```

`placement` 是一个**从上往下依次执行**的修饰器链，读法是从上往下：

- `count`：每个区块尝试 6 次。注意是「尝试次数」，不是「生成 6 条矿脉」——每次尝试都可能因为位置不合适而失败。
- `in_square`：把生成点在一个区块内随机水平偏移，避免所有矿都堆在区块的同一个角上。
- `height_range`：垂直范围。`trapezoid` 是梯形分布，中间高度概率最高；`uniform` 是均匀分布；`constant` 是固定高度。`absolute` 表示「从世界最低点算起的绝对 y」，另外还有 `above_bottom` 和 `below_top` 两种锚点。
- `biome`：标记「这个地物属于生物群系」，缺了它有些版本会拒绝生成。

**第三个：生物群系修改器**，就是上一节那段 json，把 `features` 指向 `dafeiyu:ruby_ore`。

三个文件放好，进游戏就能在主世界挖到红宝石矿了。没有一行 Java 代码。

## 五、什么时候真的需要自定义 `Feature`

`minecraft:ore` 只会放「一团椭圆形的方块」。当你的需求超出这个范围，才需要写 `Feature` 子类。典型场景：

- 形状不是矿脉：比如贴着洞壁生长的晶簇、悬空的晶体、沿一条曲线排列的方块。
- 生成时要放实体：比如「矿石里偶尔蹦出一只怪」。
- 生成结果依赖周围环境：比如「只在岩浆湖边缘生成黑曜石壳」。

这里有一个**版本陷阱**必须提醒：网上 1.21.2 以后的教程会让你注册 `FeatureType`，但 **1.21.1 没有这个类**。1.21.1 注册的是 `Feature` 实例本身，泛型是 `Feature<?>`。照抄新版教程会直接编译不过。

先写配置类。它是一个 record，字段就是 json 里 `config` 对象的内容：

```java
// src/main/java/com/dafeiyu/worldgen/RubyClusterFeature.java
package com.dafeiyu.worldgen;

import com.mojang.serialization.Codec;
import com.mojang.serialization.codecs.RecordCodecBuilder;
import net.minecraft.core.BlockPos;
import net.minecraft.util.RandomSource;
import net.minecraft.world.level.WorldGenLevel;
import net.minecraft.world.level.levelgen.feature.Feature;
import net.minecraft.world.level.levelgen.feature.FeaturePlaceContext;
import net.minecraft.world.level.levelgen.feature.configurations.FeatureConfiguration;
import net.minecraft.world.level.levelgen.feature.stateproviders.BlockStateProvider;

public class RubyClusterFeature extends Feature<RubyClusterFeature.Config> {

    public RubyClusterFeature(Codec<Config> codec) {
        super(codec);
    }

    @Override
    public boolean place(FeaturePlaceContext<Config> context) {
        WorldGenLevel level = context.level();
        RandomSource random = context.random();
        BlockPos origin = context.origin();
        Config config = context.config();

        boolean placedAny = false;
        for (int i = 0; i < config.size(); i++) {
            // 在起点附近 3x3x3 的范围里随机挑一格
            BlockPos pos = origin.offset(random.nextInt(3) - 1, random.nextInt(3) - 1, random.nextInt(3) - 1);
            if (level.isEmptyBlock(pos)) {
                level.setBlock(pos, config.state().getState(random, pos), 2);
                placedAny = true;
            }
        }
        return placedAny;
    }

    // 配置类：对应 json 里的 config 对象
    public record Config(BlockStateProvider state, int size) implements FeatureConfiguration {
        public static final Codec<Config> CODEC = RecordCodecBuilder.create(instance -> instance.group(
                BlockStateProvider.CODEC.fieldOf("state").forGetter(Config::state),
                Codec.intRange(1, 64).fieldOf("size").forGetter(Config::size)
        ).apply(instance, Config::new));
    }
}
```

几个关键点：

- 构造器把 `Codec` 交给父类，父类用它把 json 的 `config` 反序列化成 `Config` 对象。
- `place` 返回 `boolean`，表示「这次有没有放成功」。返回 `false` 不会报错，游戏只是认为这次尝试白费了。
- `context.origin()` 是这次生成尝试的落点，**不保证是空气**，所以要先 `isEmptyBlock` 判断。
- `setBlock(pos, state, 2)` 里的 `2` 是「只发给客户端、不触发邻居更新」的标志位，世界生成阶段的标准写法。
- `BlockStateProvider` 让 json 可以写 `simple_state_provider`、`randomized_block_state_provider` 等不同来源，比直接写死一个方块灵活。

注册它：

```java
// src/main/java/com/dafeiyu/worldgen/ModFeatures.java
package com.dafeiyu.worldgen;

import com.dafeiyu.DafeiyuMod;
import net.minecraft.core.registries.Registries;
import net.minecraft.world.level.levelgen.feature.Feature;
import net.neoforged.neoforge.registries.DeferredHolder;
import net.neoforged.neoforge.registries.DeferredRegister;

public class ModFeatures {
    public static final DeferredRegister<Feature<?>> FEATURES =
            DeferredRegister.create(Registries.FEATURE, DafeiyuMod.MOD_ID);

    public static final DeferredHolder<Feature<?>, RubyClusterFeature> RUBY_CLUSTER =
            FEATURES.register("ruby_cluster", () -> new RubyClusterFeature(RubyClusterFeature.Config.CODEC));
}
```

别忘了在主类里 `ModFeatures.FEATURES.register(modEventBus);`。

然后写它的配置地物，`type` 就是注册名：

```json
// src/main/resources/data/dafeiyu/worldgen/configured_feature/ruby_cluster.json
{
  "type": "dafeiyu:ruby_cluster",
  "config": {
    "state": {
      "type": "minecraft:simple_state_provider",
      "state": { "Name": "dafeiyu:ruby_block" }
    },
    "size": 6
  }
}
```

再给它配一个 placed_feature（可以复用上一篇的写法，把 `feature` 换成 `dafeiyu:ruby_cluster`，高度改到洞穴层），最后用一个 `add_features` 修改器挂到 `underground_decoration` 阶段——因为它是洞穴装饰，不是矿。

## 六、怎么验证它真的生成了

世界生成最大的痛苦是「没有报错，但东西就是不出现」。按下面顺序验证，能省掉大量瞎猜。

**第一步，手动放一次。** 站在你想看的位置，执行：

```text
/place feature dafeiyu:ruby_ore ~ ~ ~
```

`/place feature` 的参数是 **placed_feature 的 id**，它会按那个 placed_feature 的 placement 规则在附近生成一次。如果这一步就有东西，说明 configured_feature 和 placed_feature 都是好的，问题出在 biome_modifier。如果这一步什么都没发生，问题在 json 本身。

**第二步，确认群系对不对。** 用 `/locate biome minecraft:plains` 看你脚下到底是什么群系。你写了 `#minecraft:is_overworld`，但如果你在自定义维度里测试，那个维度的群系可能不在这个标签里。

**第三步，看密度。** 创造模式按 `F3 + G` 打开区块边界，然后开旁观者模式穿到地下（`/gamemode spectator`）。想看统计结果，可以用 `/fill` 把一片区域清空再数——比如 `/fill ~-16 ~-40 ~-16 ~16 ~-10 ~16 air`，清完之后数一下露出来的矿。这比「凭感觉觉得少」靠谱。

**第四步，改完 json 要重进世界。** 生物群系修改器是在构建群系时应用的，`/reload` 重载的是数据包内容，不保证重新跑一遍修改器。改完 json 后退出到主菜单再进，或者直接新建一个世界（新世界一定用新配置）。

## 完整示例

红宝石矿的完整文件清单：

```text
src/main/java/com/dafeiyu/worldgen/ModFeatures.java            # 只有自定义地物才需要
src/main/java/com/dafeiyu/worldgen/RubyClusterFeature.java     # 只有自定义地物才需要
src/main/resources/data/dafeiyu/worldgen/configured_feature/ruby_ore.json
src/main/resources/data/dafeiyu/worldgen/configured_feature/ruby_cluster.json   # 只有自定义地物才需要
src/main/resources/data/dafeiyu/worldgen/placed_feature/ruby_ore.json
src/main/resources/data/dafeiyu/neoforge/biome_modifier/add_ruby_ore.json
```

红宝石矿那三个 json 的内容在前面的小节里都给全了，直接落盘即可（`ruby_cluster` 只在你要做第五节的自定义地物时才需要，并且要再配一个指向它的 placed_feature）。目录名有几个坑要盯住：

- `worldgen/configured_feature/` 和 `worldgen/placed_feature/` 都是**单数**。
- `neoforge/biome_modifier/` 也是单数，而且 `neoforge` 这一层不是 `data/neoforge/`，是 `data/dafeiyu/neoforge/`。
- 文件名就是 id 的路径部分：`ruby_ore.json` 对应 `dafeiyu:ruby_ore`。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 完全不生成，也没有报错 | `step` 写成了 `underground_decoration` 或 `vegetal_decoration` | 矿石统一用 `underground_ores` |
| `/place feature` 有东西，正常游戏没有 | 修改器的 `features` 指向了 configured_feature，或者 biome_modifier 目录写错 | `features` 必须是 placed_feature 的 id；目录是 `data/dafeiyu/neoforge/biome_modifier/` |
| 只在部分群系生成 | `biomes` 写了标签但漏了 `#`，或者测试的维度群系不在标签里 | 补 `#`；用 `/locate biome` 确认群系 |
| 启动崩溃，日志里有 `Feature cycle violation` | 同一个 placed_feature 被多个修改器加到同一群系、且阶段顺序不一致 | 每个 placed_feature 只由一个修改器负责；需要复用时复制一份新的 id |
| 矿特别密，像蜂窝 | 把 `count` 当成「每区块矿脉数」调得很大 | `count` 是尝试次数，原版铁矿也才 10；先试 4~8 |
| 矿特别稀，几乎找不到 | `height_range` 的 `min_inclusive` 比 `max_inclusive` 大，或者 `size` 设成 1 | 检查区间方向；`size` 至少 4 |
| 报 `Unknown registry key dafeiyu:ruby_ore` | json 放错目录，或文件名和 id 不一致 | 目录必须是 `worldgen/placed_feature/`，文件名必须是 `ruby_ore.json` |
| 自定义地物编译不过，提示 `FeatureType` 找不到 | 抄了 1.21.2+ 的教程 | 1.21.1 直接注册 `Feature<?>`，没有 `FeatureType` |
| 自定义地物生成了但全是单个方块 | `place()` 里每次都用同一个 `origin`，没有随机偏移 | 用 `origin.offset(random.nextInt(3) - 1, ...)` 打散 |
| 矿石替换掉了泥土和沙砾 | `target` 的标签写成了 `#minecraft:base_stone_overworld` 之外的东西 | 石头用 `stone_ore_replaceables`，深板岩用 `deepslate_ore_replaceables` |

## 练习

1. **基础**：把红宝石矿的 `count` 从 6 改成 20，重进世界后挖一条竖井，感受一下「密」是什么程度；再改回 6，对比差异。
2. **进阶**：让红宝石矿只在 y = -64 到 -16 之间生成，并且只在山地类群系生成（提示：`biomes` 换成 `#minecraft:is_mountain`），用 `/place feature` 和实地挖掘两种方式验证。
3. **挑战**：把第五节的自定义地物改成「贴着洞壁生成」——只在某个方块的六个面之一是空气时才放置，挂在 `underground_decoration` 阶段，并解释为什么它不能用 `underground_ores`。
