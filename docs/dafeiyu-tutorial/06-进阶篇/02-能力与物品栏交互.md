# 能力与物品栏交互

> 读完这篇，你的红宝石箱子就能被漏斗、被别的模组的管道、被任意一台机器当成「一个标准物品栏」来用——而它们完全不需要知道「红宝石箱子」这个类存在。

## 学习目标

- 能用自己的话说清「能力（Capability）」解决的到底是什么问题，以及什么时候**不该**用它。
- 能记住 `IItemHandler`、`IFluidHandler`、`IEnergyStorage` 三大能力分别对应什么，以及 `BLOCK`/`ENTITY`/`ITEM` 三个变体的区别。
- 能用 `level.getCapability(...)` 查到别人的物品栏，并知道为什么要判断 `null`。
- 能让自己的方块实体通过 `RegisterCapabilitiesEvent` 暴露 `IItemHandler`，并按 `Direction` 给出不同的行为。
- 能解释「漏斗为什么能跟你的方块交互」，以及为什么客户端拿到的能力通常是空的。

## 一、没有能力的时候，世界有多糟

假设你写了一个红宝石箱子，想让它能被漏斗抽东西。漏斗的代码是原版写的，它当然不认识你的 `RubyChestBlockEntity`。那怎么办？

最朴素的办法是让漏斗写一堆 `instanceof`：

```java
// 假想的"没有能力"的世界
if (be instanceof RubyChestBlockEntity chest) {
    // 抽红宝石箱子的物品
} else if (be instanceof SomeOtherModChest other) {
    // 抽别人箱子的物品
} else if (be instanceof YetAnotherMachine machine) {
    // ...
}
```

这段代码的问题显而易见：**每装一个新模组，漏斗就得改一次**。而原版漏斗不可能知道你存在。

于是有了另一种思路：大家约定一个**接口**，谁想被抽就实现它。漏斗只认接口，不认类：

```java
if (be instanceof IItemHandler handler) {
    // 不管你是谁，只要能按这个接口干活就行
}
```

这个思路就是「能力」的雏形。但直接让方块实体 `implements IItemHandler` 有个新问题：**一个方块实体可能同时是物品栏、流体罐、能量电池**，它得同时实现三个接口，而这些接口的方法名还可能撞车；更麻烦的是「同一个方块，从上面看是输入，从下面看是输出」，接口方法里没有「从哪一面」这个参数。

所以 NeoForge 的能力系统做了两件事：

1. **把「能做什么」和「怎么做到」分开**：能力是一张「能力身份证」，注册时告诉游戏「我这个方块实体能提供 `IItemHandler`」，查询时游戏帮你把实例递过去。
2. **查询时带上上下文**：`(level, pos, side)` 三个参数一起传，实现方就能根据 `side` 返回不同的实例。

官方文档里那三个自测问题很好用，抄在这里：

> 1. 我是否只关心它**能做什么**，而不关心它**如何做到**？
> 2. 这个「什么」是否只对部分方块/实体/物品可用？
> 3. 这个「如何」是否依赖于具体的方块/实体/物品？

三个都是「是」，就用能力。如果只是「判断某个实体在不在我机器范围内」，那是普通方法的事，别硬套能力。

## 二、三大常用能力

| 能力接口 | 管什么 | 典型场景 |
|---|---|---|
| `IItemHandler` | 一堆物品槽位：读、插、抽、每格上限 | 箱子、机器、背包 |
| `IFluidHandler` | 一堆流体罐：灌、抽、查容量 | 储罐、管道、桶 |
| `IEnergyStorage` | 一个能量缓冲区：收、放、查储量 | 发电机、电池、线缆 |

每个接口都有三个「变体」，区别只在于**挂在什么东西上**：

| 变体 | 挂在 | 查询方式 |
|---|---|---|
| `Capabilities.ItemHandler.BLOCK` | 方块 / 方块实体 | `level.getCapability(cap, pos, side)` |
| `Capabilities.ItemHandler.ENTITY` | 实体 | `entity.getCapability(cap, ctx)` |
| `Capabilities.ItemHandler.ITEM` | 物品堆 | `stack.getCapability(cap, ctx)` |

方块为什么特殊？因为**没有方块实体的方块也能有能力**（比如原版堆肥桶，它压根没有方块实体）。所以方块能力的查询入口在 `level` 上，而不是在方块实体上——这样「有实体」和「没实体」两种情况就能用同一个入口。

## 三、查询：怎么拿到别人的物品栏

文件：`src/main/java/com/dafeiyu/RubyFunnelBlock.java`（示例片段）

```java
// 我要把东西塞进我北边那个方块
BlockPos target = pos.north();
IItemHandler handler = level.getCapability(Capabilities.ItemHandler.BLOCK, target, Direction.SOUTH);

if (handler != null) {
    // 尝试插入：返回"没插进去的剩余部分"
    ItemStack remainder = handler.insertItem(0, new ItemStack(ModItems.RUBY.get(), 4), false);
    int inserted = 4 - remainder.getCount();
}
```

四个要点：

1. **必须判 `null`。** 查不到能力时返回 `null`，不是抛异常，也不是返回空实现。忘了判就是崩溃。
2. **`Direction.SOUTH` 是「从目标的哪一面看过去」。** 我站在目标方块的南边往里看，所以传 `SOUTH`。这个参数的含义新手经常搞反，记住：**它描述的是目标方块的那一面，不是你的朝向**。
3. **`insertItem` 的返回值是「没插进去的部分」。** 插进去 3 个、剩 1 个，返回值就是 1 个。不要以为返回值是「插进去的数量」。
4. **`simulate = true` 是「试算」。** 传 `true` 不会真的改动物品栏，只告诉你「如果真插会怎样」。机器的输入预览、管道的路径规划都靠它。

如果手头已经有方块状态和方块实体，可以走更快的重载，省掉两次查表：

```java
IItemHandler handler = level.getCapability(Capabilities.ItemHandler.BLOCK, pos, state, blockEntity, side);
```

**每 tick 都要查的场景**（比如机器每刻都抽一次），用 `BlockCapabilityCache`：

```java
private BlockCapabilityCache<IItemHandler, @Nullable Direction> cache;

// 在 onLoad 里建一次
this.cache = BlockCapabilityCache.create(
        Capabilities.ItemHandler.BLOCK, level, pos.north(), Direction.SOUTH,
        () -> !this.isRemoved(),          // 缓存还有效吗
        () -> this.onNeighborChanged());  // 邻居的能力变了，通知我

// 之后每 tick 直接取
IItemHandler handler = this.cache.getCapability();
```

缓存由垃圾回收器管理，不用手动注销。但**一旦你提供了能力，就要在能力变化时主动作废**：

```java
level.invalidateCapabilities(pos);
```

方块被放置、被破坏、状态改变导致能力变了，都要调这一行。NeoForge 已经帮你处理了区块加载/卸载和方块实体创建/销毁，其余的要自己来。

## 四、让自己的方块实体提供 IItemHandler

先说结论：**九成情况下你不需要手写 `IItemHandler` 的七个方法，用 `ItemStackHandler` 就行。**

`ItemStackHandler` 是 NeoForge 提供的现成实现，内部是一个 `NonNullList<ItemStack>`，你只需要在需要的时候重写两个钩子：

```java
private final ItemStackHandler inventory = new ItemStackHandler(9) {
    @Override
    protected void onContentsChanged(int slot) {
        setChanged();          // 内容变了 → 标记区块脏，退出重进不丢
    }

    @Override
    public boolean isItemValid(int slot, ItemStack stack) {
        return stack.is(ModItems.RUBY.get());   // 只收红宝石
    }
};
```

如果你确实要自己实现（比如物品不存在一个数组里，而是算出来的），那要实现这六个方法：

| 方法 | 什么时候被调用 | 注意 |
|---|---|---|
| `getSlots()` | 任何人问「你有几格」 | 返回固定值，别返回会变的值 |
| `getStackInSlot(int)` | 读某一格 | 空格返回 `ItemStack.EMPTY`，**不要返回 `null`** |
| `insertItem(int, ItemStack, boolean)` | 往里放 | 返回剩余部分，`simulate` 为真时不能改数据 |
| `extractItem(int, int, boolean)` | 往外拿 | 返回实际拿出的那堆 |
| `getSlotLimit(int)` | 问每格上限 | 一般是 64，或 `stack.getMaxStackSize()` |
| `isItemValid(int, ItemStack)` | 判断能不能放 | 有默认实现（返回 `true`） |

**`insertItem` 和 `extractItem` 是最容易写错的两个**：它们必须尊重 `simulate`，并且在真的改动之后调 `onContentsChanged(slot)`（`ItemStackHandler` 里叫这个名字）。少调一次，物品栏就不同步、不存档。

## 五、注册：告诉游戏「我能提供什么」

光有 `ItemStackHandler` 还不够，游戏不知道要去哪儿找它。你得在**模组总线**的 `RegisterCapabilitiesEvent` 里登记：

文件：`src/main/java/com/dafeiyu/ModCapabilities.java`

```java
package com.dafeiyu;

import net.minecraft.core.Direction;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.neoforge.capabilities.Capabilities;
import net.neoforged.neoforge.capabilities.RegisterCapabilitiesEvent;

@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class ModCapabilities {

    @SubscribeEvent
    public static void registerCapabilities(RegisterCapabilitiesEvent event) {
        event.registerBlockEntity(
                Capabilities.ItemHandler.BLOCK,          // 注册哪种能力
                ModBlockEntities.RUBY_CHEST.get(),       // 给哪个方块实体类型
                (blockEntity, side) -> blockEntity.getItemHandler(side)  // 怎么拿到实例
        );
    }
}
```

第三个参数是一个**函数**，不是实例。这是关键设计：每次有人查询，游戏就调用这个函数一次，你可以根据 `side` 返回不同的对象。它接收两个参数：方块实体本身、以及查询的 `Direction`（可能是 `null`，表示「不分面」，比如漏斗从上面抽时会传具体方向，而某些机器会传 `null`）。

**为什么必须在事件里注册，不能写在构造器里？** 因为能力注册表在游戏启动的特定阶段才收集完毕，构造器执行时它还没准备好。放在 `RegisterCapabilitiesEvent` 里，NeoForge 会在正确的时机调用你。这也是「注册时机」这个坑的根源——你在 `static` 块里手动注册，只会得到一个空表。

## 六、按侧面区分：上面进、下面出

这是能力最实用的地方。假设红宝石箱子：**从上面只能塞进去，从下面只能抽出来，从侧面随便**。做法是包一层：

文件：`src/main/java/com/dafeiyu/OutputOnlyItemHandler.java`

```java
package com.dafeiyu;

import net.minecraft.world.item.ItemStack;
import net.neoforged.neoforge.items.IItemHandler;

/** 只出不进的包装器：内部转发给真正的物品栏，但拒绝一切插入 */
public class OutputOnlyItemHandler implements IItemHandler {
    private final IItemHandler delegate;

    public OutputOnlyItemHandler(IItemHandler delegate) {
        this.delegate = delegate;
    }

    @Override
    public int getSlots() {
        return delegate.getSlots();
    }

    @Override
    public ItemStack getStackInSlot(int slot) {
        return delegate.getStackInSlot(slot);
    }

    @Override
    public ItemStack insertItem(int slot, ItemStack stack, boolean simulate) {
        return stack;          // 原样退回 = 一个也没插进去
    }

    @Override
    public ItemStack extractItem(int slot, int amount, boolean simulate) {
        return delegate.extractItem(slot, amount, simulate);
    }

    @Override
    public int getSlotLimit(int slot) {
        return delegate.getSlotLimit(slot);
    }

    @Override
    public boolean isItemValid(int slot, ItemStack stack) {
        return false;          // 对"能不能放"也说不
    }
}
```

然后在方块实体里准备两个实例（**只 new 一次，别每次查询都 new**）：

```java
private final IItemHandler allSides = this.inventory;
private final IItemHandler outputOnly = new OutputOnlyItemHandler(this.inventory);

public IItemHandler getItemHandler(@Nullable Direction side) {
    return side == Direction.DOWN ? this.outputOnly : this.allSides;
}
```

注册时那个 lambda 直接返回它：

```java
(blockEntity, side) -> blockEntity.getItemHandler(side)
```

NeoForge 还自带两个现成的包装器，能用就别自己写：

- `RangedWrapper`：只暴露一段槽位，比如 `new RangedWrapper(handler, 0, 3)` 只给前三格。
- `InvWrapper`：把原版的 `Container`（比如原版箱子）包成 `IItemHandler`，方便你统一处理。

## 七、物品侧的能力

给物品加能力，写法几乎一样，只是注册方法换成 `registerItem`，第一个参数是 `ItemStack` 而不是方块实体：

```java
event.registerItem(
        Capabilities.ItemHandler.ITEM,
        (stack, context) -> new BackpackHandler(stack),
        ModItems.RUBY_BACKPACK.get()
);
```

> **警告**：上面这行如果写成 `(stack, ctx) -> new ItemStackHandler(9)`，**每次查询都会 new 一个空背包**。你放进去的东西在函数返回那一刻就丢了，因为下一次查询拿到的是另一个新实例。正确的做法是让 `BackpackHandler` 在构造时从物品的**数据组件**（`DataComponents.CONTAINER`）读出内容，在 `onContentsChanged` 时写回去。数据组件的读写见 [数据组件](../03-核心概念篇/05-数据组件.md)。

**关于 `ICapabilityProvider`**：你在别的模组源码、或者 1.20 以前的教程里会看到这个接口，以及 `Item#initCapabilities(...)` 这种写法。那是 Forge 时代的方式——「让对象自己实现一个方法，返回它能提供的能力」。NeoForge 1.21 把这条路换成了**统一的事件注册**，原因很简单：能力注册集中在一个地方，排查问题时不用满世界找 `initCapabilities`。所以：

- 看到 `ICapabilityProvider`：知道它是「能按上下文返回能力实例的东西」就够了，**不要照抄**。
- 自己写代码：一律用 `RegisterCapabilitiesEvent`。

## 八、漏斗和管道到底做了什么

现在可以回答那个问题了。原版漏斗每 tick 会做两件事：

1. **往上抽**：查自己上方方块的能力，拿到 `IItemHandler`，调 `extractItem`。
2. **往下塞**：查自己指向的方块的能力，拿到 `IItemHandler`，调 `insertItem`。

它从头到尾**没有出现过 `RubyChestBlockEntity` 这个名字**。它只认 `Capabilities.ItemHandler.BLOCK` 这张身份证。你注册了，它就能抽；你没注册，它就当你是个普通方块，什么也不做。

这也解释了一个常见困惑：**「为什么我的机器漏斗抽不出来？」** 九成是没注册能力，或者注册了但 `insertItem`/`extractItem` 里 `simulate` 处理错了（漏斗会先 `simulate` 一次再真做一次，如果 `simulate` 也真改了数据，行为就会乱）。

## 完整示例

在 [上一篇](01-菜单与容器界面.md) 的红宝石箱子上加能力，改三个文件、加一个文件。

**① 新文件 `src/main/java/com/dafeiyu/OutputOnlyItemHandler.java`** —— 就是第六节那段，原样抄。

**② `src/main/java/com/dafeiyu/RubyChestBlockEntity.java` 增加**

```java
import net.minecraft.core.Direction;
import net.neoforged.neoforge.items.IItemHandler;

// 字段：两个包装好的实例，只创建一次
private final IItemHandler allSides = this.inventory;
private final IItemHandler outputOnly = new OutputOnlyItemHandler(this.inventory);

/** 按面返回不同的物品栏：下面只出不进，其余面全开 */
public IItemHandler getItemHandler(@Nullable Direction side) {
    return side == Direction.DOWN ? this.outputOnly : this.allSides;
}
```

`@Nullable` 来自 `org.jetbrains.annotations.Nullable`，记得 import。

**③ 新文件 `src/main/java/com/dafeiyu/ModCapabilities.java`** —— 就是第五节那段。

**④ 主类里不用改。** `@EventBusSubscriber(bus = MOD)` 会自动注册到模组总线，这是它和手动 `modBus.addListener(...)` 的区别。如果你习惯手动注册，写成：

```java
public DafeiyuMod(IEventBus modEventBus, ModContainer modContainer) {
    // ...
    modEventBus.addListener(ModCapabilities::registerCapabilities);
}
```

**验证方法**：放一个箱子，上面放漏斗朝下（往箱子里灌），下面放漏斗朝上（往外抽），中间放箱子。上面的漏斗能塞进去，下面的漏斗能抽出来，而侧面用另一个模组的管道也能抽——但**从下面塞不进去**。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 漏斗完全不理会我的方块 | 没注册能力，或注册了但没在主类/事件订阅里生效 | 确认 `ModCapabilities` 被 `@EventBusSubscriber(bus = MOD)` 覆盖到 |
| 注册了还是抽不出来 | `getItemHandler(side)` 里 `side` 判断反了，或返回了 `null` | 打印一下 `side` 的实际值；`null` 表示「不分面」 |
| 抽出来的物品和放进去的对不上 | `simulate` 为 `true` 时也改了数据 | `simulate` 分支里只算结果、不写字段 |
| 客户端看到物品栏是空的 | 能力**不负责同步**，客户端拿到的是本地那份方块实体 | 用菜单/数据包同步，别指望能力 |
| 改了能力之后，机器还在用旧的 | 没调 `level.invalidateCapabilities(pos)` | 能力变化处补这一行 |
| 启动报 `Cannot register capability for unknown block entity` | 用了 `registerBlockEntity` 但类型还没注册 | 把 `ModBlockEntities.register(...)` 放在前面 |
| `new ItemStackHandler(9)` 每次查询都新建，物品丢失 | 提供者每次返回新实例 | 实例存在方块实体字段里 |

## 练习

1. **（易）** 把红宝石箱子改成「上面只能进、下面只能出、侧面全开」。提示：再写一个 `InputOnlyItemHandler`，`extractItem` 直接返回 `ItemStack.EMPTY`。
2. **（中）** 给箱子加一个「只允许放红宝石」的限制，分别用两种方式实现：`ItemStackHandler#isItemValid`，以及 `Slot#mayPlace`。然后回答：如果只在 `Slot` 里限制，漏斗还能塞进泥土吗？为什么？
3. **（难）** 写一个「红宝石熔炉」，同时提供 `IItemHandler`（燃料格 + 原料格 + 产物格，用 `RangedWrapper` 分面）和 `IEnergyStorage`（用 NeoForge 自带的 `EnergyStorage` 类继承）。要求：从上面只能塞原料，从侧面只能塞燃料，从下面只能抽产物。
