# 网络通信

> 读完这篇，你能做出这样一条完整链路：按下一个键 → 客户端发包 → 服务端发给你一个红宝石 → 服务端回包 → 客户端播放升级音效。这条链路是所有「按键触发技能」「GUI 点按钮」「机器状态同步」的原型。

## 学习目标

- 能说清「为什么客户端改了东西服务端不知道」，以及哪些事情必须发包。
- 能写出一个 `CustomPacketPayload`：`Type` + `StreamCodec` + `type()` 三件套。
- 能在 `RegisterPayloadHandlersEvent` 里按方向注册，并知道 `playToServer` / `playToClient` 用错会怎样。
- 能用 `PacketDistributor` 的四个常用发送方法。
- 能解释 `context.enqueueWork(...)` 为什么必须包一层，不包会崩在哪。

## 一、为什么非要有网络

Minecraft 是「服务端权威」的：物品、方块、实体、血量，**真正的数据全在服务端**。客户端只是拿到一份副本用来显示。

你在客户端按下一个键，如果直接写 `player.getInventory().add(...)`，会发生什么？

- 单人游戏里：客户端和服务端跑在同一个进程，但仍然是两个 `Level` 实例。你加进了客户端的背包，服务端那份没变。下一次服务端同步背包时，你的红宝石**被覆盖消失**。
- 多人游戏里：客户端根本没有权限改服务端，什么也不会发生。

所以规则是：

> **想让世界发生变化 → 发一个包给服务端，让服务端去改。**
> **想让客户端看到变化 → 服务端发一个包给客户端。**

服务端不需要「请求客户端改世界」，客户端也不需要「自己算结果」。这条单向的信任链，就是整个网络系统的骨架。

## 二、载荷：一个能过网的 record

NeoForge 把「自定义包」抽象成**载荷（Payload）**：一个 `record`，加一个类型标识，加一个 `StreamCodec`。

```java
public record GiveRubyPayload(int count) implements CustomPacketPayload {

    // 身份证：全局唯一，两个端靠它对上号
    public static final Type<GiveRubyPayload> TYPE =
            new Type<>(ResourceLocation.fromNamespaceAndPath("dafeiyu", "give_ruby"));

    // 怎么变成字节、怎么变回来（上一篇学的）
    public static final StreamCodec<ByteBuf, GiveRubyPayload> STREAM_CODEC = StreamCodec.composite(
            ByteBufCodecs.VAR_INT, GiveRubyPayload::count,
            GiveRubyPayload::new
    );

    // 接口要求实现的方法，返回上面的身份证
    @Override
    public Type<? extends CustomPacketPayload> type() {
        return TYPE;
    }
}
```

三个部分各自的职责：

| 部分 | 作用 | 写错的后果 |
|---|---|---|
| `Type<...>` | 唯一标识符，收发双方靠它匹配 | 两端注册的名字不一致 → 客户端被踢：「未知的载荷」 |
| `StreamCodec` | 把对象写成字节、从字节读回来 | 字段顺序不一致 → 读出乱码、`VarInt too big` |
| `type()` | 让框架知道这个对象是哪种载荷 | 不实现编译不过 |

**为什么 `Type` 要单独抽出来？** 因为注册的时候需要「类型」而不是「实例」——注册发生在游戏启动时，那时候还没有任何载荷对象存在。

**为什么泛型写成 `Type<GiveRubyPayload>` 而不是 `Type<?>`？** 这样 `registrar.playToServer(TYPE, ...)` 才能推断出处理器接收的参数类型，写错会在编译期报错，而不是运行时 `ClassCastException`。

## 三、注册：方向和线程

注册在**模组总线**的 `RegisterPayloadHandlersEvent` 里做：

```java
@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class ModPayloads {

    @SubscribeEvent
    public static void register(RegisterPayloadHandlersEvent event) {
        PayloadRegistrar registrar = event.registrar("1");   // "1" 是协议版本号

        // 客户端 → 服务端
        registrar.playToServer(GiveRubyPayload.TYPE, GiveRubyPayload.STREAM_CODEC,
                ServerPayloadHandler::handle);

        // 服务端 → 客户端
        registrar.playToClient(RubyGrantedPayload.TYPE, RubyGrantedPayload.STREAM_CODEC,
                ClientPayloadHandler::handle);
    }
}
```

### 方向

| 方法 | 谁发谁收 | 用错会怎样 |
|---|---|---|
| `playToServer` | 客户端 → 服务端 | 服务端发这个包 → 直接崩（服务端没有「上游」） |
| `playToClient` | 服务端 → 客户端 | 客户端发这个包 → 崩 |
| `playBidirectional` | 双向 | 需要 `DirectionalPayloadHandler` 分别给两个处理器 |

`playBidirectional` 的写法是这样，参数是一个「装着两个处理器的盒子」：

```java
registrar.playBidirectional(
        MyData.TYPE,
        MyData.STREAM_CODEC,
        new DirectionalPayloadHandler<>(
                ClientPayloadHandler::handle,   // 客户端收到时
                ServerPayloadHandler::handle    // 服务端收到时
        )
);
```

### 线程：`HandlerThread`

默认情况下，处理器在**主线程**上被调用——这很安全，你可以直接动世界。但主线程每 tick 只有 50ms，如果你在处理器里做重活（解析大 JSON、算路径），会卡顿。

这时可以切到网络线程：

```java
PayloadRegistrar registrar = event.registrar("1").executesOn(HandlerThread.NETWORK);
```

**注意 `executesOn` 返回的是新实例**，不是在原对象上改。所以要写成 `registrar = registrar.executesOn(...)`，否则后面注册的还是旧设置。切到网络线程之后，**任何动世界的操作都必须再 `enqueueWork` 回主线程**（见第五节）。

### 协议版本号

`event.registrar("1")` 里的 `"1"` 是协议版本。两端版本不一致时，客户端会在握手阶段被拒绝。你改了载荷的字段结构，就该把这个号加一——它相当于「这个模组的网络协议是第几版」。

> **顺带一提**：如果要在玩家**真正进入游戏之前**（配置阶段）就发包，比如同步客户端配置，用的是 `registrar.configurationToClient(...)` 加一个 `ICustomConfigurationTask`。这部分机制比较特殊，需要服务端主动确认任务完成，否则玩家会卡在「正在加入世界」。细节见 [使用配置任务](/docs/neoforge-1.21.1/11-网络通信/05-使用配置任务.md)。

## 四、发送：`PacketDistributor`

发送只有几个方法，全部是静态的：

```java
// 客户端 → 服务端（只有这一个方向）
PacketDistributor.sendToServer(new GiveRubyPayload(1));

// 服务端 → 某一个玩家
PacketDistributor.sendToPlayer(serverPlayer, new RubyGrantedPayload(1));

// 服务端 → 所有玩家
PacketDistributor.sendToAllPlayers(new RubyGrantedPayload(1));

// 服务端 → 正在追踪某个区块的所有玩家（方块实体同步最常用）
PacketDistributor.sendToPlayersTrackingChunk(serverLevel, chunkPos, new MyPayload(...));
```

**包体大小限制**：发往服务端的包必须 **小于 32 KiB**，发往客户端的包最多 **1 MiB**。超过不是「慢」，是直接断开连接。所以：

- 不要一次发整个 `ItemStackHandler` 的内容，发「哪一格变成了什么」。
- 不要发大段文本，发 ID 让客户端自己去查。
- 真要传大块数据，分片发，或者改成「服务端存好，客户端按需请求」。

**这四个方法都有「在哪一侧调用」的硬性限制。** `sendToServer` 只能在客户端调，另外三个只能在服务端调。写错了不会给你一个温和的警告，而是 `NullPointerException`（因为那一侧没有对应的连接对象）。所以发送代码尽量贴着触发点写：

- 按键、GUI 按钮 → 就在客户端类里调 `sendToServer`。
- 方块被破坏、命令执行、任务完成 → 就在服务端事件里调 `sendToPlayer`。

不要在公共代码里写 `if (level.isClientSide) ... else ...` 然后两边都发包——这种代码迟早会在某一侧被意外触发。

## 五、处理：`enqueueWork` 到底在干什么

处理器长这样：

```java
public static void handle(GiveRubyPayload payload, IPayloadContext context) {
    context.enqueueWork(() -> {
        // 这里的代码在主线程执行
    });
}
```

`enqueueWork` 把一段代码「排队」到主线程的任务队列里，等这一 tick 的空隙执行。它返回一个 `CompletableFuture`，所以你能接 `.exceptionally(...)` 处理异常。

**为什么不能直接写？** 如果处理器在网络线程上跑（你设了 `HandlerThread.NETWORK`），直接动世界就是「在非主线程改共享状态」——轻则数据错乱，重则 `ConcurrentModificationException` 崩服。Minecraft 的世界、实体列表、区块缓存全都不是线程安全的。

即使你用默认的主线程模式，也建议养成「一律包 `enqueueWork`」的习惯：这样以后改成网络线程时不用重写，而且能统一处理异常。

```java
context.enqueueWork(() -> {
    // 干活
}).exceptionally(e -> {
    // 出了异常，至少断开连接并说明原因，别让它静默消失
    context.disconnect(Component.literal("处理失败：" + e.getMessage()));
    return null;
});
```

> **坑**：`CompletableFuture` 里抛出的异常，如果你既不 `exceptionally` 也不 `join`，它会被**吞掉**——你只会看到「什么都没发生」，日志里一片安静。

## 六、这些情况根本不用自己发包

新手最容易犯的另一个错，是「什么都自己发包」，结果写了一大堆重复代码，还和原版机制打架。下面这些同步是**游戏已经替你做好**的：

| 场景 | 现成机制 | 你该做什么 |
|---|---|---|
| 方块实体里的数据（箱子内容、机器进度） | `getUpdateTag` + `getUpdatePacket` + `sendBlockUpdated` | 只实现这两个方法，变化时触发一次 |
| GUI 里的数字（进度条、能量） | `ContainerData` / `DataSlot` | 见 [菜单与容器界面](01-菜单与容器界面.md) |
| 物品堆上的自定义数据 | 数据组件的 `networkSynchronized` | 写好 `StreamCodec` 就行 |
| 实体身上的自定义状态 | `SynchedEntityData`（`EntityDataAccessor`） | 定义 accessor，`set` 时自动同步 |
| 玩家背包、血量、经验 | 原版封包 | 什么都别做 |

真正需要你发包的，只有三类：

1. **客户端的「意图」**：按键、GUI 里点了按钮、拖拽结束。这些服务端不可能知道。
2. **服务端的「通知」**：任务完成、播个音效、弹个标题。这些客户端算不出来。
3. **不在上述任何机制里的自定义状态**：比如「这个玩家当前选中了哪个技能」，既不是方块也不是物品。

判断方法：**先问「原版有没有现成的通道」，没有才自己开一条。**

**④ `src/main/java/com/dafeiyu/network/ServerPayloadHandler.java`**

```java
package com.dafeiyu.network;

import com.dafeiyu.ModItems;
import net.minecraft.network.chat.Component;
import net.minecraft.server.level.ServerPlayer;
import net.minecraft.world.entity.player.Player;
import net.minecraft.world.item.ItemStack;
import net.neoforged.neoforge.network.PacketDistributor;
import net.neoforged.neoforge.network.handling.IPayloadContext;

public class ServerPayloadHandler {

    public static void handle(GiveRubyPayload payload, IPayloadContext context) {
        context.enqueueWork(() -> {
            Player player = context.player();

            // 1. 发红宝石：背包塞得下就塞，塞不下掉在脚下
            ItemStack stack = new ItemStack(ModItems.RUBY.get(), payload.count());
            if (!player.getInventory().add(stack)) {
                player.drop(stack, false);
            }

            // 2. 给个提示（actionBar = true 显示在物品栏上方）
            player.displayClientMessage(
                    Component.literal("收到 " + payload.count() + " 个红宝石"), true);

            // 3. 回包给客户端，让它播音效
            if (player instanceof ServerPlayer serverPlayer) {
                PacketDistributor.sendToPlayer(serverPlayer, new RubyGrantedPayload(payload.count()));
            }
        }).exceptionally(e -> {
            context.disconnect(Component.literal("红宝石发放失败：" + e.getMessage()));
            return null;
        });
    }
}
```

**⑤ `src/main/java/com/dafeiyu/client/ClientPayloadHandler.java`**

```java
package com.dafeiyu.client;

import com.dafeiyu.network.RubyGrantedPayload;
import net.minecraft.client.Minecraft;
import net.minecraft.sounds.SoundEvents;
import net.neoforged.neoforge.network.handling.IPayloadContext;

public class ClientPayloadHandler {

    public static void handle(RubyGrantedPayload payload, IPayloadContext context) {
        context.enqueueWork(() -> {
            Minecraft minecraft = Minecraft.getInstance();
            if (minecraft.player != null) {
                // 客户端本地播放，不需要服务端再发一次声音包
                minecraft.player.playSound(SoundEvents.PLAYER_LEVELUP, 1.0F, 1.2F);
            }
        });
    }
}
```

> 这个类里出现了 `Minecraft`，所以它**必须**放在 `client` 包里。但 `ModPayloads` 在服务端也会加载，里面又有 `ClientPayloadHandler::handle` 这个方法引用——为什么不会崩？因为**方法引用只加载类本身，不加载方法体里用到的类**。只要 `ClientPayloadHandler` 的字段和方法签名里不出现客户端类型（`Minecraft`、`Screen`），服务端加载它就是安全的。这条界线要记牢。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 客户端被踢：`Unknown payload` / `Unregistered payload` | 两端 `Type` 的 `ResourceLocation` 不一致，或一方没注册 | 用同一个常量，检查 `modid:name` 拼写 |
| 服务端崩溃 `ClassCastException` 在 handler | 方向注册反了（`playToClient` 的包发给了服务端） | 按「谁改世界谁收包」重新分配 |
| 处理器里改世界，偶尔崩服 | 在非主线程动世界 | 一律包 `context.enqueueWork(...)` |
| 按键没反应 | 忘了 `RegisterKeyMappingsEvent`，或 `consumeClick` 写在 `if` 里被吞 | 用 `while` 循环消费 |
| 发出去的包在服务端读出来全是 0 | 两端 `StreamCodec` 字段顺序不同 | 两端必须引用同一个 `STREAM_CODEC` 常量 |
| 断开连接：`Packet too large` | 包体超过 32 KiB（上行）/ 1 MiB（下行） | 拆分数据，只传 ID 或差量 |
| 异常被吞，什么日志都没有 | `CompletableFuture` 的异常没处理 | 补 `.exceptionally(...)` |
| 启动崩 `NoClassDefFoundError: net/minecraft/client/...` | 客户端类被服务端加载了 | 客户端代码放 `client` 包，类上标 `value = Dist.CLIENT` |
| 改了字段后老客户端连不上 | 协议版本没变，但结构变了 | `registrar("1")` 改成 `"2"` |
| 服务端日志报 `Payload X was not registered` | 注册方法没被调用（`@EventBusSubscriber` 的 `bus` 写成了默认值） | 明确写 `bus = EventBusSubscriber.Bus.MOD` |

## 练习

1. **（易）** 把按键改成「潜行 + R」才发包：在 `ClientEvents` 里判断 `minecraft.player.isShiftKeyDown()`，不满足就 `continue`（注意还在 `while` 里）。
2. **（中）** 加一个服务端 → 客户端的包，携带「全服累计挖掘数」，玩家每次按 R 时客户端显示在 actionBar 上。要求用 `long`（提示：`ByteBufCodecs.VAR_LONG`）。
3. **（难）** 做一个「红宝石充能」：客户端按住 R 蓄力，松手时把蓄力时长（毫秒）发给服务端，服务端按 `时长 / 100` 给对应数量的红宝石，并回包让客户端播放不同音调的音效。要求处理「蓄力过程中玩家死亡/换维度」的情况——想想此时 `context.player()` 还有效吗。
