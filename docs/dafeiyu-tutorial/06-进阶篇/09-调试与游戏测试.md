# 调试与游戏测试

> 读完这篇，你能从一坨红色报错里三分钟定位到自己哪一行写错了，并且能用 GameTest 把「红宝石方块挖了掉红宝石」这件事写成一条自动跑的测试。

## 学习目标

- 能分清 `crash-reports/`、`latest.log`、`debug.log` 各是什么，知道该看哪个。
- 能从异常栈和 `Caused by` 链里找到「第一处属于 `com.dafeiyu` 的帧」。
- 会用 `/data get`、`/setblock`、F3 调试屏、`/neoforge tps` 快速验证一个猜想。
- 会用调试分析器找出「哪个方法在吃 tick」，并给自己的代码手动加 profiling 小节。
- 能写一个 `@GameTest`，用断言验证掉落行为，并用 `gradlew runGameTestServer` 在 CI 里跑。

## 一、崩溃了先看哪个文件

游戏目录下有三个地方会出现日志，用途完全不同：

| 位置 | 内容 | 什么时候看 |
|---|---|---|
| `crash-reports/crash-<日期>_<时间>-<侧>.txt` | 崩溃瞬间的快照：异常栈、加载的模组列表、系统信息、卡在哪 | **游戏直接崩了**，先看这个 |
| `logs/latest.log` | 本次运行的完整日志，从启动到崩溃/退出 | 没崩但行为不对，或者想看自己打的日志 |
| `logs/debug.log` | 更啰嗦的调试信息，含每个资源加载记录 | 怀疑资源/数据包没加载时 |
| `logs/2026-10-31-3.log.gz` | 历史日志，按启动次数编号 | 上次崩溃没留下 crash-report 时 |

`crash-reports` 的价值在于它把「崩溃原因」放在了最上面几行，还附了模组列表——如果是模组冲突，你能立刻看到可疑对象。而 `latest.log` 的价值在于**上下文**：崩溃前你打了什么日志、加载到哪一步、哪个 json 报了 warning。

### 1.1 异常栈怎么读

一段典型的栈长这样：

```text
java.lang.NullPointerException: Cannot invoke "net.minecraft.world.item.ItemStack.isEmpty()" because "stack" is null
    at com.dafeiyu.enchantment.DropRubyEffect.apply(DropRubyEffect.java:41) ~[dafeiyu.jar:?]
    at net.minecraft.world.item.enchantment.EnchantmentHelper.doPostAttackEffects(EnchantmentHelper.java:312) ~[client-1.21.1.jar:?]
    at net.minecraft.world.entity.LivingEntity.hurt(LivingEntity.java:1204) ~[client-1.21.1.jar:?]
    at net.minecraft.client.player.LocalPlayer.attack(LocalPlayer.java:120) ~[client-1.21.1.jar:?]
    ...
```

读法分两步：

**第一步，找自己的包名。** 从上往下扫，第一个 `at com.dafeiyu.` 就是「我的代码出错的位置」。上面那一行是异常类型和消息，它已经告诉你原因了：`stack` 是 `null`，你去调 `isEmpty()` 了。

**第二步，从下往上理解调用链。** 栈是「最内层在最上面」打印的，所以往下读就是「谁调用了谁」。最底下通常是线程入口（`Render thread` 或 `Server thread`），往上依次是原版逻辑，最上面是你的代码。想知道「玩家做了什么操作触发到这里」，就得从下往上看。

**第三步，遇到 `Caused by` 要看最后一条。** 有些异常是包装出来的：

```text
java.lang.RuntimeException: Failed to load datapack
Caused by: com.google.gson.JsonSyntaxException: Expected name at line 12 column 3
Caused by: java.lang.IllegalStateException: Unknown registry key dafeiyu:ruby_ore
```

真正的根因在**最后一个** `Caused by` 上。上面两条只是「谁在往上抛」。很多人只看了第一条 `RuntimeException`，然后去搜「Failed to load datapack」，永远搜不到答案。

还有一个细节：栈里带 `~[dafeiyu.jar:?]` 的是你的模组，带 `~[client-1.21.1.jar:?]` 的是原版。如果整条栈里**没有任何一帧是你的包名**，那多半是别的模组或原版的问题，先确认是不是你的模组引起的（把模组挪出去再跑一次）。

## 二、日常调试：日志和命令

### 2.1 打日志的正确姿势

```java
// 在类里声明一次
private static final Logger LOGGER = LogUtils.getLogger();

// 用占位符，不要用字符串拼接
LOGGER.info("[dafeiyu] 玩家 {} 触发了红宝石收割，等级 {}", player.getName().getString(), level);
```

为什么强调占位符？因为 `LOGGER.info("..." + expensive())` 会**先拼接再判断级别**，即使这条日志最终不输出，字符串也已经拼好了。用 `{}` 占位符时，参数只有在真的要输出时才转字符串。在高频路径（每 tick 执行的那种）里，这个差别很可观。

级别也要选对：

- `LOGGER.error`：出错了，玩家/整合包作者必须知道。
- `LOGGER.warn`：不该发生但能继续，比如配置值越界被修正。
- `LOGGER.info`：重要状态变化，比如「注册了 12 个物品」。
- `LOGGER.debug`：调试细节，**默认不输出**，需要改 log4j 配置或在启动参数里打开。

排查问题时把细节写成 `debug`，等要看了再打开，比事后删一堆 `info` 干净得多。

### 2.2 几条救命命令

| 命令 | 用途 |
|---|---|
| `/data get entity @s SelectedItem` | 看手里物品的完整 NBT/组件，确认附魔、自定义数据到底有没有写进去 |
| `/data get block ~ ~ ~` | 看脚下方块实体的数据 |
| `/setblock ~ ~1 ~ dafeiyu:ruby_block` | 快速摆一个方块验证模型/掉落 |
| `/fill ~-5 ~ ~-5 ~5 ~3 ~5 air` | 清场，方便观察生成结果 |
| `/neoforge tps` | 看服务端 tick 速率，判断是不是卡了 |
| `/debug start` / `/debug stop` | 开/关性能分析器（下一节详说） |

F3 调试屏里还有几个组合键值得记住：`F3 + G` 显示区块边界（看世界生成必备），`F3 + B` 显示实体碰撞箱和视线，`F3 + H` 让物品提示显示内部 id。

`/data get` 特别值得单独说：当你怀疑「数据组件没写进去」时，它比任何日志都直接。比如附魔到底挂上没有，执行 `/data get entity @s SelectedItem`，看输出里有没有 `enchantments` 这一段，一眼就清楚。

## 三、调试分析器：找出谁在吃 tick

TPS 掉了、游戏卡顿，靠猜是猜不出来的。Minecraft 自带一个采样分析器：

```text
/debug start
```

等 10 秒（或手动 `/debug stop`），游戏目录下会生成 `debug/profiling/2026-10-31_12_30_00-世界名-版本号.zip`。解压后进 `server/` 或 `client/`，打开 `profiling.txt`。

文件开头是「跑了多少毫秒、多少个 tick」，下面是树状结构：

```text
[00] levels - 96.70%/96.70%
[01] |   Level Name - 99.76%/96.47%
[02] |   |   tick - 99.31%/95.81%
[03] |   |   |   entities - 47.72%/45.72%
[04] |   |   |   |   regular - 98.32%/44.95%
[04] |   |   |   |   blockEntities - 0.90%/0.41%
```

四列分别是：**深度、小节名、占父级的百分比、占整个 tick 的百分比**。

看的时候盯住**第四列**（占整个 tick 的比例），而不是第三列。第三列 90% 可能只是因为它的父级本身很小。真正该优化的是「第四列数字大、且是你自己的代码」的那些行。

分析器对实体和方块实体有内建支持，其他代码要手动加小节：

```java
// level 是 ServerLevel 或 ClientLevel
ProfilerFiller profiler = level.getProfiler();
profiler.push("dafeiyu_ruby_scan");
try {
    // 你想测量的代码
} finally {
    profiler.pop();
}
```

跑完在 `profiling.txt` 里搜 `dafeiyu_ruby_scan`，就能看到它占了多少。**一定要用 `try/finally` 包住 `pop()`**，否则中途抛异常会导致 profiler 的栈不平衡，后面的数据全乱。

## 四、配置：别把可调参数写死

在讲测试之前，先补一个和调试强相关的东西：配置。

你写死一个「每级额外掉 1 个红宝石」，玩家觉得太多，只能等你发新版本。放进配置，玩家自己改文件就行，整合包作者也能按包调整。

文件：`src/main/java/com/dafeiyu/DafeiyuConfig.java`

```java
package com.dafeiyu;

import net.neoforged.neoforge.common.ModConfigSpec;

public class DafeiyuConfig {
    public static final ModConfigSpec SPEC;
    public static final ModConfigSpec.IntValue RUBY_HARVEST_BONUS;
    public static final ModConfigSpec.BooleanValue LOG_EXTRA_DROPS;

    static {
        ModConfigSpec.Builder builder = new ModConfigSpec.Builder();

        builder.push("enchantment");
        RUBY_HARVEST_BONUS = builder
                .comment("红宝石收割每级额外掉落的数量")
                .translation("dafeiyu.config.ruby_harvest_bonus")
                .defineInRange("ruby_harvest_bonus", 1, 0, 8);
        builder.pop();

        LOG_EXTRA_DROPS = builder
                .comment("是否在日志里打印额外掉落")
                .define("log_extra_drops", false);

        SPEC = builder.build();
    }
}
```

在主类里注册：

```java
// src/main/java/com/dafeiyu/DafeiyuMod.java
container.registerConfig(ModConfig.Type.COMMON, DafeiyuConfig.SPEC);
```

三种类型怎么选：`STARTUP` 只在启动时读一次，不能用于影响注册内容；`CLIENT` 只在客户端；`COMMON` 两端都读但**不同步**；`SERVER` 会同步给客户端，适合「服务端说了算」的数值。像掉落数量这种影响游戏平衡的，用 `SERVER` 更合适。

读取时用 `.get()`：`int bonus = DafeiyuConfig.RUBY_HARVEST_BONUS.get();`。值会被缓存，不用担心频繁读文件。

## 五、游戏测试：把「应该发生的事」写成代码

每次改完都手动进游戏挖一次方块，很累，而且容易漏。游戏测试（GameTest）就是让游戏自己搭一个场景、自己执行、自己判断对错。

它的三个组成部分：

1. **一个结构模板**：场景的初始状态（哪些方块、哪些实体）。
2. **一个带 `@GameTest` 的方法**：要执行的逻辑。
3. **断言**：判断成功还是失败。

如果不想用结构方块手动存 `.nbt`，可以用 `@EmptyTemplate` 让框架生成一个空场景——这正是我们需要的。

### 5.1 最小测试：红宝石方块挖了掉红宝石

文件：`src/main/java/com/dafeiyu/gametest/RubyBlockGameTests.java`

```java
package com.dafeiyu.gametest;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.core.BlockPos;
import net.minecraft.gametest.framework.GameTest;
import net.minecraft.gametest.framework.GameTestHelper;
import net.neoforged.neoforge.gametest.GameTestHolder;
import net.neoforged.testframework.gametest.EmptyTemplate;

@GameTestHolder(DafeiyuMod.MOD_ID)
public class RubyBlockGameTests {

    @GameTest
    @EmptyTemplate
    public static void rubyBlockDropsRuby(GameTestHelper helper) {
        BlockPos pos = new BlockPos(0, 1, 0);

        // 1. 摆一个红宝石方块
        helper.setBlock(pos, ModBlocks.RUBY_BLOCK.get());

        // 2. 下一 tick 再挖，确保方块已经真的放下去了
        helper.runAfterDelay(1, () -> {
            // 第二个参数 true 才会走战利品表；helper.destroyBlock 默认不掉落
            helper.getLevel().destroyBlock(helper.absolutePos(pos), true);
        });

        // 3. 每个 tick 检查一次，直到超时；出现红宝石掉落物就通过
        helper.succeedWhen(() -> helper.assertItemEntityPresent(ModItems.RUBY.get(), pos, 2.0));
    }
}
```

几个关键点：

- **`@GameTestHolder(MOD_ID)`** 注册这个类里的所有测试。没有它，方法写得再对也不会被收集。
- **`@EmptyTemplate`** 生成一个空结构，省掉手动做 `.nbt`。如果你的 NeoForge 版本里没有这个注解，用结构方块存一个空结构，改成 `@GameTest(template = "空结构名")`。
- **相对坐标**：测试里的 `BlockPos` 都是相对于结构原点的，`helper.absolutePos()` 才转成世界坐标。直接拿相对坐标去 `level.destroyBlock` 会挖到别处。
- **`runAfterDelay(1, ...)`**：`setBlock` 之后立刻挖，有时方块还没真正落到世界里。隔一 tick 是最省事的保险。
- **`succeedWhen`** 会每 tick 执行一次传入的 `Runnable`，只要某次没抛异常就判定成功；直到 `timeoutTicks`（默认 100）都没成功就失败。

`GameTestHelper` 里常用的断言：

| 方法 | 断言什么 |
|---|---|
| `assertTrue(boolean, String)` / `assertFalse` | 布尔条件，第二个参数是失败提示 |
| `assertBlockPresent(Block, BlockPos)` | 某位置是这个方块 |
| `assertBlockState(BlockPos, Predicate<BlockState>)` | 方块状态满足条件 |
| `assertItemEntityPresent(Item, BlockPos, double)` | 半径内存在该物品的掉落物 |
| `assertItemEntityCountIs(Item, BlockPos, double, int)` | 掉落物**数量**正好是 N |
| `assertEntityPresent(EntityType, BlockPos, double)` | 半径内存在该实体 |
| `succeed()` / `succeedIf(Runnable)` / `succeedWhen(Runnable)` | 标记成功 |

### 5.2 怎么跑

游戏内：

```text
/test runall
/test run dafeiyu:rubyblockgametests.rubyblockdropsruby
```

注意测试名的组成：`命名空间:类名小写.方法名小写`。名字对不上会提示找不到测试。

命令行（适合 CI）：

```bash
./gradlew runGameTestServer
```

这个任务会起一个无头服务端，跑完所有测试后退出，**退出码等于失败的必要测试数量**。0 就是全过。

如果你的测试不在当前模组 id 下（比如放在一个单独的测试模组里），需要在运行配置里显式打开命名空间：

```groovy
// build.gradle 里 gameTestServer 运行配置
systemProperty 'neoforge.enabledGameTestNamespaces', 'dafeiyu'
```

多个命名空间用逗号分隔，**逗号后面不要加空格**，加了会导致那个命名空间加载不到。

## 六、常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 崩溃报告里全是原版帧，找不到自己的代码 | 你的代码只是「被调用者」，异常在别处抛出 | 搜 `Caused by` 的最后一条；或在自己方法入口加日志确认有没有进来 |
| 只在客户端复现，服务端正常 | 逻辑写在了客户端，或没判 `level.isClientSide` | 检查 `@EventBusSubscriber` 的 `value = Dist.CLIENT`；日志里看线程名是 `Render thread` 还是 `Server thread` |
| 日志刷屏，几秒钟几百 MB | 在每 tick 的方法里打了 `info` | 改成 `debug`；必须保留时加节流（每 100 tick 打一次） |
| `/data get` 看不到自己加的数据 | 数据写在服务端但你在客户端查，或组件根本没写进去 | 在服务端执行；先确认写入那一步的日志有没有打出来 |
| 测试永远通过，改了 bug 也通过 | 断言没真正执行，比如写在 `succeed()` 之后 | 断言必须在 `succeedWhen` 的 `Runnable` 里，或者在 `succeed()` 之前 |
| 测试永远失败，游戏里手动挖是正常的 | 测试里没走战利品表（`destroyBlock` 传了 `false`），或方块没有战利品表 | 传 `true`；确认 `data/dafeiyu/loot_table/blocks/ruby_block.json` 存在 |
| `runGameTestServer` 一直失败但游戏内 `/test runall` 全过 | 模板命名空间没开，测试根本没被收集 | 设置 `neoforge.enabledGameTestNamespaces` |
| 测试报「找不到结构」 | 用了 `@EmptyTemplate` 之外的方式，但 `.nbt` 路径不对 | 结构放 `data/<命名空间>/structure/`，注意是单数 |
| 调试分析器结果里没有你的方法 | 那段代码根本没被执行到，或者没加 `push/pop` | 确认场景能触发；自定义逻辑手动加小节 |
| `profiling.txt` 数据乱掉 | `push` 之后抛异常，`pop` 没执行 | 用 `try/finally` |

## 完整示例

```text
src/main/java/com/dafeiyu/DafeiyuConfig.java
src/main/java/com/dafeiyu/gametest/RubyBlockGameTests.java
build.gradle                                  # gameTestServer 命名空间（可选）
```

配套的前置条件：`ModBlocks.RUBY_BLOCK` 已注册、有战利品表、`ModItems.RUBY` 已注册。少任何一个，测试都会以「找不到掉落物」的形式失败——这其实是好事，说明测试真的在检查。

## 练习

1. **基础**：故意把 `DropRubyEffect` 里的 `count * enchantLevel` 改成 `count * (enchantLevel + 1)`，然后不修代码，先写出你预期会看到什么现象，再进游戏验证。
2. **进阶**：把 GameTest 里的 `assertItemEntityPresent` 换成 `assertItemEntityCountIs`，断言「挖一个方块正好掉 1 个红宝石」，然后故意把战利品表改成掉 2 个，看测试怎么报错。
3. **挑战**：给「红宝石收割」附魔写一个 GameTest：生成一只僵尸、给测试玩家一把带附魔的剑、杀死僵尸、断言掉落物数量等于 `count * 等级`。提示：需要 `helper.makeMockPlayer()` 和 `helper.spawnWithNoFreeWill(...)`。
