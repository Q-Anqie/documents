# 战利品表

> 读完这篇，你能写出「挖红宝石方块掉 1~3 颗红宝石、只有精准采集才掉方块本身」这种带条件带随机数的掉落表，也能一眼看出方块「挖了什么都不掉」是哪一环断了。

## 学习目标

- 能画出战利品表的三层结构：`pools` → `entries` → `functions` / `conditions`，并说清每一层能挂什么。
- 能说清 `rolls`、`weight`、`quality` 三个数字各控制什么。
- 能写出带随机数量、时运加成、精准采集分支的完整掉落表。
- 能用 `BlockLootSubProvider` 自动生成方块掉落，并解释 `getKnownBlocks` 是干什么的。
- 能定位「方块挖了不掉东西」的三类原因：没写表、没注册 provider、`noLootTable`。
- 能避开 `type` 路径、嵌套表字段名这两个高频错误。

## 一、战利品表在说什么

战利品表（loot table）是一份「掷骰子规则」：给它一个上下文（谁挖的、用什么挖的、在哪个位置），它返回一串物品堆。

游戏里几乎所有「随机给东西」的地方都用它：

| 场景 | 战利品表位置 |
|---|---|
| 方块被破坏 | `data/<ns>/loot_table/blocks/<方块名>.json` |
| 生物死亡 | `data/<ns>/loot_table/entities/<实体名>.json` |
| 箱子 | `data/<ns>/loot_table/chests/<名字>.json` |
| 钓鱼 | `data/<ns>/loot_table/gameplay/fishing.json` |

注意目录是 **`loot_table`（单数）**，和 `recipe` 一样是 1.21 的改动。

**方块的关键约定**：每个方块默认会去找一个 id 为 `<方块命名空间>:blocks/<方块注册名>` 的战利品表。你注册了 `dafeiyu:ruby_block`，游戏就会去读 `data/dafeiyu/loot_table/blocks/ruby_block.json`。这个「默认约定」是理解后面所有问题的钥匙——**你不需要在方块代码里指定掉落表，游戏按名字自己找**。

## 二、三层结构

一份战利品表长这样：

```text
战利品表 (LootTable)
└── pools[]                     池子，可以有多个，每个独立掷
    ├── rolls / bonus_rolls     这个池子掷几次
    ├── conditions[]            池子级条件，不满足则整个池子不掷
    ├── functions[]             池子级函数，作用在池子里每件产物上
    └── entries[]               条目，掷一次时从里面选一个
        ├── type                条目类型（item / loot_table / alternatives / group / sequence）
        ├── weight / quality    被选中的概率
        ├── conditions[]        条目级条件，不满足则视为不存在
        └── functions[]         条目级函数，改数量、改附魔、改名字
```

**为什么要分「池」？** 因为不同的掉落应该独立判定。比如「必掉 1 个红宝石」和「10% 概率掉一个红宝石核」是两件事，写在一个池里会互相干扰（掷一次只能选一个条目），写成两个池就各掷各的。

### 2.1 `rolls` / `weight` / `quality`

- `rolls`：这个池子掷几次。`1` 就是掷一次、产出一份；`3` 就是掷三次、可能产出三份。可以是数字，也可以是数值提供器（`{"type": "minecraft:uniform", "min": 1, "max": 3}`）。
- `bonus_rolls`：额外掷数，公式是 `rolls + bonus_rolls × 幸运值`。玩家的幸运属性（`player.getLuck()`）越高，额外掷得越多。绝大多数方块掉落写 `0`。
- `weight`：条目被选中的权重，默认 1。同一池里两个条目权重 3 和 1，就是 75% / 25%。
- `quality`：品质，默认 0。非零时会被乘上幸运值再加到权重上——「幸运越高，好东西越容易出」。原版几乎不用，方块掉落基本都写 0 或不写。

一句话记：**`rolls` 管「掷几次」，`weight` 管「这次选中谁」，`quality` 管「幸运值怎么影响选中概率」**。

## 三、五种常见条目类型

### 3.1 `minecraft:item`——掉一个物品

```json
{
  "type": "minecraft:item",
  "name": "dafeiyu:ruby"
}
```

`name` 是物品 id。注意这里是 `name` 不是 `id`——和配方结果里的 `id` 正好相反，这是抄错最多的地方。

### 3.2 `minecraft:loot_table`——嵌套另一张表

```json
{
  "type": "minecraft:loot_table",
  "value": "dafeiyu:blocks/ruby_block"
}
```

把另一张表的结果当成一个条目塞进来。用途：多个方块共享一套掉落规则，只写一份 JSON。

1.21 里这个字段叫 **`value`**（1.20 及以前叫 `name`）。写成 `name` 会报 `No key value in MapLike[...]`。

### 3.3 `minecraft:alternatives`——满足第一个就停

子条目按顺序试，**第一个条件通过的生效**，后面的全部丢弃。这是「精准采集 vs 普通挖掘」的标准写法：

```json
{
  "type": "minecraft:alternatives",
  "children": [
    {
      "type": "minecraft:item",
      "name": "dafeiyu:ruby_block",
      "conditions": [
        { "condition": "minecraft:match_tool", "predicate": { "items": "minecraft:diamond_pickaxe" } }
      ]
    },
    {
      "type": "minecraft:item",
      "name": "dafeiyu:ruby"
    }
  ]
}
```

（上面这段只是演示结构，真正的精准采集判定在第七节。）

### 3.4 `minecraft:group`——全部都要

子条目**依次全部运行**，互不影响。等价于「把这几样东西打包成一组」：

```json
{
  "type": "minecraft:group",
  "children": [
    { "type": "minecraft:item", "name": "dafeiyu:ruby" },
    { "type": "minecraft:item", "name": "minecraft:stick" }
  ]
}
```

### 3.5 `minecraft:sequence`——一个失败就全停

按顺序运行，**任何一个失败就中断**，后面的全部丢弃。适合「先掉主产物，主产物掉了才掉副产物」这种依赖关系。

三者对比：

| 类型 | 运行方式 | 什么时候停 |
|---|---|---|
| `alternatives` | 依次试 | 第一个**成功**后停 |
| `sequence` | 依次跑 | 第一个**失败**后停 |
| `group` | 依次跑 | 从不停，全跑完 |

## 四、常用函数

函数（function）挂在池子或条目上，**按数组顺序依次执行**，作用对象是产出的物品堆。

### 4.1 `set_count`——改数量

```json
{
  "function": "minecraft:set_count",
  "count": { "type": "minecraft:uniform", "min": 1, "max": 3 }
}
```

`add: true` 表示「在原数量上增加」而不是「设成这个值」，默认 false。`count` 可以是常量数字，也可以是 `uniform`（均匀随机）、`binomial`（二项分布）、`enchantment_level`（按附魔等级）等数值提供器。

### 4.2 `loot_table` 函数——把另一张表的结果塞进当前物品

这个和第三节的 `loot_table` **条目**不是一回事，别搞混：

- 条目 `minecraft:loot_table`：另掷一张表，结果作为**独立的掉落物**。
- 函数 `minecraft:loot_table`：另掷一张表，结果**替换当前物品堆**。

函数版在方块掉落里用得少，主要是箱子里「这一个格子的内容由另一张表决定」时用。

### 4.3 `apply_bonus`——按时运加成

```json
{
  "function": "minecraft:apply_bonus",
  "enchantment": "minecraft:fortune",
  "formula": "minecraft:ore_drops"
}
```

三种公式：

| `formula` | 效果 | 额外参数 |
|---|---|---|
| `minecraft:ore_drops` | 矿石专用：有概率翻倍，最常用的那个 | 无 |
| `minecraft:uniform_bonus_count` | 数量 += 附魔等级 × 倍率 | `bonusMultiplier` |
| `minecraft:binomial_with_bonus_count` | 二项分布加量 | `extra`、`probability` |

注意它依赖 `tool` 这个上下文参数——没有工具（比如爆炸破坏）时函数**什么都不做**，不会报错。

### 4.4 `furnace_smelt`——掉落时自动烧一遍

```json
{ "function": "minecraft:furnace_smelt" }
```

原版用于「烧死的动物掉熟肉」。它查一遍熔炉配方，能烧就换成烧好的产物，烧不了就原样返回。

**坑**：这个函数在社区里常被叫做 `smelt`，但 JSON 里的真实 id 是 `minecraft:furnace_smelt`。写 `"function": "minecraft:smelt"` 会报未知函数，整个表加载失败。

### 4.5 `enchant_randomly`——随机附魔

```json
{
  "function": "minecraft:enchant_randomly",
  "options": ["minecraft:sharpness", "minecraft:fire_aspect"],
  "only_compatible": true
}
```

`options` 省略时从全部附魔里挑；`only_compatible` 默认 true，表示只挑这个物品能附上的。想做「掉落一把随机附魔的剑」就靠它。

## 五、常用条件

条件（condition）挂在池子或条目上，**全部通过**才生效。

### 5.1 `survives_explosion`——爆炸衰减

```json
{ "condition": "minecraft:survives_explosion" }
```

爆炸破坏方块时，每件掉落物有 `1 / 爆炸半径` 的概率存活。原版几乎所有方块掉落都带这一条（信标、龙蛋等少数除外）。**没有 `explosion_radius` 参数时它总是成功**，所以放在普通挖掘的表里也无害。

### 5.2 `match_tool`——看玩家手里拿的什么

```json
{
  "condition": "minecraft:match_tool",
  "predicate": {
    "items": ["minecraft:iron_pickaxe", "minecraft:diamond_pickaxe"]
  }
}
```

`predicate` 是物品谓词（item predicate），可以写 `items`（物品 id 或数组）、`count`（数量范围）、`components`（数据组件）、`predicates`（子谓词，比如附魔）。

### 5.3 `random_chance`——按概率

```json
{ "condition": "minecraft:random_chance", "chance": 0.25 }
```

25% 概率通过。`chance` 是 0~1 之间的小数，注意不是百分数——写 `25` 等于 2500%，永远通过。

## 六、为什么「挖了不掉」：`BlockLootSubProvider` 与 `noLootTable`

方块挖了不掉东西，只有三种可能，按顺序排查：

### 6.1 情况一：根本没写表

你注册了方块，但 `data/dafeiyu/loot_table/blocks/xxx.json` 不存在。游戏找不到表，就掉空气。

**这是最常见的**。用 datagen 时，如果你忘了在 `generate()` 里 `add(...)` 或 `dropSelf(...)`，生成出来的目录里就没有这个文件。

### 6.2 情况二：写了表，但没注册 provider

datagen 的结构是这样的：

```java
public class ModLootTableProvider extends LootTableProvider {
    public ModLootTableProvider(PackOutput output, CompletableFuture<HolderLookup.Provider> registries) {
        super(output,
                Set.of(),                       // 需要校验「必须存在」的表，模组一般不校验
                List.of(new SubProviderEntry(ModBlockLootProvider::new, LootContextParamSets.BLOCK)),
                registries);
    }
}
```

`SubProviderEntry` 的第二个参数是**战利品参数集**（loot parameter set），它声明「这张表能用哪些上下文参数」。方块表用 `LootContextParamSets.BLOCK`，实体表用 `ENTITY`，不确定就用 `EMPTY`。

最后一个参数 `registries` 别漏：1.21 的战利品表会引用附魔这类「数据包注册表」里的对象，所以必须把注册表查询器传进去。少了它，编译就过不去。

如果这个 provider 没注册到 `GatherDataEvent`，或者注册了但 `event.includeServer()` 传成了 false，文件根本不会被生成。

### 6.3 情况三：方块自己声明了「我没有掉落表」

```java
public static final DeferredBlock<Block> RUBY_BLOCK = BLOCKS.register("ruby_block",
        () -> new Block(BlockBehaviour.Properties.of()
                .noLootTable()          // 明确告诉游戏：这个方块没有战利品表
                .strength(3.0f)));
```

`noLootTable()` 用于空气、屏障、命令方块这类「本来就不该掉东西」的方块。你在复制别人的方块代码时，如果顺手把这一行也复制过来了，就会得到「挖了什么都不掉、连报错都没有」的诡异现象。

### 6.4 `getKnownBlocks` 是干什么的

```java
@Override
protected Iterable<Block> getKnownBlocks() {
    return ModBlocks.BLOCKS.getEntries().stream()
            .map(holder -> (Block) holder.value())
            .toList();
}
```

`BlockLootSubProvider` 会用这个返回值做**完整性校验**：你注册的每个方块，都必须在这份列表里、并且最终有一张表。它不参与生成，只负责「你漏了谁就报给你听」。

所以这个方法返回 `ModBlocks.BLOCKS` 的全部内容是对的。**不要**为了「消除报错」把它改成 `List.of()`——那样校验就形同虚设，漏掉的方块会安静地不掉落。

## 七、完整示例：红宝石方块掉 1~3 个，精准采集掉方块

需求：普通挖掘掉 1~3 颗红宝石（带时运加成、带爆炸衰减），精准采集时掉方块本身。

### 7.1 手写 JSON 版

文件：`src/main/resources/data/dafeiyu/loot_table/blocks/ruby_block.json`

```json
{
  "type": "minecraft:block",
  "random_sequence": "dafeiyu:blocks/ruby_block",
  "pools": [
    {
      "rolls": 1,
      "bonus_rolls": 0,
      "entries": [
        {
          "type": "minecraft:alternatives",
          "children": [
            {
              "type": "minecraft:item",
              "name": "dafeiyu:ruby_block",
              "conditions": [
                {
                  "condition": "minecraft:match_tool",
                  "predicate": {
                    "predicates": {
                      "minecraft:enchantments": [
                        {
                          "enchantments": "minecraft:silk_touch",
                          "levels": { "min": 1 }
                        }
                      ]
                    }
                  }
                }
              ]
            },
            {
              "type": "minecraft:item",
              "name": "dafeiyu:ruby",
              "functions": [
                {
                  "function": "minecraft:set_count",
                  "count": { "type": "minecraft:uniform", "min": 1, "max": 3 }
                },
                {
                  "function": "minecraft:apply_bonus",
                  "enchantment": "minecraft:fortune",
                  "formula": "minecraft:ore_drops"
                },
                {
                  "function": "minecraft:explosion_decay"
                }
              ]
            }
          ]
        }
      ]
    }
  ]
}
```

几处细节：

- 最外层 `"type": "minecraft:block"` 是**参数集**，不是条目类型。它声明「这张表在方块被破坏的上下文里使用」，写错成 `minecraft:item` 会得到参数校验失败。
- `random_sequence`：让同一个种子下的掷表结果可复现。原版方块表都写，建议照抄成表自己的 id。
- `explosion_decay` 是函数版的爆炸衰减（逐件判定），`survives_explosion` 是条件版（整池判定）。方块掉落用函数版更精细。
- 精准采集的判断写在 `alternatives` 的**第一个**子条目上。顺序反了的话，永远只会走第一个分支。

### 7.2 数据生成版（推荐）

文件：`src/main/java/com/dafeiyu/datagen/ModBlockLootProvider.java`

如果你跟着 [数据生成](05-数据生成.md) 已经建过这个类，不用重写，只把 `generate()` 里的内容换成下面这段就行。

```java
package com.dafeiyu.datagen;

import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.loot.BlockLootSubProvider;
import net.minecraft.world.flag.FeatureFlags;
import net.minecraft.world.level.block.Block;
import net.minecraft.world.level.storage.loot.entries.LootItem;
import net.minecraft.world.level.storage.loot.functions.SetItemCountFunction;
import net.minecraft.world.level.storage.loot.predicates.ExplosionCondition;
import net.minecraft.world.level.storage.loot.providers.number.UniformGenerator;

import java.util.Set;

public class ModBlockLootProvider extends BlockLootSubProvider {

    public ModBlockLootProvider(HolderLookup.Provider registries) {
        // 参数一：抗爆方块集合（模组一般不填）；参数二：特性开关；参数三：注册表查询
        super(Set.of(), FeatureFlags.DEFAULT_FLAGS, registries);
    }

    @Override
    protected Iterable<Block> getKnownBlocks() {
        return ModBlocks.BLOCKS.getEntries().stream()
                .map(holder -> (Block) holder.value())
                .toList();
    }

    @Override
    protected void generate() {
        // 普通方块只需要一行：挖了掉自己
        // （这里注释掉是因为红宝石方块要走下面的自定义规则，同一个方块不能 add 两次）
        // dropSelf(ModBlocks.RUBY_LAMP.get());

        // 特殊方块：精准采集掉方块，否则掉 1~3 颗红宝石
        add(ModBlocks.RUBY_BLOCK.get(), createSilkTouchDispatchTable(
                ModBlocks.RUBY_BLOCK.get(),
                LootItem.lootTableItem(ModItems.RUBY.get())
                        .apply(SetItemCountFunction.setCount(UniformGenerator.between(1.0F, 3.0F)))
                        .when(ExplosionCondition.survivesExplosion())
        ));
    }
}
```

`createSilkTouchDispatchTable(方块, 普通掉落)` 这一个方法就把整棵 `alternatives` 树搭好了：它自动生成「精准采集 → 掉方块」和「否则 → 用你传进来的 builder」两个分支。这就是为什么 datagen 比手写可靠——结构性的东西由方法保证，你只填内容。

`UniformGenerator` 在 `net.minecraft.world.level.storage.loot.providers.number` 包里。IDE 自动导入时注意别选到 `util.valueproviders` 下那些整数提供器——它们实现的是 `IntProvider`，不是战利品表要的 `NumberProvider`，传进去编译不过。

常用的辅助方法还有：

| 方法 | 生成什么 |
|---|---|
| `dropSelf(block)` | 掉方块自己，1 个 |
| `createSingleItemTable(item)` | 掉指定物品 1 个 |
| `createSingleItemTable(item, count)` | 掉指定物品 n 个 |
| `createSilkTouchOnlyTable(block)` | **只有**精准采集才掉，普通挖掘什么都不掉 |
| `createOreDrop(block, item)` | 矿石标准掉落：精准采集掉方块，否则掉物品 + 时运 + 爆炸衰减 |
| `createSlabItemTable(block)` | 台阶专用：按 `type` 属性掉 1 个或 2 个 |

注册 provider：

文件：`src/main/java/com/dafeiyu/datagen/ModLootTableProvider.java`

```java
package com.dafeiyu.datagen;

import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.loot.LootTableProvider;
import net.minecraft.world.level.storage.loot.parameters.LootContextParamSets;

import java.util.List;
import java.util.Set;
import java.util.concurrent.CompletableFuture;

public class ModLootTableProvider extends LootTableProvider {

    public ModLootTableProvider(PackOutput output, CompletableFuture<HolderLookup.Provider> registries) {
        super(output, Set.of(),
                List.of(new SubProviderEntry(ModBlockLootProvider::new, LootContextParamSets.BLOCK)),
                registries);
    }
}
```

再在 `DataGenerators#gatherData` 里加一行：

```java
event.getGenerator().addProvider(
        event.includeServer(),
        new ModLootTableProvider(event.getGenerator().getPackOutput(), event.getLookupProvider())
);
```

## 完整示例

```text
src/main/java/com/dafeiyu/datagen/
├── DataGenerators.java          ← 注册所有 provider
├── ModBlockLootProvider.java      ← 7.2 节
└── ModLootTableProvider.java    ← 7.2 节

src/generated/resources/data/dafeiyu/loot_table/blocks/
└── ruby_block.json              ← runData 自动生成
```

跑 `./gradlew runData` 后，打开生成的 `ruby_block.json`，你应该能看到一棵 `alternatives` 树，第一个分支带 `match_tool` + 附魔子谓词，第二个分支带 `set_count` + `survives_explosion`。**对照它读一遍，比读十遍文档管用**——datagen 写出来的 JSON 就是官方认可的写法。

验证：

1. `give @s dafeiyu:ruby_block`，放下来用铁镐挖 → 掉 1~3 颗红宝石。
2. 用带精准采集的镐挖 → 掉方块本身。
3. 附时运 III 挖 → 数量明显变多。
4. 用 TNT 炸 → 有概率什么都不掉。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 方块挖了什么都不掉，也不报错 | 表文件不存在 | 检查 `data/dafeiyu/loot_table/blocks/<方块名>.json` 是否生成 |
| 同上，且方块代码里有 `noLootTable()` | 复制别人代码时带过来的 | 删掉那一行 |
| 启动报 `Unknown loot entry type 'minecraft:item'` 且路径不对 | 把条目类型和参数集搞混 | 条目写 `"type": "minecraft:item"` + `"name": "..."`；表头 `"type"` 写 `minecraft:block` |
| 报 `No key value in MapLike` | 嵌套表条目用了旧的 `name` 字段 | 1.21 改成 `"value": "dafeiyu:blocks/xxx"` |
| 报 `Unknown loot function 'minecraft:smelt'` | 函数 id 记错 | 用 `minecraft:furnace_smelt` |
| 掉落表 ID 和方块对不上 | 方块注册名是 `ruby_block`，表却叫 `rubyblock.json` | 表文件名必须和注册名逐字一致 |
| `Missing loot table for block dafeiyu:xxx` | `getKnownBlocks` 里有它，但 `generate()` 里没 add | 补 `dropSelf(...)` 或 `add(...)` |
| 精准采集也掉红宝石，不掉方块 | `alternatives` 两个分支顺序反了 | 精准采集分支必须放第一个 |
| 掉落数量永远是 1 | `set_count` 写在池子级而不是条目级，被后面的条目覆盖 | 数量函数挂在条目上 |

## 练习

1. **照抄验证**：把第七节的 JSON 手写一遍放进 `src/main/resources`，用铁镐和精准采集镐各挖一次，确认行为符合预期。
2. **加副产物**：给红宝石方块加「10% 概率额外掉一颗红宝石核」，要求用 `random_chance` 条件实现，并解释为什么必须新开一个池子而不是塞进原来的 `alternatives`。
3. **矿石标准掉落**：新建 `dafeiyu:ruby_ore` 方块，用 `createOreDrop` 生成掉落，再把生成的 JSON 和第七节手写的对比，列出 datagen 多写了什么、少写了什么。
4. **挖掉不掉**：故意给某个方块加上 `noLootTable()`，观察游戏日志有没有任何提示，然后写下你是怎么定位到这一行的。
