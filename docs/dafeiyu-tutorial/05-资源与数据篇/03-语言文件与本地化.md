# 语言文件与本地化

> 读完这篇，你的模组里不会再出现 `item.dafeiyu.ruby` 这种原始 key，也不会再出现「中文变成一堆问号」的乱码，还能写出带数字、带颜色、带悬浮提示的文本。

## 学习目标

- 能默写出 `item.` `block.` `itemGroup.` `effect.` `container.` 这几类键名规则。
- 能说清 `Component.translatable` 和 `Component.literal` 的区别，知道什么时候必须用哪个。
- 能写出带参数的翻译（`%s`），并正确传参。
- 能给物品加自定义 tooltip，并且只在「高级提示信息」开启时显示额外内容。
- 能诊断并修好中文乱码，知道为什么必须是 UTF-8 无 BOM。

## 一、语言文件在哪、长什么样

语言文件是 `assets/<modid>/lang/<语言代码>.json`，内容是一个「键 → 文本」的扁平 JSON：

文件：`src/main/resources/assets/dafeiyu/lang/zh_cn.json`

```json
{
  "item.dafeiyu.ruby": "红宝石",
  "block.dafeiyu.ruby_block": "红宝石块"
}
```

就这么简单。没有嵌套，没有数组，就是一个大对象。

语言代码用**小写下划线**格式：`en_us`、`zh_cn`、`zh_tw`、`ja_jp`、`de_de`、`fr_fr`、`ru_ru`、`ko_kr`。注意全是小写——写成 `zh_CN` 游戏不认，而且**不会报错**，只是中文永远显示英文。

最少要写两个文件：

| 文件 | 作用 |
|---|---|
| `en_us.json` | 美国英语。**所有语言的最终回退目标** |
| `zh_cn.json` | 简体中文。你的主要受众 |

为什么 `en_us` 不能省？因为 Minecraft 的回退链是：**当前语言 → `en_us` → 原始键名**。玩家把语言切成日语，你没写 `ja_jp.json`，游戏会去 `en_us` 里找；`en_us` 也没有，就直接把 `item.dafeiyu.ruby` 这串东西显示出来。

所以只写 `zh_cn` 的后果是：**中文玩家正常，其他所有语言的玩家看到一串英文 key**。这在单机自己玩的时候完全没感觉，一发布就变成 issue 区第一条。

## 二、键名规则

键名的通用格式是 `类别.命名空间.路径`。**类别决定了游戏去哪里找这个键**，写错类别 = 找不到 = 显示原始 key。

| 类别 | 格式 | 用在哪 | 例子 |
|---|---|---|---|
| `item` | `item.<ns>.<path>` | 普通物品 | `item.dafeiyu.ruby` |
| `block` | `block.<ns>.<path>` | 方块，**以及方块物品** | `block.dafeiyu.ruby_block` |
| `itemGroup` | `itemGroup.<ns>.<path>` | 创造模式物品栏标签页 | `itemGroup.dafeiyu.main` |
| `effect` | `effect.<ns>.<path>` | 状态效果 | `effect.dafeiyu.ruby_glow` |
| `container` | `container.<ns>.<path>` | 容器/菜单的标题 | `container.dafeiyu.ruby_chest` |
| `entity` | `entity.<ns>.<path>` | 实体 | `entity.dafeiyu.ruby_golem` |
| `enchantment` | `enchantment.<ns>.<path>` | 附魔 | `enchantment.dafeiyu.sharpness_ruby` |
| `subtitles` | `subtitles.<ns>.<path>` | 声音字幕（无障碍） | `subtitles.dafeiyu.ruby_chime` |
| `tooltip` | `tooltip.<ns>.<path>` | 自定义提示（自由命名） | `tooltip.dafeiyu.ruby.desc` |
| `gui` | `gui.<ns>.<path>` | 自定义界面文字 | `gui.dafeiyu.ruby_chest.title` |
| `config` | `config.<ns>.<path>` | 配置项（NeoForge 约定） | `config.dafeiyu.enable_lamp` |
| `fml.menu.mods.info.description` | `fml.menu.mods.info.description.<modid>` | 模组列表里的描述 | `fml.menu.mods.info.description.dafeiyu` |

### 为什么方块物品用 `block.` 而不是 `item.`

这是新手 100% 会踩的一脚。

`ruby_block` 在游戏里其实是两个东西：世界里的 `Block`，和物品栏里的 `BlockItem`。`BlockItem` 重写了 `getDescriptionId()`，让它返回**所关联方块的**翻译键，也就是 `block.dafeiyu.ruby_block`。

所以你给方块物品写 `item.dafeiyu.ruby_block` 是**永远不会被读到**的——那个键存在，但没人查它。表现就是名字显示成 `block.dafeiyu.ruby_block`。

判断口诀：**只要这个东西能放在地上变成一个方块，就用 `block.`。**

### 创造模式标签页

```json
{
  "itemGroup.dafeiyu.main": "大肥鱼模组"
}
```

注意 `itemGroup` 是**驼峰**，不是 `item_group`、不是 `itemgroup`。这是原版少数几个不用下划线的地方，写错了标签页名字就是空的（注意不是显示 key，是显示成空白，更难查）。

## 三、`Component.translatable` 与 `Component.literal`

Minecraft 里所有给玩家看的文本都是 `Component`（旧称 `ITextComponent`）。它有两个最常用的工厂方法：

```java
// 直接显示这串字，不查语言文件
Component.literal("Hello");

// 把这串字当成翻译键，运行时去语言文件里查
Component.translatable("item.dafeiyu.ruby");
```

区别就一句话：**`literal` 是「就是这串字」，`translatable` 是「这是个键，去查表」。**

| | `literal` | `translatable` |
|---|---|---|
| 参数含义 | 最终显示内容 | 翻译键 |
| 是否随语言变化 | 否 | 是 |
| 适合 | 调试信息、玩家输入的内容、纯符号（`":"`、`"["`） | 一切固定文案 |

**判断标准：这段文字是给玩家看的固定文案吗？是 → `translatable`。是玩家自己输入/拼接的数据吗？是 → `literal`。**

举个必须用 `literal` 的例子：玩家给物品改了个名字，你要把它显示出来。这个名字是数据，不是键，用 `translatable` 会去查一个不存在的键，直接显示成一串乱码。

### 为什么服务端绝对不能翻译

`Component` 的解析是**惰性**的。你构造一个 `translatable` 组件时，它里面存的是「键 + 参数」，不是最终文本。真正查表发生在**客户端渲染的那一刻**，用的是**那个客户端自己的语言设置**。

这条特性带来一个铁律：

> **永远不要在服务端调用 `component.getString()`。**

如果你在服务端把组件解析成字符串再发给客户端，那么所有玩家看到的都是**服务器进程的语言**（通常是英文），中文玩家的客户端再也没机会翻译了。正确做法是把 `Component` 本身通过网络发过去，让每个客户端各自解析。

这也是为什么 `player.sendSystemMessage(Component.translatable("..."))` 是对的，而 `player.sendSystemMessage(Component.literal(Component.translatable("...").getString()))` 是错的——后者在服务端就把文本烧死了。

### 常用样式

```java
Component.translatable("tooltip.dafeiyu.ruby.desc")
        .withStyle(ChatFormatting.GRAY);

Component.translatable("gui.dafeiyu.warning")
        .withStyle(Style.EMPTY.withColor(0xFF5555).withBold(true));
```

`ChatFormatting` 是预设颜色/格式的枚举（`RED`、`GOLD`、`GRAY`、`BOLD`、`ITALIC`、`UNDERLINE`…）。要精确控制颜色就用 `Style.EMPTY.withColor(0xRRGGBB)`。

`withStyle` 返回的还是 `MutableComponent`，可以链式调。`Style` 本身是不可变的，每次 `withXxx` 都产生一个新对象，所以可以预先建好一个常量反复用。

## 四、带参数的翻译

翻译文本里可以留占位符，运行时填进去：

文件：`src/main/resources/assets/dafeiyu/lang/zh_cn.json`

```json
{
  "tooltip.dafeiyu.ruby.count": "你持有 %s 颗红宝石",
  "tooltip.dafeiyu.ruby.range": "挖掘等级：%s ~ %s",
  "message.dafeiyu.welcome": "欢迎，%s！你有 %s 颗红宝石。"
}
```

文件：`src/main/resources/assets/dafeiyu/lang/en_us.json`

```json
{
  "tooltip.dafeiyu.ruby.count": "You have %s rubies",
  "tooltip.dafeiyu.ruby.range": "Mining tier: %s ~ %s",
  "message.dafeiyu.welcome": "Welcome, %s! You have %s rubies."
}
```

代码里：

```java
// 一个参数
Component.translatable("tooltip.dafeiyu.ruby.count", stack.getCount());

// 两个参数，按顺序填
Component.translatable("tooltip.dafeiyu.ruby.range", 1, 5);

// 参数可以是 Component，也可以是任意对象（会调 toString）
Component.translatable("message.dafeiyu.welcome",
        player.getDisplayName(),
        stack.getCount());
```

三个必须知道的细节：

1. **只用 `%s`，不用 `%d` `%f` `%i`。** Minecraft 内部用的是 `String.format` 的变体，但它把所有格式符都归一成 `%s` 处理。你写 `%d` 传一个 `int` 通常也能跑，但传 `long` 或 `null` 就会抛异常。统一用 `%s`，永远不会错。
2. **参数的顺序在不同语言里可以不同。** 中文「你有 %s 颗红宝石」和英文「You have %s rubies」位置一样，但换成日语可能要把数量放前面。这就是为什么不能直接把数字拼进字符串——分开存，翻译者才能调整语序。
3. **`%%` 是转义的字面百分号。** 要显示「50%」就写 `"50%%"`。

如果参数本身是个 `Component`（比如玩家的名字带颜色），直接传进去就行，它会被当成组件渲染，样式也会保留。

## 五、给物品加提示文本（tooltip）

`Item` 有一个专门的方法管这个：`appendHoverText`。

文件：`src/main/java/com/dafeiyu/item/RubyItem.java`

```java
package com.dafeiyu.item;

import net.minecraft.ChatFormatting;
import net.minecraft.network.chat.Component;
import net.minecraft.world.item.Item;
import net.minecraft.world.item.ItemStack;
import net.minecraft.world.item.TooltipFlag;

import java.util.List;

public class RubyItem extends Item {
    public RubyItem(Properties properties) {
        super(properties);
    }

    @Override
    public void appendHoverText(ItemStack stack, TooltipContext context,
                                List<Component> tooltip, TooltipFlag flag) {
        // 第一行：永远显示，灰色
        tooltip.add(Component.translatable("tooltip.dafeiyu.ruby.desc")
                .withStyle(ChatFormatting.GRAY));

        // 第二行：只有按住 Shift 或开了高级提示才显示
        if (flag.isAdvanced()) {
            tooltip.add(Component.translatable("tooltip.dafeiyu.ruby.id",
                            stack.getItem().builtInRegistryHolder().key().location().toString())
                    .withStyle(ChatFormatting.DARK_GRAY));
        }
    }
}
```

要点：

- **`tooltip.add(...)` 是往列表里追加，不是覆盖。** 物品原本的名字、附魔、耐久都在这之前已经加好了，你加的在最下面。
- `flag.isAdvanced()` 对应 F3+H 打开的那个「高级提示信息」。想让内容默认隐藏、需要 Shift 才显示，判断 `Screen.hasShiftDown()`（这个类只在客户端有，所以要包在 `if (FMLEnvironment.dist.isClient())` 里，或者干脆用 `isAdvanced()` 更省事）。
- `TooltipContext` 是 1.20.5 之后加的参数，能拿到 `registryAccess()`，需要查注册表时用它。
- **不要在 `appendHoverText` 里做重活**（读文件、发网络包）。这个方法在鼠标划过物品时每帧都可能被调用。

对应的语言条目：

```json
{
  "tooltip.dafeiyu.ruby.desc": "一块蕴含魔力的红色晶体",
  "tooltip.dafeiyu.ruby.id": "注册名：%s"
}
```

## 六、中文乱码：为什么，怎么办

这是本篇最"物理"的一节，但它是真实存在的高频问题。

### 成因

Minecraft 用 **UTF-8** 读取语言文件。如果你的文件实际存成了别的编码，中文就会变成乱码。常见三种：

| 你看到的 | 文件实际编码 | 原因 |
|---|---|---|
| `çº¢å®ç³` | UTF-8 被当成 ISO-8859-1 读 | 编辑器保存时用了错误编码，或用了非 UTF-8 工具 |
| `绾㈠疂鐭` | GBK 被当成 UTF-8 读 | 用 Windows 记事本存成了「ANSI」（中文系统下就是 GBK） |
| `???` 或方块 | 编码转换时字符丢失 | 从别的程序复制粘贴时已经损坏，无法恢复 |
| 第一行失效，后面正常 | UTF-8 **带 BOM** | 文件开头有 `EF BB BF` 三个字节 |

### BOM 这一种特别阴

UTF-8 BOM 是文件开头的三个字节 `EF BB BF`。它不是内容，是「我声明这是 UTF-8」的标记。Java 的 `InputStreamReader` 用 UTF-8 解码时**不会**吃掉它，于是你的第一个键就变成了：

```text
\uFEFFitem.dafeiyu.ruby
```

这个键和游戏查的 `item.dafeiyu.ruby` 差了看不见的一个字符，永远匹配不上。**表现就是：语言文件里第一个条目失效，其他全部正常。** 很多人查了半天以为是键名写错，其实是 BOM。

### 解决

**第一步：确认编码。** 用 VS Code 打开文件，右下角会显示当前编码（`UTF-8` / `UTF-8 with BOM` / `GBK`）。

**第二步：转换。** VS Code 里点右下角编码 → `Save with Encoding` → 选 `UTF-8`（**不是** `UTF-8 with BOM`）。

**第三步：验证。** 用命令行确认没有 BOM：

```bash
# 看前三个字节，应该是 7b（也就是 "{"），不是 efbbbf
head -c 3 src/main/resources/assets/dafeiyu/lang/zh_cn.json | xxd
```

正常输出：

```text
00000000: 7b0a 2020                                {.
```

有 BOM 的输出：

```text
00000000: efbb bf7b 0a20                           ...{.
```

看到 `efbbbf` 就说明有 BOM。

### 预防

- 项目根目录放一个 `.editorconfig`，锁死编码：

文件：`.editorconfig`

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
indent_style = space
indent_size = 4

[*.json]
indent_size = 2
```

- IntelliJ IDEA 里检查 `Settings → Editor → File Encodings`，三个下拉全设成 `UTF-8`，并把 `Transparent native-to-ascii conversion` **关掉**（开了会把中文转成 `\uXXXX`，虽然能用，但 diff 里完全看不出改了什么）。
- **别用 Windows 记事本编辑 json。** 它的默认编码行为随版本变化，是乱码的头号来源。

> 补充一句：`\u7ea2\u5b9d\u77f3` 这种转义写法是**合法**的，Java 的 JSON 解析器会正确还原成「红宝石」。它不是乱码，只是不可读。有些构建工具会自动转义，遇到别慌。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 名字显示 `item.dafeiyu.ruby` | 键名拼错，或没写这个键 | 逐字符比对注册名 |
| 方块物品显示 `block.dafeiyu.ruby_block` | 你只写了 `item.dafeiyu.ruby_block` | 方块物品用 `block.` 前缀 |
| 创造标签页名字空白 | 写成 `item_group` / `itemgroup` | 必须是 `itemGroup` |
| 中文正常，英文玩家看到 key | 只写了 `zh_cn.json` | 补 `en_us.json` |
| 语言文件第一个条目失效，其他正常 | 文件带 UTF-8 BOM | 另存为 UTF-8 无 BOM |
| 中文显示成 `çº¢å®ç³` | 编码不匹配 | 统一转成 UTF-8 |
| 中文显示成 `???` | 编码转换时已丢字符，不可逆 | 重新输入 |
| 中文玩家看到英文 | 语言文件名写成 `zh_CN.json` | 全小写 `zh_cn.json` |
| tooltip 不显示 | 覆盖的方法签名不对（参数类型写错） | 1.21.1 是 `appendHoverText(ItemStack, TooltipContext, List<Component>, TooltipFlag)` |
| tooltip 里 `%s` 原样显示 | 忘了传参数 | `Component.translatable(key, arg)` |
| `%d` 抛 `IllegalFormatConversionException` | 用了 `%d` 传了不匹配的类型 | 一律用 `%s` |
| 服务器上所有玩家看到英文 | 你在服务端调了 `.getString()` | 把 `Component` 原样发出去 |
| 改了语言文件，`F3+T` 没变化 | 语言文件有时需要重进世界 | 重进世界或重启客户端 |

## 练习

1. **基础**：给 `ruby_sword` 补上中英双语的 `item.dafeiyu.ruby_sword`，然后把语言切到英文确认生效。
2. **进阶**：给红宝石加一行 tooltip，显示「挖掘等级：1 ~ 5」，用两个 `%s` 占位符。再故意把中文里的两个 `%s` 调换顺序，观察显示结果——理解为什么占位符顺序由翻译者决定。
3. **挑战**：写一个 `/dafeiyu hello` 命令，向执行者发送 `Component.translatable("message.dafeiyu.welcome", player.getDisplayName())`，然后在专用服务器（`runServer`）上让两个不同语言的客户端各连一次，确认两人看到的语言不同。这一步做完，你就彻底理解「翻译发生在客户端」了。
