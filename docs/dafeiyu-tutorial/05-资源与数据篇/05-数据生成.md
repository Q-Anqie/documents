# 数据生成

> 读完这篇，你能用代码批量生成模型、方块状态、语言文件、配方、战利品表和标签，从此不再手写几十个几乎一模一样的 json。

## 学习目标

- 能说清 datagen 解决的是「重复劳动」而不是「功能缺失」。
- 能写出 `GatherDataEvent` 处理器，并正确使用 `includeClient()` / `includeServer()`。
- 能用 `BlockStateProvider`、`ItemModelProvider`、`LanguageProvider` 生成全套显示资源。
- 能用 `RecipeProvider`、`BlockLootSubProvider`、`BlockTagsProvider` 生成服务端数据。
- 能跑 `gradlew runData`，知道产物在哪，并让它们自动进 jar。

## 一、datagen 解决什么问题

先算一笔账。假设你的模组有 40 个方块。每个方块需要：

```text
blockstates/<name>.json          1 个
models/block/<name>.json         1 个
models/item/<name>.json          1 个
loot_table/blocks/<name>.json    1 个
lang 里 1 条（×2 种语言）        2 条
```

也就是 **160 个文件 + 80 条翻译**。这些文件的内容 95% 是重复的：`cube_all` 换成纹理名、战利品表换个方块名、语言换个中英对照。

手写的问题不只是慢：

- **错一个字就静默失效。** `"all"` 写成 `"alls"`，游戏不报错，只是紫黑。
- **改一个决策要改 40 处。** 你决定所有方块都改用 `cube_bottom_top`，手写得改 40 个文件。
- **容易漏。** 加了第 41 个方块，忘了写战利品表，挖了不掉东西，而你要等到玩到那一步才发现。

数据生成（data generation，简称 datagen）就是把「写 json」变成「写 Java 代码调用生成器」。你写：

```java
simpleBlockWithItem(ModBlocks.RUBY_BLOCK.get(), models().cubeAll("ruby_block", modLoc("block/ruby_block")));
```

它替你吐出三个文件。

**关键认知：datagen 不改变游戏怎么读资源。** 它只是「用程序写 json 的工具」。生成出来的文件和你手写的一模一样，游戏完全不知道区别。所以：

- datagen **不能**生成纹理 PNG（图片得你自己画）。
- datagen **不能**生成 `.ogg` 音频。
- datagen 生成的东西**必须真的落盘**，才会被游戏读到。

## 二、三个核心概念

### `DataGenerator`：总调度

它管着「这次要生成哪些东西」。你通过 `#addProvider` 往里塞提供器（provider），它挨个跑，每个 provider 往磁盘写自己的那部分。

### `GatherDataEvent`：入口

datagen 是一个**独立的运行配置**（run config），不是游戏。它的流程是：

```text
启动 JVM
  → 走正常的模组加载流程（注册物品、方块……都会跑）
  → 注册事件全部触发完毕
  → 触发 GatherDataEvent
  → 你的处理器在这里注册 provider
  → 所有 provider 执行完毕，写文件
  → 进程退出
```

所以 `GatherDataEvent` 里能安全地 `.get()` 任何 `DeferredHolder`——因为注册早就完成了。

**注意 datagen 不是游戏**：它不加载世界、不渲染、不联网。所以你的 provider 里不能依赖任何运行时状态。

### `PackOutput`：输出路径

它决定文件往哪写。默认是项目根目录下的 `src/generated/resources`。所有 provider 的构造函数都要它。

### 事件给你的五个东西

```java
@SubscribeEvent
public static void gatherData(GatherDataEvent event) {
    DataGenerator generator = event.getGenerator();                       // 用来加 provider
    PackOutput output = event.getPackOutput();                            // 输出路径
    ExistingFileHelper existingFileHelper = event.getExistingFileHelper(); // 校验父模型是否存在
    CompletableFuture<HolderLookup.Provider> lookupProvider = event.getLookupProvider(); // 查注册表
    // 还有 event.includeClient() / includeServer() / includeDev() / includeReports()
}
```

`ExistingFileHelper` 值得单独说一句：`BlockStateProvider` 生成模型时会检查 `parent` 指向的文件**是否真的存在**。它靠 `ExistingFileHelper` 去 `src/main/resources` 和原版 jar 里找。找不到就抛异常——这是好事，能提前发现「我引用了不存在的父模型」。

### `includeClient()` 与 `includeServer()`

这两个方法返回 `boolean`，表示「这次运行要不要生成这一类」。

```java
generator.addProvider(event.includeClient(), new ModBlockStateProvider(output, existingFileHelper));
generator.addProvider(event.includeServer(), new ModRecipeProvider(output, lookupProvider));
```

第一个参数是 `boolean`，**为 `false` 时这个 provider 会被完全跳过**。

为什么要分？因为客户端资源和数据是两套东西，可以分开生成：

| 命令行参数 | `includeClient()` | `includeServer()` |
|---|---|---|
| （默认，什么都不加） | false | false |
| `--includeClient` | true | false |
| `--includeServer` | false | true |
| `--all` | true | true |

`gradlew runData` 默认会带 `--mod dafeiyu --output ... --includeClient --includeServer`，所以两类都会生成。但如果你的 `build.gradle` 自己配了参数却漏了 `--includeClient`，你会发现「模型一个都没生成，配方倒是有」——就是这里。

**判断该传哪个：**

| Provider | 传什么 |
|---|---|
| `BlockStateProvider`、`ItemModelProvider`、`LanguageProvider`、`SoundDefinitionsProvider`、`ParticleDescriptionProvider` | `includeClient()` |
| `RecipeProvider`、`LootTableProvider`、`TagsProvider`、`AdvancementProvider`、`DataMapProvider` | `includeServer()` |

## 三、模型：`BlockStateProvider` 与 `ItemModelProvider`

### `BlockStateProvider`：方块状态 + 方块模型 + 方块物品模型

它一个类管三样东西：

- `#registerStatesAndModels()` 里写的方块状态文件
- 通过 `#models()` 访问的内部 `BlockModelProvider`（生成 `models/block/*.json`）
- 通过 `#itemModels()` 访问的内部 `ItemModelProvider`（生成 `models/item/*.json`）

文件：`src/main/java/com/dafeiyu/datagen/ModBlockStateProvider.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModBlocks;
import net.minecraft.data.PackOutput;
import net.neoforged.neoforge.client.model.generators.BlockStateProvider;
import net.neoforged.neoforge.common.data.ExistingFileHelper;

public class ModBlockStateProvider extends BlockStateProvider {
    public ModBlockStateProvider(PackOutput output, ExistingFileHelper existingFileHelper) {
        super(output, DafeiyuMod.MOD_ID, existingFileHelper);
    }

    @Override
    protected void registerStatesAndModels() {
        // 最省事的一行：生成 blockstates + models/block + models/item 三个文件
        simpleBlockWithItem(ModBlocks.RUBY_BLOCK.get(),
                models().cubeAll("ruby_block", modLoc("block/ruby_block")));
    }
}
```

`simpleBlockWithItem(block, modelFile)` 展开等于：

1. 生成 `blockstates/ruby_block.json`，内容是 `{"variants": {"": {"model": "dafeiyu:block/ruby_block"}}}`
2. 把传进来的 `modelFile` 写到 `models/block/ruby_block.json`
3. 生成 `models/item/ruby_block.json`，内容 `{"parent": "dafeiyu:block/ruby_block"}`

**注意 `models().cubeAll(name, texture)` 的 `name` 决定文件路径，不一定要等于注册名**，但强烈建议保持一致，否则你以后找文件会疯。

常用的 `models()` 辅助方法（都在 `BlockModelProvider` 上）：

| 方法 | 生成什么 |
|---|---|
| `cubeAll(name, texture)` | 六面同图，等价于手写 `cube_all` |
| `cubeBottomTop(name, side, bottom, top)` | 上下不同 |
| `cubeColumn(name, side, end)` | 柱子 |
| `orientable(name, side, front, top)` | 有正面 |
| `singleTexture(name, parent, textureKey, texture)` | 任意父模型 + 一个变量 |
| `withExistingParent(name, parent)` | 只设父模型，变量留给别的模型填 |
| `getBuilder(name)` | 拿到空构建器，自己逐个设 `texture()` / `element()` |

**`modLoc("block/ruby_block")`** 是「我的命名空间下的 `block/ruby_block`」，等价于 `ResourceLocation.fromNamespaceAndPath("dafeiyu", "block/ruby_block")`。对应的 `mcLoc("block/cobblestone")` 是原版命名空间。这两个简写你会用几百次。

### `ItemModelProvider`：纯物品模型

文件：`src/main/java/com/dafeiyu/datagen/ModItemModelProvider.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModItems;
import net.minecraft.data.PackOutput;
import net.neoforged.neoforge.client.model.generators.ItemModelProvider;
import net.neoforged.neoforge.common.data.ExistingFileHelper;

public class ModItemModelProvider extends ItemModelProvider {
    public ModItemModelProvider(PackOutput output, ExistingFileHelper existingFileHelper) {
        super(output, DafeiyuMod.MOD_ID, existingFileHelper);
    }

    @Override
    protected void registerModels() {
        // 最常用的一行：item/generated + layer0 = dafeiyu:item/<注册名>
        basicItem(ModItems.RUBY.get());

        // 工具类物品：换成 item/handheld
        withExistingParent(ModItems.RUBY_SWORD.getId().getPath(), mcLoc("item/handheld"))
                .texture("layer0", modLoc("item/ruby_sword"));
    }
}
```

`basicItem(item)` 的约定是：**物品注册名的路径必须和 `textures/item/` 下的文件名一致**。注册名 `ruby` → 找 `textures/item/ruby.png`。不一致就得用 `withExistingParent` 手写。

`ModItems.RUBY.getId()` 返回 `ResourceLocation`，`.getPath()` 拿路径部分。`withExistingParent` 的第一个参数是**模型文件名**（相对 `models/item/`），所以传路径就够。

## 四、`LanguageProvider`：语言文件

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.data.PackOutput;
import net.neoforged.neoforge.common.data.LanguageProvider;

public class ModZhCnLangProvider extends LanguageProvider {
    public ModZhCnLangProvider(PackOutput output) {
        super(output, DafeiyuMod.MOD_ID, "zh_cn");   // 第三个参数是语言代码
    }

    @Override
    protected void addTranslations() {
        // 通用写法：直接给键和值
        add("itemGroup.dafeiyu.main", "大肥鱼模组");

        // 物品：自动拼 item.<modid>.<path>
        addItem(ModItems.RUBY, "红宝石");

        // 方块：自动拼 block.<modid>.<path>
        addBlock(ModBlocks.RUBY_BLOCK, "红宝石块");

        // 自定义键（tooltip、字幕等）
        add("tooltip.dafeiyu.ruby.desc", "一块蕴含魔力的红色晶体");
        add("subtitles.dafeiyu.ruby_chime", "红宝石清脆作响");
    }
}
```

三种写法对应三种场景：

| 方法 | 生成的键 |
|---|---|
| `add(key, value)` | 原样用你给的 key |
| `addItem(DeferredItem, value)` | `item.<modid>.<注册名>` |
| `addBlock(DeferredBlock, value)` | `block.<modid>.<注册名>` |

英文版就是再写一个类，把 `"zh_cn"` 换成 `"en_us"`，内容换成英文。**一个语言一个 provider 实例**，这是标准做法。

**重要提醒：`LanguageProvider` 是「全量重写」。** 每次运行 datagen，它会把整个 `zh_cn.json` 从头生成一遍。这意味着：

- 你不能在生成的文件里手动加东西——下次 datagen 就没了。
- 如果你 `src/main/resources` 里还有一份手写的 `zh_cn.json`，**两份文件会打架**，游戏读哪份取决于打包顺序，通常是你最不想看到的那份。

所以启用 datagen 之后，**把 `src/main/resources/assets/dafeiyu/lang/zh_cn.json` 删掉**，只保留生成的那份。

## 五、`RecipeProvider`：配方

```java
package com.dafeiyu.datagen;

import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.recipes.RecipeCategory;
import net.minecraft.data.recipes.RecipeOutput;
import net.minecraft.data.recipes.RecipeProvider;
import net.minecraft.data.recipes.ShapedRecipeBuilder;
import net.minecraft.data.recipes.ShapelessRecipeBuilder;

import java.util.concurrent.CompletableFuture;

public class ModRecipeProvider extends RecipeProvider {
    public ModRecipeProvider(PackOutput output,
                             CompletableFuture<HolderLookup.Provider> lookupProvider) {
        super(output, lookupProvider);
    }

    @Override
    protected void buildRecipes(RecipeOutput output) {
        // 3×3 红宝石 → 红宝石块
        ShapedRecipeBuilder.shaped(RecipeCategory.BUILDING_BLOCKS, ModBlocks.RUBY_BLOCK.get())
                .pattern("###")
                .pattern("###")
                .pattern("###")
                .define('#', ModItems.RUBY.get())
                .unlockedBy("has_ruby", has(ModItems.RUBY.get()))
                .save(output);

        // 1 个红宝石块 → 9 个红宝石
        ShapelessRecipeBuilder.shapeless(RecipeCategory.MISC, ModItems.RUBY.get(), 9)
                .requires(ModBlocks.RUBY_BLOCK.get())
                .unlockedBy("has_ruby_block", has(ModBlocks.RUBY_BLOCK.get()))
                .save(output, "ruby_from_block");
    }
}
```

三个要点：

1. **`has(...)` 是静态方法**，来自 `RecipeProvider`，用 `import static net.minecraft.data.recipes.RecipeProvider.has;` 或直接 `RecipeProvider.has(...)`。
2. **`.save(output)` 会自动生成一个同名配方 + 一个同名进度**（用来解锁配方书）。这就是为什么 `buildRecipes` 的参数叫 `RecipeOutput` 而不是 `Consumer`——它被包了一层，专门干这个。
3. **同一个结果有多个配方时，`.save(output, "自定义名")`** 必须给第二个参数，否则后一个会覆盖前一个（文件名冲突）。

`RecipeCategory` 决定配方在配方书里归到哪一栏：`BUILDING_BLOCKS`、`MISC`、`TOOLS`、`COMBAT`、`FOOD`、`REDSTONE`。写错了不影响合成，只是配方书分类不对。

## 六、战利品表：`LootTableProvider` + `BlockLootSubProvider`

这一块样板代码最多，但写一次就够用一辈子。

```java
package com.dafeiyu.datagen;

import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.loot.BlockLootSubProvider;
import net.minecraft.util.valueproviders.UniformGenerator;
import net.minecraft.world.flag.FeatureFlags;
import net.minecraft.world.level.block.Block;

import java.util.Set;

public class ModBlockLootProvider extends BlockLootSubProvider {
    public ModBlockLootProvider(HolderLookup.Provider registries) {
        // 参数：抗爆方块集合（一般空）、特性开关（默认）、注册表查询器
        super(Set.of(), FeatureFlags.DEFAULT_FLAGS, registries);
    }

    @Override
    protected Iterable<Block> getKnownBlocks() {
        // 只列出「我要生成战利品表」的方块，用于校验
        return ModBlocks.BLOCKS.getEntries().stream()
                .map(holder -> (Block) holder.value())
                .toList();
    }

    @Override
    protected void generate() {
        // 挖了掉自己
        dropSelf(ModBlocks.RUBY_BLOCK.get());
        dropSelf(ModBlocks.RUBY_LAMP.get());

        // 挖了掉 2~4 个红宝石（不掉方块本身）
        add(ModBlocks.RUBY_ORE.get(),
                createSingleItemTable(ModItems.RUBY.get(),
                        UniformGenerator.between(2.0F, 4.0F)));
    }
}
```

`getKnownBlocks()` 返回的集合会被用来**校验**：如果某个方块在集合里但没有对应的战利品表，datagen 会报错提醒你漏了。这正是它存在的意义——防止「加了新方块忘了写表」。

`BlockLootSubProvider` 的常用辅助方法：

| 方法 | 效果 |
|---|---|
| `dropSelf(block)` | 掉方块自己 |
| `createSingleItemTable(item)` | 掉一个指定物品 |
| `createSingleItemTable(item, countProvider)` | 掉指定数量 |
| `createSilkTouchOnlyTable(block)` | 只有精准采集才掉 |
| `createOreDrop(block, item)` | 矿石：普通掉物品、精准掉方块 |
| `createSlabItemTable(block)` | 台阶：双台阶掉两个 |
| `createDoorTable(block)` | 门：掉一个 |

然后包一层 `LootTableProvider`：

```java
package com.dafeiyu.datagen;

import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.loot.LootTableProvider;
import net.minecraft.world.level.storage.loot.parameters.LootContextParamSets;

import java.util.List;
import java.util.Set;
import java.util.concurrent.CompletableFuture;

public class ModLootTableProvider extends LootTableProvider {
    public ModLootTableProvider(PackOutput output,
                                CompletableFuture<HolderLookup.Provider> lookupProvider) {
        super(output,
                Set.of(),   // 需要强制校验存在的表，模组一般给空集
                List.of(new SubProviderEntry(
                        ModBlockLootProvider::new,       // 子提供器的构造器引用
                        LootContextParamSets.BLOCK)));   // 方块战利品表用 BLOCK
    }
}
```

`SubProviderEntry` 的第二个参数是「战利品上下文参数集」，决定这个子提供器处理哪类表：

| `LootContextParamSets` | 用于 |
|---|---|
| `BLOCK` | 方块 |
| `ENTITY` | 实体 |
| `CHEST` | 箱子/结构 |
| `EMPTY` | 无上下文的自定义表 |

## 七、标签：`BlockTagsProvider` / `ItemTagsProvider`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModBlocks;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.tags.BlockTagsProvider;
import net.minecraft.tags.BlockTags;
import net.neoforged.neoforge.common.data.ExistingFileHelper;

import java.util.concurrent.CompletableFuture;

public class ModBlockTagsProvider extends BlockTagsProvider {
    public ModBlockTagsProvider(PackOutput output,
                                CompletableFuture<HolderLookup.Provider> lookupProvider,
                                ExistingFileHelper existingFileHelper) {
        super(output, lookupProvider, DafeiyuMod.MOD_ID, existingFileHelper);
    }

    @Override
    protected void addTags(HolderLookup.Provider provider) {
        // 归「镐」管 + 需要铁镐
        tag(BlockTags.MINEABLE_WITH_PICKAXE).add(ModBlocks.RUBY_BLOCK.get());
        tag(BlockTags.NEEDS_IRON_TOOL).add(ModBlocks.RUBY_BLOCK.get());

        // 自己定义的标签
        tag(ModTags.Blocks.RUBY_BLOCKS).add(ModBlocks.RUBY_BLOCK.get());
    }
}
```

`tag(...)` 返回一个 `IntrinsicTagAppender`，常用方法：

| 方法 | 作用 |
|---|---|
| `.add(...)` | 加条目，可变参数 |
| `.addTag(otherTag)` | 把另一个标签整个并进来 |
| `.addOptional(ResourceLocation)` | 加可选条目，不存在就忽略 |
| `.remove(...)` | 移除条目 |
| `.replace()` | 设为替换模式（会清空下方所有贡献） |

**`BlockTags.MINEABLE_WITH_PICKAXE` 生成的路径是 `data/minecraft/tags/block/mineable/pickaxe.json`**，命名空间是 `minecraft`（因为标签本身属于原版），而不是你的模组。这一点 `TagsProvider` 会自动处理，你不用操心。

物品标签要多一步，因为它需要方块标签的查询器：

```java
public class ModItemTagsProvider extends ItemTagsProvider {
    public ModItemTagsProvider(PackOutput output,
                               CompletableFuture<HolderLookup.Provider> lookupProvider,
                               BlockTagsProvider blockTagsProvider,
                               ExistingFileHelper existingFileHelper) {
        super(output, lookupProvider, blockTagsProvider.contentsGetter(),
                DafeiyuMod.MOD_ID, existingFileHelper);
    }

    @Override
    protected void addTags(HolderLookup.Provider provider) {
        tag(ModTags.Items.RUBY_GEMS).add(ModItems.RUBY.get());
    }
}
```

自己定义的标签键要提前建好，否则编译不过：

```java
public class ModTags {
    public static class Blocks {
        public static final TagKey<Block> RUBY_BLOCKS =
                TagKey.create(Registries.BLOCK,
                        ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "ruby_blocks"));
    }

    public static class Items {
        public static final TagKey<Item> RUBY_GEMS =
                TagKey.create(Registries.ITEM,
                        ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "ruby_gems"));
    }
}
```

## 八、跑起来：`gradlew runData`

### 执行

```bash
# Windows
gradlew.bat runData

# macOS / Linux / Git Bash
./gradlew runData
```

这个任务由 ModDevGradle 自动创建（`runClient`、`runServer`、`runData`、`runGameTestServer` 四个）。它做的事情就是启动一个 JVM，带上 `--mod dafeiyu --output <绝对路径> --includeClient --includeServer`，跑完就退出。

**成功的样子**：控制台最后出现 `BUILD SUCCESSFUL`，且没有 `Failed to run task ':runData'`。中途会有大量 `Registering ...` 日志，那是正常的模组加载输出。

```text
    └── minecraft/tags/block/mineable/pickaxe.json
```

注意 `src/generated/resources` **不在** `src/main/resources` 里。Gradle 默认不会把它打进 jar，也不会让 `runClient` 读到它。所以必须显式声明。

### 让生成的文件进 jar

文件：`build.gradle`

```groovy
sourceSets {
    main {
        resources {
            srcDir 'src/generated/resources'
        }
    }
}
```

放在 `dependencies { }` 之后、文件末尾都行。加上之后：

- `runClient` 能读到生成的资源
- `build` 打出的 jar 里包含它们
- IDE 的 `src/generated/resources` 目录会变成蓝色（资源根）

**改完 `build.gradle` 一定要点 Gradle 的刷新按钮**（IntelliJ 右侧 Gradle 面板的刷新图标），否则改动不生效。这一步漏了，症状是「datagen 明明生成了文件，游戏里还是紫黑」。

### 不要提交生成的文件？

两种做法，各有利弊：

| 做法 | 好处 | 坏处 |
|---|---|---|
| 提交 `src/generated/resources` | 别人 clone 下来直接能跑；PR 里能看到 json 改动 | 仓库变大；忘记跑 datagen 会导致 json 和代码不同步 |
| `.gitignore` 掉 | 仓库干净，json 永远是代码的产物 | 别人必须先跑一次 `runData` |

**推荐提交。** 模组发布时 jar 里必须有这些 json，而 CI 环境跑 datagen 常常出问题（缺资源、编码差异）。提交上去最省心。

## 完整示例：红宝石全套 datagen

**① 汇总入口**

文件：`src/main/java/com/dafeiyu/datagen/ModDataGenerators.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.DataGenerator;
import net.minecraft.data.PackOutput;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.neoforge.common.data.ExistingFileHelper;
import net.neoforged.neoforge.data.event.GatherDataEvent;

import java.util.concurrent.CompletableFuture;

@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class ModDataGenerators {

    @SubscribeEvent
    public static void gatherData(GatherDataEvent event) {
        DataGenerator generator = event.getGenerator();
        PackOutput output = event.getPackOutput();
        ExistingFileHelper existingFileHelper = event.getExistingFileHelper();
        CompletableFuture<HolderLookup.Provider> lookupProvider = event.getLookupProvider();

        // ---------- 客户端资源（assets） ----------
        generator.addProvider(event.includeClient(),
                new ModBlockStateProvider(output, existingFileHelper));
        generator.addProvider(event.includeClient(),
                new ModItemModelProvider(output, existingFileHelper));
        generator.addProvider(event.includeClient(),
                new ModZhCnLangProvider(output));
        generator.addProvider(event.includeClient(),
                new ModEnUsLangProvider(output));

        // ---------- 服务端数据（data） ----------
        generator.addProvider(event.includeServer(),
                new ModRecipeProvider(output, lookupProvider));
        generator.addProvider(event.includeServer(),
                new ModLootTableProvider(output, lookupProvider));

        ModBlockTagsProvider blockTags =
                new ModBlockTagsProvider(output, lookupProvider, existingFileHelper);
        generator.addProvider(event.includeServer(), blockTags);
        generator.addProvider(event.includeServer(),
                new ModItemTagsProvider(output, lookupProvider, blockTags, existingFileHelper));
    }
}
```

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| `runData` 报 `Could not find parent model` | `ExistingFileHelper` 找不到父模型 | 确认父模型在 `src/main/resources` 或原版里；或加 `--existing` 参数 |
| `runData` 成功，但 `src/generated/resources` 是空的 | `includeClient()` / `includeServer()` 都返回 false | 检查 `build.gradle` 的 `runs.data.programArguments` |
| 生成的文件有，但游戏里还是紫黑 | `build.gradle` 没加 `srcDir 'src/generated/resources'` | 加上并刷新 Gradle |
| 生成的文件有，但没进 jar | 同上 | 同上，然后 `gradlew build` 重新打包 |
| 语言文件只剩几条 | `LanguageProvider` 全量重写，你手写的内容被覆盖 | 把所有翻译都搬进 provider |
| 同一个物品出现两个模型文件，游戏读错 | `src/main/resources` 和 `src/generated/resources` 有同名文件 | 删掉手写的那份 |
| `basicItem` 生成的模型紫黑 | `textures/item/<注册名>.png` 不存在 | 补齐纹理，或用 `withExistingParent` 指定别的路径 |
| `dropSelf` 后报 `Missing loot table` | `getKnownBlocks()` 返回了方块，但 `generate()` 里漏了它 | 补上，这正是校验的价值 |
| `runData` 卡住不退出 | 某个 provider 里开了线程或阻塞 IO | 不要在 provider 里做异步操作 |
| 生成的 `advancement` 一堆垃圾文件 | `RecipeOutput` 自动生成配方解锁进度 | 正常现象，别手动删 |
| `ItemTagsProvider` 编译报错找不到构造器 | 少了 `blockTagsProvider.contentsGetter()` | 按第七节写法补 |
| datagen 跑完 IDE 里看不到新文件 | IDE 没刷新 | 右键项目 → Reload from Disk |
| 改了 datagen 代码，生成结果没变 | Gradle 任务被 up-to-date 跳过 | `gradlew runData --rerun-tasks` |

## 练习

1. **基础**：把 `ruby_sword` 加进 datagen：`ItemModelProvider` 里用 `item/handheld`、语言文件里加中英、`RecipeProvider` 里加一个「两根木棍 + 一颗红宝石」的剑配方。
2. **进阶**：加一个 `ruby_ore` 方块，用 `createOreDrop` 生成「普通挖掉 1 个红宝石、精准采集掉方块本身」的战利品表，并加进 `mineable/pickaxe` 和 `needs_iron_tool` 两个标签。
3. **挑战**：把 `BlockStateProvider` 里的 `ruby_block` 从 `cubeAll` 改成 `cubeBottomTop`（顶面用 `ruby_block_top`、底面用 `ruby_block_bottom`、侧面用 `ruby_block`），重跑 datagen，对比生成的 json 和你手写版本有什么差别。这一步做完，你就能判断「哪些该 datagen、哪些该手写」了。
