# 资源包与数据包结构

> 读完这篇，你能一眼看出「我这个东西该放在哪个文件夹」，并且在游戏里显示紫黑方块、名字变成一串英文 key、方块挖了不掉的时候，知道该去哪个目录翻。

## 学习目标

- 能说清 `assets/` 和 `data/` 各自管什么，为什么同一件东西经常两边都要放文件。
- 能默写出 `assets/dafeiyu/` 与 `data/dafeiyu/` 下的完整子目录树。
- 能根据一个注册名（比如 `dafeiyu:ruby_block`）推出它所有资源的文件路径。
- 能列出「一个方块从注册到在游戏里正常显示」需要的全部文件，并按顺序检查。
- 知道 `F3+T` 和 `/reload` 分别重载什么、不重载什么。

## 一、一句话分工：assets 给眼睛看，data 给逻辑用

Minecraft 把「模组附带的外部文件」按**逻辑侧（logical side）**劈成了两半：

| 目录 | 全称 | 加载方式 | 服务于 | 典型内容 |
|---|---|---|---|---|
| `assets/` | 资源（assets） | 资源包（resource pack） | 逻辑客户端 | 纹理、模型、方块状态、语言、声音、粒子贴图 |
| `data/` | 数据（data） | 数据包（data pack） | 逻辑服务端 | 配方、战利品表、标签、进度、世界生成、数据映射 |

这个划分不是随便定的，它对应一条硬规则：**服务端不认识纹理，客户端不跑配方。**

你在写代码时可能已经体会过一次：专用服务器（dedicated server）上根本没有 `Minecraft` 类，任何引用 `net.minecraft.client.*` 的代码都会让服务器启动时直接崩掉。`assets/` 和 `data/` 的分家，是同一个道理在文件层面的体现。

由此推出三个立刻能用的结论：

1. 你把纹理放进了 `data/`，客户端永远找不到它——因为客户端只去 `assets/` 里翻。
2. 你把配方放进了 `assets/`，服务端永远读不到它——因为服务端只去 `data/` 里翻。
3. 同一件东西经常两边都要有：一个方块需要 `assets/` 里的模型纹理（看得见），也需要 `data/` 里的战利品表（挖了掉东西）。

NeoForge 在运行时会把你模组 jar 里的这两个目录**各自打包成一个内置的资源包和一个内置的数据包**，自动塞进游戏的包列表里，你不需要做任何注册。资源包列表里那个最底部的 `Mod resources` 就是它，而且**无法关闭**。

> 顺便记一个细节：资源包是「上面的覆盖下面的」，所以玩家做的材质包能覆盖你的纹理；而数据包在你新建世界时会被自动应用，同样不能被关掉。这就是为什么「我明明改了配方，游戏里还是旧的」——很可能是别的数据包在上面盖住了你。

## 二、完整目录树

下面是 `dafeiyu` 这个模组在功能做全之后，`src/main/resources/` 应该长的样子。**先整体看一眼，不要急着记，后面会一节一节拆。**

```text
src/main/resources/
├── pack.mcmeta                                  ← 可选，NeoForge 会自动生成
│
├── assets/                                      ← 客户端资源（资源包）
│   └── dafeiyu/                                 ← 命名空间 = 模组 id
│       ├── blockstates/                         ← 方块状态文件（单数！）
│       │   ├── ruby_block.json
│       │   └── ruby_lamp.json
│       ├── models/                              ← 模型
│       │   ├── block/                           ← 方块模型
│       │   │   ├── ruby_block.json
│       │   │   └── ruby_lamp.json
│       │   └── item/                            ← 物品模型（含方块物品）
│       │       ├── ruby.json
│       │       ├── ruby_block.json
│       │       └── ruby_sword.json
│       ├── textures/                            ← 纹理（全是 PNG）
│       │   ├── block/
│       │   │   ├── ruby_block.png
│       │   │   └── ruby_lamp.png
│       │   ├── item/
│       │   │   ├── ruby.png
│       │   │   └── ruby_sword.png
│       │   ├── particle/                        ← 粒子贴图
│       │   │   └── ruby_spark_0.png
│       │   ├── gui/                             ← 界面贴图
│       │   │   └── ruby_chest.png
│       │   └── entity/                          ← 实体/方块实体贴图
│       ├── lang/                                ← 语言文件
│       │   ├── en_us.json
│       │   └── zh_cn.json
│       ├── sounds/                              ← 声音文件（.ogg）
│       │   ├── ruby_chime.ogg
│       │   └── block/
│       │       └── ruby_block_break.ogg
│       ├── sounds.json                          ← 声音定义（在命名空间根目录！）
│       ├── particles/                           ← 粒子描述
│       │   └── ruby_spark.json
│       └── font/                                ← 自定义字体（很少用）
│
└── data/                                        ← 服务端数据（数据包）
    ├── dafeiyu/                                 ← 自己命名空间的数据
    │   ├── recipe/                              ← 配方（单数！）
    │   │   ├── ruby_block.json
    │   │   └── ruby_sword.json
    │   ├── loot_table/                          ← 战利品表（单数！）
    │   │   ├── blocks/
    │   │   │   └── ruby_block.json
    │   │   └── entities/
    │   ├── advancement/                         ← 进度（单数！）
    │   │   └── root.json
    │   ├── tags/                                ← 自己定义的标签
    │   │   ├── item/
    │   │   │   └── ruby_gems.json
    │   │   └── block/
    │   │       └── needs_ruby_tool.json
    │   ├── damage_type/
    │   ├── neoforge/
    │   │   ├── data_maps/                       ← 数据映射
    │   │   │   └── item/
    │   │   │       └── furnace_fuels.json
    │   │   ├── biome_modifier/                  ← 生物群系修改器
    │   │   └── loot_modifiers/                  ← 全局战利品修改器
    │   ├── worldgen/
    │   │   ├── configured_feature/
    │   │   ├── placed_feature/
    │   │   └── biome/
    │   └── dimension/
    └── minecraft/                               ← 往原版命名空间里塞东西
        └── tags/
            ├── block/
            │   ├── mineable/pickaxe.json
            │   └── needs_iron_tool.json
            └── item/
                └── swords.json
```

几个必须盯住的地方：

- **`sounds.json` 在 `assets/dafeiyu/` 根目录**，不在 `sounds/` 里面。`sounds/` 放音频文件，`sounds.json` 放「哪个事件对应哪个文件」的映射。这两个东西名字像，位置完全不同，是新手第一大坑。
- **`particles/` 是粒子描述，`textures/particle/` 是粒子贴图**，一个在 `assets/dafeiyu/particles/`，一个在 `assets/dafeiyu/textures/particle/`。注意后者是 `particle` 单数。
- **`data/minecraft/` 是你去改原版数据的地方**。想让你的方块归「镐」管，就得往 `data/minecraft/tags/block/mineable/pickaxe.json` 里加，而不是 `data/dafeiyu/`。

## 三、`pack.mcmeta` 到底要不要写

`pack.mcmeta` 是资源包/数据包的**元数据文件**，告诉游戏「我这个包的格式版本是多少、叫什么名字」。

格式长这样：

```json
{
  "pack": {
    "pack_format": 34,
    "description": "大肥鱼模组的资源"
  }
}
```

`pack_format` 是**格式版本号**，不是游戏版本号。1.21.1 对应：

| 包类型 | `pack_format` |
|---|---|
| 资源包（assets） | 34 |
| 数据包（data） | 48 |

写错了游戏会认为这个包是「为旧版本做的」，弹一个黄色警告，但通常还能加载——所以这不是致命错误，只是很难看。

**但对模组来说，你基本不需要写它。** NeoForge 会在运行时根据 `neoforge.mods.toml` 里的信息自动合成一个 `pack.mcmeta`，塞进那个 `Mod resources` 包里。你手写一个放在 `src/main/resources/pack.mcmeta` 也能生效（会覆盖自动生成的），什么时候需要手写？

- 你想让资源包在列表里显示一个自定义描述。
- 你想声明 `supported_formats` 让包在多个版本间通用。
- 你在做一个**独立的分发用资源包**（不是模组）。

其余情况，**不写**。少一个文件少一个出错点。

## 四、注册名 → 文件路径：三条铁律

这是本篇最值钱的部分。你以后 90% 的「资源不生效」都是违反了这三条之一。

### 铁律一：全小写，只允许 `a-z` `0-9` `_` `-` `.` `/`

注册名 `rubyBlock`、`Ruby_Block`、`ruby block` 都不合法。Minecraft 的资源位置（ResourceLocation）在解析时就会拒绝大写字母。**文件名也必须跟着小写**——你在 Windows 上把文件叫 `Ruby_Block.png`，本地可能能跑（Windows 文件系统不区分大小写），一上 Linux 服务器或一打包就炸。

这条坑最阴险的地方在于：**Windows 上它经常不报错**。所以养成习惯，建文件时就全小写 + 下划线。

### 铁律二：目录名用单数

1.20.5 之后，Minecraft 把一批数据目录从复数改成了单数。这是新手最容易踩的一脚，因为网上大量老教程还是复数写法。

| 1.21.1 正确 | 旧版本 / 错误写法 | 后果 |
|---|---|---|
| `textures/item/` | `textures/items/` | 纹理找不到，紫黑 |
| `textures/block/` | `textures/blocks/` | 同上 |
| `models/block/` | `models/blocks/` | 模型加载失败 |
| `data/dafeiyu/recipe/` | `recipes/` | 配方静默失效，不报错 |
| `data/dafeiyu/loot_table/` | `loot_tables/` | 方块挖了不掉东西，不报错 |
| `data/dafeiyu/advancement/` | `advancements/` | 进度不出现，不报错 |
| `data/dafeiyu/tags/block/` | `tags/blocks/` | 标签不生效 |

注意「不报错」这三个字。`assets/` 里写错目录名，日志里通常有一行 `Unable to load model` 之类的警告；但 `data/` 里写错，游戏**一声不吭**，只是那个功能默默不工作。这是数据包侧最难查的一类问题。

`blockstates/`、`models/`、`textures/`、`lang/`、`sounds/`、`particles/`、`tags/` 这几个是**本来就带 s 的固定名字**，别自作聪明改成单数。规律是：**容器目录保留原样，内容分类目录用单数**。

### 铁律三：路径 = 注册名的路径部分，命名空间靠目录体现

一个注册名是 `命名空间:路径`。比如 `dafeiyu:ruby_block`。

- 命名空间 `dafeiyu` → 对应 `assets/dafeiyu/` 或 `data/dafeiyu/` 这一层目录，**不写进文件名**。
- 路径 `ruby_block` → 对应文件名 `ruby_block.json` / `ruby_block.png`。

所以：

```text
注册名 dafeiyu:ruby_block
├─ assets/dafeiyu/blockstates/ruby_block.json
├─ assets/dafeiyu/models/block/ruby_block.json
├─ assets/dafeiyu/models/item/ruby_block.json
├─ assets/dafeiyu/textures/block/ruby_block.png
├─ data/dafeiyu/loot_table/blocks/ruby_block.json
└─ data/dafeiyu/recipe/ruby_block.json
```

而 `dafeiyu:ruby`（一个物品）对应的是：

```text
├─ assets/dafeiyu/models/item/ruby.json
├─ assets/dafeiyu/textures/item/ruby.png
└─ data/dafeiyu/recipe/ruby.json
```

**注意物品没有 `blockstates`，也没有 `models/block`。** 物品模型直接按注册名去 `models/item/<路径>.json` 找，中间没有方块状态这一层。这就是为什么方块比物品麻烦。

### 引用别人时写全名，引用自己时可以不写

在 JSON 里写资源位置时：

```json
"dafeiyu:block/ruby_block"
```

完整写法。因为 `assets/dafeiyu/models/block/ruby_block.json` 这个文件自己就在 `dafeiyu` 命名空间里，你也可以简写成：

```json
"block/ruby_block"
```

Minecraft 会自动补上「当前文件所在的命名空间」。**但方块状态文件和模型文件里，我建议你永远写全 `dafeiyu:` 前缀。** 理由：一旦你以后把这个模型复制到别的命名空间，或者用 datagen 生成，简写会变成隐式依赖，出问题时你根本看不出是哪里错了。多打 9 个字符换来的确定性，非常值。

## 五、一个方块要「看得见」，到底需要几个文件

按**渲染管线**的顺序，从下往上：

```text
① 纹理  textures/block/ruby_block.png
        ↓ 被模型引用
② 方块模型  models/block/ruby_block.json
        ↓ 被方块状态引用
③ 方块状态  blockstates/ruby_block.json
        ↓ 游戏按 BlockState 查这里，拿到模型
   → 世界里的方块画出来了
        ↓
④ 物品模型  models/item/ruby_block.json（parent 指向 ②）
        ↓
   → 物品栏/手里那个小方块也画出来了
        ↓
⑤ 语言文件  lang/zh_cn.json 里的 block.dafeiyu.ruby_block
        ↓
   → 名字显示成「红宝石块」而不是一串 key
```

清单版，可以直接当检查表用：

| # | 文件 | 缺了会怎样 |
|---|---|---|
| 1 | `assets/dafeiyu/textures/block/ruby_block.png` | 模型能加载但纹理是紫黑格子 |
| 2 | `assets/dafeiyu/models/block/ruby_block.json` | 世界里的方块整个是紫黑 |
| 3 | `assets/dafeiyu/blockstates/ruby_block.json` | 世界里的方块整个是紫黑 |
| 4 | `assets/dafeiyu/models/item/ruby_block.json` | 放下去正常，物品栏里是紫黑 |
| 5 | `assets/dafeiyu/lang/zh_cn.json` 的对应键 | 名字显示 `block.dafeiyu.ruby_block` |
| 6 | `data/dafeiyu/loot_table/blocks/ruby_block.json` | 挖了不掉东西（生存模式） |
| 7 | `data/minecraft/tags/block/mineable/pickaxe.json` | 挖得极慢、且不掉东西 |

**物品只需要 ①③⑤ 里的「物品版」**：

| # | 文件 | 缺了会怎样 |
|---|---|---|
| 1 | `assets/dafeiyu/textures/item/ruby.png` | 紫黑 |
| 2 | `assets/dafeiyu/models/item/ruby.json` | 紫黑 |
| 3 | `lang/zh_cn.json` 里的 `item.dafeiyu.ruby` | 显示原始 key |

也就是说：**物品两个文件，方块四个文件**（不含数据包）。记住这个数字，以后少文件时一眼就知道少了哪层。

## 六、数据包侧：五个你一定会用到的目录

### 1. `data/dafeiyu/recipe/` —— 配方

一件合成配方的 JSON，文件名就是配方 id。比如红宝石块：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_block.json`

```json
{
  "type": "minecraft:crafting_shaped",
  "category": "building",
  "pattern": [
    "###",
    "###",
    "###"
  ],
  "key": {
    "#": "dafeiyu:ruby"
  },
  "result": {
    "id": "dafeiyu:ruby_block",
    "count": 1
  }
}
```

注意 1.21 起 `result` 里用 `"id"` 而不是旧版的 `"item"`，`key` 里直接写物品 id 字符串而不是 `{"item": "..."}` 对象。这两个改动让 90% 的旧教程配方直接失效。无序合成、熔炉、锻造台、自定义配方类型的完整语法见 [配方](06-配方.md)。

### 2. `data/dafeiyu/loot_table/blocks/` —— 战利品表

方块的表放在 `loot_table/blocks/` 子目录下，文件名必须和方块注册名一致，游戏才会自动找到。完整的语法（多池、随机数量、附魔加成、条件）见 [战利品表](07-战利品表.md)，这里先看结构：

文件：`src/main/resources/data/dafeiyu/loot_table/blocks/ruby_block.json`

```json
{
  "type": "minecraft:block",
  "pools": [
    {
      "rolls": 1,
      "entries": [
        {
          "type": "minecraft:item",
          "name": "dafeiyu:ruby_block"
        }
      ],
      "conditions": [
        {
          "condition": "minecraft:survives_explosion"
        }
      ]
    }
  ]
}
```

### 3. `data/<命名空间>/tags/<注册表>/` —— 标签

标签是「一组同类型对象的名单」，用来做「任意木板都能合成木棍」这类判断。

**自己用的标签**放自己命名空间：

文件：`src/main/resources/data/dafeiyu/tags/item/ruby_gems.json`

```json
{
  "values": [
    "dafeiyu:ruby",
    "dafeiyu:ruby_shard"
  ]
}
```

**要影响原版行为**的标签，必须放 `data/minecraft/`：

文件：`src/main/resources/data/minecraft/tags/block/mineable/pickaxe.json`

```json
{
  "values": [
    "dafeiyu:ruby_block"
  ]
}
```

为什么？因为「哪些方块归镐管」这个标签的 id 是 `minecraft:mineable/pickaxe`，标签文件的位置由**标签的命名空间**决定，不是由你模组的命名空间决定。你想往 `minecraft:` 的标签里加东西，文件就得放在 `data/minecraft/tags/` 下。

标签的一个关键特性：**它是合并的，不是覆盖的**。你的 `mineable/pickaxe.json` 不会把原版那一长串方块冲掉，只是往后追加。所以放 `data/minecraft/tags/` 里改原版标签是安全的。标签的完整用法见 [标签](08-标签.md)。

### 4. `data/dafeiyu/advancement/` —— 进度

进度的树形结构靠 `parent` 字段串起来，根节点没有 `parent`。

文件：`src/main/resources/data/dafeiyu/advancement/root.json`

```json
{
  "display": {
    "icon": {
      "id": "dafeiyu:ruby"
    },
    "title": "大肥鱼：起源",
    "description": "获得你的第一颗红宝石",
    "frame": "task",
    "background": "minecraft:textures/block/stone.png",
    "show_toast": true,
    "announce_to_chat": true
  },
  "criteria": {
    "get_ruby": {
      "trigger": "minecraft:inventory_changed",
      "conditions": {
        "items": [
          {
            "items": "dafeiyu:ruby"
          }
        ]
      }
    }
  }
}
```

`background` 只有**根进度**需要写，子进度会继承。图标用 `"id"`（1.20.5+ 的写法），不是旧版的 `"item"`。

### 5. `data/dafeiyu/neoforge/data_maps/` —— 数据映射

数据映射（data map）是 NeoForge 提供的一套「给已有注册表对象挂额外数据」的机制，不用改原版代码。最常见的用法是给物品加燃烧时间：

文件：`src/main/resources/data/dafeiyu/neoforge/data_maps/item/furnace_fuels.json`

```json
{
  "values": {
    "dafeiyu:ruby": {
      "burn_time": 1600
    }
  }
}
```

结构是 `data/<你的命名空间>/neoforge/data_maps/<注册表名>/<映射名>.json`。注意 `neoforge` 这一层是**固定的字面量目录名**，不是你模组的 id——因为数据映射的类型是 NeoForge 定义的。

## 七、改完资源怎么让它生效

这是新手第二个高频困惑：「我改了 json，游戏里没变」。

Minecraft 有两套完全独立的重载机制，**用错哪个都不会生效**：

| 操作 | 重载什么 | 不重载什么 |
|---|---|---|
| `F3 + T` | 资源包：纹理、模型、方块状态、语言、声音、粒子贴图 | 数据包全部内容 |
| `/reload` | 数据包：配方、战利品表、标签、进度、数据映射 | 资源包全部内容 |
| 重启客户端 | 全部 | — |

所以：

- 改了 `assets/` 里的东西 → `F3 + T`。
- 改了 `data/` 里的东西 → `/reload`（需要开作弊，或者你是服主）。
- **改了 Java 代码 → 必须重启游戏**。`F3+T` 和 `/reload` 都不会重新跑你的注册代码。

还有一个更隐蔽的情况：**新增文件**（不是修改已有文件）有时 `F3+T` 也认不出来，尤其是纹理图集（atlas）的构建。这种时候直接重启客户端最省事。开发期别吝惜重启，比对着日志猜十分钟快。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 日志刷 `Unable to load model: 'dafeiyu:block/ruby_block'` | `models/block/ruby_block.json` 不存在，或文件名大小写不对 | 检查文件名全小写 |
| 方块紫黑，物品栏正常 | 缺 `blockstates/ruby_block.json` | 补上，路径指向 `dafeiyu:block/ruby_block` |
| 世界正常，物品栏紫黑 | 缺 `models/item/ruby_block.json` | 补 `{"parent": "dafeiyu:block/ruby_block"}` |
| 纹理是紫黑格子，模型形状正常 | 纹理路径写成 `textures/items/`，或 PNG 实际是大写文件名 | 目录改单数 `item`，文件改名小写 |
| 方块挖了不掉东西 | `loot_table` 写成了 `loot_tables` | 目录改单数 |
| 配方在 JEI 里查不到 | `recipe` 写成了 `recipes`，或 `result` 里用了 `"item"` 而非 `"id"` | 两处都改 |
| 进度不显示 | `advancement` 写成 `advancements`，或根进度缺 `background` | 目录单数 + 补背景 |
| 木镐也能挖下来 | 缺 `data/minecraft/tags/block/needs_iron_tool.json` | 补标签 |
| 改了 json，`F3+T` 没反应 | 改的是 `data/` 里的文件 | 用 `/reload` |
| `/reload` 后配方还是旧的 | 你改的是 `assets/`，或者有别的数据包在上面覆盖 | 确认目录；检查 `datapack list` |
| Windows 上正常，打包后纹理全丢 | 文件名含大写，Windows 不区分大小写所以本地没暴露 | 全部重命名为小写 |
| 服务器启动崩，日志提到 `NoClassDefFoundError: net/minecraft/client/...` | 你在通用代码里引用了客户端类 | 见 [侧：客户端与服务端](../03-核心概念篇/03-侧-客户端与服务端.md) |

## 练习

1. **基础**：不看上面的树，自己在纸上默写出 `assets/dafeiyu/` 下的 7 个子目录，然后对着本文核对。错的那个，就是你会踩的坑。
2. **进阶**：给模组加一个 `ruby_shard` 物品（只有物品模型和纹理），然后写一个 `data/dafeiyu/tags/item/ruby_gems.json`，把 `ruby` 和 `ruby_shard` 都放进去。用 `/give` 和 `/clear @s #dafeiyu:ruby_gems` 验证标签生效。
3. **挑战**：故意把 `models/block/ruby_block.json` 里的 `"all"` 改成 `"alls"`，启动游戏，去 `logs/latest.log` 里找到那条报错并抄下来。以后你在别人的日志里看到同样的行，就能一秒定位。
