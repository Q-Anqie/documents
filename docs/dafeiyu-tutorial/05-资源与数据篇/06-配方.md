# 配方

> 读完这篇，你能不查资料就写出有序合成、无序合成、熔炉家族、切石机、锻造台这八种配方的 JSON，也能用 `RecipeProvider` 把它们全部自动生成出来。

## 学习目标

- 能说清配方 JSON 的通用骨架：`type` 决定「这是什么机器」，其余字段由 `type` 决定。
- 能默写 `crafting_shaped` 的 `pattern` / `key` 结构，并解释图案里空格的含义。
- 能给同一份材料写出熔炉、高炉、烟熏炉、营火四种「同料不同机」的配方，并知道 `cookingtime` 该填多少。
- 能用 `Ingredient` 的三种写法（物品、标签、数组）表达「任意一种都行」。
- 能用 `RecipeProvider` + `ShapedRecipeBuilder` 生成配方，并解释 `unlockedBy` 为什么不能省。
- 能根据「配方书里不出现」「放进去没反应」「游戏启动就报错」三种现象，判断问题出在哪一层。

## 一、配方文件住在哪，长什么样

配方（recipe）是「把一组输入变成输出」的数据文件。它不写在代码里，而是放在数据包（data pack）目录下：

```text
src/main/resources/data/dafeiyu/recipe/ruby_block.json
```

注意路径是 **`recipe`（单数）**。1.21 把 `recipes`、`loot_tables`、`advancements` 这些目录全部改成了单数，你从 1.20 教程里抄来的 `recipes` 会直接失效——游戏根本不会去读那个文件夹。

一个配方文件里，所有类型**共有**的字段只有两个：

```json
{
  "type": "minecraft:crafting_shaped",
  "neoforge:conditions": []
}
```

- `type`：配方序列化器（recipe serializer）的 id，也就是「这份配方该由哪种机器、按哪种规则来解释」。它决定了文件里还能写哪些字段。写 `crafting_shaped` 就得有 `pattern`，写 `smelting` 就得有 `cookingtime`。
- `neoforge:conditions`：可选，NeoForge 加的数据加载条件。第九节再讲。

除此之外还有一个东西到处都在用，先认熟它——**结果物品的 JSON 表示**：

```json
{ "id": "dafeiyu:ruby", "count": 2 }
```

`id` 是物品的资源位置，`count` 是数量（不写默认 1）。1.21 之前这里写的是 `{"item": "..."}`，现在统一成 `id`，抄老教程时最容易在这里踩空。

## 二、有序合成 `crafting_shaped`

这是最常用的类型：材料必须按图案摆放。做一个红宝石块（3×3 红宝石）：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_block.json`

```json
{
  "type": "minecraft:crafting_shaped",
  "category": "building",
  "pattern": [
    "RRR",
    "RRR",
    "RRR"
  ],
  "key": {
    "R": {
      "item": "dafeiyu:ruby"
    }
  },
  "result": {
    "id": "dafeiyu:ruby_block",
    "count": 1
  }
}
```

逐行拆：

- `category`：配方书里的分类，可选。合成配方只接受 `building`、`redstone`、`equipment`、`misc` 四个值。填错游戏会在加载时报 `Failed to parse recipe`。
- `pattern`：图案，**最多三行、每行最多三个字符**。三行必须等长，整体必须是一个矩形。想表示「这一格空着」就写**空格**。
- `key`：把图案里出现的字符映射到一个「原料（ingredient）」。图案里所有非空格字符都必须在这里定义，少定义一个就报错。
- `result`：结果物品。

### 2.1 空格到底是什么意思

空格是「这一格必须空着」，不是「这一格随便放什么都行」。这一点极其重要，因为它决定了配方能不能被「形状平移」匹配。

拿红宝石镐举例：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_pickaxe.json`

```json
{
  "type": "minecraft:crafting_shaped",
  "category": "equipment",
  "pattern": [
    "RRR",
    " S ",
    " S "
  ],
  "key": {
    "R": { "item": "dafeiyu:ruby" },
    "S": { "item": "minecraft:stick" }
  },
  "result": { "id": "dafeiyu:ruby_pickaxe", "count": 1 }
}
```

写成 `" S "`（两边带空格）而不是 `"S"`，是为了让三行等长——`"RRR"` 是 3 个字符，`"S"` 只有 1 个，长度不一致会直接报 `Pattern must be a rectangle`。

而 `" S "` 里两边的空格确实要求那两格空着。游戏匹配时会把这个 3×3 图案在合成格里上下左右平移寻找位置，但**不会**旋转、也**不会**忽略空格。所以「镐子」你只能在中间列放木棍，把木棍放到左边列是合不出来的。

> 小技巧：图案的行列数可以小于 3。比如两格宽的配方可以写 `["RR", "RR"]`，游戏照样能在 3×3 格里匹配到。行数少一行、字符少一个，匹配的自由度就大一分。

### 2.2 `group` 是什么

加一个 `"group": "ruby_tools"` 字段，配方书里同一组的配方会折叠成一个条目，点开才展开。纯 UI 效果，不影响合成逻辑。工具、台阶这类「一个材料一堆变体」的东西建议都加上。

## 三、无序合成 `crafting_shapeless`

不关心摆放位置，只关心「放了哪几样、各几个」。红宝石块拆回 9 颗红宝石：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_from_ruby_block.json`

```json
{
  "type": "minecraft:crafting_shapeless",
  "category": "misc",
  "ingredients": [
    { "item": "dafeiyu:ruby_block" }
  ],
  "result": {
    "id": "dafeiyu:ruby",
    "count": 9
  }
}
```

三个要点：

1. 字段是 **`ingredients`（复数）**，值是一个数组。这一点和熔炉类配方的 `ingredient`（单数，一个对象）正好相反，是最高频的复制粘贴事故。
2. 数组里同一个原料写两次，就等于要两个。想让「一颗红宝石 + 一个碗」出东西，就写两个对象。
3. 原版惯例：**拆包（一个方块 → 9 个材料）一律用无序配方**，别用 3×3 的有序图案，否则玩家在 2×2 合成格里拆不了。

## 四、熔炉家族：`smelting` / `blasting` / `smoking` / `campfire_cooking`

这四种配方共用一套字段，只是 `type` 和「处理速度」不同：

| 类型 | 机器 | 原版 `cookingtime` | 备注 |
|---|---|---|---|
| `minecraft:smelting` | 熔炉 | 200（10 秒） | 万能，什么都能烧 |
| `minecraft:blasting` | 高炉 | 100（5 秒） | 只烧矿石/金属，经验给得少 |
| `minecraft:smoking` | 烟熏炉 | 100（5 秒） | **只烧食物** |
| `minecraft:campfire_cooking` | 营火 | 600（30 秒） | 不消耗燃料，但要等 |

红宝石矿石烧成红宝石：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_from_smelting_ruby_ore.json`

```json
{
  "type": "minecraft:smelting",
  "category": "misc",
  "cookingtime": 200,
  "experience": 0.7,
  "ingredient": {
    "item": "dafeiyu:ruby_ore"
  },
  "result": {
    "id": "dafeiyu:ruby"
  }
}
```

- `cookingtime`：处理时间，单位是**刻（tick）**，20 刻 = 1 秒。
- `experience`：烧一个给多少经验，可以是小数（原版铁矿 0.7、钻石矿 1.0）。**省略就不给经验**。
- `ingredient`：单数，一个原料对象。

高炉版只需要把 `type` 换成 `minecraft:blasting`、`cookingtime` 改成 100、`experience` 稍微降一点（原版惯例是高炉经验 = 熔炉经验的一半左右）：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_from_blasting_ruby_ore.json`

```json
{
  "type": "minecraft:blasting",
  "category": "misc",
  "cookingtime": 100,
  "experience": 0.7,
  "ingredient": {
    "item": "dafeiyu:ruby_ore"
  },
  "result": {
    "id": "dafeiyu:ruby"
  }
}
```

烟熏炉只能烧食物——你给矿石写 `smoking` 配方，游戏不会报错，只是永远不会匹配，因为烟熏炉的输入槽只接受食物类物品。营火则是「慢但不要燃料」：

文件：`src/main/resources/data/dafeiyu/recipe/cooked_beef_from_campfire_cooking.json`

```json
{
  "type": "minecraft:campfire_cooking",
  "category": "food",
  "cookingtime": 600,
  "experience": 0.35,
  "ingredient": {
    "item": "minecraft:beef"
  },
  "result": {
    "id": "minecraft:cooked_beef"
  }
}
```

食物例子（把生牛肉做成牛排）：

```json
{
  "type": "minecraft:smoking",
  "category": "food",
  "cookingtime": 100,
  "experience": 0.35,
  "ingredient": { "item": "minecraft:beef" },
  "result": { "id": "minecraft:cooked_beef" }
}
```

注意熔炉类的 `category` 取值是 `food`、`blocks`、`misc`，和合成配方的 `building`/`equipment` 那套**不是同一套枚举**。

## 五、切石机 `stonecutting`

最简单的一类：一个输入、一个输出，没有图案、没有时间、没有经验。

文件：`src/main/resources/data/dafeiyu/recipe/ruby_slab_from_stonecutting.json`

```json
{
  "type": "minecraft:stonecutting",
  "ingredient": { "item": "dafeiyu:ruby_block" },
  "result": { "id": "dafeiyu:ruby_slab", "count": 2 }
}
```

切石机的意义是「一份材料，多个产物，玩家自己选」。所以切石机配方通常**成组出现**：同一个输入对应台阶、楼梯、墙、砖好几个输出，每个都是一份独立 JSON。

> 这里的 `dafeiyu:ruby_slab` 是假设你做过红宝石台阶。没有的话，把输入和输出换成任意两个你自己的方块——切石机只要求「一个输入、一个输出」，不关心它们是什么。

## 六、锻造台 `smithing_transform`

锻造台有三个输入槽，字段名分别是 `template`（模板）、`base`（基础）、`addition`（附加）。原版用它做下界合金升级，我们也可以用它做「钻石镐 + 红宝石 = 红宝石镐」：

文件：`src/main/resources/data/dafeiyu/recipe/ruby_pickaxe_smithing.json`

```json
{
  "type": "minecraft:smithing_transform",
  "template": { "item": "minecraft:netherite_upgrade_smithing_template" },
  "base": { "item": "minecraft:diamond_pickaxe" },
  "addition": { "item": "dafeiyu:ruby" },
  "result": { "id": "dafeiyu:ruby_pickaxe", "count": 1 }
}
```

关键点：`smithing_transform` 会**保留 base 物品的全部数据组件**（附魔、改名、耐久损伤），只把物品本身换掉。这就是为什么下界合金装备升级后附魔还在。你用它做自定义升级，玩家辛苦攒的附魔也不会丢。

另外还有一个 `minecraft:smithing_trim`（盔甲纹饰），它**没有 `result` 字段**——结果是「在 base 上贴一层纹饰」，由游戏自己算。

## 七、`Ingredient` 的写法

「原料（ingredient）」是配方的输入单元。它有四种写法，能力从弱到强：

| 写法 | JSON | 含义 |
|---|---|---|
| 单个物品 | `{"item": "dafeiyu:ruby"}` | 只接受这一种物品 |
| 标签 | `{"tag": "dafeiyu:rubies"}` | 接受标签里的**任意**物品 |
| 数组 | `[{"item": "dafeiyu:ruby"}, {"item": "minecraft:diamond"}]` | 数组内任意一项匹配即可（OR） |
| 方块标签 | `{"type": "neoforge:block_tag", "tag": "minecraft:convertable_to_mud"}` | 用方块标签当原料，少见的场景 |

数组写法最实用。比如「红宝石或钻石都能做这把剑」：

```json
"key": {
  "R": [
    { "item": "dafeiyu:ruby" },
    { "item": "minecraft:diamond" }
  ]
}
```

标签写法是**模组互相兼容**的关键：你写 `{"tag": "c:gems"}`，别人往 `c:gems` 里塞了自己的宝石，你的配方就自动能吃他的材料，一行代码都不用改。自己建标签的方法见 [标签](08-标签.md)。

还有一个细节：原料里的 `count` **会被忽略**。`{"item": "minecraft:stick", "count": 8}` 和 `{"item": "minecraft:stick"}` 在配方里完全等价——「要 8 根木棍」必须靠在数组里写 8 次（有序配方则是在图案里放 8 个字符）。

## 八、用 `RecipeProvider` 生成配方

手写 JSON 最大的问题是：物品 id 打错、文件名和内容对不上、忘了写配方解锁进度。数据生成（datagen）能一次性解决这三件事。

datagen 的整体流程（`GatherDataEvent`、`PackOutput`、`runData`）在 [数据生成](05-数据生成.md) 里已经讲过，这一节只讲配方相关的部分。

先建一个 provider：

文件：`src/main/java/com/dafeiyu/datagen/ModRecipeProvider.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModBlocks;
import com.dafeiyu.ModItems;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.recipes.RecipeCategory;
import net.minecraft.data.recipes.RecipeOutput;
import net.minecraft.data.recipes.RecipeProvider;
import net.minecraft.data.recipes.ShapedRecipeBuilder;
import net.minecraft.data.recipes.ShapelessRecipeBuilder;

import java.util.concurrent.CompletableFuture;

public class ModRecipeProvider extends RecipeProvider {

    public ModRecipeProvider(PackOutput output, CompletableFuture<HolderLookup.Provider> registries) {
        super(output, registries);
    }

    @Override
    protected void buildRecipes(RecipeOutput recipeOutput) {
        // 3x3 红宝石 -> 红宝石块
        ShapedRecipeBuilder.shaped(RecipeCategory.BUILDING_BLOCKS, ModBlocks.RUBY_BLOCK.get())
                .pattern("RRR")
                .pattern("RRR")
                .pattern("RRR")
                .define('R', ModItems.RUBY.get())
                .unlockedBy("has_ruby", has(ModItems.RUBY.get()))
                .save(recipeOutput);

        // 红宝石块 -> 9 颗红宝石
        ShapelessRecipeBuilder.shapeless(RecipeCategory.MISC, ModItems.RUBY.get(), 9)
                .requires(ModBlocks.RUBY_BLOCK.get())
                .unlockedBy("has_ruby_block", has(ModBlocks.RUBY_BLOCK.get()))
                .save(recipeOutput, "ruby_from_ruby_block");
    }
}
```

逐段解释：

- `super(output, registries)`：`registries` 是 `CompletableFuture<HolderLookup.Provider>`，也就是「等注册表都填好了再给我」。配方里可能引用附魔、药水这类注册表对象，所以要等。
- `buildRecipes(RecipeOutput)`：你只重写这一个方法。`RecipeOutput` 不只是「写文件」，它还负责**顺手生成配方解锁进度**——这就是为什么你手写 JSON 时还得额外写 `advancement/recipes/...`，而 datagen 不用。
- `ShapedRecipeBuilder.shaped(分类, 结果)`：结果可以直接给 `ItemLike`（物品或方块），也可以给「物品 + 数量」。每次 `.pattern(...)` 加一行，每次 `.define(字符, 原料)` 定义一个字符。`.define` 的第二个参数可以是 `ItemLike`、`TagKey<Item>`，也可以是 `Ingredient`——所以「红宝石或钻石」要写成 `Ingredient.of(...)`。
- `unlockedBy(名字, 条件)`：**不能省**。省了 builder 会在生成时直接抛异常。它的语义是「玩家满足这个条件后，这个配方才会出现在配方书里」，`has(...)` 是最常用的条件（「背包里有这个物品」）。
- `.save(recipeOutput)`：文件名默认取结果物品的 id（这里是 `ruby_block.json`）。想改名就用两参数版本 `.save(recipeOutput, "自定义名字")`。

其余类型的 builder 一一对应（下面几段都写在 `ModRecipeProvider#buildRecipes` 里，紧跟在上面两个配方后面）：

```java
// 熔炉：SimpleCookingRecipeBuilder.smelting(原料, 分类, 结果, 经验, 时间)
SimpleCookingRecipeBuilder.smelting(
                Ingredient.of(ModBlocks.RUBY_ORE.get()),
                RecipeCategory.MISC,
                ModItems.RUBY.get(),
                0.7f,
                200)
        .unlockedBy("has_ruby_ore", has(ModBlocks.RUBY_ORE.get()))
        .save(recipeOutput, "ruby_from_smelting_ruby_ore");

// 高炉：把方法名换成 blasting；烟熏炉 smoking；营火 campfireCooking
SimpleCookingRecipeBuilder.blasting(
                Ingredient.of(ModBlocks.RUBY_ORE.get()),
                RecipeCategory.MISC,
                ModItems.RUBY.get(),
                0.7f,
                100)
        .unlockedBy("has_ruby_ore", has(ModBlocks.RUBY_ORE.get()))
        .save(recipeOutput, "ruby_from_blasting_ruby_ore");

// 切石机：SingleItemRecipeBuilder.stonecutting(原料, 分类, 结果, 数量)
// 假设你做过红宝石台阶，没有就换成任意你自己的方块物品
SingleItemRecipeBuilder.stonecutting(
                Ingredient.of(ModBlocks.RUBY_BLOCK.get()),
                RecipeCategory.BUILDING_BLOCKS,
                ModItems.RUBY_SLAB.get(),
                2)
        .unlockedBy("has_ruby_block", has(ModBlocks.RUBY_BLOCK.get()))
        .save(recipeOutput, "ruby_slab_from_stonecutting");

// 锻造台：注意参数顺序是 模板 -> 基础 -> 附加
SmithingTransformRecipeBuilder.smithing(
                Ingredient.of(Items.NETHERITE_UPGRADE_SMITHING_TEMPLATE),
                Ingredient.of(Items.DIAMOND_PICKAXE),
                Ingredient.of(ModItems.RUBY.get()),
                RecipeCategory.TOOLS,
                ModItems.RUBY_PICKAXE.get())
        .unlocks("has_ruby", has(ModItems.RUBY.get()))
        .save(recipeOutput, "ruby_pickaxe_smithing");
```

上面这几段要额外 import：`net.minecraft.data.recipes.SimpleCookingRecipeBuilder`、`net.minecraft.data.recipes.SingleItemRecipeBuilder`、`net.minecraft.data.recipes.SmithingTransformRecipeBuilder`、`net.minecraft.world.item.Items`、`net.minecraft.world.item.crafting.Ingredient`。

三个容易记混的地方：
1. 熔炉类 builder 的参数顺序是「原料、分类、结果、经验、时间」，**经验和时间在最后**，和 JSON 里的书写顺序不一样。
2. 锻造台的解锁方法叫 `unlocks`（带 s），不叫 `unlockedBy`。
3. `SingleItemRecipeBuilder`（切石机）只接受 `ItemLike` 结果，**不支持带数据组件的结果**。要给产物打附魔，只能手写 JSON 或自己写 builder。

最后把 provider 注册到 `GatherDataEvent`：

文件：`src/main/java/com/dafeiyu/datagen/DataGenerators.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import net.neoforged.bus.api.SubscribeEvent;
import net.neoforged.fml.common.EventBusSubscriber;
import net.neoforged.neoforge.data.event.GatherDataEvent;

@EventBusSubscriber(modid = DafeiyuMod.MOD_ID, bus = EventBusSubscriber.Bus.MOD)
public class DataGenerators {

    @SubscribeEvent
    public static void gatherData(GatherDataEvent event) {
        event.getGenerator().addProvider(
                event.includeServer(),                       // 服务端数据：配方、战利品表、标签、进度
                new ModRecipeProvider(event.getGenerator().getPackOutput(), event.getLookupProvider())
        );
    }
}
```

然后在项目根目录跑 `./gradlew runData`。生成的 JSON 会出现在 `src/generated/resources/data/dafeiyu/recipe/` 下，**不要手改这些文件**——下次生成会被覆盖。

## 九、条件配方：`neoforge:conditions`

有时候你希望「装了某个模组，这个配方才存在」。NeoForge 提供了数据加载条件：

```json
{
  "type": "minecraft:crafting_shaped",
  "neoforge:conditions": [
    { "type": "neoforge:mod_loaded", "modid": "create" },
    { "type": "neoforge:item_exists", "item": "create:brass_ingot" }
  ],
  "pattern": [" B ", "BRB", " B "],
  "key": {
    "B": { "item": "create:brass_ingot" },
    "R": { "item": "dafeiyu:ruby" }
  },
  "result": { "id": "dafeiyu:ruby_casing" }
}
```

条件数组是**与**关系：全部满足才加载。条件不满足时，整份配方文件被安静地跳过，不会报错。

用 datagen 时不要手写这个字段，而是用 `RecipeOutput#withConditions` 包一层：

```java
recipeOutput.withConditions(new ModLoadedCondition("create")).accept(...);
```

条件系统的完整写法见 [数据加载条件](/docs/neoforge-1.21.1/06-资源/03-服务端/02-数据加载条件.md)。

```text
src/generated/resources/data/dafeiyu/recipe/
├── ruby_block.json

├── ruby_from_blasting_ruby_ore.json

```

一份「手写版」的红宝石块配方，放在 `src/main/resources/data/dafeiyu/recipe/ruby_block.json`：

```json
{
  "type": "minecraft:crafting_shaped",
  "category": "building",
  "group": "ruby",
  "pattern": [
    "RRR",
    "RRR",
    "RRR"
  ],

  }

```

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 启动日志 `Couldn't parse recipe ... Pattern must be a rectangle` | `pattern` 三行长度不一致 | 用空格补齐，或统一缩短 |
| `Unknown recipe category` / 解析失败 | `category` 填了不存在的值 | 合成用 `building`/`redstone`/`equipment`/`misc`，熔炉用 `food`/`blocks`/`misc` |
| 配方在配方书里不显示，但手动摆能合 | 没写 `unlockedBy` 对应的解锁进度，或条件永远不满足 | datagen 补 `unlockedBy`；手写则补 `advancement/recipes/...` |
| 配方整个消失，日志 `Unknown item 'dafeiyu:ruby'` | 结果或原料的 id 写错/物品没注册 | 对着 `ModItems` 里的注册名逐字核对 |
| 引用了不存在的标签，配方失效 | 标签文件缺失，或路径写错 | 见 [标签](08-标签.md)，确认 `data/dafeiyu/tags/item/xxx.json` 存在 |
| 熔炉配方放进熔炉没反应 | 用了 `ingredient` 的单数/复数写错，或烟熏炉烧非食物 | 熔炉类必须是 `"ingredient": {...}`；烟熏炉只烧食物 |
| 拆包配方在 2×2 里合不出来 | 用了 `crafting_shaped` 的 3×3 图案 | 改成 `crafting_shapeless` |
| 生成时报 `Recipe provider must call unlockedBy` | builder 少了 `.unlockedBy(...)` | 每个 builder 至少补一个解锁条件 |
| 改了 JSON 但游戏里没变化 | 改的是 `src/generated/` 下被覆盖的文件 | 改 datagen 源码后重跑 `runData` |

## 练习

1. **照抄改**：把第二节的红宝石镐配方改成红宝石剑（图案 `R`、`R`、`S`），进游戏验证能合出来。
2. **加家族**：给红宝石块补齐高炉、烟熏炉、营火三种「同料」配方，思考哪两种其实没有游戏意义，为什么。
3. **用标签**：先按 [标签](08-标签.md) 建一个 `dafeiyu:rubies` 标签，然后把红宝石块的配方改成 `{"tag": "dafeiyu:rubies"}`，再往标签里加一个假想物品，观察配方是否自动接受。
4. **datagen 迁移**：把本节手写的 4 个 JSON 全部删掉，改用 `ModRecipeProvider` 生成，对比生成出来的 JSON 和你手写的有什么不同（提示：`neoforge:conditions` 和多出来的 advancement 文件）。
