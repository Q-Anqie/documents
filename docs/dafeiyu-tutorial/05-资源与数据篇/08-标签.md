# 标签

> 读完这篇，你能自己定义「红宝石」这一类物品，让配方、战利品表、工具挖掘规则都能「泛指一类」而不是逐个列举，并且知道 1.21 把标签目录改名这件事会怎么坑到你。

## 学习目标

- 能用自己的话解释标签是什么，以及它和「物品列表」的区别。
- 能说出五个以上原版常用标签（`minecraft:planks`、`minecraft:swords`、`minecraft:mineable/pickaxe` 等）分别被谁用。
- 能写出合法的标签 JSON，并解释 `values`、`replace`、`remove` 三个字段。
- 能记住 1.21 的目录是 `tags/item`（单数），并解释为什么 `tags/items` 会静默失效。
- 能在代码里用 `TagKey` + `stack.is(...)` 做成员判断，也能用 `TagsProvider` 自动生成标签。
- 能说清「把物品加进 `minecraft:planks` 就能用原版配方」背后的机制。

## 一、标签是什么

标签（tag）是**同一类注册表对象的分组名单**。它是数据文件，不是代码；它给一组物品、方块、实体类型、流体等起一个共同的名字，让其它数据可以「泛指一类」。

举个最熟悉的例子：木棍的配方是「两块任意木板竖着放」。原版并没有写 11 份配方（橡木、云杉、白桦……），而是写了一份：

```json
{
  "type": "minecraft:crafting_shaped",
  "pattern": ["#", "#"],
  "key": { "#": { "tag": "minecraft:planks" } },
  "result": { "id": "minecraft:stick", "count": 4 }
}
```

`{"tag": "minecraft:planks"}` 的意思是「`minecraft:planks` 这个标签里的任何一个物品都行」。原版把 11 种木板都登记进了这个标签，所以一份配方就覆盖了所有木头。

**为什么需要它？** 三个理由：

1. **不用重复写**。11 种木板写 11 份配方，加一种木头就要再加一份。
2. **别人能扩展**。你写「任意木板」，别的模组加了一种新木头，只要把自己的木板加进 `minecraft:planks`，你的配方立刻就能用它——双方都不用改代码。
3. **代码里能问「是不是这一类」**。比如「拿任意剑右键时触发技能」，判断的是「这个物品在 `minecraft:swords` 里吗」，而不是 `if (stack.is(SWORD) || stack.is(AXE) || ...)`。

标签和「物品列表」的区别只有一个：**标签是数据，可以在不重编译的情况下被数据包改写；物品列表是代码，改一次要重新构建**。

## 二、内置常用标签

写模组时，先查有没有现成的，别急着造新的。常用的这些：

### 2.1 物品标签（`ItemTags` 类）

| 标签 | 内容 | 谁在用 |
|---|---|---|
| `minecraft:planks` | 所有木板 | 木棍、箱子、工作台等大量配方 |
| `minecraft:logs` | 所有原木 | 木炭烧制、营火配方 |
| `minecraft:wool` | 所有羊毛 | 床、地毯、画 |
| `minecraft:swords` | 所有剑 | 剑的附魔、部分进度、属性判断 |
| `minecraft:pickaxes` / `axes` / `shovels` / `hoes` | 各类工具 | 工具附魔、`enchantable/*` 的判定 |
| `minecraft:coals` | 煤炭与木炭 | 燃料判定 |
| `minecraft:creeper_drop_music_discs` | 苦力怕该掉哪些唱片 | 苦力怕战利品表 |
| `c:ingots` / `c:gems` / `c:raw_materials` | 跨模组统一的锭/宝石/原矿 | 其它模组的配方兼容 |
| `c:storage_blocks` | 跨模组统一的存储方块 | 同上 |

注意 `c:` 这个命名空间：它是 NeoForge 和 Fabric **共用**的「通用标签」命名空间，专门用来做跨模组兼容。你要加一种新金属，正确的做法是同时提供 `c:ingots/ruby` 和 `c:ingots`。

### 2.2 方块标签（`BlockTags` 类）

| 标签 | 含义 |
|---|---|
| `minecraft:mineable/pickaxe` | 用镐挖更快 |
| `minecraft:mineable/axe` | 用斧挖更快 |
| `minecraft:needs_iron_tool` | 木/石镐挖了不掉落，需要铁镐及以上 |
| `minecraft:incorrect_for_iron_tool` | 铁镐挖了不掉落（工具等级标签） |
| `minecraft:logs` / `planks` | 方块版的同名标签 |
| `minecraft:dirt` | 泥土类，用于草方块蔓延等 |

`mineable/*` 和 `needs_*_tool` 是**两套独立的标签**，很多人只加了前者，结果「挖得动但挖了不掉」——因为掉落与否由 `needs_*_tool`（或者自定义的 `incorrect_for_*`）决定，速度由 `mineable/*` 决定。

### 2.3 其它注册表的标签

标签不限于物品和方块。流体（`minecraft:water`）、实体类型（`minecraft:sensitive_to_smite`）、伤害类型、附魔、生物群系、结构，全都有标签。只要一个注册表里的东西需要「分组」，就会有标签。

## 三、标签 JSON 的格式

文件位置规则：

```text
data/<标签所属命名空间>/tags/<注册表名>/<标签名>.json
```

举例，`minecraft:planks` 这个物品标签，你要往里面加东西，就放在：

```text
src/main/resources/data/minecraft/tags/item/planks.json
```

注意两点：

1. 目录名是**标签的命名空间**（`minecraft`），不是你的模组 id。你想改原版标签，就要写进 `data/minecraft/`。
2. 注册表名是 **`item`（单数）**，方块是 `block`（单数）。1.21 之前是 `items` / `blocks`，**1.21 改了**。

文件内容：

```json
{
  "values": [
    "dafeiyu:ruby",
    { "id": "dafeiyu:ruby_shard", "required": false },
    "#c:gems"
  ],
  "replace": false,
  "remove": [
    "minecraft:diamond"
  ]
}
```

三个字段：

- `values`：条目数组。每一项有三种写法：
  - `"dafeiyu:ruby"`：一个 id，**必须存在**，不存在则整个标签加载失败。
  - `{"id": "dafeiyu:ruby_shard", "required": false}`：可选条目，不存在就跳过。给「可能装了也可能没装的模组」用。
  - `"#c:gems"`：**标签引用**，前面加 `#`，表示「把 `c:gems` 里的所有东西也算进来」。标签可以嵌套，但**不能循环**（A 引用 B，B 又引用 A），循环会导致整个数据包加载失败。
- `replace`：默认 `false`，表示「追加到已有内容后面」。设为 `true` 表示「先清空别人写的，只留我的」。**几乎永远应该保持 false**，第六节详细说。
- `remove`：NeoForge 加的字段，从标签里剔除指定条目。这是「我只想去掉钻石，不想清空整个标签」的正确做法。

## 四、1.21 的目录变化：`tags/item` 不是 `tags/items`

这是升级到 1.21 后最阴的一个坑，因为它**不报错**。

| 版本 | 物品标签目录 | 方块标签目录 |
|---|---|---|
| 1.20 及以前 | `data/<ns>/tags/items/` | `data/<ns>/tags/blocks/` |
| **1.21 起** | `data/<ns>/tags/item/` | `data/<ns>/tags/block/` |

如果你从旧教程抄了 `tags/items/rubies.json`，游戏会把它当成「一个叫 `items` 的注册表下、名为 `rubies` 的标签」，而这个注册表根本不存在，于是这个文件被**完全忽略**。日志里通常只有一行不起眼的 `Skipping unknown tag` 之类，很容易漏掉。

结果就是：标签文件明明在那儿，`stack.is(ModTags.Items.RUBIES)` 却永远返回 `false`，配方里的 `{"tag": "dafeiyu:rubies"}` 永远匹配不上。

**排查口诀**：先看目录是不是单数，再看文件名（标签名）是不是和代码里的 `TagKey` 完全一致。

## 五、自定义标签：`dafeiyu:rubies`

### 5.1 先写标签文件

文件：`src/main/resources/data/dafeiyu/tags/item/rubies.json`

```json
{
  "values": [
    "dafeiyu:ruby"
  ]
}
```

就这么多。文件名 `rubies` 就是标签名，命名空间是 `dafeiyu`，所以完整 id 是 `dafeiyu:rubies`。

命名约定：**用复数**（`planks`、`ingots`、`rubies`）。同类型多层级时用文件夹，比如 `c:ingots/ruby` 和 `c:ingots`。

> 如果你跟着 [数据生成](05-数据生成.md) 建过 `ModTags`，那里用的是 `RUBY_GEMS` / `ruby_gems`。名字本身没有对错，全章统一成 `rubies` 就行——改代码里的字符串和文件名两个地方，别只改一个。

### 5.2 在代码里引用它

标签在代码里用 `TagKey<T>` 表示。`TagKey` 是一个「标签的钥匙」——它只存「哪个注册表 + 哪个资源位置」，不存内容。内容要等世界加载、数据包读完才有。

文件：`src/main/java/com/dafeiyu/ModTags.java`

```java
package com.dafeiyu;

import net.minecraft.core.registries.Registries;
import net.minecraft.resources.ResourceLocation;
import net.minecraft.tags.TagKey;
import net.minecraft.world.item.Item;
import net.minecraft.world.level.block.Block;

public class ModTags {

    public static class Items {
        /** 所有「红宝石类」物品，对应 data/dafeiyu/tags/item/rubies.json */
        public static final TagKey<Item> RUBIES = create("rubies");

        private static TagKey<Item> create(String name) {
            return TagKey.create(
                    Registries.ITEM,                                        // 这个标签属于哪个注册表
                    ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, name));
        }
    }

    public static class Blocks {
        /** 所有红宝石类方块，对应 data/dafeiyu/tags/block/ruby_blocks.json */
        public static final TagKey<Block> RUBY_BLOCKS = TagKey.create(
                Registries.BLOCK,
                ResourceLocation.fromNamespaceAndPath(DafeiyuMod.MOD_ID, "ruby_blocks"));
    }
}
```

三个细节：

- `Registries.ITEM` 是注册表的**键**，不是注册表本身。`TagKey.create` 要的是键。
- 泛型 `<Item>` 必须和注册表匹配。`TagKey<Block>` 配 `Registries.BLOCK`，写错了编译期不报错，运行期会炸。
- `TagKey` 是 record，构造器是公开的，但**不要直接 `new`**——必须用 `create`，否则内部缓存会失效。

### 5.3 判断「是不是这一类」

```java
// 物品堆：这个物品在不在标签里
if (stack.is(ModTags.Items.RUBIES)) {
    // 是红宝石类物品
}

// 方块状态：这个方块在不在方块标签里
if (level.getBlockState(pos).is(ModTags.Blocks.RUBY_BLOCKS)) {
    // 是红宝石类方块
}
```

`ItemStack#is(TagKey<Item>)` 和 `BlockState#is(TagKey<Block>)` 是标签系统最常用的两个入口，它们内部就是查一次标签集合，很快。

需要遍历标签内容时：

```java
Stream<Item> all = BuiltInRegistries.ITEM.getOrCreateTag(ModTags.Items.RUBIES).stream();
```

注意这个方法**只在标签加载完之后才有内容**。如果你在静态初始化块里调用它，拿到的是空流——那时候数据包还没读。

## 六、用 `TagsProvider` 生成标签

手写标签文件和手写配方有一模一样的问题：id 打错、目录放错、忘了加新物品。datagen 能治。

### 6.1 物品标签

文件：`src/main/java/com/dafeiyu/datagen/ModItemTagsProvider.java`

```java
package com.dafeiyu.datagen;

import com.dafeiyu.DafeiyuMod;
import com.dafeiyu.ModItems;
import com.dafeiyu.ModTags;
import net.minecraft.core.HolderLookup;
import net.minecraft.data.PackOutput;
import net.minecraft.data.tags.ItemTagsProvider;
import net.minecraft.data.tags.TagsProvider;
import net.minecraft.resources.ResourceLocation;
import net.minecraft.tags.ItemTags;
import net.minecraft.world.level.block.Block;
import net.neoforged.neoforge.common.data.ExistingFileHelper;

import java.util.concurrent.CompletableFuture;

public class ModItemTagsProvider extends ItemTagsProvider {

    public ModItemTagsProvider(PackOutput output,
                               CompletableFuture<HolderLookup.Provider> lookupProvider,
                               CompletableFuture<TagsProvider.TagLookup<Block>> blockTags,
                               ExistingFileHelper existingFileHelper) {
        super(output, lookupProvider, blockTags, DafeiyuMod.MOD_ID, existingFileHelper);
    }

    @Override
    protected void addTags(HolderLookup.Provider provider) {
        // 自己的标签
        tag(ModTags.Items.RUBIES)
                .add(ModItems.RUBY.get())
                .addOptional(ResourceLocation.fromNamespaceAndPath("othermod", "ruby"));

        // 加进原版标签（假设你后来做了红宝石木板）
        // tag(ItemTags.PLANKS).add(ModItems.RUBY_PLANKS.get());

        // 物品标签镜像方块标签：方块在 RUBY_BLOCKS 里，对应的物品也在 RUBY_BLOCKS 里
        copy(ModTags.Blocks.RUBY_BLOCKS, ModTags.Items.RUBY_BLOCKS);
    }
}
```

- `tag(TagKey)` 返回一个 `TagAppender`，可以链式 `.add(...)`、`.addTag(...)`、`.addOptional(...)`、`.remove(...)`。
- `ItemTagsProvider` 是「内在提供器（intrinsic provider）」，可以直接传 `Item` / `Block` 对象，不用手动构造 `ResourceKey`。这是它比通用 `TagsProvider` 好用的地方。
- `copy(方块标签, 物品标签)`：把方块标签的内容原样复制到物品标签。绝大多数方块都有同名物品（`BlockItem`），这个镜像关系是刚需，手动维护两份迟早会漏。
- `addOptional`：加一个「可能不存在」的 id。别的模组没装时它会被跳过，不会导致标签加载失败。

### 6.2 注册到 `GatherDataEvent`

`ItemTagsProvider` 需要一个「方块标签的结果」作为输入（因为 `copy` 要用），所以**必须先注册方块标签 provider**：

```java
BlockTagsProvider blockTags = new ModBlockTagsProvider(output, lookupProvider, existingFileHelper);
generator.addProvider(event.includeServer(), blockTags);
generator.addProvider(event.includeServer(),
        new ModItemTagsProvider(output, lookupProvider, blockTags.contentsGetter(), existingFileHelper));
```

`blockTags.contentsGetter()` 返回一个 `CompletableFuture<TagLookup<Block>>`，正是 `ItemTagsProvider` 构造器要的第三个参数。顺序反了会拿到一个永远不完成的 future，`runData` 卡住不动。

## 七、为什么「加进 `minecraft:planks` 就能用原版配方」

回到第一节的例子：木棍的配方写的是 `{"tag": "minecraft:planks"}`。配方加载时，`Ingredient` 并不会「展开」成 11 个物品——它保存的是**标签的引用**，每次匹配时现查标签内容。

所以只要你的物品出现在 `minecraft:planks` 的成员列表里，它就自动满足了木棍配方、箱子配方、工作台配方、船配方……所有用「任意木板」的地方。

而标签文件是**合并**的，不是覆盖的：

> 如果两个数据包都提供了 `minecraft:planks` 这个标签文件，它们的内容会被**合并**（除非某个文件写了 `"replace": true`）。

这就是为什么你可以只写：

文件：`src/main/resources/data/minecraft/tags/item/planks.json`

```json
{
  "values": [
    "dafeiyu:ruby_planks"
  ]
}
```

而不需要把 11 种原版木板重新列一遍。你的文件只负责「加一个」，原版的 11 个还在。

**这就是 `replace` 危险的地方**：你一旦写成 `"replace": true`，原版的 11 种木板就从这个标签里消失了，全游戏的木棍、箱子、工作台配方同时失效——而且不报错，只是「合不出来」。所以 `replace` 只该在「我要彻底重做这个标签」时使用，比如做整合包时故意禁用某些配方。

## 完整示例

```text
src/main/java/com/dafeiyu/
├── ModTags.java                     ← 5.2 节
└── datagen/
    ├── DataGenerators.java          ← 6.2 节
    ├── ModBlockTagsProvider.java    ← 方块标签（结构同上）
    └── ModItemTagsProvider.java     ← 6.1 节

src/main/resources/data/dafeiyu/tags/
├── item/rubies.json                 ← 5.1 节
└── block/ruby_blocks.json

src/main/resources/data/minecraft/tags/item/
└── planks.json                      ← 第七节，往原版标签里加东西
```

一份完整的自定义标签文件（`data/dafeiyu/tags/item/rubies.json`），带可选条目和标签引用：

```json
{
  "values": [
    "dafeiyu:ruby",
    {
      "id": "dafeiyu:ruby_shard",
      "required": false
    },
    "#c:gems"
  ]
}
```

配套的用法：

```java
// 任意「红宝石类」物品都能修红宝石工具
public class RubyRepairRecipeCheck {
    public static boolean canRepair(ItemStack tool, ItemStack material) {
        return material.is(ModTags.Items.RUBIES);
    }
}
```

验证步骤：

1. 进游戏，`/give @s dafeiyu:ruby`。
2. 按 `F3 + H` 打开高级提示框，把鼠标放到红宝石上，物品 id 下面会多出一行 `#dafeiyu:rubies`——这就是「它在标签里」的可视化证据。
3. 改一下 `ModTags.Items.RUBIES` 的名字（比如改成 `ruby`），重进游戏，那一行会消失，`stack.is(...)` 返回 false。这是验证「代码和文件对不对得上」最快的方法。

## 常见坑与报错

| 现象 | 原因 | 解决 |
|---|---|---|
| 标签文件在，但 `stack.is(...)` 永远是 false | 目录写成了 `tags/items/`（1.20 写法） | 1.21 改成 `tags/item/` |
| 同上，目录对了 | 标签名和 `TagKey` 里的名字不一致（`rubies` vs `ruby`） | 文件名必须和 `create("...")` 的字符串逐字相同 |
| 启动报 `Failed to load tag ... could not find item` | `values` 里有写错/未注册的 id，且没标 `required: false` | 改成 `{"id": "...", "required": false}`，或修好 id |
| 加了自己的木板进 `minecraft:planks`，原版配方全崩了 | 文件里写了 `"replace": true` | 删掉 `replace`，或改成 `false` |
| `runData` 卡住不动 | 物品标签 provider 注册在方块标签 provider 之前 | 先 `addProvider(blockTags)`，再传 `blockTags.contentsGetter()` |
| 数据包加载失败，日志提到 `circular` | 标签互相引用成环（A 引用 B，B 引用 A） | 拆掉一环，让引用变成单向 |
| 方块挖得动但什么都不掉 | 只加了 `mineable/pickaxe`，没加 `needs_*_tool` 或工具等级标签 | 两套标签都要加，见 [战利品表](07-战利品表.md) |
| 改了标签但游戏里没生效 | 单机没重载数据包 | 用 `/reload`，或退回主菜单重进世界 |

## 练习

1. **建标签**：给 `dafeiyu:ruby` 建一个 `dafeiyu:rubies` 物品标签，用 `F3 + H` 确认游戏认到了它。
2. **改配方**：把 [配方](06-配方.md) 里红宝石块的配方从 `{"item": "dafeiyu:ruby"}` 改成 `{"tag": "dafeiyu:rubies"}`，再往标签里加一个假想物品 `dafeiyu:ruby_shard`（`required: false`），观察配方是否自动接受。
3. **镜像标签**：给红宝石方块建一个 `dafeiyu:ruby_blocks` 方块标签，用 `copy(...)` 生成对应的物品标签，打开生成的两个 JSON 对比内容。
4. **故意犯错**：把 `tags/item` 改成 `tags/items`，重进游戏，写下你在日志里看到的第一条相关警告——以后遇到「标签不生效」时，这就是你要找的那一行。
