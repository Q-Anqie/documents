# 版本管理

本文详细说明 Minecraft 与 NeoForge 中版本号的工作方式，并给出一些关于模组版本号的建议。

## Minecraft

Minecraft 使用[语义化版本][semver]。语义化版本（简称 "semver"）的格式为 `major.minor.patch`。因此，例如 Minecraft 1.20.2 的主版本号为 1，次版本号为 20，修订版本号为 2。

Minecraft 自 2011 年推出 Minecraft 1.0 起，就一直把 `1` 作为主版本号。在此之前，版本号方案经常变动，曾出现过 `a1.1`（Alpha 1.1）、`b1.7.3`（Beta 1.7.3），甚至完全不遵循明确版本方案的各种 `infdev` 版本。由于 `1` 这个主版本号已经沿用了十多年，再加上"Minecraft 2"这个内部玩笑，一般认为它不太可能再改变。

### 快照

快照偏离了标准的 semver 方案。它们的标记形式为 `YYwWWa`，其中 `YY` 表示年份的后两位（例如 `23`），`WW` 表示该年的第几周（例如 `01`）。因此，快照 `23w01a` 就是 2023 年第一周发布的快照。

`a` 后缀用于同一周内发布两个快照的情况（此时第二个快照会被命名为类似 `23w01b` 的形式）。Mojang 过去偶尔使用过这一做法。另一种后缀也曾被用于 `20w14infinite` 这样的快照，即 [2020 年无限维度愚人节玩笑][infinite]。

### 预发布版与候选发布版

当一个快照周期接近完成时，Mojang 开始发布所谓的预发布版（pre-release）。预发布版被认为在功能上已经完整，只专注于修复漏洞。它们使用对应版本的 semver 记法，并加上 `-preX` 后缀。例如，1.20.2 的第一个预发布版名为 `1.20.2-pre1`。预发布版可以有多个，而且通常确实有多个，相应地加上 `-pre2`、`-pre3` 等后缀。

同样地，当预发布周期结束时，Mojang 会发布候选发布版 1（Release Candidate 1，在版本号后加 `-rc1`，例如 `1.20.2-rc1`）。Mojang 的目标是只有一个候选发布版，若没有更多漏洞就可以直接发布。但如果出现了意料之外的漏洞，也可能会有 `-rc2`、`-rc3` 等版本，与预发布版类似。

## NeoForge

NeoForge 使用一套改编过的 semver 体系：主版本号是 Minecraft 的次版本号，次版本号是 Minecraft 的修订版本号，修订版本号则是"实际的" NeoForge 版本号。因此，NeoForge 20.2.59 是 Minecraft 1.20.2 的第 60 个版本（从 0 开始计数）。开头的 `1` 被省略，因为它极不可能改变，原因见[上文][minecraft]。

NeoForge 中还有少数地方使用 [Maven 版本范围][mvr]，例如 [`neoforge.mods.toml`][neoforgemodstoml] 文件中的 Minecraft 与 NeoForge 版本范围。这些范围与 semver 大部分兼容，但并非完全兼容（例如它不考虑 `pre` 标记）。

## 模组

不存在绝对最佳的版本号体系。不同的开发风格、项目范围等都会影响选用哪种版本号体系。有时，版本号体系也可以组合使用。本节尝试概述一些常用的版本号体系，并给出真实案例。

通常，模组文件名形如 `modid-<version>.jar`。因此，如果我们的模组 id 是 `examplemod`、版本是 `1.2.3`，模组文件就命名为 `examplemod-1.2.3.jar`。

> **注意**
> 版本号体系只是建议，而非强制执行的规则。在何时变更（"bump"）版本号以及如何变更方面尤其如此。如果你想使用别的版本号体系，没人会阻止你。

### 语义化版本

语义化版本（"semver"）由三部分组成：`major.minor.patch`。当代码库发生重大变更时提升主版本号，这通常对应重要的新功能与漏洞修复。引入次要功能时提升次版本号，而修订版本号的提升发生在更新仅包含漏洞修复时。

普遍认为任何 `0.x.x` 版本都是开发版本，在首次（完整）发布时，版本号应提升至 `1.0.0`。

"功能提升次版本、修复提升修订版本"这条规则在实践中常被忽略。一个流行的例子就是 Minecraft 本身：它通过次版本号做重要功能，通过修订版本号做次要功能，而漏洞修复放在快照中（见上文）。

视模组更新频率不同，这些数字可能较小或较大。例如，[Supplementaries][supplementaries] 的版本为 `2.6.31`（撰写本文时）。三位甚至四位数是完全可能的，尤其是在 `patch` 位上。

### "缩减"与"扩展" semver

有时 semver 只由两个数字组成。这是一种"缩减"的 semver，或称"两段式" semver。其版本号只有 `major.minor` 方案。这通常被那些只添加少量简单对象、因而很少需要更新（除 Minecraft 版本更新外）的小型模组使用，往往永远停留在 `1.0` 版本。

"扩展" semver，或称"四段式" semver，有四个数字（例如 `1.0.0.0`）。视模组而定，格式可以是 `major.api.minor.patch`，也可以是 `major.minor.patch.hotfix`，或者完全不同的形式——没有标准做法。

对于 `major.api.minor.patch`，`major` 版本与 `api` 版本是解耦的。这意味着 `major`（功能）位和 `api` 位可以独立提升。这通常被那些对外提供 API 供其他模组作者使用的模组采用。例如，[Mekanism][mekanism] 当前版本为 10.4.5.19（撰写本文时）。

对于 `major.minor.patch.hotfix`，修订级别被拆分为两部分。这是 [Create][create] 模组采用的方式，它当前版本为 0.5.1f（撰写本文时）。注意 Create 用字母而非第四位数字表示 hotfix，以保持与常规 semver 兼容。

> **说明**
> 缩减 semver、扩展 semver、两段式 semver 与四段式 semver 都不是官方术语，也并非任何标准化的格式。

### Alpha、Beta、Release

与 Minecraft 本身一样，模组开发通常也遵循软件工程中经典的 `alpha`/`beta`/`release` 阶段：`alpha` 表示不稳定/实验性版本（有时也称为 `experimental` 或 `snapshot`），`beta` 表示半稳定版本，`release` 表示稳定版本（有时用 `stable` 代替 `release`）。

有些模组用主版本号表示 Minecraft 版本更替。一个例子是 [JEI][jei]，它对 Minecraft 1.19.2 使用 `13.x.x.x`，对 1.19.4 使用 `14.x.x.x`，对 1.20.1 使用 `15.x.x.x`（1.19.3 和 1.20.0 没有对应版本）。另一些则在模组名后附加标记，例如 [Minecolonies][minecolonies] 模组，撰写本文时版本为 `1.1.328-BETA`。

### 包含 Minecraft 版本

在文件名中包含模组所对应的 Minecraft 版本很常见。这能让终端用户更容易弄清模组适用于哪个 Minecraft 版本。常见的位置是在模组版本之前或之后，前者比后者更普遍。例如，JEI 面向 1.20.2 的版本 `16.0.0.28`（撰写本文时的最新版）会变成 `jei-1.20.2-16.0.0.28` 或 `jei-16.0.0.28-1.20.2`。

### 包含模组加载器

你大概知道，NeoForge 并非唯一的模组加载器，许多模组开发者会在多个平台上开发。因此，需要一种方式来区分同一模组、同一版本但面向不同模组加载器的两个文件。

通常的做法是在名称中某处包含模组加载器。`jei-neoforge-1.20.2-16.0.0.28`、`jei-1.20.2-neoforge-16.0.0.28` 或 `jei-1.20.2-16.0.0.28-neoforge` 都是有效写法。对于其他模组加载器，把 `neoforge` 部分替换为 `forge`、`fabric`、`quilt` 或你在 NeoForge 之外同时开发的任何加载器即可。

### 关于 Maven 的说明

Maven 是用于托管依赖的系统，它使用的版本号体系在某些细节上与 semver 不同（不过大体的 `major.minor.patch` 模式仍然相同）。相关的 [Maven 版本范围（MVR）][mvr] 体系在 NeoForge 的某些地方被使用（见[上文][neoforge]）。在选择版本号方案时，应确保它与 MVR 兼容，否则其他模组将无法依赖你模组的特定版本！
