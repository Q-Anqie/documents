# 游戏测试

游戏测试（Game Test）是一种运行游戏内单元测试的方式。该系统在设计上可扩展且可并行，以便高效地运行大量不同的测试。测试对象交互与行为只是该框架众多应用中的一小部分。

## 创建游戏测试

一个标准的游戏测试遵循三个基本步骤：

1. 加载一个结构（或称模板），其中持有用于测试交互或行为的场景。
1. 一个方法执行要在该场景上进行的逻辑。
1. 该方法的逻辑被执行。如果达到成功状态，则测试成功。否则测试失败，结果会存储到场景旁的书与笔中（讲台）。

因此，要创建游戏测试，必须存在一个持有场景初始起始状态的模板，以及一个提供执行逻辑的方法。

### 测试方法

游戏测试方法是一个 `Consumer<GameTestHelper>` 引用，意味着它接收一个 `GameTestHelper` 且不返回任何内容。要被识别为游戏测试方法，它必须带有 `@GameTest` 注解：

```java
public class ExampleGameTests {
    @GameTest
    public static void exampleTest(GameTestHelper helper) {
        // Do stuff
    }
}
```

`@GameTest` 注解还包含用于配置游戏测试应如何运行的成员。

```java
// In some class
@GameTest(
    setupTicks = 20L, // The test spends 20 ticks to set up for execution
    required = false // The failure is logged but does not affect the execution of the batch
)
public static void exampleConfiguredTest(GameTestHelper helper) {
    // Do stuff
}
```

#### 相对定位

所有 `GameTestHelper` 方法都会使用结构方块的当前位置，将结构模板场景内的相对坐标转换为其绝对坐标。为便于在相对定位与绝对定位之间转换，可以分别使用 `GameTestHelper#absolutePos` 和 `GameTestHelper#relativePos`。

结构模板的相对位置可以在游戏内获取：通过[测试命令][test]加载该结构，将玩家放到想要的位置，最后运行 `/test pos` 命令。这会抓取玩家相对于其 200 格内最近结构的坐标。该命令会将相对位置作为可复制的文本组件导出到聊天栏，用作最终的局部变量。

> **提示**
>
> 由 `/test pos` 生成的局部变量可以通过在命令末尾附加内容来指定其引用名：
>
> ```bash
> /test pos <var> # Exports 'final BlockPos <var> = new BlockPos(...);'
> ```

#### 成功完成

游戏测试方法只负责一件事：在有效完成时标记测试成功。如果在超时（由 `GameTest#timeoutTicks` 定义）之前未达到成功状态，则测试自动失败。

`GameTestHelper` 中有许多抽象方法可用于定义成功状态；不过有四个方法极其重要，需要了解。

方法                 | 描述
:---:                | :---
`#succeed`           | 测试被标记为成功。
`#succeedIf`         | 立即测试所提供的 `Runnable`，如果未抛出 `GameTestAssertException` 则成功。如果测试未在当前 tick 成功，则被标记为失败。
`#succeedWhen`       | 每个 tick 都测试所提供的 `Runnable`，直到超时；如果在某个 tick 上的检查未抛出 `GameTestAssertException` 则成功。
`#succeedOnTickWhen` | 在指定 tick 上测试所提供的 `Runnable`，如果未抛出 `GameTestAssertException` 则成功。如果该 `Runnable` 在任何其他 tick 成功，则被标记为失败。

> **警告**
>
> 游戏测试会每个 tick 执行一次，直到测试被标记为成功。因此，在给定 tick 上安排成功的方法必须小心，确保在任何更早的 tick 上都失败。

#### 安排操作

并非所有操作都会在测试开始时发生。操作可以被安排为在特定时间或间隔执行：

方法             | 描述
:---:            | :---
`#runAtTickTime` | 该操作在指定 tick 上执行。
`#runAfterDelay` | 该操作在当前 tick 之后 `x` 个 tick 执行。
`#onEachTick`    | 该操作每个 tick 都执行。

#### 断言

在游戏测试期间的任何时候，都可以进行断言以检查给定条件是否为真。`GameTestHelper` 中有许多断言方法；不过归根结底，它们在未满足相应状态时就是抛出 `GameTestAssertException`。

### 生成的测试方法

如果游戏测试方法需要动态生成，可以创建测试方法生成器。这些方法不接收参数，并返回 `TestFunction` 的集合。要被识别为测试方法生成器，它必须带有 `@GameTestGenerator` 注解：

```java
public class ExampleGameTests {
    @GameTestGenerator
    public static Collection<TestFunction> exampleTests() {
        // Return a collection of TestFunctions
    }
}
```

#### TestFunction

`TestFunction` 是 `@GameTest` 注解所持有的装箱信息，以及运行测试的方法。

> **提示**
>
> 任何使用 `@GameTest` 注解的方法都会通过 `GameTestRegistry#turnMethodIntoTestFunction` 转换为 `TestFunction`。该方法可作为在不使用注解的情况下创建 `TestFunction` 的参考。

### 批处理

游戏测试可以按批执行，而非按注册顺序执行。只要提供相同的 `GameTest#batch` 字符串，测试就会被加入同一批。

批处理本身并不提供什么有用的东西。不过，批处理可用于在测试所运行的当前维度上执行设置与清理状态。这通过在方法上标注 `@BeforeBatch`（用于设置）或 `@AfterBatch`（用于清理）来完成。`#batch` 方法必须与提供给游戏测试的字符串匹配。

批处理方法是 `Consumer<ServerLevel>` 引用，意味着它们接收一个 `ServerLevel` 且不返回任何内容：

```java
public class ExampleGameTests {
    @BeforeBatch(batch = "firstBatch")
    public static void beforeTest(ServerLevel level) {
        // Perform setup
    }

    @GameTest(batch = "firstBatch")
    public static void exampleTest2(GameTestHelper helper) {
        // Do stuff
    }
}
```

## 注册游戏测试

游戏测试必须注册后才能在游戏内运行。有两种注册方式：通过 `@GameTestHolder` 注解或 `RegisterGameTestsEvent`。两种注册方式仍然要求测试方法带有 `@GameTest`、`@GameTestGenerator`、`@BeforeBatch` 或 `@AfterBatch` 注解。

### GameTestHolder

`@GameTestHolder` 注解会注册该类型（类、接口、枚举或记录）内的任何测试方法。`@GameTestHolder` 包含一个具有多种用途的方法。在此场景下，所提供的 `#value` 必须是该模组的模组 id；否则在默认配置下测试不会运行。

```java
@GameTestHolder(MODID)
public class ExampleGameTests {
    // ...
}
```

### RegisterGameTestsEvent

`RegisterGameTestsEvent` 也可以通过 `#register` 注册类或方法。事件监听器必须[添加][event]到模组事件总线。以这种方式注册的测试方法必须在每个带有 `@GameTest` 注解的方法上通过 `GameTest#templateNamespace` 提供其模组 id。

```java
// In some event handler class
@SubscribeEvent  // on the mod event bus
public static void registerTests(RegisterGameTestsEvent event) {
    event.register(ExampleGameTests.class);
}

// In ExampleGameTests
@GameTest(templateNamespace = MODID)
public static void exampleTest3(GameTestHelper helper) {
    // Perform setup
}
```

> **注意**
>
> 提供给 `GameTestHolder#value` 和 `GameTest#templateNamespace` 的值可以与当前模组 id 不同。此时需要修改[构建脚本][namespaces]中的配置。

## 结构模板

> 相关 Minecraft Wiki：[生成结构](https://zh.minecraft.wiki/w/生成结构)

游戏测试在由结构（或称模板）加载的场景中执行。所有模板都定义了场景的尺寸以及将要加载的初始数据（方块和实体）。模板必须以 `.nbt` 文件形式存储在 `data/<namespace>/structure` 中。

> **提示**
>
> 可以使用结构方块创建并保存结构模板。

模板的位置由几个因素决定：

- 是否指定了模板的命名空间。
- 是否应将类名前置到模板名称。
- 是否指定了模板名称。

模板的命名空间由 `GameTest#templateNamespace` 决定；若未指定，则由 `GameTestHolder#value` 决定；若两者都未指定，则为 `minecraft`。

如果 `@PrefixGameTestTemplate` 应用于带有测试注解的类或方法并设为 `false`，则简单类名不会前置到模板名称。否则，简单类名会被转为小写并前置，且后面跟一个点，再接模板名称。

模板名称由 `GameTest#template` 决定。若未指定，则改用方法名的小写形式。

```java
// Modid for all structures will be MODID
@GameTestHolder(MODID)
public class ExampleGameTests {

    // Class name is prepended, template name is not specified
    // Template Location at 'modid:examplegametests.exampletest'
    @GameTest
    public static void exampleTest(GameTestHelper helper) { /*...*/ }

    // Class name is not prepended, template name is not specified
    // Template Location at 'modid:exampletest2'
    @PrefixGameTestTemplate(false)
    @GameTest
    public static void exampleTest2(GameTestHelper helper) { /*...*/ }

    // Class name is prepended, template name is specified
    // Template Location at 'modid:examplegametests.test_template'
    @GameTest(template = "test_template")
    public static void exampleTest3(GameTestHelper helper) { /*...*/ }

    // Class name is not prepended, template name is specified
    // Template Location at 'modid:test_template2'
    @PrefixGameTestTemplate(false)
    @GameTest(template = "test_template2")
    public static void exampleTest4(GameTestHelper helper) { /*...*/ }
}
```

## 运行游戏测试

> 相关 Minecraft Wiki：[命令](https://zh.minecraft.wiki/w/命令)

游戏测试可以使用 `/test` 命令运行。`test` 命令高度可配置；不过只有少数几个对运行测试比较重要：

| 子命令      | 描述                                                  |
|:-----------:|:------------------------------------------------------|
| `run`       | 运行指定的测试：`run <test_name>`。                     |
| `runall`    | 运行所有可用的测试。                                    |
| `runclosest`| 运行玩家 15 格内最近的测试。                            |
| `runthese`  | 运行玩家 200 格内的测试。                               |
| `runfailed` | 运行上一次运行中失败的所有测试。                         |

> **注意**
>
> 子命令跟在 test 命令之后：`/test <subcommand>`。

## 构建脚本配置

游戏测试在构建脚本（`build.gradle` 文件）中提供额外的配置设置，以运行并集成到不同设置中。

### 启用其他命名空间

如果构建脚本是[按推荐方式设置][buildscript]的，则只会启用当前模组 id 下的游戏测试。要启用其他命名空间以从中加载游戏测试，运行配置必须将属性 `neoforge.enabledGameTestNamespaces` 设置为以逗号分隔各命名空间的字符串。如果该属性为空或未设置，则加载所有命名空间。

```gradle
// Inside a run configuration
property 'neoforge.enabledGameTestNamespaces', 'modid1,modid2,modid3'
```

> **警告**
>
> 命名空间之间不能有空格；否则该命名空间将无法正确加载。

### 游戏测试服务器运行配置

游戏测试服务器（Game Test Server）是一种特殊配置，会运行一个构建服务器。该构建服务器返回的退出码为所需但失败的游戏测试数量。所有失败的测试，无论必需还是可选，都会被记录。该服务器可以使用 `gradlew runGameTestServer` 运行。

<details>
<summary>Important infromation on NeoGradle</summary>

> **警告**
>
> 由于 Gradle 工作方式的一个怪癖，默认情况下，如果某个任务强制系统退出，Gradle 守护进程将被杀死，导致 Gradle 运行器报告构建失败。NeoGradle 默认会在 run 任务上设置强制退出，以便任何子项目不会按顺序执行。然而正因如此，游戏测试服务器将总是失败。
>
> 这可以通过使用 `#setForceExit` 方法在运行配置上禁用强制退出来修复：
>
> ```gradle
> // Game Test Server run configuration
> gameTestServer {
>     // ...
>     setForceExit false
> }
> ```
</details>


### 在其他运行配置中启用游戏测试

默认情况下，只有 `client`、`server` 和 `gameTestServer` 运行配置启用了游戏测试。如果其他运行配置也应运行游戏测试，则必须将 `neoforge.enableGameTest` 属性设为 `true`。

```gradle
// Inside a run configuration
property 'neoforge.enableGameTest', 'true'
```
