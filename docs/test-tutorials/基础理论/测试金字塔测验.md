## 选择题

测试金字塔从下到上的正确顺序是？

 单元测试 → 接口（服务）测试 → UI / E2E 测试
 UI / E2E 测试 → 接口（服务）测试 → 单元测试
 接口（服务）测试 → 单元测试 → UI / E2E 测试
 单元测试 → UI / E2E 测试 → 接口（服务）测试

💡 金字塔底宽顶窄：越往下数量越多、执行越快、成本越低；越往上数量越少、执行越慢、维护越贵。接口层处在中间，是收益和成本最平衡的一层

为什么不能把测试全部交给 UI 自动化？

 UI 自动化工具授权费用普遍更高
 UI 自动化无法断言页面上显示的文字
 执行慢、稳定性差、维护成本高，问题反馈也最滞后
 UI 自动化只能由开发人员编写

💡 UI 层要经历完整链路的渲染和交互，脚本对页面结构极其敏感，一处样式改动就可能让一批用例失败。大量 UI 用例会让回归时间失控、误报频发，反而削弱团队对自动化的信任

折扣规则、金额计算这类分支组合很多的业务逻辑，最适合放在哪一层验证？

 UI 层，通过页面操作逐个验证
 单元层，直接覆盖各种输入组合
 手工探索，靠经验抽查
 性能测试，通过高并发暴露问题

💡 分支组合最容易出错、也最需要穷举，而单元测试执行成本最低，可以在毫秒级跑完几十种组合。放到 UI 层等于用最贵的资源做最该由底层承担的事

手工测试和探索式测试在分层策略中的位置是？

 已经被自动化完全取代，可以省略
 只在 UI 层做，替代部分 UI 自动化用例
 只在项目上线后做，用于收集用户反馈
 独立于金字塔存在，用来发现自动化覆盖不到的问题

💡 自动化擅长"验证已经想到的"，探索式测试擅长"发现还没想到的"——易用性、交互细节、异常路径、跨模块组合问题。两者是互补关系，不是替代关系

"把所有手工用例都转成 UI 脚本"这一做法的典型问题是什么？

 会让测试用例数量变少，覆盖度下降
 维护成本远超收益，脚本很快变成负担
 会让缺陷数量上升
 会导致无法再使用测试管理工具

💡 手工用例里大量是一次性验证、低频路径和需要主观判断的内容，转成脚本后每次需求变更都要跟着改，投入产出比极低。自动化要挑"稳定、重复、高价值"的场景

决定一个测试点该放在哪一层，主要依据是？

 风险高低、变更频率和执行成本
 团队里谁的脚本写得更熟练
 客户是否要求提供自动化覆盖率报告
 用例在测试管理工具里的编号顺序

💡 分层的本质是资源分配：高风险、逻辑复杂、频繁回归的内容尽量下沉到便宜的层；只有"必须验证真实链路"的部分才留在 UI 层

在 CI/CD 中，比较合理的分层运行策略是？

 每次提交都把单元、接口、UI 全套跑一遍，保证绝对安全
 只在发版当天跑一次完整回归
 每次提交跑单元和接口测试，UI / E2E 定时或发布前运行
 只跑 UI 测试，因为最接近用户真实操作

💡 分层运行的核心是"反馈速度匹配触发频率"：提交级流水线要快，所以放单元和接口；UI / E2E 慢，放在每日构建或发布前跑，既控住风险又不拖慢开发

相比 UI 层，接口层做自动化测试的主要优势是？

 能覆盖页面布局和视觉问题
 执行更快、更稳定，且能覆盖前端绕过的场景
 不需要任何测试数据
 可以直接替代安全测试

💡 接口层绕过了浏览器渲染，执行速度通常比 UI 快一个数量级，也不受页面结构变动影响。更重要的是，直接调用接口才能验证前端已经做过的校验在服务端是否同样成立

落地分层策略时提到的"最小自动化集"指的是？

 一套只在下班后运行的夜间用例
 由一名成员独立完成的最小脚本集合
 只覆盖单个模块的全部自动化用例
 用最少用例覆盖核心业务流程关键路径的集合

💡 起步阶段不要追求覆盖率数字，先用少量用例守住"登录、下单、支付"这类断了就影响生意的链路，跑稳之后再逐步扩面

单元测试的典型特征是？

 执行快、相互隔离、不依赖外部环境和数据
 必须连接真实数据库才能运行
 需要缺陷管理系统中存在对应编号
 需要人工逐条点击确认结果

💡 单元测试对数据库、网络等外部依赖要用打桩或 Mock 隔离，这样才能毫秒级执行、结果稳定，也才能在每次提交时都跑一遍

按照落地步骤，开展分层建设的第一步应该是？

 先采购自动化测试平台和云测设备
 直接把现有的 UI 脚本拆成单元测试
 列出核心业务流程，再按风险排序
 要求开发团队先把覆盖率提到 90%

💡 先看清"业务上什么最不能出问题"，才谈得上选择层级和投入顺序。跳过这一步直接上工具，很容易做出规模很大但没人看的用例集

"冰淇淋甜筒"反模式描述的是？

 单元测试过多，UI 测试几乎为零
 UI 用例数量最多，单元测试最少，金字塔被倒置
 只做手工测试，完全不做自动化
 只做性能测试，忽略功能测试

💡 冰淇淋甜筒是金字塔倒过来：大量 UI 脚本压顶、底层空洞。表现就是回归时间长、误报多、维护成本失控，团队最终对自动化失去信心
