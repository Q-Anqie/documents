# 第 5 阶段：项目与面试通关检查

!!! abstract "通关说明"
    完成项目与面试阶段后，用这个清单检查自己是否具备了项目实战能力和面试表达能力。如果 80% 以上都能做到，说明你已经具备了测试工程师的基本能力。

!!! warning "这一阶段最容易走的弯路：以为"做完项目"就等于"能讲项目""
    前面四个阶段的产物是**能力**，这一阶段的产物是**证据**。

    同一件事，写成「我做过电商系统的测试」和写成「我用 3 周覆盖了 42 个接口，发现 17 个缺陷，其中 1 个支付漏单缺陷在压测中才暴露，推动研发在订单表加了唯一索引」——后者才是证据。

    下面每一节的模板都配了「不合格 vs 合格」对照，请照着自己填一遍再比对。

---

## 一、阶段目标

完成项目实战，输出作品集材料，并能进行面试表达。

!!! tip "三个可验收的终点"
    1. **一份作品集**：别人只看材料，就能说清"你测了什么、发现了什么、结论是什么"。
    2. **一段两分钟表达**：录音回放，结构清晰、有量化、答得上追问。
    3. **一次反向验证**：关掉教程、换一个不同的需求，你能独立再走一遍完整流程。

## 三、实操任务

下面 5 个任务不是"五选一"，而是**建议按顺序都做一遍**——每一个补的是不同的能力缺口。每个任务后面都写了「验收判据」，做不到就不算完成。

### 任务 1：电商系统测试实战

- [ ] 完成需求分析和测试范围确定
- [ ] 设计完整的测试用例
- [ ] 执行接口测试并输出报告
- [ ] 记录和跟踪缺陷
- [ ] 输出测试报告

!!! success "验收判据"
    - 测试范围里**写清了"不测什么"**——只写测什么，等于没划定边界。
    - 用例数量与实际功能点匹配：一个模块至少 3 条异常/边界用例，不能全是正向流程。
    - 至少有 **1 个缺陷是你自己发现的，不是教程里给出的**，且能说清定位过程（看了哪张表、哪行日志）。
    - 测试报告的结论能回答"能不能上线"，而不是只列出通过率。

### 任务 2：接口自动化项目实战

- [ ] 搭建接口自动化框架
- [ ] 实现核心接口自动化
- [ ] 生成 Allure 测试报告
- [ ] 整理项目文档

!!! success "验收判据"
    - 换一个环境（改配置文件的 baseURL）**测试代码零改动**即可运行。
    - 断言不止看状态码：至少一处校验响应体字段值，一处校验数据库或下游结果。
    - 连跑 3 次结果一致，无偶发失败。
    - README 里能让一个没参与的人 10 分钟内跑起来。

### 任务 3：Web 自动化项目实战

- [ ] 搭建 Web 自动化框架
- [ ] 实现核心流程自动化
- [ ] 使用 Page Object 模式
- [ ] 生成测试报告
- [ ] 整理项目文档

!!! success "验收判据"
    - 代码里**没有裸 `sleep`**——等待都是显式条件等待。
    - 失败时自动留下证据：截图、URL、页面标题至少留两样。
    - 定位方式以 `data-testid` / id / 可访问名称为主，**CSS 层级选择器（`div > div:nth-child(3)`）不超过 20%**。
    - 能说清哪几个流程你**没有**做成自动化，以及为什么。

### 任务 4：性能测试项目实战

- [ ] 设计性能测试方案
- [ ] 实现性能测试脚本
- [ ] 执行性能测试
- [ ] 分析性能瓶颈
- [ ] 输出性能测试报告

!!! success "验收判据"
    - 方案里写清了**压测目标**（是多少并发、什么响应时间算达标），不是"压一下看看"。
    - 报告里同时给出平均值、P90/P95、错误率，并解释**P95 与平均值差距**的含义。
    - 至少给出一个瓶颈判断及其依据（应用 / 数据库 / 缓存 / 网络 / 第三方），并说明验证方法。
    - 明确写出**本次压测不做结论的部分**（比如没有覆盖真实网络、数据量小于生产）。

### 任务 5：CI/CD 自动化回归实战

- [ ] 配置 Jenkins 流水线
- [ ] 集成自动化测试
- [ ] 配置测试报告
- [ ] 配置失败通知
- [ ] 完成 [持续集成测验](../持续集成/持续集成测验.md) 检验 CI/CD 基础概念

!!! success "验收判据"
    - 流水线能**从提交代码自动触发到出报告**，全流程不需要人工点。
    - 失败通知里带得上关键信息：哪条用例失败、失败原因、报告链接。
    - 密钥（账号、Token）通过凭据管理注入，**没有硬编码在脚本或仓库里**。

## 六、作品集模板

!!! tip "先看一个整体判断标准"
    作品集不是"材料越多越好"，而是**别人看完能回答三个问题**：

    1. 这个人测的是什么系统，测到什么程度？
    2. 他怎么发现问题、怎么定位、怎么推动解决？
    3. 他的结论靠不靠得住？

    做不到这三点的材料，写得再长也是负担。下面每一块都配了「不合格 vs 合格」对照。

### 项目背景

```text
项目名称：
项目背景：
我的角色：
项目周期：
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 不合格 | 电商系统测试项目，我负责测试，做了 2 个月。 | 看不出系统规模，看不出你负责哪一块 |
| ✅ 合格 | 某 B2C 电商交易域，覆盖购物车、下单、支付、退款 4 个模块共 42 个接口。我是唯一测试，从需求评审参与到上线验证，周期 3 周（含 2 轮回归）。 | 有范围、有规模、有角色、有周期 |

### 测试范围

```text
功能模块：
测试类型：
测试环境：
不测的部分：
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 不合格 | 测试类型：功能测试、接口测试、性能测试、安全测试、兼容性测试 | 全都写=都没深入，面试官会挑最弱的一项追问 |
| ✅ 合格 | 重点：交易链路（下单→支付→退款）功能与接口测试、支付幂等专项。简做：首页与搜索只做冒烟。不测：后台运营端（由另一名同事负责）、跨境支付（本期未开放）。 | 有重点、有取舍、有边界 |

!!! warning "「不测的部分」这一栏不要省"
    它有两个作用：一是证明你真的划过范围（新手最常犯的错是想全测），二是提前化解面试官"那 XX 你测了吗"的追问。

### 测试用例

```text
用例总数：
执行数量：
通过数量：
失败数量：
```

!!! tip "只报数字不够，要报结构"
    在数字后面补一句维度分布，比如：**「共 156 条，其中正向 61 条、异常与边界 72 条、权限与安全 23 条；接口用例 48 条，其中 12 条做了数据一致性校验。」**

    这一句比"156 条"有信息量得多，因为它说明你知道用例该怎么配比。

### 缺陷统计

```text
缺陷总数：
严重缺陷：
一般缺陷：
轻微缺陷：
已修复：
遗留：
遗留原因与影响：
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 不合格 | 缺陷总数：35，已修复：35 | 零遗留反而不可信，且看不出质量趋势 |
| ✅ 合格 | 共 35 条（P0 2 / P1 7 / P2 19 / P3 7），已修复 32，遗留 3 条均为 P3（文案与样式），已与产品确认不影响上线。缺陷收敛：第一轮 21 条，第二轮 9 条，第三轮 3 条。 | 有分级、有遗留说明、有收敛趋势 |

!!! tip "「收敛趋势」是最容易被忽略、也最加分的一栏"
    它直接对应「能不能上线」这个判断。只报总数的人，看起来像在数数；报收敛趋势的人，看起来像在做质量决策。

### 技术栈

```text
接口测试：Postman / Python + Requests + Pytest
Web 自动化：Selenium / Playwright
性能测试：JMeter
CI/CD：Jenkins
报告：Allure
```

!!! warning "技术栈清单里别写"了解""
    写「了解 Docker」在面试里是负分——它等于主动邀请对方深挖，而你大概率答不上。

    只写**能当场做出来**的：写「会用 Docker 起 MySQL 和 Redis 作为测试环境」比写「了解 Docker」强十倍。

### 项目收获

```text
技术收获：
业务收获：
沟通收获：
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 不合格 | 技术收获：学会了自动化测试。 | 没有具体动作，人人都能这么说 |
| ✅ 合格 | 技术收获：把 12 个核心接口从 Postman 手工执行改成 pytest 参数化，回归时间从 40 分钟降到 6 分钟；为此第一次真正理解了 fixture 的作用域和会话级复用。 | 有前后对比、有具体技术点、有真实的理解过程 |

## 七、面试表达模板

!!! danger "模板只是骨架，面试官听的是细节"
    下面每一段都给了「照着填 vs 真正能用」的对照。**能被追问三次还不塌的，才算你的答案。**

### 项目介绍（2 分钟版本）

```text
这个项目是一个 [业务类型] 系统，主要功能包括 [功能列表]。
我在项目中负责 [职责范围]，使用了 [技术栈] 进行测试。
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 照着填 | 这个项目是一个电商系统，主要功能包括商品、订单、支付。我负责测试，使用了 Postman 和 Pytest。 | 30 秒就讲完了，面试官没有可追问的点 |
| ✅ 能用 | 这是一个 B2C 电商交易系统，日订单约 2 万。我是交易域的测试，负责购物车到退款这条链路。最有代表性的一次，是在支付回调的幂等测试里发现重复推送会重复扣款——这个缺陷在功能测试里完全没暴露，是压测并发才出来的。 | 有规模、有范围、有一个具体的故事钩子 |

!!! tip "自我介绍要留一个「钩子」"
    上面合格示例的最后一句，就是钩子——面试官大概率会接着问"那个幂等问题你怎么发现的"。**你准备得最充分的那件事，就应该被主动抛出来。**

### 测试方法

```text
我采用了 [测试策略]，覆盖了 [测试类型]。
对于核心功能，我设计了 [用例数量] 条测试用例。
对于接口测试，我使用了 [工具] 进行自动化。
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 照着填 | 我采用了黑盒测试，覆盖了功能测试和接口测试，设计了 156 条用例。 | 术语堆砌，说不出"为什么这么设计" |
| ✅ 能用 | 交易链路我用场景法串主流程，每个环节再按「正常 / 参数异常 / 状态异常 / 权限」四类补用例。比如下单接口，除了参数边界，我专门测了"购物车里有已下架商品"和"库存刚好被抢完"这两个状态，后者是我看代码时发现没加乐观锁才想到的。 | 有方法、有判据、有来源 |

### 缺陷案例（面试高频，务必准备 2-3 个）

```text
我发现了一个 [缺陷类型] 缺陷，具体表现是 [现象]。
通过 [分析方法]，我定位到问题是 [原因]。
最终通过 [解决方案] 修复了这个问题。
```

!!! success "一个能被追问三次的完整示例"
    **现象**：压测时 50 并发下，同一个支付回调推送两次，订单被扣两次款，但接口每次都返回成功。

    **怎么发现的**：功能测试阶段单次调用完全正常，我是在写接口用例时想到"第三方回调一定会重试"，于是用 JMeter 让同一个回调报文连发 5 次，对比数据库余额才发现的。

    **怎么定位**：查 `payment_callback_log` 表发现两条相同 `trade_no` 记录，说明服务端没有做去重；再看代码，回调处理是先查订单状态再更新，两步之间没有事务和唯一约束，并发下两个请求都能查到"未支付"。

    **怎么推动解决**：我把复现步骤和日志发给研发，建议在 `trade_no` 上加唯一索引，并把"查询+更新"改成条件更新（`UPDATE ... WHERE status = 'unpaid'`）。改完后同样压测 1000 次回调，只产生 1 条扣款记录。

    **事后总结**：这个缺陷教我一件事——**功能测试只能验证"一次调用对不对"，验证不了"同一件事发生很多次会怎样"**。后来我把幂等性单独列成了一个检查项。

!!! tip "为什么这个答案能过"
    它有 5 个要素：**明确现象 → 触发条件 → 定位路径（具体到表名和字段）→ 推动方案 → 复盘出的认知**。
    少了任何一个，面试官都会继续追问；全都有，追问就只能往深处走，而深处你更熟。

### 技术难点

```text
在项目中，我遇到了 [困难]。
我通过 [方法] 解决了这个问题。
这个经历让我学到了 [收获]。
```

| 写法 | 示例 | 问题 / 好在哪 |
|------|------|---------------|
| ❌ 照着填 | 我遇到了自动化脚本不稳定的问题，通过加等待解决了，学到了要加等待。 | 太浅，等于说"我百度了一下" |
| ✅ 能用 | 自动化用例有 20% 偶发失败。我先统计了失败分布，发现集中在 3 个用例、且都是"操作后立刻断言"；进一步排查是前端异步渲染，`sleep` 只是把概率降低。最后改成等具体元素状态（`waitForSelector` + 业务态判断），并把重试从 3 次降到 0 次，失败率降到 2% 以下，这 2% 全部是真实缺陷。 | 有数据、有排查路径、有取舍、有可验证的结果 |

## 八、通关判断

### 通过标准

- 必备能力清单完成 80% 以上
- 实操任务全部完成，且每个任务都达到上面的验收判据
- 有完整的项目作品集
- 能进行面试表达

!!! tip "「80% 以上」怎么算"
    必备能力清单共 21 条，**至少完成 17 条**。但注意：**「作品集产出」7 条必须全完成**——那一组是硬性的，缺一份材料就等于没有作品集。

### 自我评估

如果你能做到以下几点，说明已经具备了测试工程师的基本能力：

1. 能完成一个完整的项目实战
2. 能输出可展示的作品集材料
3. 能用项目经验进行面试表达
4. 能说清楚"为什么这样测、怎么测、发现了什么问题"

!!! success "最后一道自测：找一个真人来验"
    把你的作品集发给一位在职测试、同学或朋友，**只发材料，不做任何解释**，然后问他三个问题：

    1. 这个项目测的是什么，测到什么程度？
    2. 他记得最清楚的一个缺陷是什么？
    3. 他觉得这个项目的测试结论靠不靠得住？

    **三个问题他都能答上来，作品集才算合格。** 他要是答不上来，说明材料缺的不是内容，而是结构。

## 九、下一步

如果通关检查通过，恭喜你！你已经具备了测试工程师的基本能力。

建议：

- 继续完善项目作品集
- 准备面试表达
- 学习更多高级技能（性能调优、安全渗透、测试开发）
- 关注行业动态，持续学习

如果还有薄弱点，建议：

- 回看 [项目实战](../项目实战/index.md)
- 回看 [面试专题](../面试专题/index.md)
- 回看 [Jenkins CI/CD](../持续集成/Jenkins-CICD教程-软件测试版.md)、[GitHub Actions](../持续集成/GitHub-Actions教程-软件测试版.md)
- 完成更多项目实战
- 用 [测试岗位技能对照与补课指南](../面试专题/测试岗位技能对照与补课指南.md) 定位自己距离目标岗位的具体缺口

!!! tip "关于「继续学习」的一个更具体的建议"
    「关注行业动态」这种话很难执行。换成三件具体的事：

    1. **每季度重做一次简历**，看有多少条需要更新——更新得少说明这一年没长进。
    2. **每半年挑一个陌生方向做一次小实验**（比如用 AI 生成一批用例并评估其可用率），写成一页笔记。
    3. **把踩过的坑记在一个固定文件里**，它比任何教程都更贴合你的工作。
