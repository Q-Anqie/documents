# 测试计划模板

测试计划的作用是提前说清楚：测什么、不测什么、谁来测、什么时候测、风险在哪里。它不是形式文档，而是项目开始前的约定。

## 纯文本骨架（推荐直接复制）

粘进飞书文档、语雀、Confluence 都不会散架。小项目砍到只剩「范围 / 排期 / 风险」三节也够用。

```text
# 项目名称 —— 测试计划

## 一、基本信息
测试负责人：
参与人员：
需求来源：
提测版本：
计划上线时间：

## 二、测试范围
本次测试：
本次不测试：（写清楚，避免后续扯皮）
不测原因：

## 三、测试策略
测试类型：功能 / 接口 / 兼容性 / 性能 / 安全 / 回归
重点区域：（本次改动最大的地方、历史缺陷密集的地方）
深度：只验主流程 / 主流程 + 异常分支 / 全量回归
委外或第三方依赖：

## 四、环境与数据
测试环境地址：
数据库：
测试账号：
需要准备的数据：
第三方或 mock：

## 五、排期
用例设计：__ 至 __
提测时间：
第一轮执行：__ 至 __
第二轮回归：__ 至 __
测试报告：__

## 六、准入条件
- [ ]
## 七、准出条件
- [ ]

## 八、风险与应对
| 风险 | 影响 | 应对 |
|------|------|------|
|      |      |      |
```

## 基础模板

| 模块 | 内容 |
|------|------|
| 项目名称 | 例如：商城优惠券功能测试 |
| 测试负责人 | 负责整体进度和质量结论的人 |
| 需求来源 | 需求文档、原型、接口文档、会议纪要 |
| 测试范围 | 本次明确要测试的功能 |
| 不测试范围 | 本次不覆盖的内容，避免后续扯皮 |
| 测试类型 | 功能、接口、兼容性、性能、安全、回归 |
| 测试环境 | 测试环境地址、数据库、账号、版本 |
| 测试数据 | 需要准备的账号、订单、商品、权限 |
| 排期计划 | 用例设计、执行、缺陷修复、回归、报告时间 |
| 准入条件 | 什么时候可以开始测试 |
| 准出条件 | 满足什么条件可以上线或交付 |
| 风险与应对 | 可能影响测试的风险和解决办法 |

## 示例

| 模块 | 示例内容 |
|------|----------|
| 项目名称 | 商城优惠券领取与使用功能 |
| 测试范围 | 优惠券列表、领取、下单使用、过期失效、退款返还 |
| 不测试范围 | 优惠券后台配置页面本次不测，只使用已有配置数据 |
| 测试类型 | 功能测试、接口测试、数据库校验、回归测试 |
| 测试环境 | `https://test-shop.example.com`，测试库 `shop_test` |
| 测试数据 | 普通用户、会员用户、已领取用户、库存为 0 的优惠券 |
| 准入条件 | 需求评审完成，测试环境部署成功，主流程可访问 |
| 准出条件 | P0/P1 缺陷全部关闭，核心用例 100% 通过，无阻塞风险 |
| 风险与应对 | 支付回调不稳定，提前准备模拟支付接口 |

## 准入条件示例

- [ ] 需求文档或原型已确认。
- [ ] 开发提测范围清楚。
- [ ] 测试环境可以访问。
- [ ] 基础测试账号可用。
- [ ] 关键接口文档已提供。
- [ ] 数据库表结构或字段说明已确认。

## 准出条件示例

- [ ] 核心业务流程测试通过。
- [ ] 严重和阻塞缺陷已修复并回归通过。
- [ ] 遗留缺陷已评估影响并得到确认。
- [ ] 测试报告已输出。
- [ ] 上线检查项已完成。

## 排期怎么估才不离谱

排期估算写「大概三天」就是在给自己挖坑。新手最常见的失误是**只算执行用例的时间，忘了算用例设计、缺陷回归和环境等待**。

一个经过验证的比例：如果执行用例需要 1 天，那整个测试周期通常是 2 天左右。剩下的时间花在：

| 环节 | 通常占比 | 说明 |
|------|----------|------|
| 需求理解 + 用例设计 | 30% | 最容易被漏算的一块，全量用例通常写 2 天起 |
| 用例执行（第一轮） | 35% | 按「每天有效执行 60~80 条」估算，别按理论最优值 |
| 缺陷复测 + 回归 | 20% | 取决于缺陷数量和修复速度，不可控 |
| 环境等待 + 阻塞处理 | 15% | 提测延期、环境挂、数据造不出来，几乎每个项目都会遇到 |

!!! warning "两个必须写进计划的假设"
    1. **提测时间假设**：如果开发延后一天提测，测试周期是压缩还是整体顺延？写清楚，不要默认「测试加班消化」。
    2. **回归轮次假设**：计划里写的是「两轮回归」。如果缺陷超过预期导致需要三轮，多出来的时间从哪来？

    这两条不写，到项目后期就只能靠加班补，而且没人觉得这是计划的问题。

## 测试策略怎么写：别把所有测试类型都勾上

新手写计划喜欢在「测试类型」里把功能、接口、性能、安全、兼容性全部勾选。结果实际只做了功能测试，计划却显得很丰满——这是自欺欺人，而且后期追溯时很难解释。

**每种勾选的测试类型，都要能回答：谁来测、用什么测、测到什么程度。** 答不上来的就别勾。

| 勾了 | 需要补充的说明 | 不补充会怎样 |
|------|----------------|--------------|
| 功能测试 | 覆盖哪些模块、多少条用例 | 无法判断是否测完 |
| 接口测试 | 测多少接口、用什么工具、是否进自动化 | 到验收时拿不出接口测试结果 |
| 性能测试 | 压测哪个链路、目标 TPS 和响应时间 | 「测过性能」但没有任何数据 |
| 兼容性测试 | 哪些浏览器/机型/分辨率组合 | 上线后才发现某机型不兼容 |
| 安全测试 | 只做基础项（越权、SQL 注入）还是完整渗透 | 承诺了做不到的范围 |

对于完全没有专职性能或安全测试的小团队，实用做法是在计划里写明：**「本次不做性能测试，原因为无压测环境；上线后由运维监控响应时间」**。写清楚不做，比含糊地勾上更专业。

## 风险要写成「会发生的事」

「风险：暂无」是最没用的写法。风险不是「可能出问题」的抽象担心，而是具体到「什么条件下会发生什么，我们准备怎么办」。

好的风险描述长这样：

| 风险 | 影响 | 应对 |
|------|------|------|
| 支付回调依赖第三方沙箱，历史上有过不稳定记录 | 无法验证支付成功后的订单状态流转 | 提前准备 mock 回调接口；若沙箱不可用，改用 mock 验证并标注为遗留风险 |
| 需求在提测前仍在变更 | 用例刚写完就要改，浪费设计时间 | 约定提测后需求冻结；变更需走评审并重新评估排期 |
| 只有一名测试，且与上线时间无缓冲 | 突发请假或漏测将直接影响上线 | 关键用例提前交接给同事；核心流程准备自动化脚本兜底 |

注意每条都有「条件 → 影响 → 动作」三段。只有担心没有动作的，那不是风险，是抱怨。

## 常见错误

| 错误写法 | 问题 |
|----------|------|
| 测试范围：测试全部功能 | 太空泛，无法判断是否覆盖 |
| 测试环境：测试环境 | 没有地址、账号、版本，无法复现 |
| 风险：暂无 | 很多项目都有风险，不写不代表没有 |
| 准出条件：测试通过 | 没有明确通过标准 |
| 排期：3 天 | 没有起止日期，也没有拆到设计/执行/回归 |
| 测试类型：全部勾选 | 实际做不到，事后无法解释 |
