# 缺陷报告模板

好的缺陷报告能让开发快速复现、快速定位、快速修复。新手提交缺陷时最常见的问题是：标题太模糊、步骤不完整、实际结果和期望结果混在一起。

!!! tip "直接复制下面这段去填"
    下面「纯文本骨架」一节可以直接整段复制，粘进禅道、Jira、飞书、语雀都不会散架。
    表格版的字段说明用来理解每个字段为什么存在，**填的时候用纯文本骨架**。

## 纯文本骨架（推荐直接复制）

复制后把尖括号里的内容换成实际情况。这个格式的好处是：粘进任何工具都不变形，开发在通知栏预览里也能直接看到关键信息。

```text
【缺陷标题】模块 + 操作 + 触发条件 + 实际现象

所属模块：
发现版本：
测试环境：
前置条件：
复现步骤：
1.
2.
3.
实际结果：
期望结果：
复现概率：必现 / 偶现（约 N 次出 M 次）
附件：截图 / 录屏 / 接口响应 / 日志时间点
关联信息：用例编号 / 需求编号 / 接口地址
```

## 标准字段

| 字段 | 说明 |
|------|------|
| 缺陷标题 | 简短说明问题和触发条件 |
| 所属模块 | 登录、订单、支付、后台管理等 |
| 发现版本 | 出问题的版本号或构建号 |
| 测试环境 | 测试地址、浏览器、设备、系统 |
| 前置条件 | 复现前需要准备的数据或状态 |
| 复现步骤 | 按 1、2、3 写清楚 |
| 实际结果 | 实际发生了什么 |
| 期望结果 | 按需求应该发生什么 |
| 严重程度 | Blocker/Critical/Major/Minor |
| 优先级 | P0/P1/P2/P3 |
| 附件 | 截图、录屏、日志、接口响应 |
| 关联信息 | 用例编号、需求编号、接口地址 |

## 标题写法

| 不推荐 | 推荐 |
|--------|------|
| 登录有问题 | 登录页输入错误密码后提示文案为空 |
| 下单失败 | 购物车包含下架商品时提交订单返回 500 |
| 页面异常 | iPhone 13 Safari 下商品详情页规格弹窗遮挡确认按钮 |

## 示例

用上面那段纯文本骨架填出来，就是下面这样（直接照这个密度写，开发基本不会再问你）：

```text
【缺陷标题】购物车包含已下架商品时提交订单，接口返回 500 且页面只提示「系统异常」

所属模块：购物车 / 订单创建
发现版本：test-2026.06.10-01
测试环境：测试环境 https://test-shop.example.com，Chrome 125 / Windows 11，账号 user01
前置条件：购物车中存在 1 个已下架商品（商品 A，后台操作下架后未刷新购物车页面）
复现步骤：
1. 使用普通用户 user01 登录
2. 将商品 A 加入购物车
3. 在后台管理端将商品 A 下架
4. 回到前台购物车页面，点击「结算」
实际结果：页面提示「系统异常」，接口 POST /api/order/create 返回 HTTP 500，
         后端日志 14:32:07 有 NullPointerException（OrderService.java:184）
期望结果：页面提示「商品已下架，请重新选择商品」，订单不创建，
         购物车中该商品标记为失效并置灰
复现概率：必现（5 次 5 次）
附件：
  - screenshot-cart-500.png（前端提示）
  - order-create-500.har（Postman/F12 导出的请求响应）
  - backend-20260610.log 第 14:32 行附近
关联信息：用例编号 CART-014；需求 PRD-2026-037「商品下架处理」；
         接口文档 /api/order/create
```

对应的字段说明版本：

| 字段 | 内容 |
|------|------|
| 缺陷标题 | 购物车包含下架商品时提交订单返回 500 |
| 所属模块 | 购物车 / 订单 |
| 发现版本 | `test-2026.06.10-01` |
| 测试环境 | Chrome 125，测试环境 `https://test-shop.example.com` |
| 前置条件 | 购物车中存在一个已下架商品 |
| 复现步骤 | 1. 登录普通用户；2. 将商品 A 加入购物车；3. 后台将商品 A 下架；4. 回到购物车点击结算 |
| 实际结果 | 页面提示“系统异常”，接口 `/api/order/create` 返回 500 |
| 期望结果 | 页面提示“商品已下架，请重新选择商品”，订单不创建 |
| 严重程度 | Major |
| 优先级 | P1 |
| 附件 | 截图、接口响应、后端日志时间点 |

## 严重程度参考

| 级别 | 说明 |
|------|------|
| Blocker | 阻塞测试或系统无法使用 |
| Critical | 核心流程失败、数据错误、资金风险、安全风险 |
| Major | 主要功能异常，但有绕过方式 |
| Minor | 文案、样式、低频兼容性问题 |

## 严重程度和优先级不是一回事

这是新手最容易混的一处。**严重程度由缺陷本身决定，你改不了；优先级由这个迭代要不要修决定，可以商量。**

- 严重程度看「坏得多厉害」：影响多少用户、有没有资金和数据风险、有没有替代路径。
- 优先级看「什么时候修」：这个版本上不上线、有没有临时规避方案、客户会不会明天投诉。

两者可以不一致，下面四种组合都是真实的：

| 情况 | 严重程度 | 优先级 | 为什么 |
|------|----------|--------|--------|
| 支付金额少算 1 分钱 | Critical | P0 | 资金问题，一例都不能留 |
| 首页轮播图错位 | Minor | P0 | 不影响功能，但首页第一屏，老板明天要看 |
| 后台导出功能报错 | Major | P2 | 只有运营月度用一次，本月可手工导出 |
| 帮助中心某段文字错别字 | Minor | P3 | 有空再改，记着就行 |

!!! warning "别把优先级当护身符"
    「这个我标了 P3」不能成为漏测 P0 场景的借口，反过来「我标了 Blocker」也不等于开发必须今天修。
    写缺陷时把严重程度和优先级的**理由**写进备注（例如「影响所有下单用户」「仅后台低频功能」），
    评审会上才有据可依，而不是各说各话。

## 开发说“这不是 bug”时怎么办

缺陷报告真正的难点不在写，而在被驳回。下面五种回应都有固定的应对套路，照着做能省掉大量拉扯。

| 开发的说法 | 背后可能是 | 你要做的 |
|------------|------------|----------|
| 「这是设计如此」 | 需求没写清楚，或他理解错了需求 | 拿需求文档/原型的具体段落出来对齐。如果文档确实没写，这不是 bug，但要去推动补需求，并记录为「需求待明确」 |
| 「我这里是好的，你环境问题」 | 环境差异、缓存、脏数据、配置不同 | 把你的环境、版本号、账号、数据来源列清楚，请他报一下他的环境。差异点通常就在这里 |
| 「复现不了」 | 你步骤有隐含前提没写 | 补录屏。录屏是从头到尾连续操作，比步骤文字有说服力得多。再补上复现概率（几次出几次） |
| 「这个是历史问题，不是这次改的」 | 可能是真的 | 先确认是否影响本次上线判断。若是老问题，改为独立缺陷并标注「存量问题」，不要因此放过 |
| 「优先级没那么高」 | 他手上的活排满了 | 这条可以谈。但要把用户影响说清楚，让产品/测试负责人来定优先级，而不是你和开发两个人定 |

!!! danger "最不该做的一件事：在群里争论"
    把争论留在缺陷单里。缺陷单有记录、有附件、有状态流转，群里吵完第二天谁也说不清。
    正确做法是在缺陷单里追加评论，附上新证据（日志、录屏、需求截图），然后 @ 相关人。
    这既是推进，也是留痕。

## 提交前检查

- [ ] 缺陷单里没有「应该」「不正常」「有问题」这类没有信息量的词。
- [ ] 开发是否能按步骤复现。
- [ ] 实际结果和期望结果是否分开写。
- [ ] 是否说明测试环境和版本。
- [ ] 是否附上截图、接口响应或日志。
- [ ] 是否判断了影响范围。
- [ ] 是否关联了用例或需求。
- [ ] 标题是否能让人一眼看懂「哪里、什么条件、什么现象」。
- [ ] 严重程度和优先级是否写了理由。
- [ ] 偶现问题是否写明了复现概率。
