# 上线检查清单

上线检查清单用于发布前最后确认。它不能替代测试用例，但可以降低“忘记关键步骤”的风险。

## 先解决「清单没人执行」的问题

大部分上线事故不是因为清单漏项，而是**清单上没人负责、没人签字、没卡在流程里**。一份没有执行人的清单，只是一份文档。

所以本页的每一项都建议按下面三列补齐（在自己团队的工具里加列即可）：

| 列 | 填什么 | 为什么必须填 |
|----|--------|--------------|
| 负责人 | 具体到人名，不写「测试组」 | 集体负责等于没人负责 |
| 时点 | T-1 天 / 发布前 1 小时 / 发布后 30 分钟 | 没有时点就会拖到最后一刻集中做，做不完 |
| 证据 | 截图、报告链接、命令输出、监控截图 | 「我确认过了」不算证据，无法追溯 |

!!! tip "小团队的低成本做法"
    不需要上系统。把关键的三项（负责人、时点、证据）写进同一个共享表格，发布时投屏，逐项口头确认并打勾。
    比「默认大家都记得」可靠得多，而且事后复盘有据可查。

## 可复制的发布记录（推荐）

发布时用这段记录，比逐条打勾更容易留证据。把它粘进发布群或发布单，边执行边填。


## 功能确认

- [ ] 核心业务流程已测试通过。
- [ ] P0/P1 缺陷已全部关闭。
- [ ] P2 缺陷已评估影响并确认是否允许遗留。
- [ ] 回归测试已完成。
- [ ] 兼容性测试已按范围完成。
- [ ] 产品已确认关键页面和文案。

## 接口与数据

- [ ] 关键接口返回正常。
- [ ] 数据库字段变更已确认。
- [ ] 初始化数据或配置数据已准备。
- [ ] 缓存更新策略已确认。
- [ ] 定时任务影响已确认。
- [ ] 第三方接口或支付回调已验证。

## 配置与环境

- [ ] 发布版本号已确认。
- [ ] 配置文件已区分测试环境和生产环境。
- [ ] 域名、证书、端口、反向代理配置已确认。
- [ ] 数据库连接、Redis 连接、消息队列连接已确认。
- [ ] 日志路径和日志级别已确认。

## 安全与权限

- [ ] 管理员、普通用户、游客权限已验证。
- [ ] 未登录访问受限接口会被拦截。
- [ ] 敏感信息不会在页面、接口、日志中明文暴露。
- [ ] 文件上传类型和大小限制已验证。
- [ ] 关键操作有必要的权限校验或二次确认。

## 性能与稳定性

- [ ] 核心接口响应时间在可接受范围内。
- [ ] 高访问页面没有明显慢查询。
- [ ] 错误日志没有持续新增。
- [ ] 监控告警已配置或确认。
- [ ] 高峰访问风险已评估。

## 回滚方案

- [ ] 已确认回滚负责人。
- [ ] 已确认回滚命令或操作步骤。
- [ ] 数据库变更是否可回滚已确认。
- [ ] 静态资源或配置是否可恢复已确认。
- [ ] 回滚后如何验证已明确。

## 上线后验证

- [ ] 首页或入口页面可访问。
- [ ] 登录、查询、下单等核心流程可用。
- [ ] 关键接口无大量报错。
- [ ] 日志无明显异常。
- [ ] 监控指标正常。
- [ ] 用户反馈渠道已有人关注。

## 上线后 30 分钟：最关键的窗口

发布完成不等于上线成功。大部分线上事故在前 30 分钟就有信号，只是没人盯。这一段不是重复上面的「上线后验证」，而是**按时间顺序执行的动作清单**。

| 时间点 | 做什么 | 怎么判断正常 |
|--------|--------|--------------|
| T+0 | 打开首页和登录页，走一遍最短主流程（登录 → 查询/下单 → 退出） | 页面能开、能登录、能完成一次核心操作 |
| T+5 | 看错误日志增速，对比发布前的基线 | 没有出现新的异常堆栈；错误量级与发布前持平 |
| T+5 | 看核心接口的成功率和响应时间 | 成功率不下降，P95 响应时间没有明显抬升 |
| T+15 | 看监控大盘：CPU、内存、连接数、队列积压 | 没有持续爬升的曲线（持续爬升往往比瞬时尖峰更危险） |
| T+30 | 抽查一条真实业务数据，确认落库正确 | 数据库里能查到刚才操作产生的记录，字段值正确 |

!!! danger "这三个信号出现就该考虑回滚，不要等"
    1. **错误日志持续新增同类异常**，且随流量增长而增长——说明是代码问题，不会自己好。
    2. **核心接口成功率下跌且不回升**，或响应时间 P95 突破可接受范围。
    3. **数据错乱**：金额、库存、订单状态出现不一致。这类问题拖得越久，修复成本越高。

    回滚的决定权要**在发布前就明确交给某个人**（通常是测试负责人或技术负责人）。事故现场临时讨论「要不要回滚」是最耗时间也最容易出错的环节。

## 新手提醒

上线前不要只问“开发说没问题了吗”。测试需要用证据说话：用例结果、缺陷状态、接口响应、数据库数据、日志、监控指标都可以作为判断依据。

另一件同样重要的事：**上线检查不是发布那一刻才开始的。** 回滚方案、监控告警、负责人分工这些内容，如果发布当天才准备，基本等于没有准备。把它们提前到 T-1 天完成，发布日只做执行和确认。
