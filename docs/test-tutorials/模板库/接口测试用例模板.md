# 接口测试用例模板

接口测试用例要说明请求怎么发、断言怎么写、数据怎么校验。不要只写“调用接口成功”，那样无法判断是否真的测到了业务逻辑。

## 纯文本骨架（推荐直接复制）

一条接口用例只针对**一个接口的一个测试点**。填的时候如果发现「预期响应」要写三件互不相关的事，说明该拆成三条。

```text
用例编号 | API-模块-序号
接口名称 |
请求方法 | GET / POST / PUT / PATCH / DELETE
请求路径 | /api/xxx
优先级 | P0 / P1 / P2 / P3
测试点 | 正常 / 必填缺失 / 类型错误 / 越权 / 幂等 / 边界
前置条件 | 需要登录？需要什么角色？需要准备什么数据？
请求头 | Content-Type: application/json
        Authorization: Bearer <token>
请求参数 |
预期响应 | HTTP 状态码：
        业务码：
        关键字段：
        错误提示：
数据校验 | 数据库：     缓存：     下游调用：     日志：
依赖清理 | （用例执行后是否需要清理数据，怎么清）
```

!!! tip "「数据校验」这一行是接口测试和接口调试的分界线"
    只在 Postman 里看到返回 200 就结束，那叫调试，不叫测试。
    接口测试必须验证**副作用**：数据库有没有正确落库、缓存有没有更新、下游有没有被正确调用、日志里的信息是否泄露敏感字段。
    这四类校验能捞出一大批「接口返回正常但业务已经错了」的问题，比如返回成功但金额没扣、返回成功但库存没减。

## 标准字段

| 字段 | 说明 |
|------|------|
| 接口名称 | 例如：用户登录接口 |
| 请求方法 | GET、POST、PUT、PATCH、DELETE |
| 请求路径 | 例如 `/api/login` |
| 前置条件 | 是否需要登录、是否需要准备数据 |
| 请求头 | `Content-Type`、`Authorization` 等 |
| 请求参数 | Query、Path、Body 参数 |
| 测试点 | 正常、异常、边界、权限、幂等等 |
| 预期响应 | 状态码、业务码、字段值、错误提示 |
| 数据校验 | 数据库、缓存、日志、下游接口 |
| 优先级 | P0/P1/P2/P3 |

## 登录接口示例

| 编号 | 接口 | 方法 | 路径 | 测试点 | 请求数据 | 预期响应 | 数据校验 | 优先级 |
|------|------|------|------|--------|----------|----------|----------|--------|
| API-LOGIN-001 | 登录 | POST | `/api/login` | 正确账号密码 | `{"username":"user01","password":"Aa123456"}` | HTTP 200，业务码 0，返回 token | 登录日志新增成功记录 | P0 |
| API-LOGIN-002 | 登录 | POST | `/api/login` | 密码错误 | `{"username":"user01","password":"wrong"}` | HTTP 200 或 401，业务码非 0，提示账号或密码错误 | 登录失败次数增加或记录失败日志 | P0 |
| API-LOGIN-003 | 登录 | POST | `/api/login` | 用户名为空 | `{"username":"","password":"Aa123456"}` | 返回参数校验错误 | 不生成 token | P1 |
| API-LOGIN-004 | 登录 | POST | `/api/login` | 缺少 password 字段 | `{"username":"user01"}` | 返回缺少必填字段 | 不生成 token | P1 |
| API-LOGIN-005 | 登录 | POST | `/api/login` | 被禁用用户登录 | 禁用用户账号 | 登录失败，提示账号不可用 | 用户状态不被修改 | P1 |

## 常见断言

```python
assert response.status_code == 200
assert response.json()["code"] == 0
assert "token" in response.json()["data"]
assert response.elapsed.total_seconds() < 1
```

业务接口不要只断言 HTTP 状态码，还要断言业务码、关键字段和数据变化。

!!! warning "`assert response.status_code == 200` 单独出现时，几乎等于没测"
    很多团队的后端架构是「HTTP 永远返回 200，业务错误放在响应体 code 里」。
    这种情况下，一个权限校验完全失效的接口依然会返回 200，而上面的断言会全部通过。
    写断言时先确认你们团队的约定，然后**业务码和关键字段必须单独断言**。

## 断言要写三层

同一个接口，断言写得越深，能捞出的缺陷越多。三层缺一不可：

| 层 | 断言什么 | 缺了会漏掉什么 |
|----|----------|----------------|
| 响应层 | HTTP 状态码、业务码、错误码 | 接口 500 了却在看业务码 |
| 内容层 | 关键字段存在性、字段值正确、字段类型正确、不返回多余敏感字段 | 返回成功但字段是 null；返回了别人的手机号 |
| 数据层 | 数据库落库正确、缓存已更新、下游接口被调用、日志无敏感信息 | 返回成功但订单没创建；优惠券用了没扣 |

内容层有一个容易被忽视的点：**断言不该存在的东西**。比如查询用户信息的接口，除了断言昵称正确，还要断言响应里**没有** `password`、`idCard`、`salt` 这类字段。这类问题在功能上毫无感觉，在安全上却是高危。

## 完整填写示例

一条带三层断言的接口用例，按骨架填出来是这样：

```text
用例编号 | API-ORDER-006
接口名称 | 创建订单
请求方法 | POST
请求路径 | /api/order/create
优先级 | P0
测试点 | 正常流程，单商品下单成功
前置条件 | 用户 user01 已登录；商品 A 库存 10；购物车中有 1 件商品 A
请求头 | Content-Type: application/json
        Authorization: Bearer <user01 的有效 token>
请求参数 | {"skuId": "A", "count": 1, "addressId": 1001}
预期响应 | HTTP 状态码：200
        业务码：0
        关键字段：data.orderNo 为 20 位数字串；data.amount 等于商品单价
        错误提示：无
数据校验 | 数据库：order 表新增 1 条记录，status=待支付；
                sku 表商品 A 库存 10 → 9
        缓存：购物车 key 中商品 A 已被移除
        下游调用：库存服务收到扣减请求；支付服务未发起调用
        日志：orderNo 可追踪，无 token 明文打印
依赖清理 | 执行后删除本条订单，库存回补 1，避免影响后续用例
```

## 接口测试覆盖角度

- [ ] 必填参数为空。
- [ ] 参数类型错误。
- [ ] 参数长度超限。
- [ ] 枚举值非法。
- [ ] 未登录访问。
- [ ] token 过期访问。
- [ ] 普通用户访问管理员接口。
- [ ] 重复提交。
- [ ] 数据库是否正确落库。
- [ ] 错误信息是否暴露敏感信息。

## 覆盖角度怎么用：写用例前先过一遍这张表

上面的清单不是拿来打勾的，而是**设计用例时的检查方向**。每个接口都按下面五类各问一遍，会得到完整的用例集：

| 类别 | 问自己 | 典型用例 |
|------|--------|----------|
| 正常 | 按文档正确调用会怎样 | 全字段合法 → 成功，数据正确落库 |
| 参数异常 | 少一个、多一个、类型错、超长、为空、特殊字符 | 缺必填字段、传 `"abc"` 给整型、传 10 万字符、传 `null` |
| 鉴权异常 | 没带 token、token 过期、token 属于别人、角色不够 | 不带 Authorization → 401；普通用户调管理员接口 → 403 |
| 业务规则 | 这个接口在边界业务状态下会怎样 | 库存为 0 时下单、余额不足时支付、重复提交同一订单 |
| 数据一致性 | 接口说成功，数据真的一致吗 | 并发下单后库存是否为负；退款后订单金额与流水是否匹配 |

!!! tip "优先测「业务规则」和「数据一致性」"
    参数异常类问题开发自己就会修，而且大多数框架会自动拦住。
    真正难发现、影响也最大的是后两类：**边界业务状态**和**数据一致性**。这两类需要你理解业务，也正是测试工程师相对自动化的价值所在。

## 一个常被忽略的角度：接口幂等

「重复提交」这一项值得单独说，因为它在真实事故里出现频率极高。

判断一个接口该怎么测幂等，先看它的**语义**：

| 接口类型 | 天然幂等？ | 要测什么 |
|----------|-----------|----------|
| 查询（GET） | 是 | 连续调用两次，结果一致且无副作用 |
| 更新为固定值（PUT） | 是 | 连续提交相同数据，数据库最终状态与提交一次相同 |
| 创建（POST） | 否 | 连续提交相同请求，是否创建了两条？重复下单、重复支付都出在这里 |
| 删除（DELETE） | 通常是 | 第二次删除应返回明确结果，而不是 500 |

对于非幂等的创建类接口，标准做法是要求带一个**幂等键**（requestId / 订单号由前端生成）。测试方法是：用同一个幂等键连续发 5 次，断言数据库里只有 1 条记录，且后续 4 次返回的结果与第 1 次相同。

如果接口没有幂等设计，这本身就是一条需要提出的风险，而不是「测不过就算了」。
