## 选择题

相比 Web 测试，移动端测试特有的关注点是？

 需要验证页面元素的正确性
 需要验证接口返回的数据
 设备碎片化、网络环境多变、系统权限、安装升级与推送
 需要验证用户登录功能

💡 移动端多出了几个 Web 没有的维度：几十种机型与系统版本、随时波动的网络、运行时会动态询问的系统权限、覆盖安装与卸载重装、以及依赖厂商通道的推送。这些恰恰是缺陷最集中的地方

想模拟"2G 弱网"环境测试 App 的表现，常用做法是？

 把手机放进电梯或地下室等信号差的场所
 用 Charles / Fiddler 的网络限制（Throttling）功能设置带宽、延迟和丢包率
 关闭 App 的缓存功能后重新测试
 降低手机屏幕亮度以模拟低性能状态

💡 真实弱网不可复现、无法量化，所以要用代理工具人为构造：设定带宽（如 50-100 kbps）、延迟（300-500ms）和丢包率。这样才能稳定复现问题、也能横向对比不同版本的表现

下列哪一项是弱网环境下最典型的缺陷？

 页面配色在不同机型上不一致
 应用图标在低分辨率屏幕上模糊
 后台待机时流量持续消耗
 请求超时后无任何提示，用户重复点击导致重复下单

💡 弱网会同时暴露两类问题：反馈缺失（转圈不停、白屏、没有网络异常提示）和幂等性缺陷（重复提交、重复下单、重复扣款）。后者风险最高，通常需要在需求阶段就确认防重方案

测试"断网恢复"场景时，重点要验证什么？

 网络恢复后数据能否正确同步、操作是否可以重试且不重复
 断网时 App 是否直接退出
 断网时是否能继续使用所有在线功能
 断网后是否需要重新安装 App

💡 断网恢复是移动端最容易出数据问题的路径：本地缓存的草稿能否补传、提交中断的订单状态是否一致、会不会重复发送。测的时候要"断网 → 操作 → 恢复 → 核对数据"完整走一遍

设计移动端兼容性测试矩阵，比较合理的思路是？

 把所有在售机型都买回来逐台测试
 只测试最新的旗舰机型，保证性能体验
 结合用户市场占有率、系统版本分布和分辨率，选取有代表性的机型组合
 随便挑两款手机，主要靠开发自测

💡 机型无穷无尽，但用户分布是集中的。按后台统计的市场占有率和系统版本占比选主流机型，再用少量低端机覆盖性能下限、用高分辨率机型覆盖 UI 适配，才是在有限成本下覆盖最多风险的方案

关于真机测试与云测平台的选择，下列说法正确的是？

 云测平台可以完全替代真机，不需要再买设备
 云测适合覆盖大量机型做批量回归，真机适合排查需要真实交互的问题
 云测平台的测试结果一定比真机准确
 真机测试只能做手工测试，无法跑自动化脚本

💡 云测的优势是机型多、成本低、适合批量跑兼容性回归；但音频、摄像头、传感器、震动、发热、真实网络切换等场景，云测很难真实还原，需要真机补位。两者是配合关系

Android 上出现 ANR 的典型原因是？

 手机电量低于 20%
 应用被用户手动切换到后台
 图片分辨率过高导致内存不足
 主线程被耗时操作阻塞，长时间无响应

💡 ANR = Application Not Responding，本质是主线程（UI 线程）被网络请求、大文件读写、复杂计算等耗时操作卡住。图片过多导致内存不足属于 OOM，是另一类问题

移动端测试"后台待机流量"，合理的预期是？

 静置一段时间后后台流量应接近 0，持续消耗通常意味着异常上报或轮询
 后台驻留时持续产生流量是正常现象
 后台流量无法通过工具测量
 只要不影响前台使用就不必关注

💡 用户对"偷跑流量"非常敏感，这类问题常常直接变成投诉和差评。测试时把 App 切到后台静置一段时间，再观察流量增量，就能发现无节制的轮询、心跳过密或日志上报过多

获取 Android 崩溃日志，最常用的方式是？

 让开发重新编译一个带日志的版本
 截图崩溃弹窗即可，不需要日志
 通过 adb logcat 抓取，或从崩溃收集平台按设备与时间查找
 重启手机后系统会自动保存崩溃原因

💡 崩溃日志里的异常类型和堆栈是开发定位问题的关键线索，直接决定这个缺陷能不能被快速修掉。缺陷报告里带上崩溃时间点和设备信息，能让开发在崩溃平台上精准捞到那条记录

覆盖升级（在旧版本基础上装新版本）测试，最需要关注的是？

 安装包体积是否变小
 原有用户数据是否保留、登录态是否正常、本地数据库能否平滑迁移
 升级后图标是否更换
 升级提示文案是否美观

💡 全新安装永远是最干净的路径，最容易出问题的是"带着历史数据升级"：本地库表结构变更、缓存格式不兼容、旧 token 失效。测的时候要先在旧版本造好数据，再覆盖安装验证数据完整性

推送通知测试需要覆盖的场景中，下列哪项不属于重点？

 推送到达率与延迟
 点击推送后能否正确跳转到目标页面
 免打扰模式下、通知权限被关闭时的表现
 推送文案的字数统计是否符合运营规范

💡 推送的核心风险在"送不到"和"点错地方"：不同厂商通道的到达率差异很大，App 在前台/后台/被杀进程时点击跳转行为也不同。文案字数属于运营侧规范，不是技术测试重点

测试系统权限时，除了"允许"和"拒绝"，还必须覆盖哪种情况？

 永久拒绝后在设置中重新开启，以及"仅本次允许"这类临时授权
 用户从不点击任何权限弹窗
 用户连续点击弹窗十次
 权限弹窗的字体大小是否合适

💡 权限状态是有"记忆"的：拒绝一次可能只影响本次，拒绝两次可能变成永久拒绝且不再弹窗；"仅本次允许"在下一次启动时又会重新询问。这些状态组合最容易出现"功能静默失效却没有任何提示"的问题
