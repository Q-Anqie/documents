## 选择题

从 Postman 过渡到接口自动化，推荐的学习顺序是？

 先搭好完整框架，再往框架里填用例
 先用 Postman 调通接口 → 改成 Python 代码 → 用 Pytest 管理用例 → 再加数据、断言、报告和 CI
 先写 Allure 报告配置，再补测试用例
 先做数据驱动，再写第一个请求

💡 教程反复强调：框架是从重复代码中提炼出来的，不是第一天凭空设计出来的。一开始就搭大框架是新手最常见的卡点，容易堆出一堆难排查的错误

"接口自动化 = 用代码代替 Postman"，那么一次自动化请求至少要判断哪些内容？

 只要接口有返回就算通过
 只要 HTTP 状态码是 200 就算通过
 HTTP 状态码、业务 code、响应字段、数据库结果，以及异常场景是否被正确拒绝
 只要响应时间在阈值内就算通过

💡 教程把"只断言状态码 200"列为典型新手错误：业务失败同样可能返回 200。所以必须同时看协议层、业务层、数据层，并确认异常场景确实被拒绝

第一版自动化应该优先覆盖哪类接口？

 P0/P1 且稳定、关键、高频的接口
 项目里的全部接口，越多越好
 变化频繁的后台配置接口
 依赖第三方支付的真实回调接口

💡 教程主张第一阶段只覆盖 P0/P1 接口，优先做稳定流程。变化频繁的接口先保留手工验证，把所有接口都自动化会带来过高的维护成本

按照教程的目录结构，common/ 目录应该放什么？

 测试用例
 请求封装、日志、通用断言等通用能力
 测试数据
 环境配置

💡 教程的划分是：common/ 放通用能力（client、logger、assert_utils），data/ 放测试数据，tests/ 放用例，config/ 放环境配置，utils/ 放数据库、Token 等工具函数

为什么建议第一个用例"先不要急着封装"？

 封装之后用例就无法运行了
 requests 库不支持类封装
 先跑通最简单的请求确认链路可用，再按"边写边运行"的节奏逐步抽出重复代码
 封装会让断言失效

💡 教程建议每新增一个文件就执行一次 pytest，确认问题发生在哪一步。先写裸请求能快速验证环境、地址和账号是否可用，把问题挡在最前面

生产环境的密码、Token、数据库密码为什么不建议写在 config/env.yaml 里？

 YAML 不支持特殊字符
 配置文件会拖慢用例执行速度
 配置文件无法被 Python 读取
 敏感信息应使用环境变量或 CI Secret，避免随仓库泄露

💡 教程的边界是：测试环境账号可以写在配置文件里，但生产环境密码、Token、数据库密码必须走环境变量或 CI Secret。这也是维护规范里"敏感信息泄露"这一行的处理方式

请求封装里使用 requests.Session() 的主要好处是？

 自动生成 Allure 测试报告
 复用连接并统一维护 Header 等会话级配置，例如通过 set_token 注入 Token
 可以省掉断言步骤
 请求失败时会自动重试

💡 教程的 ApiClient 用 Session 统一管理 base_url、timeout 和 Header，再提供 set_token 更新 Authorization。这样用例里只关注业务行为，不用每次都拼地址、传 Token

数据驱动（例如 data/login.yaml 配合 @pytest.mark.parametrize）最适合什么场景？

 所有用例都必须数据驱动，否则不算自动化
 步骤繁多、前后依赖复杂的业务流程
 参数组合清晰的接口，例如登录的成功、密码错误、账号不存在
 只需要执行一次的一次性验证

💡 教程提醒"复杂业务流程不要过度数据化，否则可读性会下降"。数据驱动的收益来自同一套步骤跑多组数据，参数越多、步骤越简单，收益越明显

分层断言中，"业务层"断言指的是？

 业务 code、message、关键字段
 HTTP 状态码、响应时间、Content-Type
 数据库记录、库存、订单状态
 鉴权、越权、敏感字段

💡 教程把断言分成四层：协议层看状态码和响应时间，业务层看业务 code 和关键字段，数据层看数据库落库结果，安全层看鉴权和越权。四层组合才能覆盖接口的真实质量

创建订单接口只断言 code == 0 不够，还应该补充哪些校验？

 响应时间是否小于 100ms
 订单号不为空、订单金额正确、状态为待支付、库存被正确扣减、订单归属当前用户
 响应头是否包含 Set-Cookie
 服务端进程是否被重启过

💡 这几项正是教程列举的创建订单校验清单。下单是资金和库存强相关的操作，只看业务码很容易放过"金额算错"或"库存没扣"这类严重问题

把 Token 写死在脚本里会带来什么问题？

 会让用例执行速度明显变慢
 会导致 Allure 报告无法生成
 Token 过期后全部用例失败，应改为通过登录接口动态获取
 会导致数据库连接失败

💡 教程把"Token 写死"列为常见新手错误，改法是登录接口动态获取。否则 Token 一过期，整批用例集体报错，排查时很难分辨是脚本问题还是业务问题

生成并查看 Allure 报告，正确的命令组合是？

 执行 pytest --html=report.html 即可
 直接执行 allure serve，它会自动运行测试
 执行 pytest -n auto 打开图形报告
 先用 pytest --alluredir=reports/allure-results 产出结果，再用 allure serve reports/allure-results 查看

💡 --alluredir 负责生成原始结果文件，allure serve 负责渲染成可浏览的报告，两步分工不同。配合 @allure.feature、@allure.story 和 with allure.step 才能让报告读出模块、用例名和失败原因
