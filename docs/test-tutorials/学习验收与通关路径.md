# 学习验收与通关路径

!!! abstract "新手导读"
    这份通关路径用于把学习过程变成可验收的训练任务。学完不等于掌握，能独立完成任务、输出证据、讲清思路，才算真正过关。

!!! tip "这一页和其他几页的分工"
    - **这一页**：告诉你「每个阶段要交什么、怎么打包、怎么打分」——重点在**证据和判据**。
    - [阶段学习检查清单](阶段学习检查清单.md)：逐条自查能力项，勾选自动保存——重点在**自查**。
    - [学习路线](学习路线.md)：五个阶段学什么、多久、什么顺序——重点在**规划**。
    - [学习进度说明](学习中心/学习进度说明.md)：站内进度怎么算、怎么备份——重点在**机制**。

---

## 使用方式

| 步骤 | 说明 |
|------|------|
| 选择阶段 | 从当前能力匹配的阶段开始，不必跳到最高阶段 |
| 完成任务 | 每个阶段都要有可提交的文档、脚本、截图或报告 |
| 自我评分 | 按通关标准打分，低于 80 分继续补练 |
| 复盘补缺 | 写下不会的点，回到对应教程重学 |

建议把每个阶段产出放到自己的学习仓库或笔记目录中。

!!! warning "自评打分最常见的两个失真"
    1. **给自己放水**：验收表里每一项都给了「判据」，就是为了防这个。判据是**可检查的事实**（有没有写、写了几条、别人能不能照做），不是感觉。
    2. **只看做完没做完，不看怎么做的**：同一份测试报告，一种是"全通过，可以上线"，另一种是"P0/P1 全部关闭，遗留 3 条 P3 已与产品确认，建议灰度发布"。分值一样，能力差一个档。

    一个防放水的办法：**把材料发给一个没参与的人，让他按验收表打分**。他只需要材料就能判断，说明你的证据是完整的。

!!! tip "打分怎么用"
    每张验收表的总分是 100。评分方式是「按判据逐项给自己 0 / 半 / 全」：

    - **全**：判据全部满足。
    - **半**：做了但有一处不满足（比如用例有 8 条但预期结果有 2 条写了"正常"）。
    - **0**：没做，或做了但判据的核心要求不满足。

    80 分以上进下一阶段；70-79 分把扣分项补齐再走；**低于 70 分不要硬进下一阶段**——下一阶段会反复用到这一阶段的东西。

## 二、第 1 阶段：测试入门

**建议学时：2-3 周**

### 学习目标

- 理解软件测试目的、流程和常见分类。
- 能拆测试点。
- 能写基础测试用例。
- 能提交清晰缺陷。

### 必学教程

- [软件测试理论基础](基础理论/软件测试理论基础教程.md)
- [ISTQB 软件测试术语速查](基础理论/ISTQB软件测试术语速查.md)
- [测试金字塔与分层策略](基础理论/测试金字塔与自动化分层策略.md)
- [探索式测试](基础理论/探索式测试教程-软件测试版.md)
- [敏捷测试](基础理论/敏捷测试教程-软件测试版.md)

### 通关任务

围绕"手机号密码登录"完成：

1. 写 15 条测试点。
2. 写 8 条测试用例。
3. 写 2 条缺陷报告示例。
4. 说明冒烟测试和回归测试区别。
5. 说明严重程度和优先级区别。

### 验收标准与判据

| 项目 | 分值 | 怎样才算拿到这 N 分 |
|------|------|--------------------|
| 测试点覆盖正常、异常、边界、权限、安全 | 30 | 15 条里**五类各至少 2 条**（正常 3 条以上更符合实际）；每条是「一个可验证的点」而不是一句功能描述——「密码长度 7 位时提示格式错误」算，写成「测试密码」不算 |
| 用例包含前置条件、步骤、预期结果 | 25 | 三条都写全且**预期结果可判断真假**；出现「正常」「正确」「符合预期」这类词即为不满足（要写成「提示『密码长度需 8-20 位』并停留在登录页」）；步骤与预期一一对应编号 |
| 缺陷报告可复现、有证据、有影响说明 | 25 | 换一个人按你写的步骤能复现；**含环境、复现概率（必现/偶现）、实际结果 vs 预期结果**；有一条有截图或日志片段；写明影响范围（影响哪些用户/流程） |
| 能准确解释基础术语 | 20 | 能**不看资料**说清冒烟 vs 回归、严重程度 vs 优先级，且各举一个自己的例子；只背定义但举不出例子的，给半 |

通关标准：80 分以上。

!!! tip "想省时间：两份模板直接用"
    [测试用例模板](模板库/测试用例模板.md) 和 [缺陷报告模板](模板库/缺陷报告模板.md) 都给了一段可整段复制的纯文本骨架，用它们起稿比从空白开始快得多。

!!! success "可以自动验证的两道题"
    第 1 阶段有一道在线判分练习《用例设计：边界与等价类》，答对会点亮进度：

    → [测试用例设计方法论教程 · 在线自测](基础理论/测试用例设计方法论教程-软件测试版.md#sec-lab)

### 常见扣分点

- 用例只有一句"测试登录是否正常"。
- 预期结果写"正常""正确"。
- 缺陷没有环境、步骤和实际结果。
- 把严重程度和优先级混为一谈。

### 通关任务

1. 写 5 条订单查询 SQL。
2. 用 Linux 命令定位一个端口占用问题。
3. 用 Git 新建分支、提交一次修改、合并回主分支。
4. 用 Docker 启动 MySQL 或 Redis。
5. 用 Postman 调试登录接口并获取 Token。
6. 用 Fiddler 抓取登录请求分析参数。
7. 写一份"接口 500 初步排查记录"。

### 验收标准与判据

| 项目 | 分值 | 怎样才算拿到这 N 分 |
|------|------|--------------------|
| SQL 能正确关联表、过滤条件、排序和限制数量 | 25 | 5 条里**至少 2 条用了 JOIN**、至少 1 条用了聚合（GROUP BY / COUNT / SUM）；每条写出「这条查什么业务问题」；能说清为什么用 LEFT JOIN 而不是 INNER JOIN |
| Linux 排查步骤清楚，有命令和结论 | 20 | 有完整的「先查什么→看到什么→再查什么」链条，**命令原文贴出**，最后一句话给结论（哪个进程占了 8080、能不能杀） |
| Git 操作流程完整 | 15 | 有分支、提交、合并的**命令历史或截图**；能把冲突解决过程说出来（哪两个文件冲突、怎么选的） |
| Docker 服务能启动并验证可用 | 10 | 不只是 `docker run` 成功，还要**连进去验证**（MySQL 能建表、Redis 能 set/get），并贴出验证命令和结果 |
| Postman 能调试接口并提取 Token | 15 | Token 通过 Tests 脚本自动写入变量，**后续接口直接引用而不是手抄**；断言里能看到 token 非空的检查 |
| 排查记录有证据和下一步建议 | 15 | 记录里有**响应体原文或日志片段**，有「我判断是哪一层的问题」和「下一步该找谁 / 查什么」；只写「接口报 500，可能后端问题」给 0 |

### 常见扣分点

- SQL 不会用 JOIN 关联多表。
- Linux 不会用 grep 搜索日志。
- Git 遇到冲突直接覆盖。
- Docker 不理解镜像和容器的区别。

## 四、第 3 阶段：专项测试

**建议学时：2-3 周**

### 学习目标

- 理解 HTTP 请求、响应、Header、Cookie、Token。
- 能用 Postman 调试接口。
- 能设计接口测试用例。
- 能检查接口返回和数据库结果。
- 能做基础性能测试。
- 能识别常见安全风险。

### 必学教程

- [接口测试方法论](专项测试/接口测试完整教程-软件测试版.md)
- [JMeter 性能测试](专项测试/JMeter性能测试教程-软件测试版.md)
- [Web 安全测试](专项测试/Web安全测试教程-软件测试版.md)
- [小程序与 H5 测试](专项测试/小程序与H5测试教程-软件测试版.md)

### 通关任务

围绕"登录 -> 商品详情 -> 创建订单"完成：

1. 建一个 Postman Collection。
2. 配置测试环境变量。
3. 登录后自动提取 token。
4. 写 5 个接口断言。
5. 设计 10 条接口测试用例。
6. 写 3 条数据库校验 SQL。
7. 对登录接口做 10 并发性能测试。
8. 检查接口是否存在安全漏洞。

### 验收标准与判据

| 项目 | 分值 | 怎样才算拿到这 N 分 |
|------|------|--------------------|
| Collection 命名清楚，接口按模块组织 | 10 | 有文件夹分组（如 登录 / 商品 / 订单），接口名是「动词 + 资源」（如「创建订单」）而不是「新建请求 1」；换个人打开能直接读懂结构 |
| 环境变量使用正确，不硬编码环境地址 | 10 | **全 Collection 里搜不到 `http://` 开头的完整地址**（用 grep 或 Postman 搜索验证）；至少有 `baseUrl` 和 `token` 两个变量 |
| token 能自动提取并用于后续接口 | 15 | 登录请求的 Tests 里把 token 写进环境变量，后续接口引用 `&#123;&#123;token&#125;&#125;`；**能通过切换环境跑通另一套地址** |
| 断言覆盖状态码、业务码、字段和安全点 | 20 | 5 个断言里四类都要出现：HTTP 状态码、业务 code、关键字段值、安全点（如响应不含 password/手机号明文）；只断言 200 的给 0 |
| 用例覆盖正常、异常、鉴权、数据一致性 | 20 | 10 条里**四类各至少 2 条**；数据一致性类必须写明「接口返回什么 → 数据库该是什么」，不是只写「检查数据库」 |
| 性能测试有指标和结论 | 15 | 有并发数、持续时间、平均响应时间、P90/P95、错误率；**有一句结论**（这个接口在 10 并发下能不能用，瓶颈在哪一层） |
| 安全测试在授权环境执行并保留证据 | 10 | 有明确的「测了什么权限场景」（未登录、越权访问他人订单、参数篡改）；证据是请求响应截图而不是口头描述；**只在自己搭建或靶场环境做** |

### 常见扣分点

- 只断言 HTTP 200。
- token 写死。
- 不测未登录和越权。
- 不检查数据库。
- 性能测试没有结论。

### 通关任务

1. 画出一个项目的自动化分层表。
2. 写 5 条接口自动化用例。
3. 使用数据驱动跑登录成功和失败场景。
4. 生成一次 Allure 报告。
5. 写 3 条 Web UI 冒烟用例。
6. UI 用例失败时能保存截图或 Trace。

### 验收标准与判据

| 项目 | 分值 | 怎样才算拿到这 N 分 |
|------|------|--------------------|
| 能说明为什么某些场景不适合 UI 自动化 | 15 | 分层表里**同时列出了要做和不做的**，每条不做都有理由（频率低、界面易变、有更好的层级可测）；只说「UI 慢所以少做」给半 |
| 接口用例可独立运行，断言清楚 | 25 | **逐条单独运行都能过**（不依赖执行顺序）；断言至少覆盖状态码 + 一个业务字段；有一条校验了数据库或下游结果 |
| 数据驱动结构清晰 | 15 | 用例数据与用例逻辑分离（数据在参数化/外置文件里，不在函数体里硬写）；**同一段代码能跑成功和失败两个场景** |
| 报告能展示用例名称、步骤和失败原因 | 15 | Allure 报告里能看到中文用例标题、步骤、失败堆栈；失败用例能看到实际值 vs 期望值 |
| Web 用例不用固定 sleep 作为主要等待方式 | 20 | 代码里搜 `sleep(` 要么为 0 处，要么每处都有注释说明为什么必须留；等待以显式条件等待为主 |
| 使用 Page Object 模式组织代码 | 10 | 页面元素定位和页面操作用独立类封装，**测试脚本里不出现选择器字符串** |

### 常见扣分点

- 不理解测试金字塔，盲目堆 UI 自动化。
- 接口用例没有断言。
- Web 用例大量使用 sleep。
- 不会使用 Page Object 模式。

### 通关任务

围绕一个电商主流程输出：

1. 测试计划。
2. 30 条测试用例。
3. 5 条接口自动化用例。
4. 3 条缺陷示例。
5. 一份测试报告。
6. 一条 Jenkins 流水线。
7. 准备一段 2 分钟项目介绍。
8. 准备 5 个项目中的测试亮点。

### 验收标准与判据

| 项目 | 分值 | 怎样才算拿到这 N 分 |
|------|------|--------------------|
| 测试计划范围清楚，有准入准出和风险 | 15 | 范围里**写清了「不测什么」**；准入准出是**可判断的条件**（如「P0/P1 全部关闭」而不是「质量达标」）；风险写成「会发生的事 + 影响 + 动作」 |
| 用例覆盖主流程、异常、权限、数据一致性 | 20 | 30 条里正向不超过一半；异常与边界合计 ≥ 12 条；权限和数据一致性各 ≥ 2 条 |
| 自动化能在本地或流水线运行 | 15 | 换环境或换机器**能跑起来**，有 README 说明步骤；失败时能看到报告链接或截图 |
| 缺陷报告清晰可复现 | 10 | 3 条里至少 1 条有完整定位过程（查了哪张表、哪行日志），不是只写现象 |
| 测试报告能给出上线建议 | 15 | 结论明确回答「能不能上线 / 需不需要灰度」，并附依据（缺陷收敛情况、遗留项影响、性能数据）；只列通过率的给 0 |
| 项目介绍有背景、职责、范围、结果 | 15 | 2 分钟内讲完，**有量化数字**（接口数、用例数、缺陷数、回归耗时变化），并留了一个可被追问的钩子 |
| 能讲清测试设计思路 | 10 | 被追问「为什么这么设计」时能回答到**具体方法或具体来源**（看代码发现的、参考某类测试），不是「按经验」 |

### 常见扣分点

- 测试计划没有范围和风险。
- 用例只测正常路径。
- 自动化不能在 CI 运行。
- 项目介绍背八股答案。

## 七、通关证据清单

「我有做过」和「我能证明我做过」是两件事。每个阶段结束，把证据整理到自己的仓库或笔记里。

| 阶段 | 证据 | 合格证据长什么样 | 缺了怎么补 |
|------|------|------------------|-----------|
| 第 1 阶段 | 测试点、测试用例、缺陷报告 | 一份含 15 条测试点的表格 + 8 条用例 + 2 条带截图的缺陷报告，放在同一个目录里 | 用 [测试用例模板](模板库/测试用例模板.md) / [缺陷报告模板](模板库/缺陷报告模板.md) 的骨架起稿 |
| 第 2 阶段 | SQL、Linux 排查记录、Git 提交记录、Docker 截图、Postman Collection | 5 条 SQL 脚本 + 一份带命令原文的排查记录 + `git log --graph` 截图 + 容器运行截图 + 导出的 Collection JSON 文件 | 没有测试库就用 Docker 起一个，或去 [练习靶场](项目实战/练习靶场与工具清单.md) 找公开靶场 |
| 第 3 阶段 | 接口用例、数据库校验、性能测试报告、安全测试记录 | 一份可导入的 Postman Collection + 10 条接口用例表 + JMeter 报告（含 P90/P95）+ 越权测试的请求响应截图 | 用 restful-booker 之类的公开靶场练手，性能测试压自己搭的服务 |
| 第 4 阶段 | 自动化代码、Allure 报告、截图或 Trace | 一个能跑的代码仓库（README 有运行步骤）+ 一份 Allure 报告 + 失败截图样例 | 从 3 条冒烟用例开始，别一开始就写 50 条 |
| 第 5 阶段 | 测试计划、测试报告、CI/CD 运行记录、项目介绍稿、面试复盘表 | 一个仓库装下全部材料，README 就是一页目录；面试稿能离开屏幕讲完 | 用 [第 5 阶段作品集模板](学习中心/第5阶段-项目面试通关.md) 逐块填 |

!!! warning "「证据」不等于「截图」"
    截图只能证明你按下了按钮，证明不了你理解了。**能说明"为什么这么做"的文字比截图重要**：一条 SQL 后面写一句「查的是昨天未支付但已过期的订单」，价值高于一张数据库客户端截图。

!!! tip "一个低成本的证据习惯"
    每做完一个阶段，花 10 分钟写一页 `复盘.md`，只写三件事：**卡在哪、怎么解决的、下次怎么更快**。

    到面试时会发现，这一页比任何教程都更像你的东西——问「你遇到过什么困难」时，答案直接从这儿来。

## 八、最终通关标准

当你能做到下面这些，说明已经具备初级到中级测试工程师的基础能力：

- [ ] 能独立阅读需求并拆测试点。
- [ ] 能写清晰测试用例和缺陷报告。
- [ ] 能用 SQL、Linux、日志辅助定位问题。
- [ ] 能用 Postman 完成接口调试和断言。
- [ ] 能写基础接口自动化和 Web 冒烟自动化。
- [ ] 能理解测试金字塔，不盲目堆 UI 自动化。
- [ ] 能完成基础性能、安全、探索式测试。
- [ ] 能输出测试计划、测试报告和上线建议。
- [ ] 能把项目经历讲清楚，而不是只背八股答案。

通关的标志不是"看完所有教程"，而是你能拿一个真实功能，从需求分析一路做到测试结论。

!!! success "最后一道反向验证"
    找**一个你没测过的功能**（公司真实需求、靶场里的另一个模块、自己做的小项目都行），在**不翻教程**的前提下走一遍：

    需求 → 测试点 → 用例 → 执行 → 缺陷 → 报告 → 一句上线建议。

    走通了，说明你学到的是能力；走不通但知道卡在哪、该回去看哪一篇，说明你学到的是索引。两者都算有收获，但只有前者能写在简历上。
