# 测试用例模板

测试用例不是简单记录“点哪里”，而是把测试思路变成可执行、可复查、可回归的步骤。

## 纯文本骨架（推荐直接复制）

粘进 Excel、飞书表格、禅道用例库都不会散架。一行一条用例，用 `|` 或 Tab 分隔都行。

```text
用例编号 |
所属模块 |
用例标题 |
优先级 | P0 / P1 / P2 / P3
用例类型 | 功能 / 边界 / 异常 / 权限 / 兼容性
前置条件 |
测试数据 |
操作步骤 | 1.  2.  3.
预期结果 | 1.  2.  3.（与步骤一一对应）
设计方法 | 等价类 / 边界值 / 判定表 / 场景法
关联需求 | 需求编号或 PRD 链接
备注 | 截图路径、关联缺陷、特殊说明
```

!!! tip "预期结果要和步骤编号对齐"
    步骤写 3 步、预期结果只写 1 句，是最常见的用例缺陷。开发执行时不知道该在哪一步检查什么。
    正确做法：步骤 1 对应预期 1，步骤 2 对应预期 2。这样用例失败时能直接定位到哪一步出了偏差。

## 用例写到多细才够

这是新手最难把握的度。写太粗没法执行，写太细维护成本高得离谱。判断标准只有一个：**换一个人来执行，能不能得到同样的结果。**

| 粒度 | 例子 | 评价 |
|------|------|------|
| 太粗 | 测试登录功能 | 无法执行，不知道测什么、怎么算通过 |
| 太细 | 点击账号输入框 → 光标出现 → 输入 u → 输入 s → 输入 e → 输入 r | 把一步操作拆成五条，维护成本爆炸 |
| 合适 | 1. 打开登录页；2. 输入账号 `user01`、密码 `Aa123456`；3. 点击登录<br>预期：跳转首页，右上角显示昵称 `user01` | 一个用例覆盖一个可判断的验证点 |

一个实用的经验：**一条用例只验证一个测试点**。如果你发现自己在预期结果里写了三个互不相关的检查项，那说明应该拆成三条用例。

## 标准字段

| 字段 | 说明 |
|------|------|
| 用例编号 | 例如 `LOGIN-001`，方便引用和追踪 |
| 模块 | 登录、注册、购物车、订单等 |
| 测试点 | 本条用例验证什么 |
| 前置条件 | 执行前必须满足的状态 |
| 测试数据 | 账号、密码、商品、订单等 |
| 操作步骤 | 按顺序写清楚怎么执行 |
| 预期结果 | 系统应该出现什么结果 |
| 优先级 | P0/P1/P2/P3 |
| 实际结果 | 执行后填写 |
| 状态 | 通过、失败、阻塞、未执行 |
| 备注 | 截图、日志、关联缺陷等 |

## 完整填写示例

拿一条真实用例按纯文本骨架填出来，就是下面这样。注意步骤和预期是**一一对应编号**的。

```text
用例编号 | LOGIN-002
所属模块 | 用户中心 / 登录
用例标题 | 输入正确账号和错误密码，登录被拒绝并给出提示
优先级 | P0
用例类型 | 异常
前置条件 | 账号 user01 已注册且状态正常，未被锁定
测试数据 | username=user01，password=wrongpwd（长度合规但非真实密码）
操作步骤 | 1. 打开登录页 /login
          | 2. 输入 username=user01，password=wrongpwd
          | 3. 点击「登录」按钮
预期结果 | 1. 登录页正常加载，账号、密码输入框均有焦点样式
          | 2. 输入内容正常回显，密码框显示为密文圆点
          | 3. 停留在登录页，页面提示「账号或密码错误」，不跳转首页；
          |    POST /api/login 返回业务码非 0；登录失败次数 +1
设计方法 | 等价类（无效密码）
关联需求 | PRD-2026-012 用户登录与安全策略
备注 | 第 3 步的失败次数校验需查数据库 login_log 表
```

## 预期结果怎么写

好的预期结果应该具体、可判断。

| 不推荐 | 推荐 |
|--------|------|
| 登录失败 | 页面提示“账号或密码错误”，用户仍停留在登录页 |
| 添加成功 | 商品加入购物车，购物车数量 +1，数据库购物车表新增记录 |
| 系统正常 | 页面不报错，请求返回 200，列表展示 10 条数据 |

判断标准：**写成这样，别人能据此判「通过」还是「不通过」吗？** 能，就是好预期。不能，就要继续具体化。

## 用例评审：写完就完了是不够的

用例写完不代表能用。评审是发现「漏测」和「理解偏差」最便宜的一步——在评审会上发现漏了一个异常分支，比上线后被用户发现要便宜得多。

评审重点看四件事，不需要逐条读用例：

| 看什么 | 具体查 | 典型漏测 |
|--------|--------|----------|
| 覆盖面 | 需求的每一条验收标准，是否都有用例对应 | 需求写了「支持批量删除」，用例只有单条删除 |
| 异常分支 | 每个正常用例，是否都有对应的异常用例 | 只测了「支付成功」，没测「支付超时」「重复支付」 |
| 数据边界 | 长度、金额、数量、时间的边界值 | 只测了「金额 100」，没测「0 元」「负数」「两位小数」「最大限额」 |
| 状态与权限 | 不同角色 × 不同状态 是否覆盖 | 只测了正常用户，没测「未登录」「已注销」「无权限角色」 |

!!! tip "一个省时间的评审技巧"
    评审时不要从第一条读到最后一条，改成**对着需求文档的验收标准逐条问：这条的用例在哪？**
    需求和用例双向核对，漏测会自己冒出来。

## 检查清单

- [ ] 是否覆盖正常流程。
- [ ] 是否覆盖异常输入。
- [ ] 是否覆盖边界值。
- [ ] 是否覆盖权限和登录状态。
- [ ] 是否覆盖重复提交。
- [ ] 是否有明确预期结果。
- [ ] 是否能让别人照着执行。
- [ ] 步骤和预期结果是否编号对应。
- [ ] 一条用例是否只验证一个测试点。
- [ ] 需求里的每条验收标准是否都有用例覆盖。
